## 2. Objective

Lisa is a personal secretary for one owner. R1 delivers a working Swift system that:

- **Takes in information only through owner-authorized paths:** Lisa's own mailbox (read-only; mail the owner forwards or CCs), read-only calendar subscriptions, RSS/Atom feeds, X and Discord through their official or bot APIs, shared Apple News links and text, and direct captures.
- **Understands it** as tasks, event proposals ("this isn't on your calendar"), ideas and preferences. Every item links back to its evidence, and owner corrections always override model suggestions.
- **Plans and briefs:** a deterministic daily rundown that keeps fixed calendar events separate from Lisa's proposed blocks (including time to explore ideas), and a grounded morning brief in readable and spoken versions.
- **Follows up** with reminders, email and Twilio phone calls, governed by deterministic, owner-configured policy and dry-run until enabled.
- **Runs** headless on Linux, or embedded in a native SwiftUI macOS app that acts as the authoritative host, with an iPhone companion, Siri/App Intents, and a Shortcuts automation that plays the brief around the morning alarm.

R1 succeeds (R1 §18) when Lisa can preserve an idea, understand supplied commitments with traceable evidence, propose a feasible day, prepare a grounded morning brief, and follow up reliably within the owner's configured communication permissions.

Completion gates (R1 §3):

- **Linux handoff complete:** portable builds and tests pass; production adapters and Apple source are present; documentation and verification reports are complete. This is the furthest the Linux sandbox can reach.
- **R1 release verified:** additionally requires the Apple build and device checks on the owner's Mac and iPhone, and live setup checks, with the owner's credentials, for every integration the owner enables.

## 3. Working constraints

`CONSTRICTION.md` overrides R1 and any plan, decision or instruction.

- **Git:** work on `main` only, using `git add` and `git commit` locally. No branching, checkout/switch, push, pull/fetch, merge/rebase/cherry-pick, stash/clean, or `git config`. `git reset` only with scoped permission; never amend, squash or rewrite commits.
- **Commits:** exactly one file-level operation (add, change, remove) per commit, staging only that file. Implementation and its documentation go in separate commits, in the existing `add: …` / `change: …` style.
- **Modularity:** one responsibility per file and module; explicit protocols wherever the core depends on platform facilities or external services; no catch-all utility file; no unnecessary or circular module dependencies; Swift 6 access control and concurrency safety.
- **Platform:** the portable core imports no Apple-only frameworks. Apple code may be written in the sandbox but is never described as compiled, run, tested or verified. No mocks, stubs, no-ops or Linux-only substitutes stand in for required production behavior.
- **Tests:** every test harness written during implementation is a temporary file in `.tmp/`. A persistent, package-level `Tests/` suite is built only when the owner explicitly requests it, separately, and without referring to the temporary harnesses.
- **Temporary files:** only in `.tmp/` directly under the project root. Existing temporary files are never removed, overwritten, renamed or repurposed.
- **Environment:** use the installed Swift 6.4.2 toolchain with SwiftPM. No sudo, apt, toolchain or global-environment changes; the one-time setup permissions (P1–P3) are consumed. No third-party dependency without explicit permission, and that includes linking system C libraries such as SQLite. `Package.resolved` is preserved.
- **Security and privacy:** no secrets in source, fixtures, documentation or Git history; synthetic data only; no access to live personal accounts; nothing transmitted to external services; redacted logs.
- **External actions:** implemented behind explicit interfaces with enforced authorization; dry-run by default; persisted outbox and audit record; no live sends or calls during development; failed, skipped or unverified actions are never reported as successful.
- **Reporting:** distinguish implemented, compiled, executed, tested and verified, naming the platform for each claim, using R1's statuses `PASS`, `FAIL`, `NOT_RUN_ENVIRONMENT`, `NOT_RUN_CREDENTIALS` and `OUT_OF_SCOPE`.

### 5.2 Design decisions

These are recorded in `docs/DECISIONS.md` once implementation starts, unless the owner changes them.

1. **Both apps reach the engine only through the API contract.** The iPhone uses HTTPS. The macOS app calls its embedded host through an in-process transport, or connects to a running `lisa serve` that already owns the data directory (ARCH-03). With one presentation path, view-model logic lives in a portable module that can be built and tested on Linux, and the SwiftUI views stay thin.
2. **Host-side outbound HTTP and SMTP use libcurl on both Linux and macOS.** Behavior is identical on both platforms, loopback, private and cloud-metadata addresses can be blocked at connect time (SEC-02), and SMTP is included. The client modules use URLSession and import `FoundationNetworking` explicitly on Linux (ARCH-01).
3. **Configuration is a versioned JSON5 file read by Foundation**, with no YAML or TOML dependency. Owner preferences live in SQLite and override configuration defaults. Consequential settings (approved recipients and phone number, email and call enablement, model endpoint and data-sharing policy) can never be changed by inference or by a paired remote device.
4. **The brief is composed deterministically from evidence-linked items.** Grounding and the parity between readable and spoken versions hold by construction. The model only proposes extractions, classifications and summaries, each validated. Without a configured model everything keeps working (MODEL-04), and the demo sends nothing off the machine.
5. **Delivery intent is persisted before any external side effect.** Claims are transactional and carry a lease. A lease that expires without a recorded result becomes "outcome unknown" and is never blindly retried.
6. **Other defaults:** minimum deployment targets macOS 15 and iOS 18 (Observation, Synchronization, mature App Intents). Only the Mac host delivers reminder notifications, so the iPhone never acts as a second scheduler. Apple News items arrive through a share-sheet App Intent, are labeled as shared content, and are never fetched by Lisa.

## 6. Phases

Every phase ends with debug and release builds, `swift format lint`, verification in the temporary harness, file-by-file commits, documentation updates, and a status report. Work stops for the owner's review at the end of every phase and at every permission gate.

### Phase 1 — Foundations

- **Delivers:** `Package.swift` (Swift 6 language mode), `LisaTime`, `LisaDomain`, `LisaSecrets`, `LisaLogging`; first versions of `docs/DECISIONS.md`, `docs/ARCHITECTURE.md` and `docs/REQUIREMENTS-MATRIX.md`.
- **Requirements:** ARCH-01, ARCH-02, DATA-01, DATA-03, SEC-01 (environment and file secret stores).
- **Gate:** none.
- **Verification:** daylight-saving spring-forward and fall-back, date-only deadlines, ambiguous relative dates, timezone changes, state-machine transitions.

### Phase 2 — Pure engines

- **Delivers:** `LisaICalendar` with its documented supported subset, `LisaMIME`, `LisaXML`/`LisaFeeds`/`LisaHTMLText`, `LisaPlanning`, `LisaPolicy`, `LisaMatching`, `LisaRanking`, `LisaBriefComposer`, `LisaInference`.

### Phase 6 — Network adapters

## 8. Verification and commits

- **Temporary harness:** a new SwiftPM package at `.tmp/r1-verify/` that depends on the root package by path and exercises only public module APIs, using swift-testing and synthetic data. Logs are kept. Networking is loopback-only; nothing touches the public internet.
- **Reports:** results from the temporary harness are labeled as such; unit, integration, platform-specific and live-service results are reported separately.
- **Commits:** for each work package, write and verify the files, then commit them one file at a time in dependency order, followed by the `Package.swift` change and then one commit per documentation file. Each phase ends in a building state; single-file commits in between may not build on their own. `git status` is checked before every commit, and changes not made by Claude are never staged. Expect several hundred commits.

## 9. Risks

- swift-nio-imap is pre-1.0; its API may change.
- The SQLite, libcurl and libxml2 module maps must also work in the macOS build, which cannot be checked in the sandbox.
- The Xcode project and all SwiftUI and App Intents code remain unverified until the first build on the owner's Mac; a round of fixes is expected.
- Alarm triggers, playback on a locked iPhone, and the iPhone's trust in the host's TLS certificate depend on the actual devices.
- The sandbox firewall may block package downloads or R1's reference pages [S1]–[S9]; any block is reported rather than worked around.
