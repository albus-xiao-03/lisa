## 2. Objective

Lisa is a personal secretary for one owner. R1 delivers a working Swift system that:

- **Takes in information only through owner-authorized paths:** Lisa's own mailbox (read-only; mail the owner forwards or CCs), read-only calendar subscriptions, RSS/Atom feeds, X and Discord through their official or bot APIs, shared Apple News links and text, and direct captures.
- **Understands it** as tasks, event proposals ("this isn't on your calendar"), ideas and preferences. Every item links back to its evidence, and owner corrections always override model suggestions.
- **Plans and briefs:** a deterministic daily rundown that keeps fixed calendar events separate from Lisa's proposed blocks (including time to explore ideas), and a grounded morning brief in readable and spoken versions.
- **Follows up** with reminders, email and Twilio phone calls, governed by deterministic, owner-configured policy and dry-run until enabled.
- **Notifies** the owner with native notifications on iPhone and iPad, and on the Mac, for applicable reminders, important commitment changes and brief availability. Notification actions feed back into the authoritative host.
- **Runs** headless on Linux, or embedded in a native SwiftUI macOS app that acts as the authoritative host, with a universal iPhone and iPad companion, Siri/App Intents, and a Shortcuts automation that plays the brief around the morning alarm.

R1 succeeds (R1 §18) when Lisa can preserve an idea, understand supplied commitments with traceable evidence, propose a feasible day, prepare a grounded morning brief, and follow up reliably within the owner's configured communication permissions. Completion criteria, including R1's two gates, are in §13.

## 3. Working constraints

`CONSTRICTION.md` overrides R1 and any plan, decision or instruction.

- **Git:** work on `main` only, using `git add` and `git commit` locally. No branching, checkout/switch, push, pull/fetch, merge/rebase/cherry-pick, stash/clean, or `git config`. `git reset` only with scoped permission; never amend, squash or rewrite commits.
- **Commits:** exactly one file-level operation (add, change, remove) per commit, staging only that file. Implementation and its documentation go in separate commits, in the existing `add: …` / `change: …` style.
- **Modularity:** one responsibility per file and module; explicit protocols wherever the core depends on platform facilities or external services; no catch-all utility file; no unnecessary or circular module dependencies; Swift 6 access control and concurrency safety.
- **Platform:** the portable core imports no Apple-only frameworks. Apple code may be written in the sandbox but is never described as compiled, run, tested or verified. No mocks, stubs, no-ops or Linux-only substitutes stand in for required production behavior.
- **Tests:** every test harness written during implementation is a temporary file in `.tmp/`. A persistent, package-level `Tests/` suite is built only when the owner explicitly requests it, separately, and without referring to the temporary harnesses.
- **Temporary files:** only in `.tmp/` directly under the project root. Existing temporary files are never removed, overwritten, renamed or repurposed.
- **Environment:** use the installed Swift 6.4.2 toolchain with SwiftPM. No sudo, apt, toolchain or global-environment changes; the one-time setup permissions (P1–P3) are consumed. No third-party dependency without explicit permission, and that includes linking system C libraries such as SQLite. `Package.resolved` is preserved.
- **Network:** the owner authorized read-only access to official documentation, approved dependency repositories, SwiftPM download endpoints and the configured package repositories. A host that still needs a host-side sandbox approval is reported, never worked around, and independent work continues.
- **Security and privacy:** no secrets in source, fixtures, documentation or Git history; synthetic data only; no access to live personal accounts; nothing transmitted to external services; redacted logs.
- **External actions:** implemented behind explicit interfaces with enforced authorization; dry-run by default; persisted outbox and audit record. Delivering a notification is an external action: no live pushes, emails or calls during development, only dry-run transports and controlled substitutes. Failed, skipped or unverified actions are never reported as successful.
- **Reporting:** distinguish implemented, compiled, executed, tested and verified, naming the platform for each claim, using R1's statuses `PASS`, `FAIL`, `NOT_RUN_ENVIRONMENT`, `NOT_RUN_CREDENTIALS` and `OUT_OF_SCOPE`.

### 5.2 Boundaries

- **Repository protocols** live in LisaPorts (19), next to the domain types they use. LisaStore (24) conforms to them; for example, its delivery repository implements the transactional claim and lease operations. Services receive protocol-typed dependencies, and LisaHost injects the SQLite implementations. Persistence therefore sits beside the services, not beneath them.
- **API contracts and DTOs** are owned by LisaAPIContract (20), versioned independently of LisaDomain. LisaAPI (45) maps between domain types and DTOs; clients never see domain types. The contract also owns the push-payload schema and the notification category and action identifiers that LisaAPNs (41) and the apps share.
- **Composition root:** LisaHost (47) builds, in order:
  1. validated configuration;
  2. the data-directory lock (if another runtime holds it, the caller connects as a client or fails clearly);
  3. platform services supplied by the caller: secret store, clock, log sinks and, for the Mac app, the local-notification transport;
  4. the store and its migrations;
  5. adapters;
  6. services;
  7. LisaApplication;
  8. the runtime;
  9. the API router;
  10. the optional network server;
  11. the in-process transport.

  Shutdown runs in reverse. LisaHost gains network adapters in Phase 6 and the server in Phase 7; earlier phases compose only offline adapters.
- **Shared behavior for in-process and remote clients:** every client action goes LisaClient → `APITransport` → LisaAPI → LisaApplication. Remote devices use the URLSession transport with a paired-device principal. The Mac app's embedded mode uses LisaHost's in-process transport with the local-owner principal. Validation, idempotency, revision checks and business rules are identical; only the principal's permissions differ.
  - Paired devices can read the owner's day, capture items, act on tasks, reminders and proposals, and manage their own registration, preferences and pairing.
  - They cannot change consequential settings, sources or other devices.
- **Notification placement:**
  - Device registration: LisaDevices (29).
  - Routing, content and validity rules: LisaPolicy (14).
  - Notification intents: LisaAgenda (28).
  - Per-device delivery: LisaDelivery (27).
  - APNs: LisaAPNs (41), implementing the push-transport protocol from LisaPorts (19).
  - Payload parsing and action handling on devices: LisaClient (48).
  - Apple presentation adapters: the shared Apple sources.

### 5.3 Design decisions

These are recorded in `docs/DECISIONS.md` once implementation starts, unless the owner changes them.

1. **Both apps reach the engine only through the API contract** (§5.2). One presentation path keeps view-model logic portable and testable on Linux.
2. **All host-side network traffic uses libcurl** on Linux and macOS: HTTP/1.1 connectors, HTTP/2 for APNs, SMTP and the IMAP session. `CURLOPT_OPENSOCKETFUNCTION` vetoes disallowed addresses before connecting, and `CURLOPT_PREREQFUNCTION` re-checks the connected address before any request bytes are sent (SEC-02). Client modules use URLSession only to reach the host, importing `FoundationNetworking` explicitly on Linux (ARCH-01).
3. **Configuration is a versioned JSON5 file read by Foundation.** Owner preferences live in SQLite and override configuration defaults. Consequential settings can never be changed by inference or by a paired device. They are: approved recipients and phone number, email and call enablement, model endpoint and data sharing, and APNs credentials and environments.
4. **The brief is composed deterministically from evidence-linked items**, so grounding and readable/spoken parity hold by construction. The model only proposes validated extractions, classifications and summaries. Without a model everything keeps working, and the demo sends nothing off the machine.
5. **Every delivery is recorded before any external side effect**, one record per recipient or device, with transactional claims and leases. An attempt whose outcome is unknown is never resent automatically.
6. **Notifications use ordinary APNs alert pushes** to every enabled iPhone, iPad and client-mode Mac. The Mac app's embedded host posts local notifications at delivery time. There are no silent pushes, PushKit, Critical Alerts or companion-side scheduling, and payloads are generic by default (§6). The Time Sensitive level is used only for urgent confirmed deadlines, by the owner's opt-in (§6.7). This replaces revision 1's decision that only the Mac delivers reminder notifications.
7. **IMAP uses a libcurl-authenticated session with an in-house read-only command subset**, provided milestone M6a passes; otherwise the pre-authorized swift-nio-imap fallback is evaluated against the same checks (§7.3).
8. **Deployment minimums:** macOS 15 and iOS/iPadOS 18 (Observation, Synchronization, mature App Intents).
9. **Apple News items** arrive through a share-sheet App Intent, are labeled as shared content, and are never fetched by Lisa.

## 6. Notification architecture

The APNs facts in this section (endpoints, headers, limits, response reasons, token rules) come from prior knowledge. They are verified against [S10]–[S15] in milestone M6b, before LisaAPNs's Apple-specific parts are implemented. Read access to developer.apple.com is authorized, but the sandbox still requires a host-side approval; until it is granted, those parts are reported as blocked (§13).

### 6.1 End-to-end path

Authoritative decision → persistent outbox → provider adapter → registered device → owner interaction → authoritative state update:

1. **Decision (host).** LisaAgenda, applying LisaPolicy, decides one of three things: a reminder occurrence is due, a confirmed commitment changed materially, or the daily brief is ready. It records a notification intent with a stable identity, the subject's current revision, a category and a validity window.
2. **Outbox (host).** In the same transaction, LisaDelivery creates one delivery for each eligible device. By default that is every paired device with notifications enabled and not reporting permission denial, filtered by that device's preferences. Nothing is sent before these records are durable (REM-03).
3. **Provider adapter (host).** A runtime worker claims due deliveries transactionally under a lease and re-checks staleness, eligibility and quiet hours. It then hands each delivery to its transport:
   - LisaAPNs for iPhone, iPad and a Mac running as a client;
   - the Mac app's local-notification transport for its embedded host;
   - the dry-run transport until delivery is configured.
4. **Registered device.** The operating system presents the notification according to the device's settings and Focus, whether or not the companion is running.
5. **Owner interaction.** Opening a notification shows the item. Acknowledge, snooze and complete are submitted through LisaClient with a stable request identity and the subject's revision, and are queued durably if the host is unreachable.
6. **Authoritative update (host).** LisaApplication applies the action, records an audit event, suppresses obsolete deliveries for every device and recomputes reminders. Other devices reconcile when they next connect.

### 6.2 Provider transport and credentials

- **Transport:** the APNs provider API over HTTP/2 and TLS, through libcurl with nghttp2. Requests use `CURL_HTTP_VERSION_2TLS`, and LisaAPNs requires the response to report HTTP/2 (`CURLINFO_HTTP_VERSION`).
  - libcurl otherwise falls back to HTTP/1.1. LisaAPNs treats that as a capability failure, never a degraded success.
  - One long-lived connection is kept per APNs environment.
  - Endpoints are fixed per environment and cannot be redirected by configuration: `api.sandbox.push.apple.com` for development and `api.push.apple.com` for production, both on port 443.
- **Capability verification:**
  - Build: confirmed (`HTTP2`, nghttp2 1.64.0).
  - Run time: LisaAPNs checks `curl_version_info()` for HTTP/2 at startup, and `lisa doctor` reports the result.
  - Loopback (M6b): TLS and ALPN `h2` negotiation, certificate validation against a synthetic test CA, and a full HTTP/2 request/response exchange with `nghttpd`. A handshake alone is not accepted as evidence.
  - Mac: the embedded host uses macOS's own libcurl, whose HTTP/2 support must be verified on the Mac (`NOT_RUN_ENVIRONMENT` until then). If it cannot support the required APNs behavior, the Mac app uses the owner-approved Apple-only URLSession APNs transport, which keeps the fixed endpoints, full TLS validation and the same adapter contract. That approval does not cover a general-purpose URL fetcher.
- **TLS validation:** peer and host verification always on; TLS 1.2 or later; the system trust store (Debian bundle, macOS system roots); no CA override or verification bypass in production configuration.
- **Authentication:** token-based provider authentication.
  - The JWT has header `alg: ES256`, `kid: <Key ID>` and claims `iss: <Team ID>`, `iat`. It is signed with the APNs authentication key through LisaCrypto (swift-crypto).
  - The token is cached and refreshed on a fixed schedule inside Apple's documented refresh window. It is regenerated early only after an expired-token response, and it is never logged.
  - Certificate-based authentication is not used.
- **Credentials:** the signing key (`.p8`) stays on the host in the platform secret store. That is Keychain for the Mac app, and a protected file (owner-only permissions) or an environment variable for headless hosts. Key ID, Team ID and app topics are non-secret configuration.
- **Environments:** development and production are configured separately (endpoint, topics, enablement). Each registration records its environment. Deliveries use only the matching endpoint, and a token is never sent to the other environment.

### 6.3 Device registration

- **Pairing:** the owner creates a one-time, short-lived pairing code on the host (`lisa device pair` or Mac app settings). The device presents it with its installation ID, device class (iPhone, iPad or Mac), app bundle ID and APNs environment. The host returns a revocable device credential once; the device stores it in Keychain and the host keeps only a verifier. iPhone and iPad pair separately.
- **Token association:** `PUT /v1/devices/current/push-registration` requires the device credential. The host accepts only configured topic and environment pairs and binds the token to that registration. Possessing a token never authenticates anything.
- **Updates:** the app re-registers its token at each launch. A changed token replaces the old one, which is kept in history for invalidation checks.
- **Invalidation:** an "unregistered" or "bad device token" response deactivates the token. "Unregistered" counts only if Apple's timestamp is newer than the token's registration. The registration then shows that it needs re-registration.
- **Reinstallation:** a fresh install has a new installation ID and must pair again. Keychain items left by a previous install are discarded. The old registration is deactivated by provider feedback or removed by the owner.
- **Removal:** revoking a device, either on the host or by the device unpairing itself, revokes its credential, deletes its token and cancels its pending deliveries. Its next request receives 401, and it clears its cached data and delivered notifications.
- **Protection:** tokens are stored only on the host, never returned by the API, and logged only as a short fingerprint.

### 6.4 Delivery identities, states and retries

- **Notification occurrences** are identified by (category, subject kind, subject ID, occurrence key):
  - Reminder: the reminder ID plus its scheduled instant.
  - Important change: the subject plus its *change sequence*, a counter that increases with every material change to a confirmed commitment. A later important change always gets a new occurrence and can produce a new delivery, even after an earlier change was delivered.
  - Brief availability: the local date and timezone. One notification per daily brief is an explicit policy, and regenerations do not notify again.
- **Revisions:** each occurrence records the subject revision and change sequence it was based on. At send time, a change occurrence that is no longer the latest is suppressed as superseded only if none of its deliveries was ever submitted; the newer occurrence carries the latest content.
- **Coalescing** applies only to pending occurrences. When a new material change arrives while an earlier change occurrence for the same subject has no submitted delivery, the earlier one is cancelled as coalesced and the new one replaces it. A change made after an earlier delivery is never coalesced away.
- **Deliveries** are identified by (occurrence, device registration) under a unique constraint, so recomputation, retries and restarts cannot repeat the same occurrence on the same device.
- **APNs headers:** `apns-collapse-id` is a fixed-length digest of the subject and category (for reminders, of the occurrence), so a newer change replaces the older one on the device instead of stacking. `apns-id` is derived from the delivery identity, and `apns-expiration` is the end of the validity window.
- **Verification:** two successive important changes to the same event are each delivered once to every enabled device, including retries and restart recovery (L32).
- **States** use R1's REM-03 vocabulary.
  - A delivery moves from pending to in progress. In progress means claimed under a lease, with two attempt phases: *preparing*, before any network I/O, and *submitting*.
  - It ends as accepted by provider, failed, outcome unknown, suppressed or cancelled.
  - *Confirmed delivered* is recorded only when the device later reports the notification, either opened or still present in Notification Center.
  - Dry-run deliveries are recorded as captured, not accepted.
- **Restart:** a delivery whose lease expires in *preparing* is retried. One that expires in *submitting* becomes outcome unknown and is not resent automatically.
- **Acknowledgement and completion:** when either reaches the host, pending deliveries for that subject are suppressed on every device. Completion also cancels future reminders. Acknowledgement stops repeats and escalation of that occurrence but not later scheduled reminders (REM-01).
- **Other devices:** on their next activation they fetch current state, remove delivered notifications for resolved subjects (matched by the payload's notification ID), and show current status. There is no promise for a device that stays offline, and no silent push is used for removal.
- **No overclaiming:** exactly-once delivery is never claimed, and provider acceptance is never reported as display.

| Situation | Classification | Action |
|---|---|---|
| Failure before any request byte is sent (DNS, connect, TLS handshake) | Not sent | Retry with exponential backoff and jitter, within the attempt limit and validity window |
| HTTP 200 | Accepted by provider | Record the APNs ID; no further attempts |
| 400 bad device token or token not for topic; 410 unregistered | Permanent (token) | Failed; token deactivated (410 only when Apple's timestamp is newer than the registration); no retry |
| Other 400, or 413 | Permanent (request) | Failed; health warning, since it indicates a defect in Lisa |
| 403 expired or invalid provider token | Provider authentication | Regenerate the provider token once and retry once; then failed with a configuration warning |
| Other 403 (for example, wrong topic or environment) | Configuration | Failed; health warning; no retry |
| 429 too many requests | Throttled | Back off; retry within the validity window |
| 429 too many provider-token updates | Token churn | Keep the cached token; retry later |
| 500 or 503 | Temporary | Back off; retry within the validity window |
| Timeout or connection loss after request bytes were sent | Outcome unknown | Record; no automatic resend |
| Response not over HTTP/2 | Capability | Failed; health warning |
| Validity window passed | Expired | Cancelled, reason "expired" |
| Subject resolved or superseded; device disabled, revoked or reporting permission denied | Not eligible | Suppressed, reason recorded |
| Inside quiet hours | Deferred | Rescheduled to the end of quiet hours if still valid; otherwise expired |

### 6.5 Presentation and notification actions

- **Universal companion:** one iPhone and iPad app with adaptive layouts (sidebar and detail at regular width on iPad; tabs and stacks on iPhone), plus iPad multitasking and hardware-keyboard support.
- **Categories and actions**, registered at launch:

| Category | Sent for | Actions |
|---|---|---|
| Reminder | Upcoming confirmed deadline | Open, acknowledge, snooze, complete |
| Overdue | Overdue confirmed task | Open, acknowledge, snooze, complete |
| Plan block | Upcoming accepted plan block | Open, acknowledge, snooze |
| Event proposal | Unresolved proposal follow-up | Open (review happens in the app) |
| Commitment change | Important change to a confirmed commitment | Open, acknowledge |
| Brief | Daily brief available | Open |

- **Complete and snooze:** "complete" requires the device to be unlocked. Snooze uses the configured snooze duration, and the host computes the next reminder.
- **Action handling:** for actions that don't open the app, the system launches it in the background.
  - The handler writes the action to the durable queue, with request identity = (installation, notification, action).
  - It tries to submit the action within the allowed time, and otherwise leaves it pending.
  - Pending actions stay visible in the app until the host confirms them. Conflicts are shown as recoverable.
- **Locked devices:** the queue and the device credential use data-protection classes that are available after first unlock, so actions taken on the lock screen can be recorded.
- **Permissions:**
  - Pairing offers to turn notifications on, and authorization is requested only then. Once it is granted, the device receives every category by default.
  - Settings are read at launch and on each return to the foreground, and reported to the host (`PUT /v1/devices/current/notification-status`).
  - While a device reports denial, the host suppresses its pushes and shows the reason in settings and health. It resumes after a report shows notifications allowed again.
  - Changes made while the app isn't running become known only at its next launch.
- **Mac:** the embedded host posts a local notification at delivery time, never scheduled in advance, and handles its actions in-process. A Mac app in client mode registers for APNs like an iPhone or iPad.
- **Not used in R1:** notification service extensions, silent pushes, PushKit, Critical Alerts and badge counts.

### 6.6 Connectivity and host availability

- **Push path:** host → APNs → device over the Internet. It works wherever the device has Internet access, as long as the host is running and online. The device does not need to reach the host.
- **Data and action path:** device → host API, which needs an authenticated route to the host:
  - on the same network, with TLS per API-01 and the iOS Local Network permission; or
  - the intended remote arrangement (owner decision): an owner-configured private VPN route to the Mac's authenticated HTTPS API, configured as the host endpoint. Lisa supports any configurable endpoint and depends on no VPN vendor or SDK. `docs/SETUP-APPLE.md` and `docs/OPERATIONS.md` cover endpoint reachability, TLS trust, pairing and troubleshooting.
- **Outage behavior, without a route to the host:** the app shows the cached rundown and brief with their age, and queues captures and actions with pending status. Meanwhile the host continues on its own state: it may send later reminders, and may escalate only as CALL-01 allows. This is outage behavior, not the intended remote experience.
- **Offline devices:** APNs keeps only the most recent notification per app for an offline device, for a limited time (to verify against [S10]). The app shows the full current state when opened.
- **Host asleep, stopped or disconnected:** no new notifications are generated or sent. Notifications already accepted by APNs may still arrive. When the host resumes, REM-04 applies: obsolete reminders are suppressed, missed low-priority notifications coalesced, limits respected, at most one catch-up brief generated, and skipped items recorded.
- **No local scheduled notifications on companions:** they would be a second timing source and would go stale after actions on other devices. Adding them later would be a separate decision.
- **No relay, tunnel service, public endpoint or cloud backend:** any of these would be a new architectural decision requiring approval (§15).

### 6.7 Privacy and presentation

- **Default payload:** `aps.alert` uses localization keys for generic text ("Reminder", "Your brief is ready"), plus `category`, `thread-id`, `sound` and `interruption-level: active`. A custom `lisa` object carries the schema version, kind, opaque notification and subject IDs, and revision. There are no titles, bodies, people, places or links, and the payload stays within APNs size limits.
- **Optional per-device "show titles":** adds a truncated item title. It never adds descriptions, email content, addresses or calendar URLs.
- **Lock screen:** generic by default. Each category sets a hidden-preview placeholder, and the system's "Show Previews" setting is respected.
- **System settings:** Focus and notification summaries are respected. Critical Alerts and PushKit are never used.
- **Time Sensitive (owner opt-in):** used only for urgent confirmed deadlines. The deterministic rule in LisaPolicy is a high-priority confirmed deadline within 15 minutes whose task is still incomplete. Ordinary reminders, brief availability, news and general updates use `active`. Time Sensitive respects device settings, Focus and Lisa's quiet-hour policy, and never authorizes calls, changes recipients or bypasses delivery limits. It needs the Time Sensitive Notifications capability (§6.9). Verification: L33 and A17.
- **Data routing:** `docs/SECURITY.md` (SEC-03) states what Apple receives: the device token, topic, timing headers and the minimal payload.

### 6.8 Escalation boundaries

- Email and call escalation stay governed by REM-02 and CALL-01.
- A missing push acknowledgement can satisfy only CALL-01's "unacknowledged earlier reminder" condition. Every other condition must still hold: calls enabled, approved owner number, confirmed commitment, urgency rule, incomplete, quiet hours and rate limits.
- An earlier reminder counts toward that condition only if at least one of its deliveries was accepted by a provider or presented locally. Failed or unknown deliveries don't count.
- Provisional availability never triggers escalation (PLAN-05).

### 6.9 Apple account and configuration prerequisites

Documented in `docs/SETUP-APPLE.md` and validated on the owner's devices:

- **Apple Developer Program:** a paid membership, which the owner will obtain later. Push Notifications is not available to free personal teams (to verify). Until then, placeholders and secret references stand in for team, key and bundle values; there is no purchase, account access, real signing credential or live push.
- **App IDs:** one each for the companion and the Mac app, with the Push Notifications capability enabled.
- **APNs authentication key:** the `.p8` key with its Key ID, plus the Team ID.
- **Signing:** development signing in Xcode yields sandbox (development) tokens. Production APNs needs distribution signing (Ad Hoc or TestFlight); an App Store release stays out of scope.
- **Entitlements:** `aps-environment` on iOS and iPadOS and `com.apple.developer.aps-environment` on macOS, each matching the build configuration, plus the Time Sensitive Notifications capability (`com.apple.developer.usernotifications.time-sensitive`).
- **Info.plist:** a Local Network usage description. There is no `remote-notification` background mode, because there are no silent pushes.

## 7. IMAP decision

### 7.1 Options compared

| Option | Read-only retrieval | TLS and authentication | Protocol parsing | Added dependencies | Assessment |
|---|---|---|---|---|---|
| A. swift-nio-imap 0.5.0 on swift-nio and swift-nio-ssl | `EXAMINE` and `UID FETCH … BODY.PEEK[]` can be expressed | swift-nio-ssl (BoringSSL); Lisa drives authentication | Maintained codec, full grammar | swift-nio-imap plus about 15 transitive packages (§11) | Upstream says it is not ready for production; 0.x API; largest dependency set |
| B. libcurl's URL-based IMAP | No: `SELECT`, then `UID FETCH … BODY[…]`, which sets `\Seen` | libcurl | libcurl | None beyond libcurl | Rejected: violates MAIL-01 |
| C. libcurl connect-only session plus an in-house read-only subset | Lisa sends only `EXAMINE`, `UID SEARCH` and `UID FETCH (UID RFC822.SIZE BODY.PEEK[])` | libcurl: implicit TLS or required STARTTLS, certificate validation, SASL or LOGIN, all completed before hand-over | In-house, strictly bounded parser for a small response subset | None beyond libcurl | **Recommended**, if M6a passes |
| D. In-house IMAP on swift-nio and swift-nio-ssl | As C | swift-nio-ssl | In-house | swift-nio stack | No advantage over C while libcurl is approved |
| E. libetpan or MailCore2 | Yes | Own | Full | Not installed (apt needed); not in the macOS SDK | Not pursued |

### 7.2 Recommendation

Option C is recommended, for four reasons:

- It is the only route with source-level evidence (§1) that meets MAIL-01 without a pre-production dependency.
- It adds nothing beyond libcurl, which outbound HTTPS, SMTP and APNs already need.
- It avoids a codec whose maintainers say it is not production-ready.
- Lisa needs only a small response subset: greeting and tagged status, `CAPABILITY`, `EXISTS`, the `UIDVALIDITY` and `UIDNEXT` response codes, `SEARCH`, `FETCH` with `UID`, `RFC822.SIZE` and a `BODY[]` literal, and `BYE`.

Limitations:

- It relies on libcurl's connect-phase ordering, read in the curl 8.14.1 source. The macOS SDK's libcurl must be checked on the Mac, and a runtime check confirms the session state before any command is sent.
- Lisa parses untrusted protocol input itself, in memory-safe Swift with strict size, count and time limits.
- It uses one mailbox per connection and no `IDLE`, so new mail is seen on the next bounded poll.
- Authentication mechanisms are limited to those libcurl supports.

### 7.3 Milestone M6a — IMAP feasibility

- **When:** immediately after REC-SYS-02 (libcurl) is approved, before any other IMAP integration work. It uses no unapproved dependency.
- **Bounded scope:** the checks below run as temporary test code in `.tmp/` against the candidate production code for option C (the LisaCurl session hand-over and the LisaIMAP command subset), before the connector, cursor and ingestion integration is built. Evidence kept: the command transcript, flag state, TLS and authentication results, malformed-response results and resource-limit measurements.
- **Setup:** a scripted loopback IMAP server in the temporary harness with a synthetic mailbox. It uses an ephemeral synthetic CA and server certificate, generated at run time with the `openssl` CLI, and records every command it receives. No live mailbox is involved.
- **Checks:**
  1. Read-only mailbox access: only `EXAMINE`; no `SELECT`, `STORE`, `EXPUNGE`, `COPY`, `MOVE` or `APPEND` is ever sent.
  2. Retrieval with `BODY.PEEK[]` leaves the server's flags unchanged.
  3. UID and UIDVALIDITY: the cursor is (UIDVALIDITY, last UID), and a UIDVALIDITY change triggers a full, deduplicated resynchronization (MAIL-02).
  4. TLS and authentication:
     - implicit TLS, and STARTTLS required;
     - untrusted or mismatched certificates rejected, and plaintext refused;
     - LOGIN and AUTHENTICATE PLAIN, with authentication failures classified;
     - credentials never logged.
  5. Disconnect and reconnect: a drop mid-literal advances no cursor; reconnection uses backoff.
  6. Partial or malformed responses: truncated or oversized literals, garbage lines, and `BYE` mid-session each produce a bounded error, never a crash.
  7. Bounded resources: message-size limit, per-pass message limit, per-command and per-pass timeouts, and measured memory.
- **Exit:**
  - If every check passes, LisaIMAP is built on option C.
  - If any check fails, the failure is recorded and the pre-authorized REC-DEP-05 fallback (swift-nio-imap 0.5.0) is evaluated automatically against the same read-only, security, recovery and malformed-input checks, isolated behind the same LisaIMAP interface. It is adopted only if it satisfies the requirements, with its upstream limitation reported. Otherwise live IMAP is reported blocked and `.eml` import keeps working.
- **Reporting:** the results count as integration tests against a synthetic server. A live mailbox check stays `NOT_RUN_CREDENTIALS`.

- **Reports:** results carry R1's statuses and are separated into unit, integration, recovery, platform-specific and live-service results. Temporary-harness evidence is labeled as such.

## 13. Completion criteria

- **Phase complete:** its deliverables exist, the Linux debug and release builds pass, its temporary verification ran with recorded outcomes, and its documents are updated.
- **Implementation complete (Linux):** Phases 1–9 and Phase T are complete; every required production adapter exists and works within the Linux verification boundary, APNs and IMAP included; the Apple source and project definition are present; and the documentation and implementation report are complete. This is not one of R1's gates.
- **Partial/blocked:** a blocked required production adapter or feature prevents the label "complete". Examples: live IMAP if neither route passes; Apple-specific APNs details that could not be verified against Apple's documentation. Independent work is still finished, and the result is reported as partial/blocked, naming each unmet requirement.
- Implementation status, Linux verification and Apple-device verification are always reported separately.
- **Linux handoff complete (R1 §3):** additionally, the persistent Phase T suite passes L01–L33 on Linux in debug and release, without credentials or public network access. The gate is claimed only when this is actually satisfied.
- **R1 release verified:** additionally, A01–A18 pass on the owner's Mac, iPhone and iPad, and the live setup checks pass for every integration the owner enables, including APNs in each environment used. It is never claimed from Linux results.
- **Not complete:** anything represented only by a protocol, a substitute, a static screen or an unexecuted branch is reported as incomplete.

## 14. Risks

- The recommended IMAP route depends on libcurl's connect-phase ordering, read in the 8.14.1 source. The macOS SDK's libcurl may differ, so it gets a runtime check and validation on the Mac.
- HTTP/2 support in macOS's libcurl is unverified. If it is missing, APNs from the Mac needs the Apple-only transport described in §6.2.
- The APNs details are unverified until developer.apple.com is reachable, and M6b may change parts of §6.
- Push notifications cannot be validated without a paid Apple Developer Program membership.
- Away from home without a route to the host, notification actions stay queued. Meanwhile the host keeps sending reminders and may escalate as CALL-01 allows before those actions arrive.
- APNs keeps only the latest notification for an offline device (to verify), so earlier ones are lost; the app shows the full state when opened.
- Permission changes made while the app isn't running are detected only at its next launch.
- The SQLite, libcurl and libxml2 module maps must also work in the macOS build.
- The Xcode project and all SwiftUI, App Intents and UserNotifications code remain unverified until the first build on the owner's Mac; a round of fixes is expected.
- Alarm triggers, locked-device behavior and the Local Network permission depend on the actual devices.
- The sandbox firewall may block package downloads or reference pages. Any block is reported, not worked around.
