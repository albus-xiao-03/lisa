## 2. Objective

R2 turns Lisa into a distributed system with one authoritative service:
- **Lisa Core** runs in Docker on the owner's Linux server, behind the owner's VPN. It owns the canonical dataset, the connectors, the scheduler and every external delivery.
- **Lisa for Mac, iPhone and iPad** are clients. Each one:
  - keeps a durable local database and keeps working fully offline (R2-CAP-03);
  - applies the owner's changes immediately;
  - synchronizes with Core over HTTPS, and with nearby enrolled devices without Internet access;
  - uses an explicitly configured model provider when Core cannot be reached.

R2 succeeds as R2 §20 defines. Lisa may be in any of these conditions: Core reachable, Internet without Core, nearby devices only, isolated, reconnecting after concurrent changes, or after a Core restart or restore. In each one, owner work is preserved, uncertainty stays visible, state reconciles without silent loss, and the boundaries around personal data and external actions hold.

## 3. Working constraints

`CONSTRICTION.md` overrides R2, this plan and every other instruction. For R2 that means:
- **Git:**
  - Stay on `feature/distributive`, using `git add` and `git commit` locally.
  - Never branch, push, pull, fetch, merge, rebase, cherry-pick, stash, clean or run `git config`. Use `git reset` only with scoped permission, and never amend.
  - Consult only the current branch's history.
- **Commits:** one file-level operation per commit, staging only that file. Implementation and its documentation are committed separately, in the `add: …` / `change: …` / `remove: …` style.
- **Modularity:** one responsibility per file and per module; a protocol wherever the core meets a platform facility or an external service; no catch-all utility file; an acyclic module graph; Swift 6 access control and concurrency safety.
- **Platforms:**
  - The portable package imports no Apple-only framework.
  - Apple code is written here but only syntax-checked with `swiftc -parse`. It is never described as compiled, run, tested or verified.
  - No mock, stub, no-op or Linux-only substitute stands in for required production behavior.
- **Tests:**
  - Every harness written during implementation is a temporary file under `.tmp/r2/<run-id>/` (R2-DEV-02).
  - There is no persistent R2 suite unless the owner asks for one separately (O-6).
  - Existing R1 tests are run, and never edited to make a failing implementation pass.
- **Temporary files:** only in `.tmp/` at the project root. They are never removed, overwritten, renamed or repurposed.
- **Environment:**
  - Use the installed Swift 6.3.2 with SwiftPM.
  - No `sudo`, package installation, toolchain change, container or virtual machine without explicit permission (§15).
  - `Package.resolved` is preserved, and no dependency is added without permission.
- **Security and privacy:** no secrets in source, fixtures, documentation or history; synthetic data only; no live accounts; nothing private is sent to an external service.
- **External actions:** only dry-run transports and controlled substitutes during development. No live email, call, push or paid inference.
- **Reporting:**
  - Use R2's statuses: `PASS`, `FAIL`, `NOT_RUN_ENVIRONMENT`, `NOT_RUN_CREDENTIALS`, `BLOCKED_PERMISSION`, `OUT_OF_SCOPE`.
  - Keep implemented, compiled, executed, tested and verified apart, and name the platform for every claim.

## 6. Where R2 refactors R1

These are the major refactors this plan proposes. Each one keeps the R1 behavior the suite checks, unless R2 replaces it.

1. **Owner data changes only through operations.**
   - Tasks, ideas, captures, preferences, proposal reviews, reminder actions and plan-block actions change only when a semantic operation is applied to a merge state (§8.3).
   - The R1 records become projections of that state, written in the same transaction. So the planner, composer, outbox, API mapping and export keep reading the types they know.
   - LisaOwnerData, LisaReview's task and proposal writes, LisaAgenda's actions and the facade become builders of operations.
   - Validation moves into pure domain code, which clients run too.
2. **The store records every change.**
   - LisaStore appends a change-log entry for every write to a replicated collection, inside the writing transaction, and keeps a tombstone for every deletion. That gives a complete canonical change feed from the existing R1 code, without touching every service.
   - It also gains a second, read-only connection, streaming queries, savepoints and an explicit disk-full error.
3. **Agenda inputs become portable.** The code that gathers planner and composer inputs from records moves out of LisaAgenda into a portable module that reads through a protocol. Core and clients then build plans and briefs the same way.
4. **Delivery learns ownership.**
   - Per-device delivery records gain delegated ownership and generations (§8.9).
   - Fan-out reaches devices that become eligible later.
   - Token feedback uses the token that was actually sent.
5. **Devices get keys.** Enrollment binds a device signing key and a key-agreement key. Pairing secrets are hashed, persisted and single use. Core keeps a signed roster. R1's bearer credentials stay, for HTTP authentication.
6. **The API gains a synchronization version.** A v2 router sits beside v1. v1 changes run through the ledger, in the same transaction as their idempotency record.
7. **Clients get a new core.** For R2 apps, LisaClientCore, with the replica store and the sync engine, replaces the queue-and-cache client. LisaPresentation is rebuilt on it. LisaClient stays, for v1 callers and for migration.
8. **The apps change shape.**
   - The Mac app stops embedding a host and links only client modules.
   - All three apps get every workflow.
   - New adapters are added for the Network framework, local notification scheduling, BackgroundTasks and the Secure Enclave.

## 7. Target architecture

### 7.1 Topology and authority (R2-ARCH-01, R2-ARCH-02)

- **Lisa Core** (one container on the owner's Linux server):
  - **Holds:** the canonical SQLite dataset, the operation ledger, change log, snapshots and the signed device roster.
  - **Runs:** the connectors (Lisa's mailbox, calendars, feeds, X, Discord), the scheduler and the outbox for email, calls and APNs.
  - **Serves:** the v2 API and v1 compatibility over HTTPS on the VPN address.
  - **Administration:** the administrative CLI runs in the same container.
  - **Secrets:** it holds every Core-only secret.
- **Each client** (Mac, iPhone, iPad):
  - **Holds:** its own replica database, the journal of pending operations and its device keys.
  - **Runs:** local planning, briefs and search; nearby sync and relay; delegated and locally created notifications; optional direct inference; and owner-requested public retrieval.
  - **Interfaces:** SwiftUI and Siri.
  - **Secrets:** it holds no Core secret.
- **Connections:**
  - Each client talks to Core over the VPN and HTTPS.
  - Clients talk to each other over authenticated nearby sessions.
  - APNs and model providers are reached by outbound connections only.

R2-ARCH-02's allocation of responsibilities is followed row by row. The modules that carry out each row are named in §11.

- **Nearby:** `NWListener`, `NWBrowser` and `NWConnection` with peer-to-peer enabled, TLS with a pre-shared key, and length-prefixed framing, behind LisaSyncEngine's peer port.
- **Local notifications:** a `UNUserNotificationCenter` scheduler and reconciler, behind LisaNotificationOwnership's port.
- **Background:** `BGTaskScheduler` requests for bounded Core synchronization on iPhone and iPad.
- **Keys:** Secure Enclave P-256 keys where the device has one, otherwise software keys kept in the Keychain, behind LisaTrust's key port.
- **Public fetching:** an `NWConnection` byte stream for LisaHTTP1, which checks the connected address before writing anything.
- **The rest:** the app environment, the App Intents and the UI change as §8.12 describes.

### 7.3 Platform separation (R2-ARCH-03)

- **Core-only.** The clients never link these:
  - LisaStore, LisaIngestion, LisaReview, LisaAgenda, LisaDelivery, LisaDevices, LisaOwnerData and LisaApplication;
  - LisaRuntime, LisaAPI, LisaAPIServer, LisaHost, LisaCoreLedger, LisaCoreAPI and LisaMigration;
  - LisaCurl, and every adapter except LisaOpenAICompatible;
  - LisaCLI.
- **What the clients link:** LisaClientCore and the modules beneath it. That closure has no libcurl and no NIO, no Core module and no Core credential.
- **Guard:** a temporary check fails verification if any client product's dependency closure contains a Core-only target.
- **Apple-only code** stays in `Apps/`: SwiftUI, App Intents, UserNotifications, the Network framework, BackgroundTasks, the Keychain and the Secure Enclave.

## 8. Designs

These sections turn R2's design defaults into concrete decisions. Each becomes a `docs/DECISIONS.md` entry, from D-53 on, when implemented.

### 8.1 Identity, enrollment, trust and secrets (R2-TRUST-01–05)

- **Dataset identity:**
  - **`datasetID`:** random 128 bits, created by `lisa core init` or by migration.
  - **`recoveryEpoch`:** random 128 bits plus a sequence number. A restart keeps it. A restore, or any recovery that can move history backward, replaces it.
  - **Core's signing key:** P-256, held in a secret file such as `/run/secrets/lisa_core_signing_key`.
- **Device identity:**
  - **`deviceID`:** issued by Core at enrollment.
  - **Installation `incarnation`:** random 128 bits, new for every fresh install and for every restore that is detected. A restore is detected when the replica's incarnation doesn't match an anchor kept in the Keychain as this-device-only.
  - **Keys:** a P-256 signing key and a P-256 key-agreement key. They are Secure Enclave keys where the device has one; otherwise Keychain items available after first unlock, on this device only.
  - **Core credential:** revocable; this is R1's 256-bit bearer token, of which Core keeps only the SHA-256 verifier.
  - **Trust anchor:** Core's signing key and TLS pin, protected in the Keychain.
  - **Authorization record:** signed by Core, binding the device ID, incarnation, keys and capabilities.
- **Pairing (owner-controlled, single use):**
  - `lisa core device enroll --name … --class iphone|ipad|mac` prints a pairing payload, as text and as a QR code. It holds the format version, Core's URL, the SHA-256 of Core's TLS public key, the fingerprint of Core's signing key, the dataset ID and a one-time 128-bit secret.
  - The payload expires after 10 minutes. Core keeps only the secret's hash, in the database, so the code outlives the CLI process (fixing the R1 gap).
  - The device connects only if Core's TLS key matches the pin, and continues only once Core has proven its signing key.
  - The device then sends its public keys, incarnation and details, with an HMAC over them keyed by the secret.
  - Core marks the secret used and returns the credential (shown once), the authorization record and the roster.
  - A short code alone is never enough, because the payload pins Core's identity. Enrollment needs a live, authenticated path to Core; there is no offline enrollment (R2-TRUST-01).
- **Upgrade enrollment (R2-MIG-02):** an R1-paired device may present its R1 credential together with a fresh pairing payload. Core then links the new identity to the old registration, keeping its device ID, preferences, push token and delivery history.
- **Roster (R2-TRUST-03):**
  - **Contents:** signed by Core, with a version that only increases. It names the dataset and epoch, its issue time, the policy version and the maximum trust age for nearby sessions (30 days by default, configurable). For each device it lists the ID, class, public keys, status and capabilities.
  - **What devices do with it:** keep the newest verified roster and refuse older versions. Pass rosters on to peers. Refuse revoked peers, and stop applying or forwarding their new operations.
  - **Trust age:** nearby sessions need a roster younger than the maximum age. An expired roster stops new nearby exchanges only, never local reading or capture.
- **Revocation:**
  - `lisa core device revoke` is an administrative command, for the owner only. It raises the roster version, revokes the credential, cancels the device's pending deliveries and assignments, and rejects every operation that device submits from then on, whatever creation time the operation claims.
  - Data already committed stays.
  - Documented limitation: a device that hasn't yet received the revocation keeps trusting the revoked peer until it does, or until its roster expires.
- **Transport (R2-TRUST-02):**
  - HTTPS with application authentication, even over the VPN. Certificate validation is never turned off.
  - Core's certificate is supplied by the owner (from a private CA, or self-signed) and pinned at enrollment.
  - Nearby sessions use TLS with mutual authentication (§8.6).
  - A Bonjour name, a radio signal or an APNs token never authenticates anything.
- **Secrets (R2-TRUST-04):**
  - Core-only secrets live only in Core's secret files: the mailbox, calendar addresses, SMTP, Twilio, the APNs key, Core's model key and administrative credentials.
  - LisaSyncProtocol has no field that could carry one. Replication drops every Core-only field, and a temporary check scans every encoded message type.
  - The fallback model credential is a separate Keychain item on each device, never synchronized.
- **Rotation, reinstall and loss** (documented in `docs/SECURITY.md`):
  - A device rotates its keys with an enrollment update signed by its old key.
  - Core rotates its signing key with a roster that carries the new key, signed by the old one.
  - A reinstall is a new incarnation and needs a new enrollment.
  - A lost device is revoked. Its unsynchronized work is lost unless it was already copied to a peer: signed operations a peer holds stay valid after their device is lost.

### 8.2 Operations and encoding (R2-SYNC-01, R2-SYNC-02)

- **Envelope fields:**
  - protocol and schema versions, and the dataset ID;
  - origin: device ID, incarnation and sequence number;
  - operation ID: random 128 bits, stable for the life of the logical action;
  - entity type and ID; operation type and payload;
  - dependencies (operation IDs) and the field versions observed;
  - policy version;
  - creation time, for display and audit only;
  - payload digest (SHA-256), and the origin's signature.
- **Canonical encoding:** a strict JSON subset:
  - UTF-8; object keys sorted by Unicode scalar value; no whitespace;
  - integers only: instants are milliseconds and decimals are strings;
  - minimal escaping; no duplicate keys; nesting depth at most 16; bounded size.

  The signature covers `"lisa-r2-op\n"` followed by these bytes. Relays forward the exact bytes, and nobody re-encodes a signed body. CryptoKit's ECDSA signatures are randomized, so the test vectors check verification, not signing.
- **Strict decoding:**
  - A bounded parser runs before any typed decoding.
  - Duplicate keys and unknown envelope fields are rejected.
  - An unknown payload field is rejected, unless its operation type declares it optional for that schema version.
  - An operation of a newer schema is kept but not applied, with outcome `rejected: unsupported_schema` and the recovery path (upgrade).
- **Bounds:** an operation is at most 64 KiB encoded, a batch at most 100 operations and 512 KiB, and a nearby frame at most 1 MiB. Each is checked from the declared length before anything is read.
- **Idempotency:**
  - An operation ID keeps its identity across retries, peers, restarts and relay paths.
  - The same ID with the same digest returns the outcome already recorded.
  - The same ID with a different digest is `rejected: identity_reuse` and raises a security diagnostic.
  - A sequence number never proves that earlier operations arrived; gaps are tracked for each origin incarnation.
- **The operation catalog:**
  - capture: create;
  - tasks: create, edit a field, complete, cancel, and reopen (naming the terminal actions being reopened);
  - notes and tags: add a note, change tags;
  - ideas: edit a field, move to another stage;
  - reminder occurrences: acknowledge, dismiss or snooze;
  - event proposals: review, dismiss or correct;
  - preferences: set or delete a permitted one, confirm an inferred one;
  - plan blocks: accept, lock, reject, defer, complete or move;
  - any owner item: delete; restore a deleted one (as a new identity);
  - conflicts: resolve.

  Operations that Core originates carry model, source and system writes (for example, extraction results), each under its own authority.
- **Documentation:** `docs/SYNC-PROTOCOL.md` specifies all of this, with test vectors (valid, tampered, duplicate-key and oversized cases) that the temporary harness checks.

### 8.3 Merge rules (R2-SYNC-06, R2-WORK-03)

Each owner field has a merge class, and each operation names the versions it observed.

| Situation | Rule |
|---|---|
| Duplicate operation | Applied at most once, by operation ID and digest |
| Edits to different fields | Each field is its own register, so the edits merge |
| Concurrent edits to one scalar field | A multi-value register: an edit replaces only the versions it observed, so concurrent edits leave every candidate and open a conflict |
| Owner correction versus a model or source value | Every value carries an authority. A model or source write never replaces an owner value, whether concurrent or later; it is kept as a suggestion. An owner write replaces what it observed, whatever its authority |
| Concurrent note additions | Notes are an add-wins set of entries, so both are kept |
| Concurrent tag additions and removals | An observed-remove set: a removal removes only the additions it saw |
| Completion or cancellation versus another edit | Status is held apart from the other fields. The edit applies, and the terminal state stays |
| Concurrent completion and cancellation | Both terminal actions are recorded. The task is terminal ("completed and cancelled", shown for review), and its reminders and deliveries are suppressed |
| Reopening | The reopen must name the terminal actions it reopens, and cancels only those. A terminal action it did not see stays in effect |
| Acknowledge or dismiss versus a concurrent snooze | That occurrence is suppressed; the snooze stays in its history |
| Concurrent snoozes | The latest snooze instant, capped at the policy maximum; all of them stay in the history |
| Deletion versus stale or concurrent edits | The tombstone dominates every operation on the item, in any order. Later edits are recorded as superseded and kept while retention allows. Restoring creates a new identity, linked to the old one |
| Concurrent plans or briefs | Separate derived artifacts, each with its own identity; never merged |
| Conflict in a planning field (deadline, estimate, priority, splittable, block intent) | The item is planned with the earliest deadline and the longest estimate among the candidates, and marked uncertain. Escalation (calls, Time Sensitive notifications) is held until the conflict is resolved |
| Resolving a conflict | The resolution names every candidate version reviewed and replaces exactly those. A candidate that arrived in the meantime remains, as a new conflict |

- **Causal readiness:**
  - An operation waits until its dependencies are present. It is never applied out of causal order, and never skipped.
  - A device that holds an operation depending on another device's operation also holds that dependency, and forwards it.
  - If a dependency is rejected, the dependent operation still gets a visible outcome. It is rejected (`dependency_rejected`) when its entity never existed; otherwise it is applied with the rejected version ignored.
- **Convergence:**
  - Every rule is a join of sets, with a deterministic order for display: multi-value registers, observed-remove sets, grow-only note sets, terminal-action sets with explicit reopen references, the snooze maximum, and dominating tombstones.
  - So any two replicas that hold the same operations reach the same state, whatever order those operations arrived in.
  - The temporary harness checks every permutation of a representative set of operations (R2-L11), and the scenario in R2 §18.2.
- **No last-writer-wins, and no clock authority:** timestamps never pick a winner. `docs/CONFLICTS.md` records these rules and how the owner resolves conflicts.

### 8.4 Core: ledger, receipts, change feed, snapshots and epochs (R2-SYNC-03, -05, -07, R2-CORE-04, -06)

- **New tables in schema v5:**
  - dataset identity and epoch;
  - operations: signed bytes, origin, sequence number, digest, outcome, commit position, and how each arrived;
  - dependencies, entity merge states, conflicts and receipts;
  - progress for each origin: the contiguous sequence reached, plus gaps;
  - the change log and tombstones;
  - roster versions and device keys, and pairing secrets;
  - replication checkpoints for each device;
  - snapshots and notification ownership;
  - delivery control (suspension);
  - runtime schedules and the model budget, which move here from their JSON files.
- **Intake.** Each operation is handled inside one write transaction, with a savepoint per operation so that a batch can partly succeed:
  1. Check bounds, dataset, epoch and schema.
  2. Check that the origin is active in the current roster; check the signature and digest; check for identity reuse.
  3. Check authorization for that operation and principal (R2-TRUST-05). Consequential settings are refused.
  4. Check dependencies. A missing one is recorded durably as `waiting_for_dependencies`.
  5. Apply the merge rule, then update the projection, conflicts and tombstones.
  6. Suppress or cancel deliveries for the affected subjects.
  7. Write the change-log entries and the operation record. That record is also the idempotency record.
  8. Record follow-up work: replanning, reminder sync, marking briefs stale. It runs after commit and is safe across crashes.
- **Receipts:**
  - **Contents:** signed by Core; they name the dataset, epoch, operation, digest, commit position and outcome: `accepted`, `accepted_with_conflict`, `duplicate`, `waiting_for_dependencies`, or `rejected` with a reason and recovery path.
  - **Timing:** a receipt is issued only after commit.
  - **Lost responses:** receipts stay retrievable by operation ID, so a lost response is recovered by lookup or by resubmission.
- **Change feed:**
  - Positions increase within each epoch.
  - Serving `changes?after=` reads entries in one read transaction and keeps only the latest state of each record.
  - Replication rules apply: Core-only fields are dropped, Core-only collections are never sent, and the working-set filter is applied.
  - The result is a Core-signed batch that peers can forward.
  - A client advances its checkpoint only after it has installed a batch durably.
- **Snapshots:**
  - **Building:** each snapshot is built on the separate read connection from one consistent cut. It is streamed into chunks of at most 1 MiB under `<data>/snapshots/<id>/`, which use bounded disk space and expire.
  - **Manifest:** every chunk is hashed in a signed manifest. The manifest also records the dataset, epoch, cut position, schema and protocol versions, record and tombstone counts, and the causal summary.
  - **Fetching:** clients and peers fetch one chunk at a time, so no snapshot is ever held whole in memory.
- **Retention:**
  - Incremental history is kept for 90 days by default. An older cursor gets `cursor_expired` and recovers with a snapshot.
  - Operation identity, digest and outcome, and tombstones, are kept for as long as the dataset is live. Operation bodies older than the window may be dropped once their effects are in the merge state.
  - Under storage pressure, Core answers `insufficient_storage` and raises a maintenance warning; it never gives up these guarantees.
- **Single owner:**
  - The `flock` lock on the data directory stays.
  - A migrated or replaced data directory also carries a fence marker, and Core refuses to start on a fenced dataset.
  - `docs/DEPLOYMENT.md` states that a file lock cannot stop two servers each running its own copy of a backup.
- **Recovery epochs:**
  - A restore, or any recovery that can move history backward, sets a new epoch and suspends outbound delivery (§8.9).
  - A client that sees a new epoch takes the recovery path: it installs a snapshot, then resubmits its journaled operations, including those committed under the old epoch. Core verifies them again.
  - `docs/OPERATIONS.md` explains which gaps a backup cannot fill.

### 8.5 Clients: store, journal and effective view (R2-DATA-01–05, R2-SYNC-04, -08, R2-LIMIT-02)

- **One SQLite database per installation:**
  - It lives in the app's container: owner-only, protected until first unlock on iPhone and iPad, and excluded from device backups as in R1 (O-8).
  - It is never copied between devices.
  - A snapshot is installed from a separate staging database file, and swapped into the canonical view atomically. Pending operations, original captures, conflicts and unconfirmed receipts are kept across the swap.
- **What it holds:**
  - canonical merge states and derived records: the calendar from 30 days back to 90 days ahead, briefs for 30 days, plans, evidence excerpts and source freshness;
  - tombstones and the metadata that prevents replay;
  - the journal of local and relayed operations, with their signed bytes, and Core receipts;
  - peer progress, conflicts and the owner's draft resolutions;
  - local plans and briefs;
  - notification assignments and scheduling results;
  - inference requests and budget, and settings for this device only;
  - the search index, quarantined items from the R1 queue, and coverage metadata for every collection.
- **Atomic local change (R2-DATA-02).** One write transaction:
  1. validates the command;
  2. allocates the operation ID and the next sequence number;
  3. signs the envelope, and stores it with the original input;
  4. updates the effective view and the search index;
  5. records follow-up work, such as replanning or local notification changes.

  The app says "saved" only after the commit. A disk-full error, an I/O error or a signing failure is reported as it is, and nothing is shown as saved.
- **Synchronization states (R2-SYNC-04):** saved on this device; copied to another device (a peer acknowledged it); submitted to Core; committed; committed with a conflict; rejected; waiting for dependencies; needs review. A copy on a peer never counts as a Core commitment. An operation stays in the journal until a verified Core receipt arrives.
- **Effective view:**
  - The view is the canonical state plus every pending local and relayed operation, in causal order, through LisaMerge.
  - It is recomputed for each affected item whenever an operation, batch, receipt, rejection or revocation arrives.
  - Revoked or rejected operations drop out of the view but stay in the journal, for inspection and export (R2-L17).
- **Reconciliation order (R2-SYNC-08):**
  1. Authenticate and negotiate.
  2. Fetch trust, revocation, policy and epoch.
  3. Stop using any authority that is no longer valid.
  4. Recover the baseline: changes, or a snapshot when the cursor or epoch no longer fits.
  5. Submit pending operations in dependency order.
  6. Collect outcomes, then rebuild the view.
  7. Surface conflicts and rejections.
  8. Recompute plans, briefs and local schedules.
  9. Resume incremental sync.

  Pending work is never discarded before it is preserved.
- **Working set (R2-DATA-03):**
  - The defaults are configurable.
  - Eviction removes cached material only. It never removes owner records, pending operations, conflicts, uncertain delivery records or replay metadata.
  - A filtered replica says it is incomplete, and nothing missing from it is taken as deleted.
- **Provenance and time (R2-DATA-04, -05):**
  - Every item keeps its origin (a source, a capture or a device), its source times, its last retrieval or sync, revisions, interpretation status, and whether it is canonical, local or provisional.
  - The owner's planning zone is a replicated preference; the device's own zone is used for display only.
  - Instants are UTC milliseconds. Timeouts and backoff use the monotonic clock.
- **Search:** the token index is updated in the same transaction as the view, and a deletion removes its tokens.
- **Protected export:** unsynchronized work (the journal, conflicts and quarantined items) can be exported to a file the owner chooses.

### 8.6 Nearby synchronization (R2-NEAR-01–05)

- **Transport (Apple):**
  - Network framework `NWListener`, `NWBrowser` and `NWConnection`, available on the macOS 15 and iOS 18 deployment targets, with `includePeerToPeer` set and the Bonjour type `_lisa-sync._tcp`.
  - The newer Network APIs are not adopted, because they would raise the deployment targets. Multipeer Connectivity is not used.
- **Discovery:**
  - Only the Lisa service is advertised, under a random name chosen per session. The TXT record holds only the protocol version: no names, owner data or stable identifiers.
  - Browsing runs in the foreground while nearby sync is on. It stops after a bounded time or once a useful connection is made, and backs off after failures.
  - Idle sessions close after 30 seconds. "Sync nearby devices" runs everything on demand.
- **Mutual authentication:**
  - TLS with a pre-shared key unique to each pair of devices. The key is derived with HKDF from a P-256 key agreement between the two devices' roster keys, so only those two devices can compute it.
  - The listener finds the right key from a random PSK identity, carrying a MAC, chosen for each connection, so no stable identifier is ever transmitted.
  - Inside TLS, each side signs the session nonces and a TLS exporter value with its signing key, and checks the other side against its newest roster. Knowing the Bonjour name proves nothing.
  - Still to verify, against Apple's documentation and on devices, before this design is final: which PSK cipher suites the Network framework offers, and whether they give forward secrecy. If none does, the strongest supported suite is used and the limitation is documented.
- **Session:**
  1. Hello and authentication.
  2. Inventories: the operations held for each origin incarnation, the roster version, the canonical position and whether a snapshot is available.
  3. Bounded exchanges of whatever the other side is missing, each frame at most 1 MiB: signed operations, Core receipts, Core-signed change batches, snapshot chunks and rosters.
  4. Peer acknowledgements, which record "copied to another device" and nothing more.

  An interrupted transfer resumes from durable progress kept for each peer. When two devices connect to each other at the same time, the connection opened by the lower device ID survives.
- **Relay:**
  - A peer stores other devices' signed operations, forwards them to Core with its own credential, and returns the Core-signed receipts and batches.
  - It never rewrites or re-signs another device's operation, never invents a receipt, never shares its credential, and never forwards URLs, commands or general traffic.
  - Direct and relayed paths may overlap; idempotency makes the duplicate harmless.
- **Background limits:**
  - Work is durable before the app is suspended.
  - Bounded background refresh (`BGTaskScheduler`) is requested for Core sync on iPhone and iPad. Nearby sessions run only in the foreground, because Apple decides background time.
  - No audio, location or VoIP background mode is used.
  - The UI distinguishes "available now", "waiting for the app to be open", "background time requested but not yet granted" and "permission or radio unavailable" (local network denied, Wi-Fi off), each with recovery guidance.
- **Portable side:**
  - The session protocol, framing, authentication and relay rules live in LisaSyncProtocol, LisaTrust and LisaSyncEngine, behind a byte-stream port, so they run on Linux over an in-memory link.
  - That link is a test transport and is labeled simulated wherever it is used. It never verifies Apple's peer-to-peer behavior (R2-GOV-04).

### 8.7 Capabilities and transitions (R2-CAP-01–04)

- **Each client tracks these separately:**
  - authenticated Core reachability, and API and sync compatibility;
  - each fallback provider's reachability, and model availability;
  - nearby availability;
  - data freshness and coverage;
  - notification permission and schedule coverage;
  - enrollment and trust state;
  - storage health.

  Core reachability is known only from an authenticated exchange, never from a network-path or VPN signal.
- **Features follow the capability they need,** not a global mode switch. The R2-CAP-02 matrix becomes a table in `docs/OFFLINE-BEHAVIOR.md`, listing the checks that enforce each row.
- **Transitions are safe:**
  - A connectivity change never interrupts a durable capture, replaces a draft, clears the database, resends a finished inference, replays expired deliveries, resets retry counters indefinitely or promotes a provisional plan.
  - Retries use cancellation, bounded timeouts, exponential backoff with jitter, and a manual "Try again".
  - Authentication failure, revocation and incompatible versions stop the retries and show what to do. They never fall back to anything insecure.

### 8.8 Offline intelligence, fallback inference and public retrieval (R2-CAP-03, R2-INT-01–05, R2-WORK-01–04)

- **Offline baseline, with no model:**
  - search;
  - sorting by deadline, priority and state, and detecting overdue tasks;
  - a provisional plan built from the replica with R1's planner and constraints, with explanations of unscheduled work and conflicts;
  - a structured local brief;
  - preference changes within the permitted set;
  - managing tasks and reminders.

  Free-form captures stay pending ("awaiting interpretation"); nothing is invented.
- **Local plan (R2-WORK-01):**
  - It records the canonical checkpoint, the provisional operations included, calendar coverage and freshness, open conflicts, the algorithm version and when it was made.
  - It is shown as provisional until Core has the owner's actions and canonical planning has reconciled.
  - Gaps in a stale calendar are shown as unverified, never as confidently free. Locked and accepted blocks are owner intent and never silently move.
- **Local brief (R2-WORK-02):**
  - It has its own identity (device and input version), and never replaces the canonical brief, however old that is.
  - The app shows the latest canonical brief and any local brief, their ages and missing sources, and any regeneration failure.
  - The readable and spoken versions carry the same uncertainty.
- **Fallback provider (R2-INT-01):**
  - The OpenAI-compatible adapter runs over URLSession.
  - It is configured on each device: endpoint, model, a Keychain credential reference, explicit consent to share data, timeout, input and output bounds, the request budget, and its status.
  - Nothing is enabled by default, and Core's provider settings never authorize a client to send data anywhere.
- **Fallback workflows (R2-INT-02):** interpret a new capture into proposed tasks, ideas or events; summarize selected local evidence; improve the local brief; explain the provisional plan; answer bounded questions from the local working set. Every result says it was made from local data, names missing or stale sources, and passes the same validation and permission checks as Core's suggestions.
- **Requests (R2-INT-04, -05):**
  - **Record:** each request stores its identity (derived from its intent and input revisions), its inputs, provider and model, template version, status, validated result and usage.
  - **No duplicates:** repeated taps and connectivity changes reuse the same request. A timeout after sending is "outcome uncertain" and is not resent automatically.
  - **Limits:** one request in flight, ten per device per day, and at most one repair. The count is persisted per day of the owner's planning zone, and clock changes cannot reset it.
  - **No global cap:** per-device limits are not a global spending cap, and the documentation says so.
  - **On reconnection:** results reach Core as proposals with their evidence. A result built on deleted or obsolete evidence is invalidated or revalidated first.
- **Public retrieval (R2-INT-03):**
  - **Scope:** owner-configured public feeds and owner-supplied URLs, fetched only in the foreground and only on request, with R1's URL, redirect, size and parser limits.
  - **Address safety:** R1 enforces it at connect time inside libcurl, which iOS doesn't have. Clients therefore fetch through LisaHTTP1 over an `NWConnection` that checks the connected address before sending a single byte.
  - **Links:** links found in content are never followed.
  - **Provenance:** results carry client provenance. They never advance Core's cursors or count as a canonical refresh, and private connectors stay on Core.

### 8.9 Notifications and external delivery (R2-NOT-01–06)

- **Core decides, under R1's unchanged policy:** eligibility, escalation, quiet hours, owner-only destinations, generic content, validity windows and stale suppression. Provider acceptance, app receipt and owner acknowledgement stay separate.
  - Every enabled paired device is targeted by default.
  - That now includes the Mac, which registers for APNs as a device. The embedded host that caused D-51's double notifications is gone.
- **Ownership records:**
  - There is one record per occurrence and target device, with a generation that only increases.
  - Its states are: Core-owned, reserved for local scheduling, local scheduling confirmed, scheduling failed, suppressed or cancelled, expired, and outcome unknown.
  - A content change updates the occurrence; it never creates a new one.
- **Handoff:**
  1. In one transaction, Core reserves the slot for the device and suppresses its own push for that slot.
  2. The device fetches the signed assignment.
  3. The device stores it and schedules the OS notification under an identifier derived from the occurrence and the generation.
  4. The device reports the result.
  5. Core records it, never treating scheduling as proof of display.

  Core never reclaims an uncertain assignment just because the device cannot be reached. It takes the slot back only after a confirmed cancellation, or after a reconciliation report proving the device will not fire it. An occurrence that has expired is recorded as expired. A coverage gap left by a crash or partition is shown in health, not hidden.
- **Local schedules:** up to 48 hours ahead and at most 32 Lisa requests per device, preferring confirmed and time-sensitive reminders. The app shows "Notifications scheduled through <time>".
- **Locally created reminders:**
  - A reminder created offline belongs to the device that created it. Peers show it as pending but schedule nothing for that slot.
  - Once Core accepts it, Core adds future slots for the other devices and keeps the creator's, without replaying past reminders that were missed.
  - No device takes over a Core-owned slot because of an outage.
- **Reconciliation** runs on launch, on return to the foreground, after sync, and on notification actions:
  - compare assignments with the operating system's pending requests;
  - restore those that are missing and still owned; cancel those that are obsolete;
  - remove stale delivered notifications where the platform allows;
  - apply acknowledgements, completions, cancellations and deletions;
  - keep handoffs whose outcome is still uncertain;
  - report permission changes.

  OS, APNs and collapse identifiers are never used as idempotency keys, and APNs stays best effort.
- **Email and calls:**
  - Only Core sends them, keeping R1's outbox, claiming, recipient enforcement, quiet hours, confirmation and urgency rules, rate limits and handling of unknown outcomes.
  - A missing acknowledgement or a disconnected device never authorizes a call.
  - A restored Core starts with outbound delivery suspended until the owner reviews it with `lisa core delivery review`, then `resume`.

### 8.10 Core deployment (R2-CORE-01–05)

- **Image:** a multi-stage Dockerfile.
  - The build stage is the official Swift image of the pinned version (O-3), selected by digest. It builds `lisa` in release mode with `--force-resolved-versions` and the static Swift runtime.
  - The runtime stage is a pinned base image with only the SQLite, libxml2, libcurl, CA-certificate and time-zone packages.
  - Both `linux/amd64` and `linux/arm64` are declared. The build and the run are reported separately for each architecture.
- **Container boundaries:**
  - The container runs as a non-root user (UID 10001).
  - It mounts `/var/lib/lisa` (the data volume), `/etc/lisa` (configuration, read-only) and `/run/secrets` (Compose file secrets), plus a bounded tmpfs for `/tmp`.
  - Its root filesystem is read-only.
  - It runs with no privileges and no added capabilities (`cap_drop: ALL`, `no-new-privileges`), and no Docker socket.
  - No secret goes into a layer or a build argument.
  - Logs are bounded, by the log driver's size limits and Lisa's own rotation.
  - `SIGTERM` is handled, with a grace period longer than Lisa's shutdown.
  - Secret files keep R1's protection: on the host they belong to the container's UID with mode 0400, which Compose's file secrets preserve. The file-secret checks are not weakened.
- **Network exposure (R2-CORE-03):**
  - The default configuration listens on loopback only.
  - A production configuration names an explicit VPN address.
  - The Compose file publishes only on `${LISA_VPN_ADDRESS}`, which must be set, so there is no fallback to all interfaces. IPv6 is published only when an IPv6 VPN address is given explicitly.
  - Outside a container, Lisa binds the VPN address itself and refuses to start if that address is missing.
  - `docs/DEPLOYMENT.md` gives the IPv4 and IPv6 exposure checks, firewall and routing verification, and a test from a client outside the VPN. The firewall checks cover Docker's own forwarding rules, which bypass host firewall front-ends.
  - There is no public API. APNs and providers are reached only by outbound connections. Lisa installs and changes no VPN software.
- **Health (R2-CORE-05):**
  - Each of these is reported separately: liveness, database readiness, sync readiness, each source, the model, each delivery channel, storage, backup age, and sync lag for each device.
  - The running Core writes them to `<data>/run/health.json`. `lisa core health` reads that file without taking the lock or using the network, and serves as the container's health check.
  - A failing news source never makes Core unready.
- **Restart:**
  1. Recover transactions and waiting operations.
  2. Inspect uncertain outcomes.
  3. Reconcile schedules and assignments.
  4. Suppress obsolete work.
  5. Resume bounded processing.
  6. Report degraded capabilities.

  A persistent provider failure is a health state, not a restart loop.
- **Backup and restore (R2-CORE-06):**
  - **Method:** SQLite's online backup API, so WAL content is included.
  - **Manifest v2:** schema, dataset, epoch, cut position, record counts taken from the same snapshot, and file digests.
  - **Coverage:** canonical records, operations, receipts, tombstones, delivery history with unknown outcomes, and device enrollment metadata. Secrets are restored separately, through the secret files.
  - **Commands:** `lisa core backup validate` checks a backup. `lisa core restore` fences the replaced data directory, sets a new epoch and suspends delivery.

### 8.11 API, errors and CLI (R2-API-01–04)

- **Negotiation (R2-API-01):** every v2 request carries the protocol version and the client's features.
  - `GET /v2/capabilities` returns the API and operation-schema versions, the features, the dataset ID, the epoch, the trust and policy versions, and the redacted capability and health state.
  - An unknown required capability fails with `upgrade_required`.
- **Routes (R2-API-02):**

| Operation | Route |
|---|---|
| Capabilities and health | `GET /v2/capabilities` |
| Enrollment | `POST /v2/enrollments` |
| Trust and policy | `GET /v2/trust` |
| Submit operations | `POST /v2/operations`: at most 100 operations and 512 KiB, with an outcome for each operation |
| Look up receipts | `POST /v2/receipts/lookup` |
| Incremental changes | `GET /v2/changes?after=&limit=` |
| Snapshots | `POST /v2/snapshots`, `GET /v2/snapshots/{id}`, `GET /v2/snapshots/{id}/chunks/{n}` |
| Replication checkpoint | `PUT /v2/devices/current/replication` |
| Conflicts | `GET /v2/conflicts`. Resolving one is a `resolveConflict` operation |
| Working set | `GET /v2/working-set` (coverage and freshness) and `GET /v2/working-set/{collection}` |
| Notification assignments | `GET /v2/devices/current/notification-assignments` and `POST /v2/devices/current/notification-reports` |
| Push registration, permission, preferences, receipts | As in v1, under `/v2/devices/current/…` |
| Revocation | `DELETE /v2/devices/{id}`, owner credential only |
| Export | `GET /v2/export`, owner only; it includes waiting, rejected and quarantined work |

- **v1:**
  - It is kept, and reads work as before.
  - Changes run as Core-attested operations through the ledger, with no bypass, in the same transaction as their idempotency record. So the CLI, the demo and R1 apps keep working (O-4).
  - A v1 request with no safe R2 mapping gets `upgrade_required` and is never silently reinterpreted.
  - `GET /v2/tasks` stays a typed 404, as the R1 suite requires, and both versions share one error shape.
- **Errors (R2-API-03):**
  - Typed codes for: malformed data, unauthenticated, forbidden, revoked device, expired trust, wrong dataset, epoch mismatch, unsupported version (`upgrade_required`), missing dependency, conflict, oversized, throttled, insufficient storage, cursor expired and temporary failure.
  - A batch answers for each operation separately.
  - A client checkpoint never moves past changes the client has not installed.
- **CLI (R2-API-04):**
  - **New `lisa core` commands:**

    | Group | Subcommands |
    |---|---|
    | Lifecycle | `init`, `serve`, `health` |
    | Devices | `device enroll`, `device list`, `device revoke` |
    | Synchronization | `sync status`, `operations pending`, `conflicts list`, `conflicts show` |
    | Backup | `backup`, `backup validate`, `restore` |
    | Migration | `migrate inspect`, `migrate prepare`, `migrate fence`, `migrate run` |
    | Delivery | `delivery status`, `delivery suspend`, `delivery review`, `delivery resume` |
    | Protocol diagnostics | `protocol decode`, `protocol verify` (for an operation, receipt, batch or frame) |

  - Output redacts secrets and private content.
  - The existing commands stay.

### 8.12 Apple applications and Siri (R2-UI-01–05)

- **All three apps** offer Today, Brief, Inbox and review, Ideas, Memory, and Settings and health, plus Conflicts and Diagnostics. When Core can't be reached, the app is never replaced by an error screen.
- **Mac:**
  - It is a client only. It links LisaClientCore, LisaPresentation and the shared Apple sources, and no Core module. It never opens a data directory or starts a Core.
  - It enrolls like the other devices, registers for APNs, schedules delegated local notifications and takes part in nearby sync.
  - With the embedded host gone, it can run in the App Sandbox (O-9).
- **iPhone and iPad:** one universal app.
  - The iPad uses a three-column split view designed for its width, with keyboard shortcuts and multitasking.
  - The iPhone uses tabs and navigation stacks.
- **Status language (R2-UI-02):** "Saved on this device", "Shared with a nearby device", "Synced with Core", "Waiting to sync", "Needs review", "Using saved calendar information", "Local brief" and "Notifications scheduled through …". Counters, hashes, versions and transport details appear only in Diagnostics.
- **Conflicts (R2-UI-03):**
  - **Shown:** the item and field; each candidate value with the device it came from; the causal or contextual explanation; and whether planning or reminders are affected.
  - **Controls:** pick a candidate, or edit the result.
  - **Drafts:** a draft resolution survives a new candidate arriving while the view is open.
  - No raw JSON is ever shown.
- **Permissions and accessibility (R2-UI-04):**
  - Notification permission, local-network permission, Keychain failures, lost enrollment, provider configuration errors and background limits each get a clear state and a way to recover.
  - Declared keys: `NSLocalNetworkUsageDescription`, `NSBonjourServices` and `BGTaskSchedulerPermittedIdentifiers`. Only the `fetch` background mode is declared, for `BGAppRefreshTask`.
  - Accessibility: VoiceOver labels, Dynamic Type, keyboard navigation on Mac and iPad, light and dark appearance, and readable empty and error states.
  - The app icon and privacy manifest that R1 lacked are added.
- **Siri (R2-UI-05):**
  - The six R1 intents call LisaClientCore's durable commands.
  - Replies distinguish: completed on this device, waiting to sync, committed by Core (when known), needs clarification, unavailable, and failed. None reports success before the local save.
  - The alarm automation reads a prepared canonical or local brief and never needs a live model.
  - Alarm-start, stopped and snoozed triggers stay distinct, and are documented as observed on the owner's iPhone.

### 8.13 Migration from R1 (R2-MIG-01–04)

- **Prepare:**
  - `lisa core migrate inspect` reports the R1 schema and application versions. It inventories identifiers, secret references (names only), source cursors, schedules, queues, delivery records and unknown outcomes.
  - `migrate prepare` writes and validates a backup, records the intended dataset ID, and checks that no R1 host holds the data directory.
- **Fence:**
  - `migrate fence` marks the R1 database so that R1 software refuses it, relying on R1's verified refusal of a newer schema, and so that R2 Core refuses it too. Nothing is deleted.
  - The owner disables any `lisa serve` service and replaces the R1 Mac app, following the checklist in `docs/MIGRATION-R1-R2.md`.
- **Run:** `migrate run` creates the Core dataset from the validated backup with migration v5.
  - **Kept:** every identifier; explicit corrections (as owner authority); preferences; source cursors; calendar occurrences; brief and plan history; reminder state; delivery attempts and unknown outcomes; and device registrations that can be upgraded.
  - **Causal metadata** starts from a documented migration origin. No "latest" timestamp is invented to make migrated values win conflicts.
  - Core starts with delivery suspended.
- **Client queues (R2-MIG-03).** On first launch, the R2 app reads the R1 queue file. For each entry it:
  1. keeps the original input and request ID;
  2. asks Core whether R1 already applied it, from the migrated v1 idempotency records;
  3. converts it to an R2 operation only when its meaning and revision still hold;
  4. otherwise quarantines it for the owner to review.

  Nothing is replayed blindly. Core-only secrets are provisioned again through the secret files.
- **Cutover:** the R1 host never resumes ingestion or delivery, the Mac connects as an R2 client, the devices reconcile, and then the owner resumes delivery.
- **Rollback:**
  1. Stop Core and fence it.
  2. Restore the pre-migration R1 backup to the R1 host.

  The R1 and R2 schedulers never run at the same time, and old software never opens a newer schema.

### 8.14 Limits and performance (R2-LIMIT-01–03)

- **Defaults (R2-LIMIT-01),** each configurable and checked in the harness:

| Resource | Default |
|---|---|
| Enrolled devices | 10 |
| Operation batches | 100 operations or 512 KiB, whichever comes first |
| Single operation | 64 KiB |
| Nearby frames | 1 MiB |
| Snapshots | Chunked, with backpressure |
| Incremental history | 90 days |
| Local notifications | 48 hours ahead, 32 requests |
| Inference | One request at a time, ten a day, one repair |
| Retries | Finite, with persisted next-attempt times |

  Limits count encoded bytes and are checked before memory is allocated.
- **Storage pressure:** a write that cannot be stored safely stops with an actionable error. Captures, pending operations, conflicts, uncertain deliveries and replay metadata are never evicted.
- **Performance (R2-LIMIT-03):**
  - **Data:** synthetic, with 10,000 searchable records, 100,000 historical operations, three clients and recurring calendars.
  - **Hardware:** this sandbox, with its details recorded.
  - **Targets:** capture p95 within 500 ms; search p95 within 1 second; 100 operations converging within 5 seconds over the simulated link.
  - **Reporting:** Linux numbers are reported as Linux numbers. Apple-device numbers stay `NOT_RUN_ENVIRONMENT` until measured on devices (R2-A16).

- **When:** built and run in debug and release at M0, M3, M5, M8 and M9.

  - an implementation defect is fixed in the implementation;

## 13. Commits and documentation

- One file-level operation per commit, staging only that file. Implementation and documentation are committed separately, in the `add: …` / `change: …` / `remove: …` style.
- Within a work package: the files are written and verified, then committed one at a time in dependency order. The `Package.swift` change follows, then one commit for each documentation file.
- Each milestone ends in a state that builds. Single-file commits in between may not build on their own.
- `git status` is checked before every commit, and changes Claude did not make are never staged. Expect many hundreds of commits.

## 14. Checkpoint and resume (R2-DEV-03)

- **Record:** a tracked `R2-CHECKPOINT.md` (O-7), holding:

  - completed requirement IDs;

## 17. Risks

- **Scale.** R2 is larger than R1. A great deal of Apple code (nearby, notifications, background, keys, UI) can only be syntax-checked here. Mitigation: portable logic first, thin Apple adapters, and view models in LisaPresentation. A round of fixes is still expected at the first Mac build.
- **Apple behavior not yet verified:**
  - the Network framework's PSK cipher suites, the TLS exporter and peer-to-peer behavior;
  - the local-network permission prompts;
  - how `BGTaskScheduler` actually grants background time;
  - Secure Enclave availability on the owner's Mac;
  - in-app App Intents, and the operating system's own limit on pending local notifications, which is believed to be above Lisa's 32;
  - Focus and Time Sensitive interactions.

  All of these stay `NOT_RUN_ENVIRONMENT` until checked on devices.
- **System libraries on Apple platforms.** SQLite and libxml2 are now linked by the client apps too, so their module maps must work in iOS and macOS SDK builds. Nothing here can confirm that.
- **Library drift on this sandbox.** libxml2 2.15 has API changes since 2.9.14, and the OpenSSL 4.0 command may differ from 3.5.7 in what the tests' certificate generation uses. Either may surface in M0.
- **Toolchains.** Sandbox evidence is Swift 6.3.2, while the owner's Xcode and the container use 6.4.2.
- **Single SQLite connection.** Snapshot and export reads move to a second connection so that they don't stall writes.
- **Client address safety.** The `NWConnection` fetcher is new code that can only be verified on Apple platforms.
- **Exposure.** Docker's port publishing can bypass host firewalls, IPv6 exposure is easy to miss, and the VPN address may be missing at boot. These are covered by the documented host checks and by the refusal to fall back to all interfaces.
- **Backups contain device push tokens and credential verifiers**, as R1's did; the documentation says backups are sensitive.
- **Revocation reaches a device only when it learns of it.** Exactly-once delivery is impossible, and handoffs can leave visible coverage gaps. All three are documented, not hidden.
- **Migration** is verified on synthetic R1 data only, never on the owner's real data.

## 18. Stopping conditions

Work on an affected item stops only when:
- an action needs authorization outside the approved scope;
- an enforced platform restriction needs the owner;
- a concrete technical blocker cannot be resolved within the approved scope;
- private credentials, Apple hardware, the owner's server or live-service validation are needed.

Independent work continues in every case, and each blocked operation is reported with its exact cause.
