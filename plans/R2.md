### 1.5 Apple documentation consulted (R2-DEV-04)

Read on 2026-11-19 from developer.apple.com's public documentation data, as the owner asked for TN3213.
- **TN3213** (republished 2026-07-14):
  - Multipeer Connectivity is deprecated in Xcode 27.
  - Network framework's TLS-PSK "doesn't work with QUIC, it doesn't support TLS 1.3, and it only works with the older Network framework API (NWConnection and friends)".
  - The technote recommends TLS-PKI: mutual authentication, a local `SecIdentity` and custom trust evaluation of the peer's certificate.
  - Apple platforms have no API to create a digital identity; it names swift-certificates as one library that can.
  - Peer-to-peer Wi-Fi is opt-in (`includePeerToPeer`). Connections are deduplicated by peer identifier. Persistent identifiers in Bonjour names and TXT records should be avoided or rotated.
  - Framing, flow control (chunks of at least 64 KiB), TCP keepalives and send timeouts are the app's job.
- **Security framework reference:**
  - The documented `tls_ciphersuite_t` values contain no PSK suite at all: only ECDHE-ECDSA, ECDHE-RSA, RSA and the TLS 1.3 suites.
  - Available from iOS 12 and macOS 10.14: `sec_protocol_options_set_local_identity`, `…_set_verify_block`, `…_set_peer_authentication_required`, `…_add_pre_shared_key`, `…_set_tls_server_name`, and `sec_protocol_metadata_create_secret` (the TLS exporter).
  - Available from iOS 13 and macOS 10.15: the PSK selection block, and the negotiated-suite and negotiated-version getters.
- **TN3151** (revised 2026-07-23):
  - URLSession is the "one really good choice" for HTTP.
  - Where URLSession doesn't meet a specific need, "a simplistic HTTP client using CFHTTPMessage on top of a TCP API" is an option, though "building a general-purpose HTTP client is hard".
  - Resolve-then-connect is an anti-pattern; connect by name. Test on IPv6-only networks with DNS64/NAT64. Use Apple's trust evaluation.
- **TN3179:**
  - Local network privacy applies from iOS 14 and macOS 15, and Bonjour types must be listed in `NSBonjourServices`.
  - On iOS, a background local-network operation while permission is undetermined is denied silently.
  - Denial appears as `kDNSServiceErr_PolicyDenied` (−65570) for Bonjour and `localNetworkDenied` for connections.
  - Test on macOS 15.1 or later.
- **`UNNotificationRequest.identifier`:** scheduling a request with the same identifier replaces the earlier one; for remote notifications the identifier is the APNs collapse ID.

## 2. Objective

R2 turns Lisa into a distributed system with one authoritative service:
- **Lisa Core** runs in Docker on the owner's Linux server, behind the owner's VPN. It owns the canonical dataset, the connectors, the scheduler and every external delivery.
- **Lisa for Mac, iPhone and iPad** are clients. Each one:
  - keeps a durable local database and keeps working fully offline (R2-CAP-03);
  - applies the owner's changes immediately;
  - synchronizes with Core over HTTPS, and with nearby enrolled devices without Internet access;
  - uses an explicitly configured model provider when Core cannot be reached.

R2 succeeds as R2 §20 defines. Lisa may be in any of these conditions: Core reachable, Internet without Core, nearby devices only, isolated, reconnecting after concurrent changes, or after a Core restart or restore. In each one, owner work is preserved, uncertainty stays visible, state reconciles without silent loss, and the boundaries around personal data and external actions hold.

## 3. Working constraints

`CONSTRICTION.md` overrides R2, this plan and every other instruction. For R2 that means:
- **Git:** stay on `feature/distributive`, using `git add` and `git commit` locally. Never branch, push, pull, fetch, merge, rebase, cherry-pick, stash, clean or run `git config`. Use `git reset` only with scoped permission, and never amend. Consult only the current branch's history.
- **Commits:** one file-level operation per commit, staging only that file. Implementation and its documentation are committed separately, in the `add: …` / `change: …` / `remove: …` style.
- **Modularity:** one responsibility per file and per module; a protocol wherever the core meets a platform facility or an external service; no catch-all utility file; an acyclic module graph; Swift 6 access control and concurrency safety.
- **Platforms:**
  - The portable package imports no Apple-only framework.
  - Apple code is written here but only syntax-checked with `swiftc -parse`. It is never described as compiled, run, tested or verified until an owner-run Xcode session reports it.
  - No mock, stub, no-op or Linux-only substitute stands in for required production behavior.
- **Tests:** every harness written during implementation is a temporary file under `.tmp/r2/<run-id>/` (R2-DEV-02). There is no persistent R2 suite unless the owner asks for one (O-6). Existing R1 tests are run unmodified, and never edited to make a failing implementation pass.
- **Temporary files:** only in `.tmp/` at the project root, never removed, overwritten, renamed or repurposed.
- **Environment:**
  - Use the installed Swift 6.3.2 with SwiftPM.
  - No `sudo`, package installation, toolchain change, container engine, container or virtual machine without explicit permission (§15).
  - Host administration stays with the owner, and this account's permissions are preserved.
  - `Package.resolved` is preserved, and no dependency is added without permission.
- **Security and privacy:** no secrets in source, fixtures, documentation or history; synthetic data only; no live accounts; nothing private is sent to an external service.
- **External actions:** only dry-run transports and controlled substitutes during development. No live email, call, push or paid inference.
- **Reporting:**
  - Use R2's statuses: `PASS`, `FAIL`, `NOT_RUN_ENVIRONMENT`, `NOT_RUN_CREDENTIALS`, `BLOCKED_PERMISSION`, `OUT_OF_SCOPE`.
  - Keep implemented, compiled, executed, tested and verified apart. Report the five evidence classes of §10.1 separately.

## 6. Where R2 refactors R1

These are the major refactors. Each keeps the R1 behavior the suite checks, unless R2 replaces it.

1. **Owner data changes only through operations.** Tasks, ideas, captures, preferences, proposal reviews, reminder actions and plan-block actions change only when a semantic operation is applied to a merge state (§8.3).
   - The R1 records become projections of that state, written in the same transaction. The planner, composer, outbox, API mapping and export keep reading the types they know.
   - LisaOwnerData, LisaReview's task and proposal writes, LisaAgenda's actions and the facade become builders of operations.
   - Validation moves into pure domain code, which clients run too.
2. **The store records every change.**
   - LisaStore appends a change-log entry for every write to a replicated collection, inside the writing transaction, and keeps a tombstone for every deletion. That yields a complete canonical change feed from the existing R1 code.
   - It also gains a second, read-only connection, streaming queries, savepoints and an explicit disk-full error.
3. **Agenda inputs become portable.** The code that gathers planner and composer inputs moves out of LisaAgenda into a portable module that reads through a protocol, so Core and clients build plans and briefs the same way.
4. **Delivery learns ownership.** Per-device delivery records gain delegated ownership and generations (§8.9). Fan-out reaches devices that become eligible later, and token feedback uses the token that was actually sent.
5. **Devices get keys.** Enrollment binds a device signing key and a nearby transport key and registers a device-generated credential's verifier (§8.1.2). Core keeps a signed roster. R1's legacy pairing stays for v1 devices only.
6. **The API gains a synchronization version.** A v2 router sits beside v1. v1 changes are translated route by route into ledger operations, in the same transaction as their idempotency record (§8.11.2).
7. **Clients get a new core.** For R2 apps, LisaClientCore, with the replica store and the sync engine, replaces the queue-and-cache client. LisaPresentation is rebuilt on it, and LisaClient stays for v1 callers and migration.
8. **The apps change shape.** The Mac app stops embedding a host and links only client modules. All three apps get every workflow. New adapters are added for the Network framework, local notification scheduling, BackgroundTasks and the Secure Enclave.

## 7. Target architecture

### 7.1 Topology and authority (R2-ARCH-01, R2-ARCH-02)

- **Lisa Core** (one container on the owner's Linux server):
  - **Holds:** the canonical SQLite dataset, the operation ledger, the change log, snapshots, content blobs and the signed device roster.
  - **Runs:** the connectors (Lisa's mailbox, calendars, feeds, X, Discord), the scheduler and the outbox for email, calls and APNs.
  - **Serves:** the v2 API and v1 compatibility over HTTPS on the VPN address. The administrative CLI runs in the same container.
  - **Secrets:** it holds every Core-only secret.
- **Each client** (Mac, iPhone, iPad):
  - **Holds:** its own replica database, the journal of pending operations and its device keys.
  - **Runs:** local planning, briefs and search; nearby sync and relay; delegated and locally created notifications; optional direct inference; owner-requested public retrieval; SwiftUI and Siri.
  - **Secrets:** it holds no Core secret.
- **Connections:** each client talks to Core over the VPN and HTTPS, and clients talk to each other over authenticated nearby sessions. APNs and model providers are reached by outbound connections only.

R2-ARCH-02's allocation of responsibilities is followed row by row; the modules that carry out each row are named in §11.

## 8. Designs

These sections make R2's design defaults concrete. Each becomes a `docs/DECISIONS.md` entry, from D-53 on, when implemented. Each review finding states its design, what happens after a failure or retry, and the acceptance check that demonstrates it.

### 8.1 Identity, enrollment and trust (R2-TRUST-01–05)

#### 8.1.1 Identities

- **Dataset:**
  - `datasetID`: random 128 bits, created by `lisa core init` or by migration.
  - `recoveryEpoch`: random 128 bits plus a sequence number. A restart keeps it; a restore, or any recovery that can move history backward, replaces it.
  - Core's signing key: P-256, in a secret file such as `/run/secrets/lisa_core_signing_key`.
- **Device:**
  - `deviceID`, assigned by Core at enrollment.
  - An operation-signing key (P-256).
  - A nearby transport key: the key-agreement key for the PSK design, or the TLS identity key for mutual TLS (§8.6).
  - A device-generated 256-bit Core credential, of which Core stores only the SHA-256 verifier.
  - Keys live in the Secure Enclave where the device has one, otherwise as Keychain items available after first unlock on this device only.
  - The dataset trust anchor: Core's signing key and TLS key pin, from the pairing payload.
- **Incarnation, per launch (finding 4):**
  - Every time the app process opens its replica, it starts a fresh random 128-bit incarnation. Sequence numbers restart at 1 within each incarnation.
  - The first operation of each incarnation carries the previous incarnation's ID and last sequence number, forming the incarnation chain.
  - This replaces revision 1's per-installation incarnation and Keychain anchor. Those could not detect a same-device restore that rolls back the replica and the Keychain together.
  - Core and peers compact closed incarnations into a summary (ID, last sequence, decided), so per-origin progress stays small.

#### 8.1.2 Enrollment (finding 1)

**Design**
1. **Creating the enrollment.** The owner runs `lisa core device enroll --name … --class iphone|ipad|mac`. In one transaction Core stores an enrollment record:
   - enrollment ID (random 128 bits);
   - `tokenHash` = SHA-256 of `"lisa-enroll-v1\n"` followed by a random 256-bit token;
   - an expiry 10 minutes ahead;
   - an attempt counter, state `open`, and the intended name and class.

   Core prints the pairing payload once, as text and as a QR code: format version, Core's URL, the SHA-256 of Core's TLS public key (SPKI), the fingerprint of Core's signing key, the dataset ID, the enrollment ID and the token. Core never stores or logs the token itself.
2. **Preparing on the device.** The device:
   - generates its operation-signing key, its nearby transport key and a random 256-bit credential, and stores them in the Keychain;
   - builds the enrollment request and signs it with the signing key;
   - stores the exact request bytes in its replica before sending anything, so every retry resends identical bytes.

   The signed request holds the enrollment ID, the token, the dataset ID, Core's TLS pin, device details, both public keys (and, for mutual TLS, the self-signed certificate), the credential's SHA-256 verifier, the start of the incarnation chain and an optional R1 link (below).
3. **Pinned connection.** The device opens HTTPS to Core's URL and continues only if the server's TLS public key matches the pin. The token is never sent to a server that fails the pin.
4. **Verifying on Core.** Core checks the request in one write transaction:
   - the enrollment exists, is `open` and is unexpired;
   - SHA-256 of the presented token equals `tokenHash`, compared in constant time;
   - the request signature verifies with the enclosed signing key, which proves possession of it;
   - the keys are valid P-256 points, the fields are within bounds, and fewer than 10 devices are enrolled.

   A failed token or signature check commits `attempts + 1` and does not consume the enrollment; at 5 attempts it becomes `invalidated`.
5. **Consuming the enrollment.** In the same transaction Core:
   - sets the state to `consumed` and records the request's SHA-256 digest;
   - assigns the device ID and stores the device record, keys and credential verifier;
   - signs a new roster (version + 1) and the device's authorization record;
   - stores the response, which holds only public data: device ID, authorization record, roster and Core's signing key.

   It commits, then answers.
6. **Completing on the device.** The device checks Core's signature against the fingerprint from the payload, then stores the device ID, authorization record and roster.

The bearer credential never travels in a response: the device generated it and sent only its verifier.

**After a failure or retry**
- **Response lost after commit, or device crash:** the device resends the stored request. Core finds the enrollment consumed with the same digest and returns the stored response (`duplicate`). No second device is created and nothing secret is lost.
- **Concurrent attempts with the same token:** the transactions serialize and the first consumes the enrollment. Any request with a different digest gets `enrollment_consumed` (409) and a security event in Core's audit log. An identical duplicate gets the stored response.
- **Pin mismatch:** the device stops before sending the token, says this isn't the owner's Core, and the enrollment expires unused.
- **Expiry and invalidation:** an expired or invalidated enrollment gets a typed error; the owner creates a new one. `lisa core device enroll --list` and `--cancel` manage open enrollments.
- **Stored responses** are kept for 7 days after consumption. A later replay gets `enrollment_consumed`. A device that never received its response shows in `lisa core device list` as "enrolled, never seen", for the owner to revoke.
- **Legacy pairing stays separate:**
  - R1's pairing codes and `POST /v1/devices/pair` create legacy registrations only. These have no keys, are not in the roster, and get no nearby or operation-signing rights.
  - An R1 device becomes an R2 peer only through this enrollment. It may include its R1 credential in the signed request, so Core links the new identity to its R1 registration (preferences, push token, delivery history). The R1 credential alone never grants R2 trust.

**Acceptance check (M3)**

A Linux harness runs against the real `LisaAPIServer` with native TLS on loopback, using a certificate generated at run time. The client side is the production enrollment logic in LisaSyncEngine, carried by a test-only libcurl transport that pins the server's public key. It checks:
- the success path;
- a wrong pin, after which the server records no enrollment request at all;
- five wrong tokens, which invalidate the enrollment;
- a bad signature, which counts an attempt without consuming the enrollment;
- two concurrent requests with different keys, which produce exactly one device;
- a response dropped after commit by a test-only relay, after which the retry returns the same device ID;
- expiry and the 10-device limit.

On Apple, session X2 enrolls an iPhone through URLSession with the public-key pin (part of R2-A08).

#### 8.1.3 Roster and revocation

- **Contents:** the roster is signed by Core and identified by (epoch, version); the version only increases within an epoch. It names the dataset, issue time, policy version and the maximum trust age for nearby sessions (30 days by default, configurable). For each device it lists the ID, class, public keys, status and capabilities.
- **Revocation entries** carry the commit position (epoch, position) at which the revocation happened. They are permanent facts: once any Core-signed roster revokes a device key, every device keeps it revoked, whatever later roster or epoch it sees (union rule).
- **What devices do:**
  - keep the newest verified roster of their epoch and refuse older versions;
  - pass rosters to peers;
  - refuse revoked peers, and stop applying or forwarding their new operations.

  An expired roster stops new nearby exchanges only, never local reading or capture.
- **Revoking:** `lisa core device revoke` is an administrative command, for the owner only. It raises the roster version, revokes the credential, cancels the device's pending deliveries and assignments, and from then on rejects every operation submitted from that origin, whatever creation time it claims. Committed data stays.
- **Documented limit:** a device that hasn't received the revocation keeps trusting the revoked peer until it does, or until its roster expires.
- **Transport:** HTTPS with application authentication, even over the VPN, and certificate validation is never turned off. Core's certificate is the owner's, from a private CA or self-signed, and is pinned at enrollment.

#### 8.1.4 Trust after a Core restore (finding 3)

**Design**
- **Recovery mode.** A restored Core starts with a new epoch, with outbound delivery suspended and in trust recovery:
  - only negotiation, trust exchange and receipt lookup are open;
  - operations, changes, snapshots and blobs are refused with `trust_recovery`.
- **Device authentication during recovery.** The restored database may lack the credential verifiers of devices enrolled after the backup. So a device authenticates by signing a Core challenge with the signing key listed in its roster.
- **Merging trust evidence.** Each connecting device presents its newest verified roster. Core checks its own signature on it, then:
  - applies every revocation found in any presented roster, with its original position;
  - re-registers devices that appear in a newer roster but not in the restored database, with their roster keys, marked "membership unconfirmed". Each such device sets a new credential verifier in a signed request.

  `lisa core trust import` merges an off-host roster copy the owner kept with `lisa core trust export`, which the documentation recommends after every revocation.
- **Owner review.** `lisa core trust review` shows the restored roster, the merged revocations and the re-registered devices, with when each was last seen. The owner can revoke any device whose later revocation no device reported. `lisa core trust confirm` then opens ordinary sync and signs a new roster (new epoch, version 1) carrying every revocation.
- **Rosters across epochs.** A device accepts a roster from a newer epoch only after verifying that epoch's Core-signed announcement on the recovery path. It keeps every revocation it already knew (union rule) and reports to Core any the new roster lacks. So the new epoch's lower version number is not mistaken for a rollback.
- **Operations from revoked origins** are rejected whenever they arrive, directly or relayed. Peers don't forward them once they know.
  - The one exception is an operation that comes with a valid Core receipt from an earlier epoch proving it was committed before the revocation (receipt position lower than revocation position, same epoch). It was legitimately committed, so it is reinstated, with that provenance.
  - Anything else is rejected and kept for inspection and export.
- **Delivery** stays suspended through recovery, until `lisa core delivery review` and `lisa core delivery resume`, separately from the trust confirmation.

**After a failure or retry**
- **No device holds the newer roster:** Core cannot learn of the revocation by itself. Sync stays closed until the owner confirms membership; this limit is documented.
- **Forged or foreign roster:** refused, with a security event.
- **Core restarted during recovery:** the recovery state is persisted, and recovery resumes.

**Acceptance check (M3)**

A Linux harness scenario:
1. Devices A, B and C sync. Core is backed up.
2. C commits operation X. The owner revokes C. C's later operation Y is rejected. A receives the new roster.
3. Core is restored from the backup. A new epoch starts, Core is in trust recovery, and delivery is suspended.
4. C's direct sync is refused until membership is confirmed.
5. A presents its roster, and Core marks C revoked.
6. B relays Y; Core rejects it.
7. A resubmits X with its earlier receipt; Core reinstates it.
8. The owner confirms membership. A and B accept the new epoch's roster without a rollback refusal.
9. Delivery stays suspended until `resume`. A forged roster is refused.

This covers R2-L16, extends R2-L29, and contributes to R2-D08 and R2-D12.

### 8.2 Operations, identity and duplicates (R2-SYNC-01, R2-SYNC-02; finding 7)

**Envelope**
- **Fields:**
  - protocol and schema versions, and the dataset ID;
  - origin: device ID, incarnation and sequence number;
  - operation ID: random 128 bits, stable for the life of the logical action;
  - entity type and ID; operation type and payload;
  - dependencies (operation IDs) and the field versions observed;
  - policy version;
  - creation time, for display and audit only.
- **Encoding:** the canonical encoding of §8.15, with a strict bounded decoder: duplicate keys and unknown envelope fields are rejected.
- **Digest:** SHA-256 over the complete canonical signed body: every field above, including origin, entity, operation type, payload and causal context.
- **Signature:** P-256 ECDSA (raw 64-byte r‖s) over `"lisa-r2-op\n"` followed by the body. It is not part of the digest, so a body signed again has the same digest.
- **Relays** forward the exact bytes and never re-encode a signed body.

**Duplicates, at Core and on every replica**
- **Same operation ID, same digest:** a duplicate. The answer is `duplicate`, carrying the operation's current receipt, final or provisional. Nothing changes.
- **Same operation ID, different digest:** `rejected: identity_reuse`, with a security event. The first operation stays authoritative.
- **Same (device, incarnation, sequence) with a different ID:** `rejected: sequence_reuse`, with a security event. Per-launch incarnations make this impossible for a working device (§8.1.1).

**From waiting to final**
- **Provisional receipts.** An operation whose dependencies are missing gets a signed provisional receipt: outcome `waiting_for_dependencies`, the missing operation IDs, and no commit position.
- **Becoming final.** When a missing dependency is decided, Core re-evaluates its waiting dependents in dependency order, in the same transaction, and stores their final receipts (`accepted`, `accepted_with_conflict` or `rejected`, each with a commit position).
- **How outcomes reach devices.** Every decision is also a change-feed entry, so the origin and any relay learn the final outcome by the feed, by receipt lookup or by resubmitting.
- **Rejected dependencies.** A dependent whose entity never existed is `rejected: dependency_rejected`. Any other dependent applies with the rejected version ignored (§8.3).
- **Missing dependencies.** A dependency that doesn't arrive within the waiting limit (14 days by default, configurable) gives `rejected: dependency_missing`, with a recovery hint.

**After a failure or retry**
- A response lost after commit is recovered by resubmission (`duplicate` with the final receipt) or by receipt lookup.
- A retry while the operation is waiting returns the same provisional receipt.

**Acceptance checks**
- R2-L05: identity reuse and sequence reuse (M1 for the codec, M3 for Core).
- R2-L06: out-of-order arrival, provisional receipts becoming final, dependency rejection and the waiting limit (M2, M3).
- R2-L14: lost responses (M3).
- R2-L04: the same operation over direct and relayed paths (M3, M6).

**Catalog of semantic operations**
- capture: create;
- tasks: create, edit a field, complete, cancel, and reopen (naming the terminal actions it reopens);
- notes and tags: add a note, change tags;
- ideas: edit a field, move to another stage;
- reminder occurrences: acknowledge, dismiss or snooze;
- event proposals: review, dismiss or correct;
- preferences: set or delete a permitted one, confirm an inferred one;
- plan blocks: accept, lock, reject, defer, complete or move;
- any owner item: delete; restore a deleted item (as a new identity);
- conflicts: resolve.

Operations Core originates carry model, source and system writes, such as extraction results, each under its own authority. `docs/SYNC-PROTOCOL.md` specifies all of this with test vectors: valid, tampered, duplicate-key, identity-reuse and oversized cases.

### 8.3 Merge rules (R2-SYNC-06, R2-WORK-03)

Each owner field has a merge class, and each operation names the versions it observed.

| Situation | Rule |
|---|---|
| Duplicate operation | Applied at most once, by operation ID and full digest (§8.2) |
| Edits to different fields | Each field is its own register, so the edits merge |
| Concurrent edits to one scalar field | A multi-value register: an edit replaces only the versions it observed, so concurrent edits leave every candidate and open a conflict |
| Owner correction versus a model or source value | Every value carries an authority. A model or source write never replaces an owner value, concurrent or later; it is kept as a suggestion. An owner write replaces what it observed, whatever its authority |
| Concurrent note additions | Notes are an add-wins set of entries, so both are kept. A v1 `notes` text edit replaces exactly the entries it observed |
| Concurrent tag additions and removals | An observed-remove set: a removal removes only the additions it saw |
| Completion or cancellation versus another edit | Status is held apart from the other fields. The edit applies and the terminal state stays |
| Concurrent completion and cancellation | Both terminal actions are recorded. The task is terminal ("completed and cancelled", shown for review), and its reminders and deliveries are suppressed |
| Reopening | The reopen names the terminal actions it reopens and cancels only those. A terminal action it did not see stays in effect |
| Acknowledge or dismiss versus a concurrent snooze | That occurrence is suppressed; the snooze stays in its history |
| Concurrent snoozes | The latest snooze instant, capped at the policy maximum; all of them stay in the history |
| Deletion versus stale or concurrent edits | The tombstone dominates every operation on the item, in any order. Later edits are recorded as superseded and kept while retention allows. Restoring creates a new identity, linked to the old one |
| Concurrent plans or briefs | Separate derived artifacts, each with its own identity; never merged |
| Conflict in a planning field (deadline, estimate, priority, splittable, block intent) | The item is planned with the earliest deadline and longest estimate among the candidates, and marked uncertain. Escalation (calls, Time Sensitive notifications) is held until the conflict is resolved |
| Resolving a conflict | The resolution names every candidate version reviewed and replaces exactly those. A candidate that arrived meanwhile remains, as a new conflict |

- **Causal readiness:** an operation waits for its dependencies; it is never applied out of causal order and never skipped (§8.2). A device that holds an operation depending on another device's operation also holds that dependency, and forwards it.
- **Convergence:**
  - Every rule is a join of sets with a deterministic display order: multi-value registers, observed-remove sets, grow-only note sets, terminal-action sets with explicit reopen references, the snooze maximum, and dominating tombstones.
  - So replicas holding the same operations reach the same state, whatever the arrival order.
  - The harness checks every permutation of a representative set (R2-L11) and the scenario in R2 §18.2.
- **No last-writer-wins, and no clock authority.** `docs/CONFLICTS.md` records these rules and how the owner resolves conflicts.

### 8.4 Core: ledger, receipts, change feed, snapshots and epochs (R2-SYNC-03, -05, -07, R2-CORE-04, -06)

- **New tables in schema v5:**
  - dataset identity and epoch, and the trust-recovery state;
  - operations: signed bytes, origin, sequence number, digest, outcome, commit position, and how each arrived;
  - dependencies, entity merge states, conflicts, and provisional and final receipts;
  - progress for each origin incarnation, plus the incarnation chains;
  - the change log, tombstones and content blobs;
  - roster versions and device keys, and enrollment records;
  - replication checkpoints for each device;
  - snapshots, and the backup watermark;
  - notification ownership, and delivery control (suspension);
  - runtime schedules and the model budget, which move here from their JSON files.
- **Intake.** One write transaction, with a savepoint per operation so a batch can partly succeed:
  1. Check bounds, dataset, epoch and schema, and that the dataset is not in trust recovery.
  2. Check that the origin is active in the roster; check the signature, digest, and identity and sequence reuse.
  3. Check authorization for that operation and principal (R2-TRUST-05). Consequential settings are refused.
  4. Check dependencies; a missing one is recorded durably, with a provisional receipt.
  5. Apply the merge rule, then update the projection, conflicts and tombstones. An entity whose encoded state would exceed 256 KiB is refused with `too_large` (§8.15).
  6. Suppress or cancel deliveries and assignments for the affected subjects.
  7. Write the change-log entries, the operation record (which is the idempotency record) and the final receipt.
  8. Record follow-up work (replanning, reminder sync, marking briefs stale), run after commit and safe across crashes.
- **Receipts** are signed by Core and name the dataset, epoch, operation, digest, outcome and commit position. They are issued only after commit, and stay retrievable by operation ID.
- **Change feed:**
  - Positions increase within each epoch.
  - `changes?after=` reads entries in one read transaction and keeps only the latest state of each record.
  - Replication rules apply: Core-only fields are dropped, Core-only collections are never sent, and the working-set filter is applied.
  - The result is a Core-signed batch of at most 512 KiB that peers can forward.
  - A client advances its checkpoint only after installing a batch durably.
- **Snapshots:**
  - Built on the separate read connection from one consistent cut.
  - Streamed into 512 KiB chunks under `<data>/snapshots/<id>/`, which use bounded disk and expire.
  - Every chunk is hashed in a signed manifest. The manifest also records the dataset, epoch, cut position, schema and protocol versions, record and tombstone counts, and the causal summary.
  - Records inside the stream are length-prefixed, so receivers parse them across chunk boundaries without holding the snapshot in memory.
  - Snapshot generation is bounded in time, because its read transaction holds back WAL checkpoints.
- **Backup watermark:** the highest commit position contained in the newest backup that `lisa core backup validate` accepted. Core publishes it in capabilities and trust responses (§8.5.3).
- **Retention:**
  - Incremental history is kept for 90 days by default. An older cursor gets `cursor_expired` and recovers with a snapshot.
  - Operation identity, digest and outcome, and tombstones, are kept for as long as the dataset is live. Operation bodies may be dropped after the window, once their effects are in the merge state.
  - Under storage pressure, Core answers `insufficient_storage` and raises a maintenance warning; it never gives up these guarantees.
- **Single owner:**
  - The `flock` lock on the data directory stays.
  - A migrated or replaced data directory also carries a fence marker, and Core refuses to start on a fenced dataset.
  - `docs/DEPLOYMENT.md` states that a file lock cannot stop two servers each running its own copy of a backup.
- **Recovery epochs:** a restore, or any recovery that can move history backward, sets a new epoch, suspends delivery and enters trust recovery (§8.1.4). Clients then take the recovery path (§8.5).

### 8.5 Clients: store, journal and effective view (R2-DATA-01–05, R2-SYNC-04, -05, -08, R2-LIMIT-02)

#### 8.5.1 Store, atomic changes and states

- **One SQLite database per installation:**
  - It lives in the app's container: owner-only, protected until first unlock on iPhone and iPad, and excluded from device backups as in R1 (O-8).
  - It is never copied between devices.
- **What it holds:**
  - canonical merge states and derived records: the calendar from 30 days back to 90 days ahead, briefs for 30 days, plans, evidence excerpts and source freshness;
  - tombstones, and the metadata that prevents replay;
  - the journal of local and relayed operations with their signed bytes, Core receipts, and blobs;
  - peer progress, conflicts and the owner's draft resolutions;
  - local plans and briefs;
  - notification assignments and scheduling results;
  - inference requests and budget, and settings for this device only;
  - the search index, quarantined R1 queue items, and coverage metadata for every collection.
- **Atomic local change (R2-DATA-02).** One write transaction:
  1. validates the command;
  2. allocates the operation ID and the next sequence number of this launch's incarnation;
  3. signs the envelope, and stores it with the original input;
  4. updates the effective view and the search index;
  5. records follow-up work.

  The app says "saved" only after the commit. A disk-full error, an I/O error or a signing failure is reported as it is, and nothing is shown as saved.
- **Synchronization states (R2-SYNC-04):** saved on this device; copied to another device; submitted to Core; committed; committed with a conflict; rejected; waiting for dependencies; needs review. A copy on a peer never counts as a Core commitment.
- **Effective view:**
  - The canonical state plus every pending local and relayed operation, in causal order, through LisaMerge.
  - It is recomputed for each affected item whenever an operation, batch, receipt, rejection or revocation arrives.
  - Revoked or rejected operations drop out of the view but stay in the journal, for inspection and export (R2-L17).
- **Working set, provenance and time (R2-DATA-03–05):**
  - Configurable defaults. Eviction removes cached material only, never owner records, pending operations, conflicts, uncertain delivery records or replay metadata.
  - A filtered replica says it is incomplete, and nothing missing from it is taken as deleted.
  - Every item keeps its origin, source times, last retrieval or sync, revisions, interpretation status, and whether it is canonical, local or provisional.
  - The owner's planning zone is a replicated preference; the device zone is for display only. Instants are UTC milliseconds; timeouts and backoff use the monotonic clock.
- **Protected export:** unsynchronized work (the journal, conflicts and quarantined items) can be exported to a file the owner chooses.

#### 8.5.2 The snapshot installation point (R2-SYNC-05, R2-L12)

1. **Staging.** Verified chunks are parsed into staged tables inside the live database: `staged_canonical_*`, `staged_effective_*` and `staged_search`. Each chunk goes in its own short transaction, recording its index, so staging can resume after interruption. No downloaded bytes ever overwrite the database; only verified, parsed records are inserted.
2. **Building the staged view.** The staged effective view is built from the staged canonical tables plus the pending operations as of journal position T.
3. **The installation point** is one short write transaction. It:
   - checks that every chunk digest in the signed manifest has been verified;
   - applies to the staged view any operations journaled after T;
   - renames the staged tables over the live ones (SQLite's schema changes are transactional);
   - sets the canonical cursor, epoch and coverage.

   Journal, captures, conflicts, receipts, local artifacts and assignments are untouched.
4. **Concurrent local captures** take the same write lock, so each one either commits before T (in the staged view), between T and the installation point (re-applied inside it), or after it (applied to the new tables). None is lost.
5. **Crashes.** A crash before the installation point leaves the old view complete; staged tables are resumed or dropped on the next launch. A crash after it leaves the new view complete.
6. **One database file.** The point is a single-file commit, because SQLite in WAL mode does not commit atomically across attached databases.

**Storage limits around installation**
- **Disk exhaustion:**
  - Staging needs free space of at least twice the snapshot size plus a 64 MiB reserve.
  - It stops before eating into the reserve, so captures keep room to save.
  - Free space is checked with `volumeAvailableCapacityForImportantUsage` on Apple platforms and `statvfs` on Linux.
  - `SQLITE_FULL` rolls the transaction back and surfaces a truthful "not saved: storage full" (R2-L33).
- **WAL growth:**
  - `journal_size_limit` is 16 MiB.
  - A passive checkpoint runs after each staging batch, and a truncating checkpoint after the installation point.
  - On Core, snapshot generation is bounded in time, because its read transaction holds back checkpoints.
- **Acceptance (M2):**
  - Crash injection, by killing the process at each step, on real SQLite files.
  - Captures made during staging and at the installation point.
  - Disk full, simulated with SQLite's `max_page_count`, so that SQLite itself returns `SQLITE_FULL`.
  - WAL size measured while installing the 10,000-record and 100,000-operation dataset.
  - The database stays usable after every injected failure.

#### 8.5.3 Journal retention, replay after restore and visibility (finding 4)

**Design**
- **Uncommitted operations** are never dropped.
- **A committed operation's signed body is kept until both:**
  - its effect is installed in the replica's canonical state; and
  - Core's backup watermark (§8.4) covers its commit position in the same epoch.

  Relays keep the bodies they carry for other devices under the same rule.
- **Visibility before the canonical change.** The local edit's overlay is removed only when the canonical state containing the operation is installed, never when the receipt arrives. So a receipt that arrives first shows "committed" while the edit stays visible.
- **Caps.** Committed bodies are kept for at most 90 days or 64 MiB per replica (configurable). Past the cap, the oldest committed bodies are dropped, visibly ("recovery coverage reduced: Core hasn't backed up recent changes"). Their ID, digest, outcome and position stay.
- **After a restore (new epoch).** The device resubmits every retained body whose commit position is above the restored backup's watermark. Core verifies each signature and the origin's roster status (§8.1.4) and applies it, keeping the old receipt as provenance.
- **What can be recovered:** owner changes made on Apple devices that some reachable device still holds, either the origin or a relay, and that the caps didn't drop.
- **What cannot be recovered:**
  - changes made through Core itself after the backup (CLI and v1 callers), which keep no signed journal;
  - Core-derived results, which are re-derived as connectors refetch from the restored cursors, with natural keys preventing duplicates;
  - delivery attempts after the backup. These come back as uncertain and are never replayed.
- **Same-device restore.** When the replica and the Keychain both roll back, the next launch starts a new incarnation anyway (§8.1.1), so no (device, incarnation, sequence) identity can repeat.
  - The new incarnation's chain link names the restored predecessor. Core and peers see that predecessor already has a successor, and report "restored installation".
  - Pending operations from before the backup return `duplicate` if Core has them, and are accepted if it doesn't.

**After a failure or retry**
- **Watermark unavailable** (Core never backed up): bodies stay until the caps.
- **A resubmission after restore is rejected** (for example, a revoked origin): kept and shown as rejected, with its input.

**Acceptance checks**
- **Extended R2-L18 (M2):**
  1. Device D creates operations in incarnation I1.
  2. The harness copies D's replica and key material, imitating an encrypted same-device backup that includes the Keychain.
  3. D continues: more I1 operations, then a new launch I2, and syncs to Core.
  4. The copy is restored and D launches again, starting I3, and creates operations.
  5. Core accepts every I3 operation, finds no identity or sequence reuse, records the fork, and answers `duplicate` for the restored pending operations.
- **Negative control:** a variant with a per-installation incarnation shows the reuse this design prevents. It exists in the harness only.
- **M3 additions:**
  - a receipt that arrives before its canonical change, checking that the edit stays visible;
  - retention against the watermark;
  - after a restore, recovery of post-backup edits from journals, extending R2-L29.

#### 8.5.4 The direct HTTPS sync path (R2-SYNC-08)

- **Component owners:**
  - `LisaSyncEngine` (the Core session);
  - `LisaClient.URLSessionTransport` (HTTP);
  - `Apps/Shared/Trust/PinnedServerTrustEvaluator` (Core's public-key pin);
  - on Core, `LisaCoreAPI` and `LisaAPIServer`.

  It is built in M3.
- **Reconciliation order:**
  1. Authenticate and negotiate.
  2. Fetch trust, revocation, policy, epoch and the backup watermark.
  3. Stop using any authority that is no longer valid.
  4. Recover the baseline: changes, or a snapshot when the cursor or epoch no longer fits.
  5. Submit pending operations in dependency order, uploading blobs first.
  6. Collect outcomes, then rebuild the view.
  7. Surface conflicts and rejections.
  8. Recompute plans, briefs and local schedules.
  9. Resume incremental sync.

  Pending work is never discarded before it is preserved.
- **Linux evidence:**
  - URLSession on Linux cannot be given a custom trust anchor (R1 D-45). So the Linux harness carries the same protocol logic over a test-only libcurl transport with public-key pinning, against the real TLS server.
  - It also runs URLSessionTransport itself over plain HTTP on loopback, the only place the server allows plain HTTP.
  - The URLSession pin is verified on a device in session X2.

### 8.6 Nearby synchronization (R2-NEAR-01–05; finding 2)

**What the target OS versions support (TN3213 and the Security reference, §1.5)**
- `NWListener`, `NWBrowser` and `NWConnection`, with `includePeerToPeer`, Bonjour and custom framing, all exist on macOS 15 and iOS 18. Lisa uses these older APIs; the newer `NetworkConnection` family needs iOS 26 and would raise the deployment targets.
- **TLS-PSK:** works only with these older APIs, only over TLS 1.2 (not TLS 1.3, not QUIC). The documented `tls_ciphersuite_t` values include no PSK suite, so a PSK suite could be requested only by its raw IANA value, and whether a forward-secret ECDHE-PSK suite is accepted is undocumented.
- **Mutual TLS (TLS-PKI):** local identity, required peer authentication, a custom verify block and the TLS exporter are all available. Apple has no API to create the identity's certificate.
- **Multipeer Connectivity** is deprecated and not used.

**Session layer, the same under both transport designs**
- **Hello:** each side sends its protocol version, device ID, roster (epoch, version) and a nonce.
- **Authentication:** each side signs, with its operation-signing key:
  - `"lisa-nearby-auth-v1"`;
  - both nonces and both device IDs;
  - a 32-byte TLS exporter value (label `EXPORTER-lisa-nearby-v1`, from `sec_protocol_metadata_create_secret`);
  - the roster (epoch, version).

  Each side checks the other's signature against its newest roster.
- **Why this binds the session:** a relay sitting between two devices has two TLS sessions with different exporter values, so the signatures fail. On a mismatch the session closes before any data moves.
- **Data exchange:** inventories, then bounded exchanges of signed operations, Core receipts, Core-signed change batches, snapshot chunks, blobs and rosters, in the frames of §8.15, then peer acknowledgements. A peer acknowledgement records "copied to another device" and nothing more.
- **Connection behavior** (set explicitly, as TN3213 advises):
  - TCP keepalives and a send timeout;
  - backpressure by awaiting each send;
  - idle sessions close after 30 seconds.
- **Deduplication:** after authentication, the connection opened by the lower device ID survives.
- **Privacy:** random Bonjour instance names per session; nothing identifying in the TXT record except, for the PSK design, the rotating tag below.

**Design A: pair-specific pre-shared keys**
- **Key:** K_ij = HKDF-SHA256 of the P-256 key agreement between devices i and j, with the dataset ID as salt and `"lisa-nearby-psk-v1"` followed by both device IDs, sorted, as info.
- **How the initiator chooses the key.** The listener publishes, in its TXT record, a tag that rotates every 15 minutes: the first 16 bytes of HMAC-SHA256(discovery key, `"lisa-disc-v1"` ‖ window ‖ device ID).
  - The discovery key is a dataset secret delivered with the authorization bundle over HTTPS. It is never put in the public roster, and it rotates on every revocation.
  - The initiator computes the tags of the active roster peers for the current and adjacent windows, finds the listener, and uses K_ij.
  - As its PSK identity it sends its own tag for the same window. The listener's PSK selection block finds the initiator the same way.
- **Privacy:** the tags change every window, and a passive observer can't link them to a device.
- **Limits:** TLS 1.2 only, and a PSK suite only by raw value. Forward secrecy exists only if an ECDHE-PSK suite is negotiated. A revoked device that still holds the old discovery key can recognize tags until the rotation reaches every device.

**Design B: roster-bound mutual TLS (the supported alternative)**
- **Identity:** each device creates a P-256 TLS key in the Secure Enclave and a self-signed X.509 certificate for it, using LisaTrust's fixed-template encoder. The certificate holds version 3, a random serial number, a one-year validity, key usage `digitalSignature`, and extended key usage server and client authentication.
  - The certificate is stored in the Keychain beside the key, so Security forms a `SecIdentity`.
  - The key's hash is listed in the device's roster entry, from enrollment or a signed key update.
  - The encoder is tested on Linux by parsing its output with the `openssl` command (test-only). The alternative is swift-certificates, as TN3213 suggests, which would need a new dependency (P-08).
- **Handshake:** TLS 1.3 with mutual authentication required. The verify block accepts the peer only if its leaf certificate's public key matches an active roster entry; no CA chain or host name is involved. Unknown or revoked keys fail.
- **Discovery:** no key selection is needed. The initiator connects to the discovered Lisa services (at most 9) and learns who answered during the encrypted handshake.

**After a failure or retry**
- **Handshake or authentication failure:** the session closes, with backoff on the monotonic clock for each endpoint. It is retried after the backoff or when the roster changes. There is never an unauthenticated fallback.
- **Interrupted transfer:** it resumes from durable progress kept for each peer (operation IDs and chunk indexes), and duplicates are harmless.
- **Revoked peer:** refused, and not retried until a roster says otherwise.
- **Local network denied** (`kDNSServiceErr_PolicyDenied` or `localNetworkDenied`): a visible unavailable state, with no retries until permission changes. The first nearby operation always runs in the foreground, because iOS silently denies a background one while permission is undetermined (TN3179).

**Deciding experiment N-1:** defined in §10.5 and run by the owner in session X1, right after M1. It runs both designs on the same devices in one session.
- **Decision rule:**
  - Design A is adopted only if it passes every criterion **and** negotiates a forward-secret ECDHE-PSK suite on every device pair.
  - Otherwise Design B is adopted. Given TN3213 and the documented suites, Design B is the expected outcome.
  - If both fail, nearby work stops and is reported. Core sync and local work are unaffected.
- **Meanwhile on Fedora:** the session layer, framing, authentication with a simulated exporter, relay, storage and all of Core continue.

**Acceptance checks**
- **Linux, over the in-memory link, labeled simulated:**
  - hello and authentication;
  - exporter mismatch, which simulates a relay in the middle;
  - an unknown peer and a revoked peer;
  - resuming an interrupted transfer, and deduplication;
  - R2-L04, L15, L17 and L36, and the R2 §18.2 scenario.
- **Apple:** N-1 (X1); then the production nearby transport on physical device pairs (X4: R2-A03–A07).

**Other rules**
- **Relay:**
  - A peer forwards other devices' signed operations to Core with its own credential, and returns Core-signed receipts and batches.
  - It never rewrites or re-signs another device's operation, never invents a receipt, and never shares its credential.
  - It never forwards URLs, commands or general traffic.
- **Background:**
  - Bounded `BGAppRefreshTask` requests for Core sync on iPhone and iPad; nearby sessions only in the foreground.
  - No audio, location or VoIP background mode.
  - The UI distinguishes "available now", "waiting for the app to be open", "background time requested but not yet granted" and "permission or radio unavailable".

### 8.7 Capabilities and transitions (R2-CAP-01–04)

- **Each client tracks these separately:**
  - authenticated Core reachability, and API and sync compatibility;
  - each fallback provider, and model availability;
  - nearby availability;
  - data freshness and coverage;
  - notification permission and schedule coverage;
  - enrollment and trust state;
  - storage health.

  Core reachability is known only from an authenticated exchange, never from a network-path or VPN signal.
- **Features follow the capability they need**, not a global mode switch. `docs/OFFLINE-BEHAVIOR.md` turns the R2-CAP-02 matrix into a table, with the checks that enforce each row.
- **Transitions are safe:**
  - A connectivity change never interrupts a durable capture, replaces a draft, clears the database, resends a finished inference, replays expired deliveries, resets retry counters indefinitely or promotes a provisional plan.
  - Retries use cancellation, bounded timeouts, exponential backoff with jitter, and a manual "Try again".
  - Authentication failure, revocation and incompatible versions stop retrying, show what to do, and never fall back to anything insecure.

### 8.8 Offline intelligence, fallback inference and public retrieval (R2-CAP-03, R2-INT-01–05, R2-WORK-01–04; finding 8)

**Offline intelligence**
- **With no model:**
  - search;
  - sorting by deadline, priority and state, and detecting overdue tasks;
  - a provisional plan from R1's planner and constraints, with explanations of unscheduled work and conflicts;
  - a structured local brief;
  - permitted preference changes;
  - managing tasks and reminders.

  Free-form captures stay pending; nothing is invented.
- **Local plan (R2-WORK-01):**
  - It records the canonical checkpoint, the provisional operations included, calendar coverage and freshness, open conflicts, the algorithm version and when it was made.
  - It is shown as provisional until Core reconciles. Gaps in a stale calendar are shown as unverified.
  - Locked and accepted blocks never silently move.
- **Local brief (R2-WORK-02):** it has its own identity (device and input version) and never replaces the canonical brief. Ages, missing sources and regeneration failures are shown, and the readable and spoken versions carry the same uncertainty.

**Fallback inference**
- **Provider (R2-INT-01):**
  - The OpenAI-compatible adapter runs over `LisaClientHTTP` (URLSession).
  - It is configured on each device: endpoint, model, a Keychain credential reference, explicit consent to share data, timeout, input and output bounds, the request budget, and its status.
  - Nothing is enabled by default, and Core's provider settings never authorize a client.
- **The five workflows (R2-INT-02):**
  - interpret a new capture into proposed tasks, ideas or events;
  - summarize selected local evidence;
  - improve the local brief;
  - explain the provisional plan;
  - answer bounded questions from the local working set.

  Each result says it was made from local data and names missing or stale sources, and passes the same validation and permission checks as Core's suggestions.
- **Requests (R2-INT-04, -05):**
  - **Record:** each request stores its identity (from its intent and input revisions), inputs, provider and model, template version, status, validated result and usage.
  - **No duplicates:** repeated taps and connectivity changes reuse the same request. A timeout after sending is "outcome uncertain" and is not resent automatically.
  - **Limits:** one request in flight and ten a day per device. At most one repair attempt, and the repair counts against the daily budget. The count is kept per day of the owner's planning zone, persisted, and clock changes cannot reset it.
  - **No global cap:** per-device limits are not a global spending cap, and the documentation says so.
  - **On reconnection:** results reach Core as proposals with their evidence; results based on deleted or obsolete evidence are invalidated or revalidated first.

**Public URL retrieval (R2-INT-03; finding 8)**

**Why `LisaHTTP1` exists, and its scope**
- TN3151 recommends URLSession for HTTP, and Lisa uses it for Core sync and for model endpoints.
- But URLSession offers no point at which the app can inspect the connected address before the request is written; its task metrics arrive after the exchange. So with URLSession, R1's control — never send a request to a non-public address, enforced in libcurl before any request byte — cannot be kept for arbitrary URLs.
- TN3151 allows "a simplistic HTTP client … on top of a TCP API" for exactly this kind of gap. `LisaHTTP1` is that, and nothing more:
  - GET only, HTTP/1.1, one request per connection;
  - `Accept-Encoding: identity`; no cookies, authentication, caching, upgrades or pipelining;
  - Content-Length or chunked bodies;
  - R1's limits on headers, body size, time and redirect count.
- It is used only for owner-requested public feeds and pages.
- A portable parser is preferred over CFHTTPMessage so that one implementation is tested on Linux and used on Apple platforms.

**The production Apple path (`Apps/Shared/PublicFetch`)**
- **DNS:** connect by name (TN3151) with `NWConnection`, so the system handles DNS, DNS64/NAT64, Happy Eyeballs and VPN On Demand. An optional early check with the system resolver refuses a name whose addresses are all non-public; the connection never dials a pre-resolved address.
- **Proxies:** `preferNoProxies` is set. A connection whose path goes through a proxy counts as unverifiable.
- **TLS:** the system TLS stack with default trust evaluation for the URL's host name (SNI and certificate name), and no custom verify block.
- **Checking the destination:**
  - When the connection is ready, its `currentPath.remoteEndpoint` must be an IP address that passes R1's address policy (LisaHTTP), for both IPv4 and IPv6.
  - IPv4-mapped addresses and the NAT64 prefix `64:ff9b::/96` are judged by the IPv4 address they embed. Link-local, unique-local, loopback, private, carrier-grade NAT and documentation ranges are refused.
  - Otherwise the connection is cancelled before a single HTTP byte is written. Only the TCP and TLS handshakes, carrying the public host name, ever reach the peer.
- **Redirects:** each hop is a new connection that passes the same checks, under R1's redirect policy (scheme rules, no credentials in URLs, at most 5 hops).
- **When verification is unavailable** — no IP remote endpoint, a proxy path, a path type the policy doesn't cover, or no endpoint reported — the fetch is refused before any request byte. It is shown as "Couldn't verify where this link leads; not fetched" and left for Core to retrieve with libcurl's checks. It is never retried through URLSession or any other unverified path.
- **Links in content** are never followed.
- **Provenance:** results carry client provenance, never advance Core's cursors, and never count as a canonical refresh. Private connectors stay on Core.

**Configured model endpoints have their own policy**
- **Transport:** URLSession to the owner-configured host only, with no redirects.
- **TLS:** HTTPS with Apple's trust evaluation, or an owner-pinned certificate for a server on the owner's network.
- **Consent and addresses:** an explicit data-sharing consent. There is no public-address requirement, because R1 already permits explicitly configured local model endpoints.

**After a failure or retry**
- **Refused or unverifiable fetches:** recorded with their reason and never retried automatically; the owner can ask again.
- **Model timeouts after sending:** uncertain, as above.

**Acceptance checks**
- **Linux (M7):** LisaHTTP1's parser, limits and redirect rules, against loopback servers. The real address policy is driven by a test byte stream that reports chosen remote addresses: public, private, NAT64, IPv4-mapped and link-local. Also the five fallback workflows against a loopback OpenAI-compatible server: success, malformed output with one repair counted against the budget, timeout, throttling and uncertain usage.
- **Apple (session X5):**
  - a public feed fetch succeeds;
  - a name that resolves to a private address is refused before any HTTP byte, checked with a listener on the owner's network that records whether a request arrived;
  - a redirect to a private address is refused;
  - fetching works on a NAT64 network (macOS Internet Sharing);
  - a configured proxy makes the fetch "unverifiable".

### 8.9 Notifications and external delivery (R2-NOT-01–06; finding 6)

**Core decides, under R1's unchanged policy:** eligibility, escalation, quiet hours, owner-only destinations, generic content, validity windows and stale suppression; provider acceptance, app receipt and owner acknowledgement stay separate. Every enabled paired device is targeted by default, now including the Mac, which registers for APNs as a device.

**Design**
- **Identifiers.**
  - **Logical occurrence:** R1's reminder occurrence key (for example `deadline:task:<id>:<change sequence>:<offset>`). Snoozes and content revisions don't change it; a moved trigger time or new content is a new generation of the same occurrence.
  - **OS request identifier:** `lisa.r.` followed by the first 26 base32 characters of SHA-256(`"lisa.local-notification.v1:"` ‖ dataset ID ‖ occurrence key ‖ device ID).
    - It is stable for each logical occurrence and target device, and opaque: it reveals nothing about the item.
    - Rescheduling with the same identifier replaces the earlier request atomically (`UNNotificationRequest.identifier`), so a replacement can never leave two Lisa requests for one occurrence on a device.
    - R1's APNs collapse identifiers stay as they are. Neither identifier is ever used for idempotency.
  - **Only reminder occurrences** (deadline, overdue, plan block, proposal follow-up, brief) are delegated. Commitment-change notifications stay Core-owned and go through APNs.
- **Generations.**
  - Each (occurrence, device) ownership record has a generation number, assigned by Core, that only increases.
  - The device stores the generation in its database and in the request's `userInfo`.
  - Assignments and reports with a lower generation than the one stored are ignored as stale, and an equal one is idempotent. Core applies a report only to the current generation.
- **Ownership states:** R2-NOT-03's list — Core-owned; reserved for local scheduling; local scheduling confirmed; scheduling failed; suppressed or cancelled; expired; outcome unknown — plus "fired", when the device has evidence the alert was presented.
  - Core pushes a slot only while it is Core-owned.
  - "Scheduling failed" (confirmed not scheduled) and a confirmed cancellation return the slot to Core.
  - A suppressed occurrence (its subject resolved) needs no delivery at all.
  - "Fired", "expired" and "outcome unknown" never return the slot to Core.
- **Handoff:**
  1. In one transaction, Core reserves the slot for the device and suppresses its own push.
  2. The device fetches the signed assignment, generation g.
  3. It stores the assignment, adds the request under the stable identifier, reads the pending list back (generation g in `userInfo`), and marks it scheduled.
  4. It reports `scheduled(g)`.
  5. Core records it, never as proof of display.
- **Replacement** (time or content changed, g+1): store, add under the same identifier, verify, mark, report.
- **Cancellation** (g+1 is a cancel):
  1. Store the cancel.
  2. Remove the pending request.
  3. Verify it is absent from the pending list.
  4. Check the delivered list.
  5. Report `cancelled(g+1)` if it never fired, or `fired(g)` if it is among the delivered notifications.
- **Expiry:** nothing is scheduled past `validUntil`. An occurrence past `validUntil` without evidence of firing is reported `expired`, and never rescheduled or replayed.
- **Alerts already delivered by the OS:**
  - If the notification is listed by `getDeliveredNotifications`, or was seen by `willPresent` or an action handler, it is `fired`.
  - The app removes stale delivered alerts for resolved subjects where the platform allows, and keeps the "fired" record.
- **Uncertainty:** an occurrence whose trigger time has passed, is absent from both the pending and delivered lists, and left no callback evidence is `outcome unknown`, because the owner may have cleared it or it may never have fired. Core keeps the slot device-owned and unknown, sends no push for it, and shows a coverage gap.
- **Local schedules** reach up to 48 hours ahead, with at most 32 Lisa requests per device, preferring confirmed and time-sensitive reminders. The app shows "Notifications scheduled through <time>".
- **Locally created reminders:**
  - A reminder created offline is owned by the device that created it. Peers show it as pending but schedule nothing for that slot.
  - Once Core accepts it, Core adds future slots for the other devices and keeps the creator's, without replaying missed past reminders.
  - No device takes over a Core-owned slot because of an outage.
- **Reconciliation** runs on launch, on return to the foreground, after sync, and on notification actions. It repeats any unfinished step above idempotently, cancels obsolete requests, applies acknowledgements, completions, cancellations and deletions, keeps uncertain handoffs, and reports permission changes.

**After a failure or retry**
- **Crash between any two steps:** reconciliation completes the step from the stored assignment and the OS's pending and delivered lists. The stable identifier rules out two pending requests for one occurrence.
- **Lost report:** the report is resent until acknowledged, and Core ignores it if its generation is stale.
- **Device unreachable during handoff:** the slot stays reserved and uncertain. Core does not reclaim it.
- **Email and calls:**
  - Only Core sends them, keeping R1's outbox, claiming, recipient enforcement, quiet hours, confirmation and urgency rules, rate limits and handling of unknown outcomes.
  - A missing acknowledgement or a disconnected device never authorizes a call.
  - A restored Core starts with delivery suspended (§8.1.4).

**Acceptance checks**
- **Linux (M8):** a simulated notification center (test-only) that reproduces the documented semantics: same-identifier replacement, separate pending and delivered lists, firing at the trigger time, and the owner clearing alerts. With a crash injected after each step, it checks:
  - never two pending requests for one occurrence;
  - stale generations ignored;
  - no push for a slot that isn't Core-owned;
  - fired-before-cancel reported as fired;
  - absent after the trigger reported as unknown, without reclaim;
  - expired occurrences never replayed;
  - completion and deletion cancelling pending work.

  This covers R2-L24 to L27.
- **Apple (session X6):** same-identifier replacement, the delivered list and termination, plus permission changes, Focus, previews and lock state (R2-A09 to A12).

### 8.10 Core deployment (R2-CORE-01–05)

- **Image:** a multi-stage Dockerfile. The build stage is `swift:6.4.2-trixie@sha256:9733821c…430097`; it builds `lisa` in release mode with `--force-resolved-versions`. The runtime stage is `swift:6.4.2-trixie-slim@sha256:42571ee8…cccea0d`, which carries the matching Swift runtime, plus Debian 13's SQLite, libxml2, libcurl, CA-certificate and time-zone packages.
  - Package versions are pinned and recorded at M4. Bit-for-bit reproducibility is not claimed.
  - Both `linux/amd64` and `linux/arm64` are declared, and each architecture's build and run are reported separately.
- **Container boundaries:**
  - a non-root user (UID 10001);
  - `/var/lib/lisa` (data volume), `/etc/lisa` (configuration, read-only) and `/run/secrets` (Compose file secrets), plus a bounded tmpfs for `/tmp`;
  - a read-only root filesystem;
  - `cap_drop: ALL`, `no-new-privileges`, no privileged mode and no Docker socket;
  - no secret in a layer or build argument;
  - bounded logs, through the log driver's limits and Lisa's own rotation;
  - `SIGTERM` handled within a stop grace period longer than Lisa's shutdown.
- **Effective secret ownership:**
  - R1's file-secret checks stay unweakened: the file must be owned by the process's user and readable only by it.
  - Under rootful Docker, host files are owned by UID 10001 with mode 0400, which Compose's file secrets preserve. A rootless engine maps container UIDs into this account's subordinate range, so the host owner must be the mapped ID.
  - Either way, `lisa core doctor --secrets` reports the owner and mode as the running process sees them, and that is what the check verifies.
- **SELinux (enforcing on Fedora):**
  - Bind mounts use `:Z` or `:z` labels.
  - Compose secret files need the `container_file_t` type on the host, which the owner sets with `chcon` or `semanage fcontext`.
  - SELinux is never disabled or relaxed with `label=disable`.
- **Network exposure (R2-CORE-03):**
  - The default configuration listens on loopback only.
  - Production names an explicit VPN address. Compose publishes only on `${LISA_VPN_ADDRESS}`, which must be set, so there is no fallback to all interfaces. IPv6 is published only when an IPv6 VPN address is given.
  - Outside a container, Lisa binds the VPN address itself and refuses to start without it.
  - `docs/DEPLOYMENT.md` gives the IPv4 and IPv6 exposure checks, and firewall and routing verification, covering Docker's own forwarding rules, which bypass host firewall front-ends.
  - No public API. APNs and providers are reached only by outbound connections. Lisa installs or changes no VPN software.
- **Health (R2-CORE-05):**
  - Reported separately: liveness, database readiness, sync readiness, each source, the model, each delivery channel, storage, backup age, and sync lag per device.
  - The running Core rewrites `<data>/run/health.json` every 15 seconds with a sequence number.
  - `lisa core health --probe live` fails if the file is missing or older than 60 seconds. `--probe ready` also requires database and sync readiness. This is the container health check: every 30 seconds, 3 retries.
  - A failing news source never makes Core unready.
- **Restart:**
  1. Recover transactions and waiting operations.
  2. Inspect uncertain outcomes.
  3. Reconcile schedules and assignments.
  4. Suppress obsolete work.
  5. Resume bounded processing.
  6. Report degraded capabilities.

  A persistent provider failure is a health state, not a restart loop.
- **Backup and restore (R2-CORE-06):**
  - **Method:** SQLite's online backup, so WAL content is included.
  - **Manifest v2:** schema, dataset, epoch, cut position, counts taken from the same snapshot, and file digests.
  - **Coverage:** canonical records, operations, receipts, tombstones, blobs, delivery history with unknown outcomes, and device enrollment metadata. Secrets are restored separately, through the secret files.
  - **`lisa core backup validate`** checks a backup and advances the backup watermark.
  - **`lisa core restore`** fences the replaced data directory, sets a new epoch, suspends delivery and enters trust recovery.

#### 8.11.1 The v2 API

- **Negotiation:** every v2 request carries the protocol version and client features. `GET /v2/capabilities` returns:

  An unknown required capability fails with `upgrade_required`.
- **Routes:**

|---|---|

- **Errors (R2-API-03):**
  - Typed codes: malformed data, unauthenticated, forbidden, revoked device, expired trust, wrong dataset, epoch mismatch, trust recovery, unsupported version (`upgrade_required`), missing dependency, conflict, oversized, throttled, insufficient storage, cursor expired and temporary failure.
  - A batch answers for each operation separately. A client checkpoint never moves past changes it hasn't installed.
  - `GET /v2/tasks` stays a typed 404, as the R1 suite requires, and v1 and v2 share one error shape.

#### 8.11.2 v1 compatibility (finding 7)

**Rules applied to every v1 mutation**
1. **Request identity stays caller-scoped.** R1's ledger key `<scope>:<request ID>` and R1's request fingerprint (method, path, sorted query and body) are checked first:
   - same key and fingerprint: the recorded response is replayed;
   - same key, different fingerprint: 422 `requestIDReused`;
   - only a first-time request is translated.
2. **Revision checks stay R1's.** `expectedRevision` is compared with the projection's revision; a mismatch is a 409 with `currentRevision`. When it matches, the translated operation observes the canonical versions of the fields it changes, so it cannot hide a concurrent edit that Core already holds.
3. **The translation is atomic.** It runs in one transaction with the operation record and the v1 idempotency record (fixing R1's non-atomic ledger).
4. **Operations are Core-attested.**
   - **Origin:** Core's v1 adapter, signed with Core's key, with the acting principal (local owner or legacy device) recorded in the payload.
   - **Operation ID:** the first 16 bytes of SHA-256(`"lisa-v1-op"` ‖ dataset ID ‖ scope ‖ request ID), so a retry maps to the same operation. Retries never rebuild an operation, because rule 1 answers them first.
5. **`upgrade_required` (HTTP 426, typed) when safe translation is impossible:**
   - the request changes a field that has an unresolved conflict, which a v1 client can neither see nor resolve;
   - the request comes from an R2-enrolled device, which must use signed v2 operations;
   - the request has a shape no R2 operation defines.
6. **Legacy pairing stays outside R2 enrollment** (§8.1.2).

**Route by route**

| v1 route | R2 behavior |
|---|---|
| `GET /v1/health` | Kept, with R2 capability fields added |
| `GET /v1/rundown`, `GET /v1/brief` | Kept: the canonical plan and brief |

| `POST /v1/briefs/regenerate` | Kept as a Core command; briefs are derived artifacts, not owner data |

| `POST /v1/captures/{id}/retrieve` | Kept as a Core command (Core-side retrieval with libcurl's checks) |
| `GET /v1/tasks`, `GET /v1/tasks/{id}` | Kept |

| `PATCH /v1/tasks/{id}` | Field-edit operations and a status operation, with the revision checked; `upgrade_required` if a changed field is in conflict |

| `GET /v1/event-proposals`, `GET …/{id}/calendar-file` | Kept |
| `POST /v1/event-proposals/{id}/actions` | Review or correction operations, with the revision checked |

### 8.13 Migration from R1 and rollback (R2-MIG-01–04; finding 5)

**Preparation, with no interval between the final backup and the fence**
1. **The owner stops every R1 writer** and disables its automatic start (the Mac app's login item; any `lisa serve` service), following the checklist in `docs/MIGRATION-R1-R2.md`.
2. **`lisa core migrate prepare --r1-data-dir <dir>`** runs where the R1 data lives. It takes R1's own data-directory lock and holds it to the end, so no R1 writer can start meanwhile. Under the lock it:
   1. inventories the R1 schema and application version, identifiers, secret references (names only), source cursors, queues, deliveries and their unknown outcomes;
   2. writes and validates the **rollback backup**: the R1 database at schema v4, plus `runtime-state.json`, `model-requests.json` and `dry-run/captures.jsonl`, with digests in a manifest;
   3. **fences** the R1 database by setting its schema version to a value R1 refuses (R1's verified refusal of newer schemas). R2 Core refuses it too, except through `migrate run`;
   4. writes the **migration input**: a backup of the fenced database, with the same files.

   No write can occur between the backups and the fence, because the lock is held throughout and the fence makes R1 refuse the database even after the lock is released.
3. **If the R1 data is on a Mac,** step 2 needs the R2 `lisa` built for macOS, which first exists after session X3. Until then:
   - the owner copies the stopped data directory to the Linux server with R1 removed from the Mac;
   - `prepare` runs against the copy;
   - the owner's confirmation that no R1 software remains on the Mac is recorded in the migration record.

**Migration (`lisa core migrate run`, on Linux)**
- **Kept:** every identifier, explicit corrections (as owner authority), preferences, source cursors, calendar occurrences, brief and plan history, reminder state, delivery attempts and unknown outcomes, and device registrations, which become legacy registrations that can be upgraded.
- **Files outside SQLite:**
  - `runtime-state.json` becomes the initial source schedule. Losing it would only make sources sync early.
  - `model-requests.json` becomes the current day's model budget, so migration doesn't reset the daily limit.
  - Dry-run captures are archived, not migrated.
- **Deliveries:**
  - `outcomeUnknown`, and attempts interrupted while submitting, stay unknown and are never resent.
  - Attempts interrupted while preparing (nothing sent) return to pending.
  - Pending deliveries past their validity expire.
  - Core starts with delivery suspended.
- **Causal metadata** starts from a documented migration origin. No "latest" timestamp is invented to make migrated values win.

**R1 client queues (R2-MIG-03)**
- On first launch, the R2 app reads the R1 queue file (`lisa-client-queue` v1). For each entry it keeps the original input and request ID, then classifies it through `POST /v2/migration/r1-requests/lookup`, authenticated with the device's R1 credential:

| Queue entry | Classification |
|---|---|
| `done` | Already applied; nothing to do |
| Never attempted (no `uncertainSince`) | Not applied. Converted to an R2 operation if its kind has a defined operation and its expected revision still matches; otherwise quarantined |
| May have been applied (`uncertainSince` set) and Core holds a migrated idempotency record with the same fingerprint | Applied; marked done, never replayed |
| Same, but the record's fingerprint differs | Quarantined (conflict) |
| Same, with no record | Absence is proof only where R1 left direct evidence in the same transaction as the change: a capture's request key, or idempotent notification receipts. Otherwise quarantined, because R1's records expire after 30 days and R1 wrote them outside the change's transaction |

- Quarantined entries are shown for the owner to apply or discard, with the current state beside the intended change.
- Core-only secrets are provisioned again through the secret files.

**Cutover:** the R1 host never resumes, the Mac connects as an R2 client, devices reconcile, and the owner resumes delivery.

**Rollback (`lisa core migrate rollback`), after R2 has accepted owner edits and recorded delivery attempts**
1. **Suspend and settle delivery.** Delivery is suspended. Core cancels every delegated local assignment and collects device confirmations. For devices that don't confirm, their slots are recorded as "may fire locally".
2. **Stop and fence Core.** Core stops and its dataset is fenced.
3. **Reverse migration (v5 to v4)** produces an R1-compatible database from Core's current state:
   - R2 tables are dropped, and archived in a v5 backup.
   - Projections are kept in R1's record shape: R2 only adds optional fields, and the note entries still produce R1's `notes` text.
   - **New owner edits** survive, because they are in the projections.
   - **Delivery attempts** keep their final state (accepted, captured, failed or unknown), so R1 never resends them.
   - **Deliveries R2 created but never attempted** become `cancelled` with reason "rollback: not attempted", and are listed in the rollback report.
   - **Slots that may fire locally** have their R1 deliveries to that device suppressed, so R1 doesn't push to that device for those occurrences.
4. **Verify before R1 delivery resumes.** The tool checks the result with R1's own read-only commands. Only then does the owner start R1.
5. **Fallback:** the rollback backup from `prepare`. Owner edits made after migration are then listed in the rollback report for re-entry, and R2's delivery attempts are imported as final states so R1 doesn't resend them.
6. **Safety:** R1 and R2 schedulers never run together, and old software never opens a newer schema.

**After a failure or retry**
- **A step fails:** each step is resumable and idempotent; a failed migration leaves the fenced R1 data and both backups intact.
- **R1 started by mistake:** it refuses the fenced database.
- **R2 Core started on the old R1 directory:** it refuses it.

**Acceptance (M9, Linux)**
1. **Fixtures from M0.** M0 keeps the R1 release `lisa` binary and synthetic R1 data directories under `.tmp/r2/<M0 run>/`, built with the R1 package before any R2 change. The data directories contain pending, uncertain and dry-run deliveries, queue files, `runtime-state.json` and `model-requests.json`.
2. **Migrate** with `prepare` and `run`, and check identities, corrections, cursors, reminder state and delivery history (R2-L30).
3. **Classify queues:** the ambiguous R1 queue entries are quarantined (R2-L31).
4. **Use R2:** an R2 replica commits a new owner edit, and Core records a delivery attempt (a dry-run capture, plus a scripted push that times out after sending, which makes it unknown).
5. **Roll back.**
6. **Check with R1's binary:**
   - the edit is present;
   - the attempted deliveries are final, not pending;
   - an R1 `run-once` sends nothing again;
   - the never-attempted delivery shows as cancelled in the report;
   - R1 refuses the fenced Core dataset, and R2 refuses the fenced R1 directory.

This covers R2-D10 and R2-D11 in their portable form. The owner repeats the cutover on the server.

### 8.15 Transfer sizes, encoding and chunking (R2-LIMIT-01; finding 8)

**Encoding**
- **Signed bodies** use one canonical JSON form:
  - UTF-8, with object keys sorted by Unicode scalar value and no whitespace;
  - integers only: instants are milliseconds and decimals are strings;
  - minimal escaping; no duplicate keys; nesting depth at most 16.
- **Signatures** are raw 64-byte P-256 ECDSA values over a domain-separated prefix plus the body. Nothing re-encodes a signed body; the exact bytes travel and are stored.
- **Over HTTP,** JSON envelopes carry signed bodies as base64url.
- **In nearby frames,** bodies travel as raw bytes, so base64 never inflates them.

**Nearby frame:** an 8-byte header (32-bit big-endian length, 16-bit type, 16-bit flags) and a payload. The total is at most 1 MiB. The length is checked from the header before any allocation, and a frame over the limit closes the session.

**What fits where**

| Unit | Limit | How it is carried | How it fits a 1 MiB frame |
|---|---|---|---|
| Operation | 64 KiB signed body | Body plus 64-byte signature, length-prefixed | Many per frame |
| Operation batch | 100 operations and 512 KiB of bodies and signatures | One `OPS` frame, or one HTTP request of at most 512 KiB after base64 | 512 KiB plus small headers |
| Core-signed change batch | 512 KiB of signed bytes | One frame or one HTTP response, never split, so its signature stays checkable | Fits |
| Entity state inside batches and snapshots | 256 KiB encoded | Length-prefixed record | Any single record fits a batch |
| Snapshot chunk | 512 KiB of the record stream | One frame or response per chunk. The chunk's SHA-256 is listed in the signed manifest. Records span chunks and are parsed as a stream | Fits |
| Content blob chunk | 256 KiB | One frame, or `PUT`/`GET /v2/blobs/{digest}/chunks/{n}` | Fits |
| Roster, receipts, hello and authentication | 64 KiB | One frame | Fits |

**Larger supported content**
- R1 allows captures of up to 20,000 characters, which can exceed 64 KiB in UTF-8.
- Such a capture's original text is stored as a content blob of at most 1 MiB. The signed operation carries the blob's SHA-256 digest and length, so the signature covers the content.
- The bytes move in verified 256 KiB chunks. Partial blobs are staged and resumable.
- An operation whose blob is incomplete waits, as a dependency, and is never applied without its content.
- Attachments are still not replicated (R2-DATA-03).

**Flow control:** chunks are 256–512 KiB, within TN3213's advice of at least 64 KiB. Each send waits for buffer space, and each receive is consumed before the next is read.

**Acceptance (M1, M2, M6):** oversized frames, batches, operations, entity states, snapshot chunks and blobs are refused before allocation, and memory is measured. A maximum-size capture travels as a blob over both HTTP and the simulated link (R2-L32).

## 13. Commits and documentation

- One file-level operation per commit, staging only that file. Implementation and documentation are committed separately, in the `add: …` / `change: …` / `remove: …` style.
- Within a work package, the files are written and verified, then committed one at a time in dependency order. The `Package.swift` change follows, then one commit per documentation file.
- Each milestone ends in a state that builds. Single-file commits in between may not build on their own.
- `git status` is checked before every commit, and changes Claude did not make are never staged. Expect many hundreds of commits.

## 14. Checkpoint and resume (R2-DEV-03)

- **Record:** a tracked `R2-CHECKPOINT.md` (O-7). It holds:
  - the branch and baseline, and the current milestone;
  - completed requirement IDs;
  - modified and uncommitted files;
  - build and test commands with their results;
  - open conflicts and blockers, and pending owner sessions;
  - the permissions granted;
  - the next concrete steps.
- **Updates:** at every milestone boundary, and before any pause.
- **Pausing:** work is brought to a coherent state and unfinished operations are recorded. Nothing is reverted to make the repository look clean.
- **Resuming:** the actual files and processes are inspected before any work is repeated.

## 17. Risks

- **Scale.** R2 is larger than R1, and much of its Apple code can only be syntax-checked here. Mitigation: portable logic first, thin Apple adapters, view models in LisaPresentation, and the early sessions X1–X3. A round of fixes is still expected at the first builds.
- **Nearby security (§8.6).** TN3213 limits TLS-PSK to TLS 1.2 and the older API, and Apple documents no PSK suites, so Design A may fail N-1. Design B needs certificates Apple can't create and depends on the Secure Enclave key working as a `SecIdentity`. N-1 decides; if both fail, nearby stops while everything else continues.
- **No Docker access for this account.** Container evidence depends on the owner-run loop or an authorized rootless engine. Rootless networking and UID mapping differ from the server's rootful Docker, so network and ownership checks are repeated on the server.
- **SELinux.** Mislabeled bind mounts or secret files fail closed; `docs/DEPLOYMENT.md` gives the labeling steps, and SELinux is never relaxed.
- **arm64** is unverifiable here.
- **Platform drift on Fedora:**
  - libxml2 2.15 has API changes since 2.9.14, and the OpenSSL 4.0 command may differ from 3.5.7 in what the tests' certificate generation uses (E-5, M0).
  - Host evidence comes from Swift 6.3.2, the image and the owner's Xcode use 6.4.2.
- **Apple behavior not yet verified:**
  - Apple SDK module maps (E-2) and URLSession pinning (E-3);
  - `BGTaskScheduler` grants (E-6);
  - local notification behavior (E-7) and `NWConnection` endpoint reporting (E-8);
  - Mac sandboxing (E-10);
  - Focus and Time Sensitive interactions.
- **Snapshot installation** briefly holds the write lock, so a capture at that moment can wait; such waits are measured and reported, never hidden.
- **Exposure.** Docker's port publishing can bypass host firewalls, IPv6 exposure is easy to miss, and the VPN address may be missing at boot. Covered by the server checks and by the refusal to fall back to all interfaces.
- **Backups contain device push tokens and credential verifiers**, as R1's did; the documentation says backups are sensitive.
- **Inherent limits, documented:** revocation reaches a device only when it learns of it; recovery after a restore depends on surviving journals; exactly-once delivery is impossible; handoffs can leave visible coverage gaps.
- **Migration** is verified on synthetic R1 data only. A Mac-hosted R1 needs the macOS build of `lisa` or the documented copy-and-remove procedure.

- an action needs authorization outside the approved scope;
- an enforced platform restriction needs the owner;
- a concrete technical blocker cannot be resolved within the approved scope;
- private credentials, Apple hardware, the owner's server or live-service validation are needed, or a deciding experiment (§10.5) has not yet run.

Independent work continues in every case, and each blocked operation is reported with its exact cause.
