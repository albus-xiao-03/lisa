## 2. Objective

R2 turns Lisa into a distributed system with one authoritative service:
- **Lisa Core** runs in Docker on the owner's Linux server behind the owner's VPN. It owns the canonical dataset, the connectors, the scheduler and every email, call and push.
- **Lisa for Mac, iPhone and iPad** are clients. Each keeps a durable local database, works fully offline (R2-CAP-03), applies the owner's changes at once, synchronizes with Core over HTTPS and with nearby enrolled devices without Internet, and uses an explicitly configured model provider when Core is unreachable.

R2 succeeds as R2 §20 defines: in every connectivity condition, and after a Core restart or restore, owner work is preserved, uncertainty stays visible, state reconciles without silent loss, and the boundaries around personal data and external actions hold.

## 6. Where R2 refactors R1

1. **Owner data changes only through operations** applied to a merge state (§8.3). R1 records become projections written in the same transaction; validation moves into pure domain code that clients run too.
2. **Every Core-originated write to owner data goes through one authority path** (§8.3.5), including R1's ingestion, extraction, planning and rematching writes.
3. **The store records every change:** change-log entries and tombstones inside each transaction; a second read-only connection; streaming queries; savepoints; explicit disk-full errors (§8.15).
4. **Agenda inputs become portable** in `LisaAgendaInputs`.
5. **Delivery learns ownership,** firings and restore holds (§8.10).
6. **Devices get keys and a lifecycle** (§8.1); R1's legacy pairing stays for v1 devices.
7. **v1 becomes a translation layer** with durable caller-scoped parents (§8.12.2).
8. **Clients get a new core** (LisaClientCore, LisaReplicaStore, LisaSyncEngine, LisaSyncHTTP); LisaClient stays for v1 callers, queue import and the shared HTTP transport.
9. **Recovery evidence lives outside the database** as well (§8.4.4, §8.5), because a restore rewinds everything inside it.

## 7. Target architecture

### 7.1 Topology and authority (R2-ARCH-01, R2-ARCH-02)

- **Lisa Core**, one container on the owner's Linux server:
  - holds the canonical SQLite dataset, the operation ledger, the change log, snapshots, content blobs and the signed device roster;
  - keeps the recovery ledger and backup sets outside the database (§8.4.4);
  - runs the connectors, the scheduler and the outbox for email, calls and APNs;
  - serves v2 and the v1 translation over HTTPS on the VPN address, an owner listener on loopback, and the administrative CLI (§8.11.5);
  - holds every Core-only secret.
- **Each client** (Mac, iPhone, iPad) holds its replica, journal and device keys; runs local planning, briefs and search, nearby sync and relay, delegated and local notifications, optional inference, owner-requested public retrieval, SwiftUI and Siri; holds no Core secret.
- **Connections:** clients reach Core over the VPN with HTTPS and each other over authenticated nearby sessions; APNs and model providers are reached by outbound connections only.

### 8.1 Identity, enrollment and the trust lifecycle (R2-TRUST-01–05; finding 4, finding 5; trust lifecycle)

#### 8.1.1 Identities

- **Dataset:** a random 128-bit `datasetID`, created by `lisa core init` or by `lisa core migrate prepare` (§8.14.1), which records it before cutover.
- **Recovery epochs:** a random 128-bit epoch ID with an epoch record in the lineage (§8.5.2).
- **Core keys** (secret files, §8.11.2):
  - the signing key (P-256) with a key history of `{key, validFromPosition, retiredAtPosition}`;
  - the export key (P-256 key agreement), whose public half the roster carries and which opens protected archives (§8.6.6), with retired keys kept;
  - the TLS key and certificate.
- **Device:** a `deviceID` assigned at enrollment; an operation-signing key; a nearby transport key (agreement key for Design A, TLS key for Design B); a device export key; a device-generated 256-bit Core credential of which Core stores only the SHA-256 verifier; the trust anchor from pairing. Keys live in the Secure Enclave where available, otherwise in Keychain items available after first unlock on this device only.
- **Incarnations:** every launch that opens the replica starts a new random 128-bit incarnation with sequence numbers from 1; its first operation names the previous incarnation and its last sequence number. A restored device copy therefore never repeats an identity: the next launch is a new incarnation and the chain shows the fork.

#### 8.1.2 Enrollment and the trust bootstrap (finding 4 fixed; finding 5 preserved)

**Required:** single-use, owner-controlled pairing that binds the intended Core identity; an authenticated Core path; no certificate acceptance outside explicit pins or private CAs (R2-TRUST-01, -02).

**Mechanism**
1. **Token.** `lisa core device enroll --name … --class iphone|ipad|mac` stores an enrollment record: random 128-bit ID, token hash, 10-minute expiry, attempt counter, state `open`, intended name and class, intended host name. The token is 32 random bytes; Core never stores or logs it.
   - One function hashes it at issuance and verification: `tokenHash = SHA-256(ASCII "lisa-enroll-token-v1" ‖ 0x00 ‖ token)`. The payload carries the token as unpadded base64url; Core decodes it, refuses any length other than 32, then hashes.
   - **Vector** (kept from revision 3; computed 2026-11-20 with coreutils `sha256sum` and OpenSSL 4.0.3, reproduced 2026-11-21): token bytes `00 01 … 1f`; input (53 bytes) `6c6973612d656e726f6c6c2d746f6b656e2d7631` `00` `000102…1f`; SHA-256 `e74f49bf65f5c648421c64994582a9b22ef0f1ab253fefaceb1241f83fe313db`; payload text `AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8`.
2. **Pairing text.** Shown once on the owner's administrative terminal; the owner's custody of it is what authenticates it. `lisa-pair:3:` followed by base64url of: format version; Core URL (scheme, host, port); trust mode `pin` or `ca`; the leaf SPKI SHA-256 (both modes); in `ca` mode the SHA-256 of the owner's CA certificate; the fingerprint of Core's current signing key; dataset ID; enrollment ID; token; expiry; a 4-byte checksum. Typing errors are pinpointed by the checksum.
3. **Getting the CA certificate (`ca` mode).** A fingerprint cannot supply a certificate the server doesn't send, and TLS servers normally omit the root. So:
   1. The device opens TLS to Core and accepts this first connection only if the leaf SPKI equals the payload's pin and the leaf names the intended host. This authenticates Core for the bootstrap.
   2. Over that connection, without the token, it fetches `GET /v2/trust/tls-anchors`: the CA certificate and every intermediate Core is configured with, signed by Core's signing key.
   3. It checks the CA certificate's SHA-256 against the payload and the bundle signature against the payload's key fingerprint, then evaluates the leaf with the server's chain plus the bundle's intermediates, the CA as the only anchor (`SecTrustSetAnchorCertificates` + `…AnchorCertificatesOnly`), and the SSL policy for the intended host.
   4. Only if all of this passes does it send the enrollment request carrying the token.
   - Afterwards, `ca` mode trusts chains to the stored CA for the intended host, so a renewal from the same CA, even with a new key, needs nothing more. `pin` mode makes the pinned leaf the only anchor after its SPKI matches, then applies the host policy.
   - **Supported Core configurations, enforced at startup and by `lisa core doctor --tls`:** a self-signed or CA-issued leaf in `pin` mode; in `ca` mode, a leaf signed directly by the root or through intermediates, sending the leaf alone, the leaf with intermediates, or the full chain. Doctor verifies that the configured leaf chains to the configured CA through the configured intermediates, that the SAN contains the configured host name, that validity stays within Apple's limit for owner-trusted CAs (825 days, as R1's evaluator documents), and that the anchors bundle matches. Startup refuses any other configuration.
   - This builds on R1's `PinnedServerTrustEvaluator`, which already anchors only to owner certificates and checks host names. R2 pins the SPKI, not the whole certificate, and adds the bundle step.
4. **Device preparation.** The device generates its keys and credential, then builds and signs the request: enrollment ID, token, dataset ID, trust mode and pins, device details, public keys (and, for Design B, the certificate), credential verifier, incarnation-chain start and, for an R1 companion, the legacy link of §8.14.5. **The exact request bytes contain the token, so they are secret-bearing:** they are kept only in a device-only Keychain item, never in the replica, logs, diagnostics or an export. The item expires at the payload expiry plus 24 hours. It is deleted on success, on `enrollment_consumed`, `enrollment_expired` or `enrollment_invalidated`, and at expiry. Diagnostics show only "enrollment retry pending until …".
5. **Core verification,** in one write transaction:
   1. unknown enrollment ID: `enrollment_unknown`;
   2. **consumed with the same request digest: return the stored response (`duplicate`), whatever the expiry.** This check comes before the open-enrollment checks;
   3. consumed with another digest: `enrollment_consumed` (409) and a security event;
   4. invalidated or expired: the typed error;
   5. token hash compared in constant time; a mismatch commits `attempts + 1`, and the fifth invalidates;
   6. signature, keys, fields, the 10-device limit, and the legacy link if present; a failure commits `attempts + 1` without consuming;
   7. consume: record state and digest; create the device, keys and credential verifier; process the legacy link; sign a new roster and the authorization record; store the public-only response for 7 days. Commit, then answer.
6. **Completion.** The device verifies Core's signature against the payload fingerprint, stores the results, and deletes the retry item.
7. **Design A's discovery secret** is fetched separately and never travels in the enrollment response (§8.7).
8. **Pairing on Apple devices.**
   - Text entry is complete on every device and is the first device's only path.
   - An enrolled Mac can show the owner's text as a QR code with CoreImage's `CIQRCodeGenerator`.
   - An iPhone or iPad can scan it with VisionKit's `DataScannerViewController` when `isSupported` and `isAvailable` are true. The Info.plist gets `NSCameraUsageDescription`: "Lisa uses the camera only to read the pairing code shown by your Lisa Core or another of your devices."
   - If the camera is denied, restricted or unsupported, the scan button explains why, offers Settings, and leaves the text field ready. Nothing else changes.
   - Core's CLI renders no QR code, because no QR encoder is approved. That missing dependency is recorded and not requested.

**After a failure or retry**
- **Lost response, crash or restart:** the identical bytes are resent and get the stored response.
- **Concurrent requests:** they serialize. The first consumes the enrollment; a different digest gets 409; an identical one gets the stored response.
- **Trust failure:** wrong pin, wrong anchor, wrong host, a CA hash mismatch or a bad bundle signature stops the attempt before the token is sent. The enrollment expires unused.
- **Expiry and invalidation:** a typed error. `lisa core device enroll --list` and `--cancel` manage open enrollments.
- **Never-completed device:** a device that never received its response appears as "enrolled, never seen" for the owner to revoke.

**Acceptance**
- **M1:** LisaTrust will reproduce the vector.
- **M3 (S-04, S-05):** a harness will run against the real TLS server with a test-only libcurl transport that implements the same evaluation (§8.6.5), using CAs and certificates made at run time. It will check:
  - `pin` mode with a self-signed and a CA-issued leaf;
  - `ca` mode with the root omitted, a direct-root leaf, a leaf behind an intermediate the server omits (supplied from the bundle), and a renewal to a new key from the same CA;
  - a wrong anchor, wrong host, wrong pin, wrong CA hash and tampered bundle. In each, Core's request log must show no enrollment request;
  - five wrong tokens, a bad signature, concurrent requests, a response dropped after commit and retried after expiry, a restart between send and response, and the 10-device limit;
  - that no replica table, log line, diagnostic output or export contains the token or the retry bytes.
- **X2 (S-04, S-05):** on an iPhone through the production `LisaSyncHTTP` transport and `Apps/Shared/Trust`, against a Core the owner runs with a test CA, the same chain matrix will run. Core's log will show no request on every trust failure, and the Keychain retry item will be seen during the attempt and gone afterwards. Text pairing will work with camera access denied.

#### 8.1.3 Roster, revocation and paged trust evidence

- **Roster:** signed by Core, identified by (epoch, version), and re-signed at least daily while Core runs. It carries the dataset, issue time, policy version, maximum nearby trust age (30 days by default), each device's keys, status and capabilities, the TLS pins (current and next), the export public key, and the anchors-bundle digest.
- **Revocations** carry the position and epoch at which they happened. They are permanent (union rule): no later roster, epoch or restore removes them.
- **Large artifacts are paged and bound as a whole.** A roster with key history, a causal summary or a snapshot manifest may span several pages. A signed header covers artifact type, dataset, epoch, version, page count and the Merkle root of the ordered pages (leaf `SHA-256(0x00 ‖ page)`, node `SHA-256(0x01 ‖ left ‖ right)`). Each page travels with its inclusion proof. A receiver accepts the artifact only with every page verified, so a peer can neither drop a revocation page nor reorder pages.
- **Devices** keep the newest verified roster, refuse older versions within an epoch, pass rosters to peers, refuse revoked peers, and stop forwarding or applying their new operations. An expired roster stops new nearby exchanges only.
- **`lisa core device revoke`** raises the roster version, revokes the credential, cancels pending deliveries and assignments, and rejects every new operation from that origin, whatever time it claims. Committed data stays.
- **Documented limit:** a device without the update can't know of a revocation.

#### 8.1.4 Key and credential lifecycle

- **Credential reset:** `lisa core device reset-credential <id>` issues a one-time token (hash label `lisa-reset-token-v1`, 10 minutes). The device presents it with a new verifier, signed by its existing key. Core replaces the verifier atomically, and the old credential stops working.
- **TLS rotation:**
  - The roster carries `tlsPins: [current, next]` with windows; devices accept either during the overlap (30 days by default), and Core switches certificates inside it.
  - In `ca` mode, renewals need no pin change. Replacing the CA itself works the same way with `anchors: [current, next]`.
  - A device that missed the overlap gets the new values from a peer's Core-signed roster, or by re-pairing.
  - Health warns 30 days before expiry, and an expired certificate is never accepted.
- **Signing-key rotation:** the new key is announced in a record signed by the old and the new key, with an activation position. Devices keep the key history, so receipts, batches and rosters verify with the key valid at their position.
  - New records must be signed by the current key; a retired key verifies only records from before its retirement.
  - The transition record is also appended to the recovery ledger (§8.4.4) and included in every later backup set.
- **Export-key rotation:** the roster announces the new key. Archives name the key they were sealed to, and Core keeps retired private keys.
- **Device key rotation:** a key-update operation signed by the old and new key, followed by a new roster.
- **Design B certificates** are renewed at 80% of their lifetime through key updates.
- **Losing the current signing key's private half:** Core cannot produce a transition that devices accept. The owner then re-anchors every device with new owner-authenticated pairing text, `lisa-reanchor:1:…`, carrying the new key fingerprint, dataset, current head and the device's ID.
  - The device keeps its identity, keys and journal, verifies the new head against the text, and resumes.
  - This is the only path that replaces trust without a signature chain, and it needs the owner at each device.
- **Owner backups:** `docs/SECURITY.md` lists the secret files the owner must keep offline and restore separately: current and retired signing keys, export keys and the TLS key (§8.11.2).

**Acceptance (M3, X2, X7; S-10):** the harness will check credential reset (the old credential refused), a pin overlap and switch, a device offline for the whole overlap recovering through a peer's roster, signing-key rotation with historical receipts, an export-key rotation with an old archive still opening, device key rotation, roster renewal, an expired certificate refused, and re-anchoring after the signing key is lost. X2 and X7 will repeat reset and pin overlap with real Keychain items.

#### 8.1.5 Challenges (recovery and other key-proven requests)

**Required:** recovery must authenticate devices whose credential verifiers a restore may have rewound (R2-CORE-06, R2-TRUST-03).

**Mechanism**
- **Issue.** `POST /v2/challenges` returns `{challengeID, nonce (32 bytes), purpose, datasetID, epochID, deviceID, expiresInSeconds: 120}`. Core keeps it with the current run generation and a monotonic deadline.
- **Response.** The device signs `"lisa-challenge-v1" ‖ 0x00 ‖ purpose ‖ datasetID ‖ epochID ‖ challengeID ‖ nonce ‖ deviceID ‖ keyID ‖ SHA-256(request body)` with its operation key. The body is the evidence upload or request that the challenge authorizes, so the signature binds the content too.
- **Verification,** in one transaction:
  - the challenge exists, is unused and belongs to this run generation and epoch;
  - Core's monotonic clock is before the deadline;
  - the key is active for that device in the roster as merged so far, including evidence imported moments ago;
  - the signature verifies.

  The challenge is then marked used.
- **Expiry and clock changes:** expiry uses Core's monotonic clock. A wall-clock step has no effect, and a Core restart invalidates every outstanding challenge, because the run generation differs.
- **Replay:** single use, and bound to purpose, epoch and body digest. A response for epoch E2 is useless in E3, and evidence signed for one upload can't authorize another.
- **Revocation mid-exchange:** if imported evidence revokes the device between issue and response, verification fails. The device's upload is kept as quarantined evidence: listed for review, never admitted.
- **Purposes:** `recovery-evidence`, `credential-refresh` (§8.5.5), `owner-import` (§8.14.4) and `legacy-link-lookup` (§8.14.5).

**Acceptance (M3, S-10):** the harness will check an expired challenge, a reused challenge, a response for another epoch, a body changed after signing, a Core restart between issue and response, a backward wall-clock step of one hour, and a revocation imported between issue and response.

### 8.2 Operations (R2-SYNC-01, -02, -03; causal processing, protocol limits)

#### 8.2.1 Envelope, digest, duplicates and receipts

- **Fields:** protocol and schema versions; dataset ID; origin (device, incarnation, sequence); operation ID (random 128 bits, stable for the life of the logical action; derived for v1 children and imported legacy requests, §8.12.2); entity type and ID; operation type and payload; dependencies (operation IDs, at most 32); observed set (§8.3.2); policy version; an optional **legacy request reference** `{scope, requestID, r1Fingerprint, discriminator}` (§8.14.4); creation time (display and audit only).
- **Encoding:** canonical JSON (§8.16.1), strict bounded decoder, no duplicate keys, no unknown envelope fields.
- **Digest:** SHA-256 over the complete canonical signed body. **Signature:** raw 64-byte P-256 ECDSA over `"lisa-r2-op\n"` ‖ body, not part of the digest. Relays forward exact bytes.
- **Duplicates, at Core and on every replica:**
  - same ID, same digest → `duplicate` with the current receipt;
  - same ID, different digest → `rejected: identity_reuse` and a security event, **except** for two operations carrying the same legacy request reference with the same `r1Fingerprint`. Those are the same legacy request reaching Core by two paths, and they get `duplicate` with the outcome already recorded on the durable parent (§8.12.2);
  - same (device, incarnation, sequence) under another ID → `rejected: sequence_reuse` and a security event.
- **Receipts:**
  - Waiting operations get signed provisional receipts (`waiting_for_dependencies`, the missing IDs, no position).
  - Decisions give final receipts: `accepted`, `accepted_with_conflict` or `rejected` with reason and recovery hint, each carrying dataset, epoch, operation ID, digest and commit position (R2-SYNC-03).
  - Every decision is also a change-feed entry. A retry while waiting returns the same provisional receipt.

#### 8.2.2 Dependencies and bounded release (causal processing)

| Situation | Outcome |
|---|---|
| A dependency not present | `waiting_for_dependencies` with a provisional receipt; after 14 days `rejected: dependency_missing` with a recovery hint |
| A dependency rejected | `rejected: dependency_rejected` if the entity never existed; otherwise applied with the rejected version ignored (§8.3.1) |
| A cycle among waiting operations (only forged or corrupt input) | Every member `rejected: dependency_cycle` and a security event. Detected when the cycle closes, by walking the waiting graph from the new operation (bounded by the waiting limits below) |
| More than 32 declared dependencies | `rejected: malformed` |
| Waiting storage | At most 1,000 waiting operations per origin incarnation and 64 MiB of waiting bodies in the dataset; beyond that new submissions get `insufficient_storage`. Waiting operations are never dropped |

**Release in bounded, restartable steps.** One decision can release thousands of waiting dependents, so release never happens inside the deciding transaction:
- The deciding transaction records the decision and inserts its direct dependents into a durable `ready_queue(operationID, enqueuedAt)` table.
- A release worker takes at most 256 entries per transaction, oldest first and round-robin across origins. For each entry it re-checks readiness (all dependencies decided), applies the operation as at intake, records the receipt, and enqueues that operation's own dependents.
- A crash loses nothing: the queue is durable and re-checking is idempotent.
- Capabilities show the queue length. Intake of new operations interleaves with release, so one huge release can't stall captures for more than one 256-entry transaction.

#### 8.2.3 The operation catalog (operation coverage)

- **Capture:** create (text, link, idea, or shared item; large text as a blob, §8.16.3).
- **Tasks:** create; edit a field (title, priority, deadline or clear, estimate, splittable, confirmation); complete; cancel; reopen (naming the terminal actions it reopens).
- **Notes and tags:** add a note piece; replace observed note pieces (a v1 `notes` text edit, §8.3.2); change tags (observed-remove).
- **Ideas:** create directly, not only through a capture; edit a field (summary, priority, estimate, deadline); change lifecycle (R1's `IdeaLifecycle`).
- **Owner reminders:** create (due time, optional subject, note), edit, cancel. Before Core accepts one, its creating device owns delivery (§8.10).
- **Reminder occurrences:** acknowledge, dismiss, snooze — each names the firing it acts on (§8.10.1).
- **Event proposals:** review, dismiss, correct.
- **Preferences:** set, delete or confirm a permitted key. Administrative keys are refused for devices (R2-TRUST-05) and stay CLI-only.
- **Plan blocks:** accept, lock, reject, defer, complete, move.
- **Plan intents** on a provisional local plan: accept, lock, move or reject a local block, keyed by date, zone, subject and range. Core reconciles them with canonical planning; an intent that no longer fits becomes a conflict and is never rescheduled silently.
- **Suggestions from fallback inference:**
  - propose (model authority, from a device);
  - accept or dismiss (owner).

  Accepting creates the task, idea or proposal through ordinary owner operations, with the suggestion as provenance.
- **Any owner item:** delete (tombstone); restore as a new identity with provenance.
- **Conflicts:** resolve, as one operation or as a paged resolution group (§8.3.2).
- **Devices:** key update.
- **Core-originated:** source, model and system writes through `AuthorityWriter` (§8.3.5); v1 children (§8.12.2).

`docs/SYNC-PROTOCOL.md` specifies each type with test vectors (valid, tampered, duplicate-key, identity-reuse, legacy-reference duplicate, oversized).

#### 8.2.4 What compacted evidence proves

After an operation body is compacted (§8.4.5), Core keeps for the life of the dataset: operation ID, digest, origin (device, incarnation, sequence), legacy reference if any, outcome and reason, epoch and commit position, and the version identifiers (dots) it created. From that:
- **Acceptance or rejection:** a resubmission with the same ID and digest gets `duplicate` with the original outcome; a different digest is still `identity_reuse`. Acceptance and rejection therefore stay provable without the body.
- **Observed versions:** a later operation whose observed set names compacted versions is checked against the retained dots and the Core-signed causal summary (decided ranges per origin), so causal validity stays checkable.
- **Not provable after compaction:** the operation's payload and the exact values it wrote once they are superseded. Replay of a compacted operation after a restore needs its body from another holder (§8.4.5); compacted metadata alone cannot re-apply it.

**Acceptance (M1 codec, M3 Core; S-16):** the harness will have a case per row of the table, including a forged two-operation cycle, the 32-dependency boundary, waiting-storage backpressure, the legacy-reference duplicate with matching and different fingerprints, and a release of 5,000 dependents interrupted by a process kill after the first batch. Capture latency during the release will be measured.

### 8.3 Merge rules (R2-SYNC-06, R2-WORK-03; finding 7; operation and authority coverage)

#### 8.3.1 Rules

Each owner field has a merge class, and each operation names what it observed.

| Situation | Rule |
|---|---|
| Duplicate operation | Applied at most once (§8.2.1) |
| Edits to different fields | Each field is its own register; the edits merge |
| Concurrent edits to one scalar field | Multi-value register: an edit replaces only the versions it observed; every unobserved candidate survives and a conflict opens |
| Owner correction versus a model or source value | Every value carries an authority. A model or source write never replaces an owner value, concurrent or later; it is kept as a suggestion. An owner write replaces what it observed, whatever its authority. A value of ambiguous authority (§8.14.2) is protected like an owner value |
| Concurrent note additions | Separate note pieces; both kept |
| Concurrent tag additions and removals | Observed-remove set |
| Completion or cancellation versus another edit | Status is separate; the edit applies and the terminal state stays |
| Concurrent completion and cancellation | Both recorded; terminal ("completed and cancelled", for review); reminders and deliveries suppressed |
| Reopening | Names the terminal actions it reopens; an unseen one stays in effect |
| Acknowledge or dismiss versus a concurrent snooze of the same firing | That firing is suppressed; the snooze stays in history and creates no new firing (§8.10.1) |
| Concurrent snoozes of the same firing | The latest snooze instant, capped at the policy maximum; one new firing |
| Deletion versus stale or concurrent edits | The tombstone dominates in any order; later edits are recorded as superseded while retention allows; restore creates a new identity |
| Concurrent plans or briefs | Separate derived artifacts; never merged |
| Plan intents versus canonical planning | Core reconciles; a clash with a busy event or a held block becomes a conflict |
| Conflict in a planning field | Planned conservatively, marked uncertain, escalation held (§8.3.4) |
| Resolving a conflict | Names the exact observed set (§8.3.2); a candidate outside it stays as a new conflict |

- **Causal readiness:** an operation waits for its dependencies and is never applied out of causal order or skipped. A device that holds an operation also holds and forwards its dependencies.
- **Convergence:** every rule is a join of sets with a deterministic display order: multi-value registers, observed-remove sets, grow-only piece sets, terminal-action sets with explicit reopen references, the snooze maximum and dominating tombstones. Replicas holding the same operations reach the same state in any order. The harness checks every permutation of a representative set (R2-L11) and the R2 §18.2 scenario.
- **No last-writer-wins and no clock authority.** `docs/CONFLICTS.md` records the rules and the owner's resolution flow.

#### 8.3.2 Bounded pieces, references and exact observed sets (finding 7)

- **Pieces reference the item, never the reverse.** Notes, conflict candidates and tag elements are separate records keyed `(itemID, pieceID)`, each at most one operation in size. The item's own state holds only field registers, and each register is bounded by its value limit (§8.3.3). An item with thousands of notes or candidates therefore never grows its own state or any operation that touches it.
- **Observed sets are bounded.** An operation that replaces or resolves "what I saw" names its observed set as:
  - **a horizon** `(epoch, partition, position P)`, meaning every committed piece of that item and field with commit position ≤ P. The replica can state this only if it has installed that partition through P (§8.4.2). Core resolves it exactly because pieces keep their commit positions;
  - **plus explicit piece IDs** for pieces the device saw that were not committed by P (its own, peers' or relayed pending pieces): at most 256 per operation.
- **Paged resolution groups.** When the explicit list exceeds 256, the device emits a group:
  - pages 1…n, each an operation with up to 256 IDs, a group ID, its index, the total count and the SHA-256 of the complete sorted ID list;
  - each page depends on the previous one, and the final page carries the resolution value.

  Core applies the group atomically when the final page arrives with all earlier pages present and the digest matching. A missing page leaves the group waiting under the ordinary dependency rules. Everything outside the horizon and the list (a later arrival) stays as a new conflict.
- **v1 `notes` edits** use the same form: they replace the pieces observed at the projection's revision (§8.12.2).
- **Aggregate limits are advisory.** For example, 1,000 notes per item is checked only when a device creates an operation from its own view, never while merging. Overflow is therefore deterministic, and past the limit the UI asks the owner to archive.

#### 8.3.3 Value sizes derived from the encoded operation

- **One rule:** the canonical body of every operation is at most 64 KiB (65,536 bytes), metadata included.
- **Derivation:** for each operation type, `LisaSyncProtocol.maximumValueBytes(type)` = 65,536 − the encoded size of that type's envelope with every optional field at its maximum (32 dependencies, 256 explicit observed IDs, a legacy reference, maximum-length IDs and names). It is computed by the codec itself and published in `docs/SYNC-PROTOCOL.md` with the derivation.
- **Measured on the encoded value:** the limit applies to the value's encoded bytes after canonical JSON escaping (UTF-8, `\uXXXX` for control characters), so worst-case escaping is covered. Clients check before saving; Core checks at intake; neither allocates beyond the limit (§8.16).
- **Larger values become blobs:** a note, capture text or description over its limit is stored as a content blob (at most 1 MiB) whose digest and length the operation carries. R1's limits fit: titles ≤ 200 characters, idea summaries ≤ 500; capture text up to 20,000 characters may need a blob; R1 notes are unbounded and use a blob when needed.

**Acceptance (S-07)**
- **M2, replica only:** two replicas without Core will check:
  - the largest valid value for a field edit and a note piece, built from the worst-case escaping, accepted, and one byte more refused before allocation;
  - two concurrent maximum-size edits to different fields, and two notes added to an item at the advisory limit, in both arrival orders, giving identical results;
  - a resolution observing 1,000 pending candidates, which becomes a four-page group: applied atomically when complete, waiting while a page is missing, and leaving a later candidate as a new conflict.
- **M3, real Core:** the same cases through Core intake, plus the encoded HTTP and frame boundaries of §8.16.

#### 8.3.4 Planning with conflicting values

While a planning field has candidates, the planner uses:
- **deadline:** the earliest;
- **estimate:** the longest;
- **priority:** the highest;
- **splittable:** false, so the work needs one contiguous block;
- **block intents in conflict** (lock against move, reject against accept): the block stays in its current canonical placement, is marked "needs review", and is never moved or dropped automatically.

The plan explains each such choice. Escalation (calls, Time Sensitive notifications) is held until the conflict is resolved. Local and canonical planners apply the same rule through `LisaAgendaInputs`.

#### 8.3.5 The authority path for source, model and system writes

**Required:** models do not overwrite explicit owner corrections (R2-ARCH-04.6); source and model content cannot alter trust or permissions (R2-L34).

**Mechanism:** every Core-originated write to an owner entity is a Core-signed operation applied through `AuthorityWriter.apply(_:authority:in:)`, inside the caller's transaction.

| R1 call site (§1.6) | Authority | Change |
|---|---|---|
| `MailBatchProcessor.commit` inserting invitation proposals, inside `ConnectorRunner.synchronize`'s write, which also advances the cursor | `source(sourceID, evidence)` | LisaIngestion changes: the insert becomes an `AuthorityWriter` call in the same transaction, so the cursor and the proposal operation commit together or not at all |
| `ExtractionService.apply` creating or updating tasks and inserting proposals | `model` | Through `AuthorityWriter`; fields flagged `ownerCorrected` stay owner values |
| `PlanService.recordUnschedulable` setting an idea's unschedulable fields | `system` | Through `AuthorityWriter` |
| `ProposalService.rematch` setting match state | `system` | Through `AuthorityWriter`; an owner's "reports added" stays an owner value |
| `PreferenceService.infer` (tests only in R1) | `model` | Same path; administrative keys refused |
| Calendar reconciliation (occurrences only) | Derived record | Unchanged: derived records sit outside owner merge |

Owner actions (reviews, corrections, edits) are owner operations. Derived records (calendar occurrences, emails, evidence, news) replicate as derived records.

**Acceptance (M3; S-01 shared fixtures):**
- an invitation-created proposal will be corrected by the owner; the email will be reprocessed; the correction will stay effective, and the model's value will be kept as a suggestion;
- a process kill inside the connector transaction will leave neither the cursor advance nor the proposal operation;
- a model attempt to change an administrative preference will be refused.

### 8.4 Core ledger, change feed, snapshots and backups (R2-SYNC-03, -05, -07, R2-CORE-04, -06; findings 8 and 9)

#### 8.4.1 Ledger and intake

- **Schema v5 adds:** dataset, epoch and recovery state; operations, dependencies, the ready queue, merge states, pieces, conflicts, provisional and final receipts; origin progress and incarnation chains; the change log with partition lists; tombstones, which keep the deleted entity's caller-scoped request key where one exists (§8.14.3); blobs and reference counts; rosters, key history, enrollments, reset tokens and challenges; replication checkpoints, snapshots, the backup catalogue and the replay floor; occurrences, firings, ownership, holds and releases; v1 parents; schedules and the model budget (moved from R1's JSON files).
- **Intake** runs in one write transaction with a savepoint per operation:
  1. bounds, dataset, epoch, schema and recovery state;
  2. origin, signature, digest, reuse and legacy-reference checks;
  3. authorization;
  4. dependencies (release is queued, §8.2.2);
  5. merge, projection, pieces, conflicts, tombstones and blob references;
  6. delivery and assignment suppression, serialized as §8.10.3 describes;
  7. change-log entries, the operation record (which is also the idempotency record) and the final receipt;
  8. durable follow-up work, run after commit.

#### 8.4.2 Change feed and interval coverage (finding 8)

**Required:** never advance a client checkpoint past changes it has not installed (R2-API-03); bounded incremental sync with gap handling (R2-SYNC-05).

**Mechanism**
- **Partitions.**
  - Unwindowed collections (tasks, ideas, captures, preferences, proposals, owner reminders, suggestions) are one partition each.
  - Windowed collections are divided into day buckets in the owner's planning zone: calendar occurrences by start date, plans and briefs by date.
  - Every change-log entry lists every partition it touches. A rescheduled occurrence touches its old and its new day; a deletion touches the bucket the record last occupied.
- **Signed change pages.** Each page is at most 512 KiB. Core signs `{dataset, epoch, partitions (an explicit list, or per collection a day range), fromPosition, toPosition, entries ascending by position}`.
  - A page proves, for every partition it lists, that its entries are all the entries in `(from, to]` touching that partition. A listed partition with no entries is proved unchanged over the interval. A deletion is an entry, so tombstones are proved like any other change.
  - Every page is self-contained, so no page depends on a page set.
- **Partition cursors.** Each replica keeps one cursor per partition it covers. Installing a page advances partition p from cursor c to `to` only if p is listed and `from ≤ c`; the page then covers everything between c and `to` for p.
  - If `c < from`, there is a gap for p. The replica asks Core, or a peer whose coverage includes p, for `(c, …]` for p, and p's cursor stays at its last proved value.
- **Overlapping windows that don't nest.** A replica with window A (days 1–60) relays a page listing days 1–60 to a replica with window B (days 30–90). B advances only days 30–60, wherever its cursors meet the contiguity rule. Days 61–90 are untouched, and nothing missing from the page is read as deleted.
- **Rolling windows.**
  - A day entering the window has no cursor. The replica fetches a bucket snapshot: the records in that bucket at a Core cut c, signed and paged (§8.4.3). It sets the cursor to c, then continues with pages from c.
  - A day leaving the window is evicted as cache: its cursor is dropped, and nothing is treated as deleted.
- **Missing pages:** a gap, refetched from the last proved cursor.
- **Compaction:** change-log entries older than the history retention (90 days, R2-SYNC-07) are compacted. A partition whose cursor is below the compaction horizon gets `cursor_expired` for that partition only, and is refilled with a bucket or collection snapshot.
- **Never backward.** A partition cursor never moves backward within an epoch. A new epoch is entered only through the recovery path with a verified head (§8.5.2).

**Acceptance (M3 with Core, M6 over the simulated link; S-08):**
- windows A and B as above, with a deletion on day 40 and no changes on day 45: B will apply the deletion, advance day 45 on the empty proof, advance days 30–60 only, and leave days 61–90 untouched;
- a missing page: refetched from the last proved cursor;
- a window roll with backfill;
- a compacted range: per-partition `cursor_expired` and a bucket snapshot;
- a page whose partition list was altered: refused.

#### 8.4.3 Snapshots and paged artifacts

- **Snapshots** come from one consistent cut on the read connection. They are streamed as length-prefixed records in 512 KiB chunks that records may span.
- **Manifests** are paged and Merkle-bound (§8.1.3). They carry the dataset, epoch, cut, the partitions covered with their cursors, the causal summary, counts and chunk digests.
- **Reader lifetime:** generation holds back WAL checkpoints, so its reader is bounded (§8.15.2). Past the bound the generation aborts and is retried later from a new cut.

#### 8.4.4 Backups: manifests, the recovery ledger and discovery (finding 9)

**Required:** consistent backups with manifest, canonical records, operations and receipts, tombstones, delivery history, enrollment metadata and non-secret configuration references; secrets documented separately (R2-CORE-06). R1's manifests have no checksums and take their counts from the live database (§1.6); R2 fixes both.

**Mechanism**
- **Backup set.** `lisa core backup` writes `<backup root>/<backupID>/`:
  - `lisa.sqlite`, from SQLite's online backup;
  - `manifest.json`, signed with the current Core key. It holds:
    - the backup ID, dataset and epoch;
    - the **lineage** from dataset creation to this epoch (epoch records with parents, cuts and confirmations, §8.5.2);
    - the cut position and its commit time, schema and application version;
    - SHA-256 of every file, and counts taken from the backup itself;
    - the Core key history and roster version at the cut;
    - the configuration file's digest and every secret reference by name or path, never a value;
  - `recovery/`, a copy of the recovery ledger up to the cut.
- **The recovery ledger** lives outside the database at `<data>/recovery/`. It is a set of append-only, hash-chained files whose records Core signs:
  - epoch records and confirmations;
  - trust records: roster versions, key transitions and revocations;
  - fence records;
  - the submission journal (§8.10.6);
  - the backup index (backup ID, location, lineage head, cut).

  Each record is also in the database. The ledger exists because restoring the database rewinds the database's own catalogue, while the ledger on the data volume does not rewind. `lisa core trust export` and `lisa core backup export --to <dir>` copy ledger and backup sets off-host, which the documentation recommends after every revocation, key rotation and backup.
- **Validation.** `lisa core backup validate <id>` recomputes the digests, runs `integrity_check`, verifies the manifest signature with the key history, and writes a signed `validation.json`. Only validated backups count as restorable.
- **Retained restorable set R:** the newest `backup.retainRestorable` (default 2) validated backups on the current head's lineage, plus any the owner pins (`lisa core backup pin <id>`). Capabilities publish R as (ID, lineage, cut).
- **Discovery after a restore.** `lisa core restore` and `lisa core backup scan --root <dir>…` rebuild the catalogue by reading every manifest under the backup roots and the off-host locations the owner names, verifying each with the key history in the ledger and in the manifests themselves. A newer backup (B after restoring A) and every trust record (a later revocation, a key transition) are therefore found, even though the restored database never knew them.

#### 8.4.5 Replay coverage and pruning across branches (finding 9)

- **Containment.** A backup X's lineage is a list of segments `(epoch, start, end)`, the last ending at X's cut. An operation committed in epoch E at position p is contained in X if and only if some segment `(E, s, e)` of X has `s < p ≤ e`. This answers containment for divergent branches: an operation committed on an abandoned sibling epoch is in no backup taken on the other branch.
- **What restoring X promises,** in three separate classes:
  1. **Guaranteed:** X's own state.
  2. **Replayable from a known holder:** every operation committed after X's cut, on any branch, whose body is held by a validated backup's database, a device that has reported holding it (§8.5.3), or an archive the owner supplies (§8.6.6).
  3. **Unknown:** operations whose possible holders haven't been heard from.

  An eviction on one device moves an operation from class 2 to class 3 for that device, never to "lost". Lisa reports "not found in any reachable source" only after every enrolled device has reported and every catalogued backup has been searched, and even then names unknown exports as a possible source.
- **Pruning rule (Core and every replica).** An operation body may be dropped only when all three hold:
  1. its canonical effect is installed on that replica, so no visible overlay needs it;
  2. it is contained in every backup of the replica's latest catalogue R, learned from the current head no more than 7 days ago (with an older catalogue, nothing is pruned);
  3. no live reference needs a blob it references.
- **Blob references are counted** across canonical records, retained bodies, pending operations, drafts, conflict candidates, staged installations and exports being assembled. A blob is deleted only at zero, so a blob shared by a prunable edit and a pending edit stays.
- **Cap eviction** on a device (90 days or 64 MiB of committed bodies) may drop a body that meets conditions 1 and 3 but not 2. It never drops a visible overlay or a live blob reference. The evicted range is recorded and reported as "replay coverage reduced on this device for backups older than …".
- **Older cuts:** a backup outside R keeps its own state, plus whatever holders still have; nothing beyond that is promised.

**Acceptance (M3; S-09):**
- **Linear A then B, keeping 2:** pruning will keep everything above A's cut, and restoring A will replay all of it from B and the devices.
- **Keeping 1:** the reported unrecoverable range will be exactly the range devices pruned.
- **Sibling histories:** two restores of A, then work on each. Operations on the abandoned sibling will appear in no backup of the other branch and will be replayed from devices.
- **An offline holder:** a device holding bodies, offline during the restore, will reconnect later and complete the replay.
- **A shared blob:** a blob shared by a prunable and a pending edit will survive pruning and cap eviction.
- **Discovering B after restoring A:** B will be found by the scan and offered as a replay source.
- **Cap eviction:** reported without the word "lost".

### 8.5 Restore, recovery and admission (R2-CORE-04, -06, R2-TRUST-03; finding 10; recovery admission and client identity)

**Required:** exactly one active Core writes a dataset; a local lock does not stop a second server running a copy; restore and migration must fence or stop the previous Core (R2-CORE-04). A restore that moves history backward establishes a new epoch; a restored Core starts with outbound side effects suspended (R2-CORE-06). Revoked origins stay rejected (R2-TRUST-03).

**Decision:** single-Core design (O-2); no cluster coordination.

#### 8.5.1 Restore procedure and fencing

`lisa core restore <backupID>` (offline mode, §8.11.5):
1. **Fence this host.** Under the data-directory lock, the replaced database is renamed aside and fenced (schema marker), so a Core started on it refuses to run. The run generation changes. A fence record goes to the recovery ledger.
2. **Fence other hosts.** Lisa cannot stop a process on another host. The restore therefore asks which previous Core may still be running, and records one of:
   - `fenced-local`: it was this host's Core, now fenced;
   - `owner-attested-stopped`: the owner states the other host is powered off or its container removed, recorded with time and text;
   - `credentials-rotated`: the owner has rotated every provider credential that Core held (APNs auth key, SMTP password, Twilio token, model key). The old Core can then send nothing even if it runs;
   - `unknown`.

   While the state is `unknown`, the restored Core stays in recovery: it never admits ordinary work, and delivery can't be released. An old Core still running elsewhere could keep receiving device work for its own epoch, and once devices learn the new head they refuse that epoch (§8.5.2).
3. **Rebuild the catalogue** from backup roots and the recovery ledger (§8.4.4).
4. **New epoch.** Create a new epoch record (parent: the backup's epoch and cut), enter recovery mode, and suspend delivery.

**What survives outside the rewound database:**
- the recovery ledger on the data volume: lineage, confirmations, trust records, fences, the submission journal and the backup index;
- backup sets;
- the secret files;
- off-host exports;
- every device's replica and evidence.

If the whole data volume is lost, only off-host copies and devices remain, and the review in §8.5.3 shows that.

#### 8.5.2 Lineage, confirmations and the current head

- **Epoch record:** `{epochID, parentEpochID, parentCut, restoredBackupID, createdAt, coreKeyID}`, signed.
- **Owner confirmation:** `{epochID, confirmationSequence, supersedes: [epoch heads], reviewedEvidenceDigest}`, signed by Core when the owner runs `lisa core trust confirm` (§8.5.4).
  - `confirmationSequence` is one more than the highest sequence in the recovery ledger, in the restored database, and in every device report received during recovery.
  - `supersedes` lists every head known at that moment that isn't an ancestor of the new epoch, including a sibling restore of the same backup.
- **How a stale client chooses the current head.** It accepts a new head H only if one of these holds:
  - H descends from the client's head through verified epoch records;
  - H's confirmation supersedes the client's head, directly or through a chain of confirmations, and its sequence is higher.

  So when two restores of the same backup both carry valid confirmations, the later one names the earlier in `supersedes` and has a higher sequence. A client holding either one can verify which is current.
- **When the supersession can't be shown:** a client whose head is neither an ancestor nor superseded refuses ordinary sync with H. It still authenticates by challenge and reports its head as recovery evidence; Core lists it in `lisa core trust review` as an unknown head. The owner then issues a supplementary confirmation that supersedes it, and the client accepts that.

  A tie can't be resolved automatically, because devices never pick between confirmed heads by time.

#### 8.5.3 Trust evidence and key history after a restore

- **Collected before confirmation, by challenge (§8.1.5):** each device uploads its newest roster, epoch records and confirmations, key-transition records, its assignment inventory and observations (§8.10.2), and an inventory of the operations it retains: IDs, digests, origin positions and receipts, not bodies.
  - Bodies may also be uploaded into a quarantined staging area.
  - Nothing is applied before confirmation.
- **Merging:** revocations are a union and are kept. Key transitions are verified as a chain from the restored key history: K1→K2 signed by K1 and K2.
  - A revocation signed by K2 after the backup is verified through that chain and applied before any work is admitted.
  - Devices enrolled after the backup are re-registered as "membership unconfirmed".
  - `lisa core trust import` adds the recovery ledger's trust records and off-host exports.
- **Core's own key:** if the restored host has K2's secret file (current), Core continues with K2 once the K1→K2 transition is back in the key history. If only K1 remains, devices that already trust K2 refuse K1-signed records after K2's activation, and re-anchoring (§8.1.4) is the only way forward.

#### 8.5.4 Admission order and gates

| Stage | Opens | Stays closed |
|---|---|---|
| 0. Fencing (§8.5.1) | Nothing | Everything |
| 1. Evidence collection | Challenges, evidence upload, receipt lookup, capabilities, read-only status | Every mutation path |
| 2. Trust review and membership confirmation (`lisa core trust review`, then `trust confirm`) | The confirmation record, new head, and credential refresh (§8.5.5) | Ordinary work |
| 3. Admission of eligible work | v2 operations and replay, v1 mutations, CLI owner mutations, connectors, scheduler (planning, reminders, briefs) | Outbox and delivery |
| 4. Delivery review and resume (`lisa core delivery review`, then `resume`) | The outbox | Held items (§8.10.6) until released one by one |

Stage 3 requires a fence state other than `unknown`, so a confirmation is impossible while it is unknown.

**Gating during stages 0–2:**
- v2 mutations get `trust_recovery`.
- v1 mutations get HTTP 503 with the R1 code `unavailable` and a retry time. A frozen R1 queue keeps those entries pending, not uncertain (§1.6).
- CLI mutations are refused with the stage named.
- Connectors and the scheduler are paused, and the outbox is suspended.

**Replay at stage 3, in dependency order:**
- Each operation is re-verified against the confirmed roster and current policy: signature, dataset, origin status.
- An operation from an origin revoked in the merged evidence is admitted only if it carries a receipt from a superseded epoch whose lineage places it before the revocation on that same lineage. Committed legitimate data stays committed. Every other operation from that origin is rejected and kept for inspection.

#### 8.5.5 Old receipts, credentials, in-flight work and delayed requests

- **Old receipts** from superseded epochs are provenance. They don't prove commitment in the new epoch: the operation is resubmitted. They serve only as evidence of pre-revocation commitment (§8.5.4) and as replay inventory.
- **Bearer credentials:**
  - The restore invalidates every device credential verifier issued before it. A reset or revocation after the backup would otherwise be undone, and an old leaked credential could work again.
  - During stage 2, each device registers a fresh verifier with a `credential-refresh` challenge signed by its key.
  - Legacy v1 devices have no keys. They stay disabled until the owner re-approves each one in `trust review`, after which they keep their R1 credential. Any legacy revocation found in the recovery ledger stays applied.
- **In-flight operations** whose responses the old Core never returned are resubmitted from journals; identity rules make this safe.
- **Delayed requests:**
  - A v2 request naming the old epoch gets `epoch_mismatch`, and the client reconciles.
  - A v1 request that arrives late is processed after stage 3 against the restored v1 parents. A legacy request that the old branch applied after the cut is unknown to the restored database, so applying it in the new epoch restores that change once. Replaying the same request again finds the new parent.
  - Replay imported from a newer backup carries its v1 parents and children, so a later retry of the same request is answered as a duplicate (§8.12.2).

**Acceptance (M3; S-10, narrative §19.1):**
1. Revoke device C with K2 after backup A was taken under K1. Restore A, then check that:
   - every mutation path (v1, v2, CLI, connectors, scheduler, outbox) is refused at stages 0–2;
   - the K1→K2 chain and C's revocation are recovered from a device report and from the ledger, separately;
   - C's pre-revocation operation is admitted through its same-lineage receipt, and its post-revocation operation is rejected.
2. Restore A a second time on another data directory: the epochs will be distinct, the second confirmation will supersede the first, and a client holding the first head will accept the second.
3. A client whose head the second confirmation doesn't name will refuse it, report it, and accept the supplementary confirmation.
4. An old credential reset after A will stay refused.
5. The fence state `unknown` will block stage 3.
6. A challenge replayed from the first restore will be refused.

### 8.6 Clients: store, states, installation, export and privacy (R2-DATA-01–05, R2-SYNC-04, -05, -08, R2-LIMIT-02; findings 5, 6, 13; privacy and local behavior)

#### 8.6.1 Store, atomic change and states

- **Location (O-8):** one SQLite database per installation, in a replica directory holding the database, its `-wal` and `-shm` sidecars, staging, blobs and export staging.
  - The directory is owner-only and protected until first unlock on iPhone and iPad.
  - It is excluded from device backups by setting `isExcludedFromBackup` on the directory, which covers its contents, and it is never copied between devices.
- **Contents:**
  - canonical merge states and derived records (calendar from 30 days back to 90 ahead, briefs for 30 days, plans in the window, evidence excerpts, source freshness);
  - tombstones and replay metadata;
  - the journal of local and relayed operations with signed bytes and receipts; drafts (§8.6.2); blobs;
  - peer progress and custody acknowledgements;
  - conflicts and draft resolutions;
  - local plans and briefs; plan intents;
  - notification assignments and scheduling results;
  - inference requests and budget; device-only settings;
  - the search index; quarantined R1 queue items;
  - partition cursors and coverage; the local change journal (§8.6.3); lineage, confirmations and key history.
- **Atomic local change (R2-DATA-02).** One write transaction:
  1. validates the command;
  2. allocates the operation ID and this incarnation's next sequence;
  3. signs through `ReplicaSigning`, or stores a draft if signing is unavailable (§8.6.2);
  4. stores the operation with its original input;
  5. updates the effective view and, through `ReplicaIndexing`, the index;
  6. appends to the local change journal and advances the local state generation;
  7. records follow-up work.

  The app says "saved" only after commit; disk-full, I/O and signing failures are reported as they are.
- **Three kinds of safety, never confused (R2-SYNC-04):**

  | State | Meaning | Shown as |
  |---|---|---|
  | Local save | Committed in this replica | "Saved on this device" |
  | Peer custody | A peer returned a signed acknowledgement that it durably holds these exact bytes | "Also held by <device>" |
  | Core commitment | A Core receipt in the current head's lineage | "Synced with Core" |

  Further states: submitted, committed with a conflict, rejected, waiting for dependencies, needs review. Peer custody protects against losing the originating device, but the origin never discards an operation because of it.
- **Effective view:** canonical state plus every pending operation in causal order, through LisaMerge. It is recomputed per affected item when an operation, page, receipt, rejection or revocation arrives. Revoked and rejected operations leave the view but stay in the journal.
- **Working set, provenance and time (R2-DATA-03–05):**
  - Defaults are configurable. Eviction removes cache only, never owner records, pending work, conflicts, uncertain delivery records or replay metadata.
  - A filtered replica says it is incomplete, and nothing missing is read as deleted.
  - Every item keeps its origin, source times, last retrieval or sync, revisions, interpretation status, and whether it is canonical, local or provisional.
  - The planning zone is a replicated preference. Instants are UTC milliseconds; timeouts and backoff use the monotonic clock.

#### 8.6.2 Saving before enrollment, before first unlock, or without signing keys

| Condition | What is stored durably | Status shown | What is recoverable |
|---|---|---|---|
| Not yet enrolled | Input as a **draft** (unsigned, with its original text and time) in the replica | "Saved on this device — not connected to your Lisa yet" | Drafts become signed operations after enrollment. They can be exported sealed to the device's own export key only, because no Core export key is known yet |
| Before first unlock after a restart (iPhone, iPad) | Nothing: the replica and Keychain are unavailable, and nothing is written to an unprotected buffer | Siri: "Unlock your iPhone to use Lisa." A notification action does nothing and the notification stays | Nothing from that attempt. The input was never accepted, and Lisa doesn't claim otherwise |
| Signing key unavailable (Keychain error; a this-device-only key missing after restoring to another device) | Input as a draft; already-signed operations are unaffected | "Saved on this device — can't be sent until this device is enrolled again" | Drafts are signed under the new identity after re-enrollment. Old signed operations still submit unless their key was revoked |
| Disk full | Nothing new | "Not saved: storage is full" with the action needed | Earlier saves are intact (§8.15) |

#### 8.6.3 Snapshot installation (finding 6 preserved and strengthened)

- **Local change journal.** Every transaction that advances the local state generation G appends `(generation, kind, references)` to `local_changes`. Kinds: journal entry, draft change, receipt, rejection, revocation, canonical page, coverage or working-set change, conflict resolution.
  - Entries are kept until no staging needs them. The store can therefore retrieve the complete, ordered sequence of changes after any generation.
- **Staging.**
  - Record G0 and the snapshot cut.
  - Write verified chunks into staged tables inside the live database, each in its own short transaction.
  - Build the staged effective view and the staged search index from the staged canonical tables plus the journal as of G0.
  - Staging reads chunks from the network or blob files, never through a long database reader.
- **Catch-up passes.** Before the swap, `local_changes` after the last applied generation are applied to the staged view and staged index in passes of at most 512 changes. Each pass is a short transaction on staged tables, without holding the main write lock between passes.
  - The passes repeat until at most 64 changes remain, or five passes have run.
- **The installation point,** one write transaction:
  1. every chunk digest in the signed manifest has been verified;
  2. the remaining changes are applied;
  3. staging is invalidated, and restarted from a newer cut, if any of these holds:
     - more than 2,048 changes remain;
     - a canonical page beyond the cut was installed after G0;
     - the epoch or coverage changed;
     - a change cannot be reconciled exactly;
  4. **never backward:** the cut must be at or after every installed partition cursor it covers, in the same epoch or a newer verified one;
  5. **swap:** staged canonical tables, staged effective-view tables and the staged search index are renamed over the live ones together, and cursors, epoch and coverage are set. Journal, drafts, captures, conflicts, receipts and assignments are untouched.
- **Under continuous writes:**
  - Captures take the same write lock, so each commits before G0, between G0 and the swap (and is reconciled), or after the swap.
  - After three invalidations in an hour, the replica asks for a fresher cut and installs when the app has had no input for five seconds, or at the next launch.
  - Writers delayed by the swap are measured and counted in capture p95 (§8.15.3).
- **Crashes:** a crash before the swap leaves the old view; a crash after it leaves the new one. Everything stays in one database file, because SQLite in WAL mode does not commit atomically across attached databases.
- **Storage:** staging needs twice the snapshot size plus a 64 MiB reserve and stops before the reserve, so captures keep room. Reader abort and WAL limits are in §8.15.2.

**Acceptance (M2; S-06):**
- a rejection, and separately a revocation, arriving during staging: both will be reconciled;
- a newer canonical page during staging: it will invalidate staging;
- an older cut: it will be refused;
- captures during staging and at the swap, with latency measured, including writers delayed at the swap;
- 3,000 changes during staging: they will invalidate staging;
- process kills at each step on real files;
- disk exhaustion inside a rootless container tmpfs.

#### 8.6.4 Journal retention and replay after a restore

- **Never dropped:** uncommitted operations and drafts.
- **Committed bodies:** kept until the pruning rule of §8.4.5 allows dropping them; blobs follow their reference counts.
- **An overlay** leaves the view only when canonical state containing its operation is installed, never when the receipt arrives.
- **Caps:** 90 days or 64 MiB of committed bodies per replica. Evictions follow §8.4.5 and are reported.
- **After a new head:** the device resubmits every retained body committed after the restored cut, on any branch. Core re-verifies and applies them (§8.5.4), keeping the old receipts as provenance.
- **Recovery limits:**
  - Owner changes that reachable devices or backups still hold can be recovered.
  - CLI and v1 changes made after the backup are recovered only from a newer backup, because their callers keep no signed journal.
  - Core-derived results are re-derived.
  - Deliveries are held (§8.10.6).

**Acceptance:**
- **M2, replica side:** a copied replica with its key material, restored after the device continued, will start a new incarnation with a correct chain and no sequence reuse; the overlay will stay visible until the canonical change installs.
- **M3, with the real ledger:** the Core incarnation test. The fork will be recorded, pre-backup pending operations will return `duplicate`, and new ones will be accepted; a per-installation incarnation will serve as the negative control.

#### 8.6.5 The direct HTTPS path and the shared transport (R2-SYNC-08)

- **One production transport:** `LisaSyncHTTP` implements `CoreTransport` on LisaClient's `URLSessionTransport` (extended to `/v2/`), with the `Apps/Shared/Trust` evaluator injected. The X2 probe (built at M3) and the full apps (M5, through LisaClientCore) link this same module, so X2 exercises the production adapter.
- **Reconciliation order:**
  1. Authenticate and negotiate.
  2. Fetch trust, revocations, policy, the head and the backup catalogue.
  3. Stop using authority that is no longer valid.
  4. Recover the baseline: pages, or a snapshot when a cursor or epoch no longer fits.
  5. Submit pending operations in dependency order, uploading blobs first.
  6. Collect outcomes, then rebuild the view.
  7. Surface conflicts and rejections.
  8. Recompute plans, briefs and local schedules.
  9. Resume incremental sync.

  Pending work is never discarded before it is preserved.
- **Linux evidence:** URLSession on Linux can't use a custom anchor (R1 D-45). So the harness runs LisaSyncEngine over a test-only libcurl transport that performs the same pin and anchor evaluation, and runs `LisaSyncHTTP` itself over plain HTTP on loopback. The Apple trust path is device evidence (X2).

#### 8.6.6 Protected export and the archive format (O-8; finding 13)

**Required:** a protected export route for unsynchronized owner work (R2-LIMIT-02); local save, peer custody and Core commitment kept apart; the loss of an only copy explained (O-8).

**Mechanism**
- **Archive (`LisaArchive`, format `lisa-archive` v1).**
  - A header names the dataset, origin device, incarnations covered, creation time, recipient key IDs, signer key ID, the roster version and the head known at export.
  - Typed, length-prefixed entries follow:
    - **signed operation:** exact bytes, known receipts and custody acknowledgements;
    - **blob:** digest and bytes;
    - **draft:** unsigned input, times and intended kind;
    - **conflict:** item, field, candidate versions and any draft resolution;
    - **quarantined legacy bytes:** the original R1 queue entry bytes, their class and evidence (§8.14.3);
    - **rollback acknowledgement** (§8.14.7).
- **Sealing.**
  - A random key encrypts the payload with AES-256-GCM.
  - The key is sealed with HPKE (RFC 9180, DHKEM(P-256, HKDF-SHA256), HKDF-SHA256, AES-256-GCM) to Core's export key or keys from the roster, and to this installation's export key.
  - The device signs the result, or marks it unsigned if its key is unavailable.
  - HPKE comes from the approved swift-crypto `Crypto` module, which on Apple is CryptoKit's (iOS 17 and macOS 14, below the targets), so no new dependency is needed.
- **Writable destinations.**
  - On the Mac, an `NSSavePanel` under `com.apple.security.files.user-selected.read-write` lets the owner save outside the sandbox container: Documents, an external disk, a server share.
  - The old-queue import stays read-only: it is opened read-only, persisted only as a read-only security-scoped bookmark, and its file is checked unchanged after the import (§8.14.4).
  - On iPhone and iPad, the document picker's export mode writes to Files: On My iPhone, iCloud Drive or an external drive.
- **Opening and executing an archive.** Possible by the same installation while its keys survive, by `lisa core import-journal`, or by the post-downgrade tool (§8.14.8). Before executing any operation, the opener re-checks:
  - the dataset;
  - that the origin is in the archived roster and not revoked at creation;
  - the signature;
  - the current admission policy: Core's, or translatability to R1 after a rollback.

  Drafts and ambiguous entries are never executed automatically. They go to a durable inspection list, where the owner applies, edits or discards each one.
- **Keys the owner must keep.** `docs/SECURITY.md` lists Core's current and retired export keys and the signing-key history as secret files to back up offline and restore separately (§8.11.2). Without them, nobody can open an archive after Core is lost, by design.
- **The only-copy risk.** Until Core commits it, work exists only on the devices holding it. An isolated device with the only copy loses it if the device is lost, wiped or restored from a device backup, because the replica is excluded from backups.
  - The app shows "Only on this device: n changes" and offers export.
  - Peer custody reduces the risk to losing both devices.
  - `docs/OFFLINE-BEHAVIOR.md` explains all of this.

**Acceptance (S-13):**
- **M5, Linux:** export, then reopen by the same installation and by `import-journal`, with no duplicates. Also:
  - a second installation will fail to open the file;
  - a modified file will fail its signature check;
  - a file sealed before an export-key rotation will open with the retired key;
  - drafts and quarantined entries will land in the inspection list, not be applied;
  - a restored installation, with and without its keys, will keep identities safe.
- **X3 on devices:** the exclusion attribute will be inspected on the directory and its sidecars. On the sandboxed Mac, export will be saved outside the container and the import file shown unchanged. On iPhone, export will be saved to Files.
- **M9 and X7:** loss of the originating installation, then recovery through Core, and after a rollback through the post-downgrade tool using only the documented key backup (§19.2).

#### 8.6.7 Deletion, expiry and privacy across copies (privacy and retention)

**Required:** deletion propagates to canonical records, replicas, search, caches, reminder and delivery work, and evidence-derived outputs, keeping only minimal metadata (R2-SYNC-07).

- **One tombstone,** propagated in the same transaction or by a durable follow-up, removes:
  - content from projections and replicas;
  - search index rows;
  - blob references, so a blob shared with something live stays;
  - derived outputs: briefs and plans are regenerated, and inference results citing the evidence are invalidated with their suggestions withdrawn and a visible reason;
  - future reminders and deliveries, with pending OS requests cancelled and delivered alerts removed where the platform allows;
  - the title copies R1 keeps in reminders and intents;
  - stored v1 response bodies that contain the item, which are redacted (§8.12.2).

  The tombstone keeps IDs, the caller-scoped request key, the deletion position and the actor.
- **Expiry by retention** uses the same propagation. Core retention is in §8.17.
- **What can still hold deleted content:**
  - older backups, until they leave the retained set and the owner deletes them;
  - archives the owner exported, which Lisa cannot reach;
  - rollback archives;
  - a device that hasn't synced yet, which cannot resurrect the item, because the tombstone dominates.

  `docs/SECURITY.md` says this plainly.
- **After a restore:** the restored database may contain items deleted after its cut. Tombstones reported by devices or replayed operations are re-applied at admission. An item whose deletion no reachable holder knows reappears, and the restore review lists the restored cut so the owner can recheck.
- **Diagnostics** carry IDs, counters, hashes and states only — no titles, notes, addresses or content.

**Acceptance (M5 local deletion, M8 notification parts; S-19):** a deleted task with notes, a shared blob, a search hit, a brief citation, an inference result and a pending reminder will lose each of these. A stale device's old edit will not resurrect it. A v1 replay of the creating request will expose nothing. A restore that loses the tombstone will list the item for review.

### 8.7 Nearby synchronization (R2-NEAR-01–05; finding 4 for Design A; trust lifecycle)

**Required:** encrypted, mutually authenticated sessions between enrolled devices, without Internet and without an access point; bounded discovery; relay that never rewrites, impersonates or invents (R2-NEAR-01–05, R2-TRUST-02).

**Platform facts (§1.5):** `NWListener`, `NWBrowser` and `NWConnection` with `includePeerToPeer`, Bonjour and custom framing exist on macOS 15 and iOS 18. Lisa uses these older APIs; the newer family needs iOS 26. TLS-PSK works only there, only over TLS 1.2, and has no documented suite constant. Mutual TLS has every hook except certificate creation. Multipeer Connectivity is deprecated and unused.

**Session layer, under either design**
- **Hello:** protocol version, device ID, roster (epoch, version), head, nonce.
- **Authentication:** each side signs, with its operation key:
  - `"lisa-nearby-auth-v1"`;
  - both nonces and device IDs;
  - a 32-byte TLS exporter value (label `EXPORTER-lisa-nearby-v1`);
  - the roster version and head.

  Each side verifies the other against its newest roster. A relay sitting between two devices sees different exporter values on its two sessions, so the signatures fail and the session closes before data moves.
- **Exchange:**
  - inventories first;
  - then bounded exchanges in §8.16 frames: signed operations, Core receipts, change pages, snapshot chunks, blobs, rosters and paged artifacts;
  - then custody acknowledgements signed by the receiver (§8.6.1).

  The newer roster and head always go first, so a stale peer is updated before it sends work.
- **Connection behavior:** TCP keepalives; send timeouts; backpressure by awaiting each send; 30-second idle close; deduplication by device ID (the connection opened by the lower ID survives); random Bonjour instance names, with nothing identifying in TXT records except Design A's rotating tags.

**Design A: pair-specific pre-shared keys**
- **Pair key:** K_ij = HKDF-SHA256 over the P-256 agreement between devices i and j, with the dataset ID as salt and `"lisa-nearby-psk-v1"` plus both sorted device IDs as info.
- **Normal discovery:**
  - The listener publishes a tag rotating every 15 minutes: the first 16 bytes of HMAC-SHA256(discovery secret, `"lisa-disc-v1"` ‖ window ‖ device ID).
  - The initiator finds its peer by tag and sends its own tag as the PSK identity.
  - The discovery secret is fetched separately (`GET /v2/trust/nearby-secret`, authenticated, `Cache-Control: no-store`, kept in the Keychain) and never travels in the enrollment response.
  - It rotates on every revocation and every 30 days. Devices keep the current and previous versions for 7 days, and a peer passes a newer version only inside an authenticated session.
- **Rejoining after the overlap.** A device whose newest secret is older than both versions in use can't compute or recognize tags. It rejoins without the secret:
  - It browses for Lisa services and opens a trial connection to each one found (at most 9).
  - As PSK identity it sends `HMAC-SHA256(K_ij, "lisa-rejoin-v1" ‖ window)` truncated to 16 bytes, one per candidate peer j.
  - The listener's PSK selection block computes the same value for each active roster peer (at most 9 HMACs) and selects K_ij on a match.
  - The handshake and the session layer then authenticate both sides. The peer sends its newer roster and the current discovery secret, but only if the rejoiner is active in that roster.

  Observers can't link these identities, which change per window and pair. A revoked device is refused at the session layer.
- **When Core is the only way back:** a device whose roster is older than the maximum nearby trust age (30 days by default) can't start any nearby exchange (R2-TRUST-03). It must reach Core, directly or by re-pairing. The UI says so precisely: "Connect to Lisa Core once to resume nearby sync (trust older than 30 days)."
- **Limits:** TLS 1.2 only; a PSK suite only by raw value; forward secrecy only if an ECDHE-PSK suite is negotiated.

**Design B: roster-bound mutual TLS**
- **Identity:** a P-256 TLS key in the Secure Enclave and an X.509 certificate for it (v3, random serial, one-year validity, `digitalSignature`, server and client authentication), stored beside the key so that Security forms a `SecIdentity`. The key's hash is listed in the device's roster entry.
- **Handshake:** TLS 1.3 with mutual authentication required. The verify block accepts a peer only if its leaf key matches an active roster entry; no CA chain or host name is involved.
- **Discovery:** connect to the discovered services (at most 9) and learn who answered during the encrypted handshake.

**Certificates: proof-only at X1, production at X4**
- **X1, proof-only provisioning.**
  - A fixed-template DER encoder, compiled only into `Apps/Proof`, signs with the Secure Enclave key through CryptoKit. It is labeled proof-only and never linked into a product.
  - The same Foundation-only encoder file is compiled by a Linux harness with a software key, and its output is checked with `openssl x509` and `openssl verify`.
  - X1 evidence covers Network framework mutual TLS with a Secure-Enclave-backed identity and roster pinning. It does not cover production issuance.
- **X4, production (P-08, pending).** If N-1 selects Design B, the production issuer is swift-certificates:
  - **Pin:** 1.21.1 at `84f03fafeca28c19f5fc4b528df3d22ce8896bd7`.
  - **Compatibility:** tools 6.1, which builds with Swift 6.3.2 and 6.4.2; swift-crypto `3.12.3..<6.0.0`, satisfied by the pinned 5.1.1; swift-asn1 `≥ 1.1.0`, satisfied by the pinned 1.7.4.
  - **Expected lockfile impact:** one new pin and no change to existing ones. This is confirmed only by resolution after authorization.
  - **Binary impact:** `_CryptoExtras` adds BoringSSL-backed code to the Apple apps; app size will be measured with and without at X4.
  - **Protected-key integration:** a Secure Enclave `SecKey` (`kSecAttrTokenIDSecureEnclave`, permanent) signs through `Certificate.PrivateKey(SecKey)` without leaving the enclave. The certificate goes into the Keychain, Security pairs it with the key as a `SecIdentity`, and `sec_identity_create` hands it to Network framework.
  - It is linked only through the conditional `LisaDeviceCertificates` module. **No package or lockfile change happens until the owner reviews and authorizes the pin.**
- **Still to verify on devices with the selected library (X4, E-11):**
  - Secure-Enclave-signed creation on the Mac, iPhone and iPad;
  - `SecIdentity` formation in the data-protection Keychain, including in the sandboxed Mac;
  - TLS 1.3 mutual authentication on all three pairs;
  - key extraction in the verify block;
  - renewal at 80% and rotation through key updates;
  - behavior while locked after first unlock;
  - reinstall followed by a key update.

**N-1 is a prerequisite.** `Apps/Shared/Nearby`'s production transport is written only after N-1's device result is recorded:
- Design A is adopted only if it passes every criterion and negotiates a forward-secret ECDHE-PSK suite on every pair.
- Otherwise Design B is adopted.
- If both fail, nearby stops and is reported, and everything else continues.

The portable session layer, relay and storage proceed meanwhile.

**After a failure or retry**
- **Handshake or authentication failure:** close; back off per endpoint on the monotonic clock; retry after the backoff or a roster change. There is never an unauthenticated fallback.
- **Interrupted transfer:** resumes from per-peer durable progress; duplicates are harmless.
- **Revoked peer:** refused until a roster says otherwise.
- **Local network denied** (−65570 or `localNetworkDenied`): a visible unavailable state, with no retries until permission changes. The first nearby operation runs in the foreground (TN3179).

**Relay rules:**
- A peer forwards other devices' signed operations to Core with its own credential, and returns Core-signed receipts and pages.
- It never rewrites, re-signs, invents a receipt, shares its credential, or forwards URLs, commands or general traffic.
- Direct and relayed paths may run at once; identity rules make duplicates harmless.

**Background:** bounded `BGAppRefreshTask` requests for Core sync on iPhone and iPad. Nearby runs only in the foreground. No audio, location or VoIP mode. The UI distinguishes "available now", "waiting for the app to be open", "background time requested but not granted", and "permission or radio unavailable" (R2-NEAR-04).

**Acceptance (proposed checks):**
- **Linux, simulated link (M6; S-08, S-12 shared):** the harness will check hello and authentication; exporter mismatch; unknown and revoked peers; resume and deduplication; the Design A rejoin with an expired discovery secret; refusal with trust older than 30 days; R2-L04, L15, L17, L36; the R2 §18.2 scenario; the coverage relay of §8.4.2.
- **Apple:** N-1 at X1; the production transport on all three pairs at X4 (R2-A03–A07), with the P-08 behaviors if Design B applies.

### 8.8 Capabilities and transitions (R2-CAP-01–04)

- **Tracked separately:** authenticated Core reachability and compatibility; each fallback provider; nearby availability; data freshness and coverage; notification permission and schedule coverage; enrollment and trust (including recovery stage and head); storage health. Core reachability comes only from an authenticated exchange, never from a VPN or path signal.
- **The mode matrix of R2-CAP-02 is kept as written.** Features follow the capability they need, as `docs/OFFLINE-BEHAVIOR.md` specifies. If a required client capability can't be provided on a platform (for example, public retrieval failing E-1), the feature is shown as unavailable there, and the Apple and release gates stay open (§22). Changing the matrix is the owner's decision.
- **Transitions:** a connectivity change never interrupts a durable capture, replaces a draft, clears the database, resends a finished or uncertain inference, replays an expired delivery or resets retries. Retries use cancellation, bounded timeouts, backoff with jitter and a manual "Try again". Authentication failure, revocation, recovery and version mismatch stop retrying and never fall back to anything insecure.

### 8.9 Offline intelligence, fallback inference and public retrieval (R2-CAP-03, R2-INT-01–05, R2-WORK-01–04; finding 14; fallback model accounting)

#### 8.9.1 Offline intelligence

- **With no model:** search; sorting by deadline, priority and state; overdue detection; a provisional plan from R1's planner and constraints, with explanations of unscheduled work and conflicts (§8.3.4); a structured local brief; permitted preference changes; managing tasks and owner reminders. Free-form captures stay pending; nothing is invented.
- **Local plan (R2-WORK-01):** records its canonical checkpoint, the provisional operations included, calendar coverage and freshness, open conflicts, the algorithm version and when it was made. It is shown as provisional until Core reconciles. Stale calendar gaps are shown as unverified; locked and accepted blocks never move silently. Actions on it are plan intents (§8.2.3).
- **Local brief (R2-WORK-02):** has its own identity (device, input version) and never replaces the canonical brief. Ages, missing sources and regeneration failures are shown, and the readable and spoken versions carry the same uncertainty.

#### 8.9.2 Fallback inference and its accounting

- **Provider (R2-INT-01):** the OpenAI-compatible adapter runs over `LisaHTTP1` (§8.9.3). It is configured per device: endpoint, model, a Keychain credential reference, explicit data-sharing consent, timeout, input and output bounds, the budget. Nothing is enabled by default, and Core's settings never authorize a client.
- **Workflows (R2-INT-02):**
  - interpret a capture into proposed tasks, ideas or events;
  - summarize selected local evidence;
  - improve the local brief;
  - explain the provisional plan;
  - answer bounded questions from the working set.

  Results name their local basis and missing or stale sources, and pass the same validation as Core's suggestions.
- **Logical intent key:** `SHA-256("lisa-infer-intent-v1" ‖ workflow ‖ sorted input references with revisions ‖ template version ‖ model ID ‖ endpoint ID ‖ SHA-256 of the owner's question, if any)`. While a request with that key exists in any state, repeated taps, restarts and reconnects return it. A new request needs a new intent: changed inputs or template, or an explicit "Ask again".
- **One in flight per device:** a durable single-row slot. Other intents wait in a local queue unreserved and show "waiting".
- **Request states:**

  | State | Budget unit | On restart |
  |---|---|---|
  | `queued` | none | stays queued |
  | `reserved` (one transaction: record the configuration snapshot and consent version, reserve one unit of the planning-zone day and of the rolling 24-hour window; refused at 10) | held | continues to send if consent, configuration and inputs are unchanged; otherwise `cancelled` and released |
  | `sending` (persisted before the first byte) | held | becomes `uncertain`, never resent |
  | `answered_valid` / `answered_invalid` | spent | final |
  | `failed_before_send` | released | final |
  | `uncertain` (timeout or connection loss after sending) | spent, labeled "may have been charged" | final until the owner acts |
  | `cancelled` (consent withdrawn, configuration changed, evidence deleted, owner cancel) before sending | released | final |

- **Repair:** at most one, reserving its own unit. If no unit is left, the invalid result is shown without repair.
- **Consent withdrawn between reservation and send:** the transaction that would persist `sending` re-checks the consent version, so a withdrawn consent cancels and releases. Nothing is sent.
- **Model or template changes:** a request keeps the configuration it reserved with. A change cancels unsent requests (released), and results under an old template stay labeled.
- **Planning zone and clock:**
  - The day key is fixed at reservation, and a zone change can't free units.
  - The last-seen wall time is persisted, and the day key uses the later of it and now, so a backward step can't return to an earlier day.
  - The rolling window counts reservations stamped within the last 24 hours, including stamps that now look like the future. A forward step followed by a reboot can release units early; this residual is documented.
- **Deleted evidence:** checked again at send (cancel and release). After an answer, results citing deleted evidence are invalidated and their suggestions withdrawn with a reason (§8.6.7).
- **After an uncertain, possibly charged attempt:** the owner sees "Outcome unknown — the provider may have processed and charged this request" and can:
  - dismiss it;
  - "Ask again", which is a new request, reserves a new unit, and warns that the request may be charged twice.

  Nothing is resent automatically.
- **No global cap:** per-device limits are not a global spending cap, and the documentation says so (R2-INT-05).
- **On reconnection:** results go to Core as proposals with their evidence. Nothing is regenerated just because Core returned.

**Acceptance (M7; S-18):** the harness will check:
- the five workflows against a loopback OpenAI-compatible server;
- a process kill in each state, and repeated taps and reconnects landing on the same request;
- consent withdrawal between reservation and send;
- a template change, a zone change at midnight, a backward clock step and a forward step with a reboot (the residual documented);
- evidence deleted before send and after the answer;
- repair counting;
- "Ask again" after an uncertain attempt.

#### 8.9.3 Public retrieval and the destination policy (finding 14)

**Required:** foreground, explicitly requested retrieval of owner-configured public feeds and owner-supplied public URLs, keeping R1's URL, redirect, size, parser and network-safety controls (R2-INT-03); required in the "Internet, Core unavailable" mode (R2-CAP-02).

**What R1 enforces, and the Apple path keeps (§1.6):**
- every resolved address checked before a socket is opened to it, with refused addresses skipped;
- the connected address checked again before the request is sent;
- no proxy;
- TLS 1.2 or later with verification;
- redirects re-checked hop by hop: none for model calls; at most 3 by default (10 at most) for sources, with credentials dropped across origins;
- a non-idempotent request sent at most once per exchange.

**Destinations**

| Destination | Policy | Client path |
|---|---|---|
| Owner-requested public URL or feed | public only | `LisaHTTP1` over `Apps/Shared/PublicFetch` |
| Model endpoint named by DNS | public only | Same, with system trust |
| Model endpoint `localhost`, or a loopback or private IP literal | local networks allowed | Same; the owner may pin its SPKI on the device |
| Model endpoint over plain `http` | loopback only (meaningful on the Mac) | Same |
| Core | The paired endpoint and trust (§8.1.2) | `LisaSyncHTTP` |

**Checks, in order**
1. **Before opening TCP:**
   - R1's URL policy: scheme, no credentials, host syntax, port.
   - The endpoint's scope, as `ConfiguredHostScope` decides.
   - Resolution through the system resolver (`getaddrinfo`, off the main thread), A and AAAA; IP literals as written.
   - Path classification by `NWPathMonitor`: IPv4 available, IPv6 available, and NAT64 presence by RFC 7050 discovery on IPv6-only paths (cached per path, repeated on a new path and ten seconds before the TTL, §1.5).
   - Each address is classified with R1's `NetworkAddress`, extended for `64:ff9b:1::/48` and the discovered prefixes; an address inside a NAT64 prefix is judged by its embedded IPv4 address. Refused addresses are skipped; if none remains, the request fails with R1's "resolves only to addresses Lisa does not connect to".
2. **Before starting TLS:** `NWConnection` to one permitted IP endpoint at a time (IPv6 first, then IPv4, staggered 250 ms), never by name, with `preferNoProxies`. TCP and TLS therefore reach only checked addresses. This deliberately departs from TN3151's advice to connect by name: connecting by name lets the system resolve again and connect before any check runs, which R1's gate never allows.
3. **TLS:** the system stack, minimum TLS 1.2. The URL's host is the TLS server name (`sec_protocol_options_set_tls_server_name`) for SNI and certificate validation. Trust is the system default, or the owner's pin for a permitted local model endpoint.
4. **Before sending HTTP:** `currentPath.remoteEndpoint` must equal the chosen endpoint. Anything else — a proxy, a relay or a rewrite — makes the destination unverifiable.
5. **HTTP:** `LisaHTTP1`, HTTP/1.1, one request per connection, `Accept-Encoding: identity`, no cookies, caching, upgrades or pipelining, Content-Length or chunked bodies, R1's header, body and time limits.
   - GET for retrieval; POST for model calls, never re-sent on a new connection.
   - Each redirect re-runs checks 1–4 on a new connection.

**Network paths**

| Path | Support |
|---|---|
| IPv4 only (including a CLAT that presents IPv4) | Supported; addresses classified directly |
| Dual stack without NAT64 | Supported; each address classified |
| IPv6 only, no NAT64 found | Supported for native IPv6; names with only A records fail with "no route" |
| IPv6 only with DNS64/NAT64 | Supported for names with A records: Lisa classifies each public A record and connects to the address it synthesizes with the first discovered prefix (RFC 7050 §3), or with `64:ff9b::/96` if that is the prefix. **Native AAAA answers are not used on such a path**, because RFC 7050 §5.1 means discovery can't learn range-specific prefixes, so a native-looking address can't be shown not to reach a private IPv4 host. A name without A records fails closed with "Can't verify this destination on this network" |
| Discovery fails or times out on an IPv6-only path | Fail closed |
| Path changes during a request (interface switch, VPN up or down, new prefix) | The connection is cancelled. A GET may restart once from check 1 on the new path; a POST is never resent and ends `uncertain` if bytes were sent |
| Split routing through a VPN | Allowed: the endpoint check still sees the destination address. A VPN-supplied proxy makes the endpoint differ, so the request fails closed |

**Fail closed.** No request byte is written when resolution fails, NAT64 discovery fails, the connected endpoint differs from the chosen one, or the path type isn't covered.
- A retrieval then shows "Couldn't verify where this link leads; not fetched" and is left for Core.
- A model call ends `unverifiable_destination` with its unit released.
- Nothing is ever retried through URLSession.
- Links in content are never followed. Results carry client provenance and never advance Core cursors.

**Feasibility first (E-1, at X1).** `Apps/Proof` runs a fetch probe with no Core configured, on the Mac and on an iPhone:
- an owner-authorized public URL fetched over `https`;
- a name resolving only to a private address, refused before any TCP connection (a listener on the owner's network records whether one arrived);
- a mixed name dialed only at its public address;
- a configured system proxy not used;
- an IPv6-only NAT64 network (macOS Internet Sharing) handled per the table.

E-1 gates the production retrieval design. If a platform can't connect to an IP endpoint while validating TLS for the URL's host, can't report the connected endpoint before the first write, or can't discover prefixes, then public retrieval and DNS-named providers stay off on that platform. The limitation is documented, and the Apple and release gates stay open until the owner decides (§22).

**Acceptance (S-14):**
- **M7, Linux:** `LisaHTTP1`'s parser, limits and redirects against loopback servers. The policy will be driven through the test resolver and byte stream across every table row: public, private, link-local, IPv4-mapped, well-known and network-specific prefixes, mixed answers, a native AAAA on a NAT64 path refused, a connected endpoint other than the chosen one, a path change during GET and during POST, a redirect to a private address, and R1's redirect limit.
- **X5, on the Mac, the iPhone and the iPad with Core unavailable,** against controlled endpoints the owner runs: a permitted public GET, a disallowed destination refused before connection, a path change (Wi-Fi to cellular, or a VPN toggle), redirect handling, and an authenticated model POST to a controlled OpenAI-compatible endpoint on a private IP literal with a pinned certificate.

### 8.10 Notifications and external delivery (R2-NOT-01–06; findings 11 and 12; notification coverage)

**Required:** stable occurrence identity with monotonically advancing assignment generations, where a content revision alone creates no new occurrence; per-device ownership records with R2-NOT-03's states; the five-step handoff; no automatic reclaim of an uncertain assignment; visible coverage gaps; a 48-hour horizon and at most 32 pending Lisa requests per device; Core-only email and calls with R1's outbox rules; no blind resend after restart or restore (R2-NOT-01–06, R2-L24–L29).

**Core decides, under R1's unchanged policy:** eligibility, escalation, quiet hours, owner-only destinations, generic content, validity windows and stale suppression. Every enabled paired device is targeted, now including the Mac, which registers for APNs.

#### 8.10.1 Occurrences, firings and identifiers

- **Occurrence ID:** the first 16 bytes, in base32, of `SHA-256("lisa-occurrence-v1" ‖ 0x00 ‖ dataset ‖ 0x00 ‖ kind ‖ 0x00 ‖ subject ‖ 0x00 ‖ slot)`. It is fixed when created and never changes.
- **Firing number `f`.** It distinguishes an intended new alert from a change to an existing one:
  - **New firing:** an explicit snooze names the firing it snoozes, f, and creates f+1 at the snooze instant, matching R1, where a snooze fires again under a new key.
  - **Same firing, new generation:** a reschedule (deadline or block moved), a content-only edit (a title change, which R1 does not treat as material), or a reopen.
  - A firing that has already fired is never re-created by a reschedule, content edit or reopen. A reopen schedules only future slots that haven't fired, as R1 creates only future offsets.
- **Scope:** ownership, reservations, submissions, observations and late reports all apply to `(occurrence, firing, recipient)`.
- **Mapping from R1's three key levels (§1.6):** the slot leaves out the mutable parts.

  | R1 key | R1 level | R2 identity |
  |---|---|---|
  | `deadline:task:<id>:<seq>:<offset>` | Reminder | occurrence (deadline, task, offset) |
  | `deadline:task:<id>:<seq>:soon` | Reminder | occurrence (deadline, task, `soon`) |
  | `dateonly:task:<id>:<seq>` | Reminder | occurrence (dateonly, task) |
  | `overdue:task:<id>:<date>` | Reminder | occurrence (overdue, task, date) |
  | `block:<plan>:<block>:<startMs>` | Reminder | occurrence (block, plan and block) |
  | `proposal:<id>:<date>` | Reminder | occurrence (proposal follow-up, proposal, date) |
  | `reminder:<reminderID>:<firingMs>` | Notification intent, one per firing | That reminder's occurrence; firing numbers in ascending `firingMs` order |
  | `brief:<date>:<zone>` | Notification intent | occurrence (brief, date and zone), firing 1 |
  | `commitmentChange:<subject>:<seq>` | Notification intent | occurrence (commitment change, subject, change sequence), firing 1 |
  | `notify:<key>:device:<id>`, `email:<key>:<address>`, `brief-email:…`, `call:task:<id>:<key>` | Delivery | Kept unchanged on migrated deliveries and linked to (occurrence, firing, recipient). New deliveries are keyed by occurrence ID, firing and recipient |
  | (new) owner reminder | — | occurrence (owner reminder, reminder) |

  When R1 logic replaces a reminder key for the same slot (change-sequence bump, moved block), the occurrence keeps its ID and gets a new generation. A change that removes the slot cancels the occurrence.
- **OS request identifier:** `lisa.r.` followed by the first 26 base32 characters of `SHA-256("lisa.local-notification.v1" ‖ 0x00 ‖ dataset ‖ 0x00 ‖ occurrenceID ‖ 0x00 ‖ deviceID)`.
  - It is one per (occurrence, device), so scheduling firing f+1 or a new generation replaces the previous request.
  - `userInfo` carries the occurrence, firing and generation. R1's APNs collapse IDs are unchanged.
  - Neither identifier is ever used for idempotency (R2-NOT-05).

#### 8.10.2 Commands and observations

- **Commands** per (occurrence, device): `schedule(f, g, trigger, content)` and `cancel(f, g)`.
  - `g` increases across all firings and is epoch-qualified: `(epochSequence, counter)`, compared in that order. A restored Core's commands therefore outrank every older-epoch generation.
  - A command at or below the stored generation is stale and ignored.
- **Observations** are facts about one firing: `scheduled(f, g)`, `fired(f, g)`, `absent(f, g)`, `failed(f, g)`, `expired(f)`. They are never discarded as stale.
  - `fired(f)` arriving after `cancel(f, g+1)` records that firing f was displayed, so its slot is not reclaimed.
  - `fired(f)` has no effect on f+1.
- **Ownership states** per (occurrence, firing, device): R2-NOT-03's list — Core-owned, reserved, local confirmed, scheduling failed, suppressed or cancelled, expired, outcome unknown — plus `fired`.
  - "Scheduling failed" (confirmed not scheduled) and a confirmed cancellation return the slot to Core.
  - `fired`, `expired` and `outcome unknown` never do.

#### 8.10.3 Reservation against push attempts

Reservation runs in one transaction that reads the delivery for the same (occurrence, firing, recipient). It uses R1's delivery states (§1.6):

| Delivery state | Reservation for firing f |
|---|---|
| none, or `pending` | Suppress the delivery and reserve |
| `inProgress` (preparing or submitting) | Not now; retried after the attempt reaches a final state |
| `acceptedByProvider`, `confirmedDelivered`, `outcomeUnknown`, `capturedDryRun` | No reservation for f, which is delivered or uncertain; firing f+1 can still be reserved |
| `failed`, `cancelled`, `suppressed` | Reserve only if the firing is still valid |

The outbox never claims a delivery whose (occurrence, firing, recipient) is reserved or device-owned. Email and calls stay Core-only and follow R1's outbox (R2-NOT-06).

#### 8.10.4 Handoff, replacement, cancellation and reconciliation

- **Handoff:**
  1. In one transaction, Core reserves (occurrence, f, device) and suppresses its own push.
  2. The device fetches the signed assignment `schedule(f, g)`.
  3. In one replica transaction, the device stores it as `accepted`.
  4. The device adds the OS request under the stable identifier with `userInfo` {occurrence, f, g}, reads the pending list back, and marks the assignment `scheduled`.
  5. It reports `scheduled(f, g)`, which Core records, never as proof of display.
- **A crash between steps 3 and 4** (command stored, OS not yet told) is completed at the next reconciliation:
  - an `accepted` assignment with no matching pending request is scheduled;
  - a pending request with an older generation is replaced;
  - a request already present with generation g is marked scheduled.

  The stable identifier rules out two pending requests for one occurrence.
- **Replacement** (new generation of the same firing): store, add under the same identifier, verify, mark, report.
- **Cancellation:** store the cancel; remove the pending request; verify it is absent; check the delivered list; report `cancelled(f, g)`, or `fired(f, g)` if it was delivered.
- **Expiry:** nothing is scheduled past `validUntil`, computed as R1's `DeliveryTiming` does. A reminder is valid until the earlier of 240 minutes after due and its deadline; a block until its end; overdue, proposal and brief notices until local midnight. A firing past `validUntil` without evidence is `expired(f)` and is never replayed.
- **Alerts already shown:**
  - Anything in `getDeliveredNotifications`, or seen by `willPresent` or an action handler, is `fired`.
  - Stale delivered alerts for resolved subjects are removed where the platform allows (R2-NOT-05), and the `fired` record is kept.
  - If the owner cleared an alert before Lisa saw it, and there is no other evidence, the result is `outcome unknown`.
- **Uncertainty:** a firing whose trigger has passed, absent from the pending and delivered lists, with no callback evidence, is `outcome unknown`. Core keeps it device-owned, pushes nothing, and shows a coverage gap.
- **Lock state:** scheduled notifications fire while the device is locked. Acknowledge and snooze work from the lock screen after first unlock; complete requires unlocking, as in R1 (`.authenticationRequired`). Reports wait until the app runs. Before first unlock, nothing is saved (§8.6.2).
- **A disconnected device** keeps its reservations, and its reports queue. Core never reclaims the slot; expiry makes it `expired` or `outcome unknown`.
- **A device ahead of a restored Core:**
  - At recovery stage 1 the device reports its assignment inventory with epoch-qualified generations and observations (§8.5.3).
  - The restored Core keeps device-owned every slot the device reports as scheduled or fired, and issues new-epoch confirm or cancel commands.
  - Slots nobody reports stay `outcome unknown` until a report arrives or they expire.
  - Core never pushes a slot that any device reports as scheduled.
- **Locally created reminders (R2-NOT-04):** owned by the creating device until Core accepts them. Peers show them as pending and schedule nothing for that slot. Once accepted, Core adds future slots for the other devices, keeps the creator's, and replays no missed past reminder. No device takes over a Core-owned slot because of an outage.
- **Reconciliation** runs on launch, foregrounding, sync and notification actions. It repeats unfinished steps idempotently, cancels obsolete requests, applies acknowledgements, completions, cancellations and deletions, keeps uncertain handoffs, and reports permission changes (R2-NOT-05).
- **The Mac:** its bundle ID joins `notifications.apns.topics`. It gains the `com.apple.developer.aps-environment` entitlement and needs an App ID with Push Notifications and a matching provisioning profile from the owner's developer account. X6 verifies this with that account; without it, `NOT_RUN_CREDENTIALS`.

#### 8.10.5 The local horizon, the 32-request cap and coverage holes

- **Selection:** each device schedules firings due within 48 hours, at most 32 Lisa requests (R2-NOT-02), in this priority: confirmed time-sensitive, then confirmed, then the rest; within each class, by time.
- **Coverage holes:** with more than 32 eligible firings, an omitted firing can be earlier than a scheduled one. For example, with 40 reminders tomorrow, a 08:00 routine reminder may be left out while a 21:00 time-sensitive one is scheduled.
  - Omitted firings stay Core-owned and are pushed through APNs when Core and the device are reachable.
  - On an offline device they don't fire. That is the hole.
- **What the owner sees:**
  - "Notifications scheduled through <time>", where the time is the earlier of the horizon's end and the earliest omitted eligible firing;
  - "n reminders not scheduled on this device (earliest 08:00)".
- **Refill** happens when the app runs (launch, foreground, a granted background refresh) and is not guaranteed while the app is suspended (R2-NEAR-04).

#### 8.10.6 External delivery after a restore (finding 11)

**Required:** a restored Core starts with outbound side effects suspended; restart or restore never blindly resends attempted communications (R2-CORE-06, R2-NOT-06, R2-D12).

**Mechanism**
- **Submission journal** (recovery ledger, outside the database).
  - Before each provider submission (APNs, SMTP, Twilio), Core appends and syncs to disk `{deliveryID, occurrence, firing, recipient, channel, epoch, runGeneration, wallTime, monotonicTime}`.
  - After the outcome, it appends the outcome.
  - Each run appends a wall/monotonic heartbeat every minute and a clean-shutdown marker. The journal is hash-chained and survives a database restore.
- **Uncertainty interval** `U = (t_cut, t_last]`:
  - `t_cut` is the backup cut's commit time.
  - `t_last` is the previous sender's last possible submission: the latest of its last journal record, the fence record, and the restore start.
  - If the journal is missing or broken, `t_last` is the fence time (owner attestation or credential rotation).
  - With the fence state `unknown`, U has no upper bound, and delivery can't resume anyway (§8.5.4).
  - **Clock changes:** if the previous run's heartbeats show a wall-clock step (wall time moving differently from monotonic time), U is widened to cover both readings. A configurable margin (1 hour by default) is added at each end.
- **Held as `uncertain_after_restore`:**
  1. every backup row in `pending` or `inProgress` (preparing or submitting) at the cut;
  2. every delivery the journal shows started after the cut, recreated as held if the restored database lacks it;
  3. every slot (occurrence, firing, recipient) due within U, whether it is in the backup, missing from it, or first regenerated after resume (a reminder created after the cut and re-derived from replayed work).

  The exception is positive evidence: a journal that is complete through `t_last` (unbroken chain ending in a clean-shutdown or fence marker) and shows no submission for that slot. Such slots are released normally.
- **`lisa core delivery resume`** resumes the outbox and keeps every hold.
- **`lisa core delivery release <id>`** asks the owner to confirm: "The previous Core may already have sent this. Sending again may duplicate it."
  - It authorizes exactly one further attempt and writes an audit record: actor, time, acknowledgement, and the evidence shown.
  - That attempt follows R1's rules for one attempt (recipient, quiet hours, urgency).
  - A transient failure returns the item to held, needing another release. An unknown outcome stays `outcomeUnknown`. No automatic retry follows.
  - An item past `validUntil` can't be released and shows as expired.
  - The apps' Lisa Core status screen lists held items read-only.
- **Interruption during a release:** the release record, the claim and the journal start are durable. A crash while submitting becomes `outcomeUnknown` on restart, as in R1, and is never retried. The owner sees "Released; outcome unknown".

**Acceptance (S-11, S-12; narrative §19.1)**
- **M3, portable, with scripted SMTP, Twilio and APNs servers:**
  1. Take backup A.
  2. An email, a call and a push will be accepted after A's cut.
  3. Restore A.

  All three will be held, and will stay held after `resume`. Also checked:
  - a reminder created after the cut, regenerated after resume, will be held;
  - one released item will be sent once and audited;
  - a crash during a release will end `outcomeUnknown` with no second attempt;
  - an intact journal will release a slot it proves unsent;
  - a backward wall-clock step in the old run's heartbeats will widen U.
- **M4:** the same in the container.
- **M8, firings, against the simulated notification center:**
  - the sequence first display → explicit snooze → a delayed `fired(1)` report → exactly one later alert for firing 2;
  - a moved deadline keeping one occurrence and one pending request with a new generation;
  - a content-only edit with no new alert;
  - close and reopen;
  - a reservation attempted while a push for the same firing is in flight;
  - a cleared alert;
  - a disconnected device;
  - a device ahead of a restored Core;
  - a crash between storing a command and scheduling it;
  - 40 eligible reminders with the coverage hole shown as specified.
- **X6:** the same on devices, plus permission changes, Focus, previews and lock state (R2-A09–A12). APNs only with the owner's account.

#### 8.11.1 Image and reproducible build

- **Platforms:** `linux/amd64` and `linux/arm64` are both declared. amd64 is built and run on the rootless engine. arm64 is `NOT_RUN_ENVIRONMENT`, and a genuine cross-build would be a separate evidence entry (O-11).

#### 8.11.2 Container boundaries, secrets and SELinux

- **Boundaries:**
  - non-root user (UID 10001);
  - writable `/var/lib/lisa` (database, recovery ledger, run files) and a backups volume;
  - read-only `/etc/lisa`; `/run/secrets` from Compose file secrets; a bounded tmpfs for `/tmp`;
  - read-only root filesystem;
  - `cap_drop: ALL`, `no-new-privileges`, no privileged mode, no Docker socket;
  - no secret in a layer or build argument;
  - bounded logs (driver limits and Lisa's rotation);
  - `SIGTERM` handled within a stop grace period longer than Lisa's shutdown.
- **Secrets:** R1's checks stay as they are: the file is owned by the effective user, has no group or other bits, and is at most 64 KiB (§1.6).
  - Under this rootless engine, container UID 10001 is host UID 599824 (589824 + 10001 − 1). Secret files must therefore be owned by 599824 with mode 0400. `docs/DEPLOYMENT.md` sets this up with a one-off container run as container root (`chown 10001:10001`, `chmod 0400` inside it).
  - `lisa core doctor --secrets` reports owner and mode as the running process sees them.
- **Secret inventory for offline backup** (`docs/SECURITY.md`):
  - Core signing keys, current and retired;
  - export keys, current and retired;
  - TLS key, certificate, CA and intermediates bundle;
  - APNs key; SMTP and Twilio credentials; the model provider key.

  They are restored separately from database backups. Backup manifests list their references, never their values (R2-CORE-06).
- **SELinux:**
  - On this host, the rootless engine has no SELinux labelling (§1.2). It can show that Compose accepts the `:Z` mount options, not that containers are confined; that check is `NOT_RUN_ENVIRONMENT` here.
  - On the target host, the owner records the engine's security options, the container process label (`ps -eZ`, expecting `container_t`), and a denial when the container tries to read an unlabelled host path.
  - If the target engine has SELinux disabled, the record says confinement isn't demonstrated there.
  - SELinux is never disabled or relaxed with `label=disable`.

#### 8.11.3 VPN-only publishing (finding 15 preserved and strengthened)

**Required:** loopback-only development defaults; an explicit production bind or publish address; no silent fallback to all interfaces; IPv4 and IPv6 checks; a way to verify that a non-VPN client can't reach the API (R2-CORE-03).

**Mechanism**
- **Configuration (schema v2):** `api.bindAddresses`, a list of IP literals; R1's single `api.bindAddress` is read as a one-item list. Also `api.publishAddresses`, the VPN addresses the owner declares.
  - Outside a container, Lisa binds each configured address and refuses wildcards in production. An unset or empty list is a configuration error. Loopback is the development default.
- **One validated value inside and outside the container.** `deploy/compose.yaml` takes both the published host address and the container's `LISA_PUBLISH_ADDRESS` from `${LISA_VPN_ADDRESS:?set LISA_VPN_ADDRESS to the VPN address}`, so they can't differ, and an unset or empty value fails at render time.
  - IPv6 uses `LISA_VPN_ADDRESS6` in `deploy/compose.ipv6.yaml` the same way.
  - Inside the container Lisa binds the unspecified address of its own namespace only when:
    - `api.deployment = "container"`;
    - `LISA_PUBLISH_ADDRESS` is a non-empty, non-wildcard, non-loopback IP literal;
    - that address is listed in `api.publishAddresses`.

    Otherwise it refuses to start a listener.
- **Normal deployment runs the check before any port is published.** `deploy/lisa-deploy up` performs, in order:
  1. `docker compose config --format json`;
  2. `docker compose run --rm --no-deps -T lisa lisa core deploy check --rendered -`, which reads that rendered file. A plain `run` publishes no service ports. The check verifies that every published port has a host IP that is non-empty, non-wildcard, equal to `LISA_VPN_ADDRESS` or `LISA_VPN_ADDRESS6`, and listed in `api.publishAddresses`;
  3. only then, `docker compose up -d`.

  The documentation names this the only supported deployment command. Someone running `docker compose up` directly still meets the in-container refusal.
- **Evidence, kept in separate classes:**
  - **Rootless amd64, this host (M4):** unset, empty, wildcard and mismatched values refused by the render, the check and the in-container check. With a stand-in address (`127.0.0.2`), the published port will be observed listening only there (`ss -ltn`) and refused elsewhere.
  - **Target host, by the owner (production-host class):** HTTPS reachable from a VPN client on the VPN address over IPv4, and over IPv6 if configured. Refused or unreachable from off-VPN clients on the host's LAN and public addresses over IPv4 and IPv6. Docker's forwarding chains inspected. Date, host and commands recorded.

#### 8.11.4 Health and freshness

- **Reported separately (R2-CORE-05):** liveness, database readiness, sync readiness, each source, the model, each delivery channel, storage, backup age, recovery stage, and sync lag per device. A failing news source never makes Core unready.
- **Publishing:** the running Core rewrites `<data>/run/health.json` every 15 seconds: `{runGeneration, sequence, wallTime, bootTimeNanos, components}`. `bootTimeNanos` is `CLOCK_BOOTTIME`, which is shared by processes on the host and continues through a stopped process.
- **One-shot probe:** `lisa core health --probe live|ready` reads only the lock file and `health.json`, and never opens the database (R1's `status` opened and wrote it, §1.6).
  - **Live:** the file's run generation equals the current lock holder's, and its age by `CLOCK_BOOTTIME` is at most 60 seconds.
  - **Ready:** live, plus database and sync readiness.
  - **After a restart:** the new run has a new generation, so the old file never counts as ready.
  - **Frozen or paused process:** the age grows, and the probe fails after 60 seconds.
  - **Wall-clock step back or forward:** no effect, because boot time is used.

  The container health check runs it every 30 seconds with 3 retries.
- **Restart sequence:**
  1. Recover transactions, the ready queue and waiting operations.
  2. Inspect uncertain outcomes, settling `submitting` as `outcomeUnknown`.
  3. Reconcile schedules and assignments.
  4. Suppress obsolete work.
  5. Resume bounded processing.
  6. Report degraded capabilities truthfully.

  A persistent provider failure is a health state, not a restart loop.

#### 8.11.5 Administrative modes

Every `lisa core` command has exactly one mode (§8.12.3 lists them):
- **listener:** needs a running Core. It talks to the loopback owner listener named in `run/owner-endpoint.json` (owner-only file, PID checked against the lock holder, as R1 does) and works in recovery mode where the stage allows.
- **offline:** needs the exclusive data-directory lock and refuses while Core runs.
- **files:** reads files only (health, manifests, archives, configuration, rendered Compose) and never opens the database.

No command opens the database just to report status.

**Acceptance (M3 portable, M4 container; S-15, S-20):** the checks will cover:
- the publishing cases above;
- the UID mapping and secret ownership and modes seen inside the container;
- the read-only root refusing writes, with the data and backup volumes writable;
- readiness after a restart reflecting only the new generation;
- a frozen container's probe failing after 60 seconds;
- a backward wall-clock step of one hour causing no false freshness or staleness;
- each command refusing the wrong mode;
- R2-D01–D04, D06–D09 and D12 on rootless amd64;
- D05 and SELinux confinement on the target host.

#### 8.12.2 v1 translation (finding 1; real v1 compatibility)

**Required:** R1 clients must not mutate through a path that bypasses the R2 ledger; a clear `upgrade_required` is acceptable; no silent unsafe reinterpretation (R2-API-01).

**Decision:** safe route-by-route v1 compatibility (O-4).

**Wire rules for frozen R1 clients (§1.6)**
- Every v1 response carries `Lisa-API-Version: 1.0`. A major version other than 1 would make R1 treat every answer, including successes, as "may have been applied".
- Error bodies use only R1's ten codes with a message. R2 adds a `lisaCode` field, which R1 ignores. An unknown code would make R1 discard the whole body.
- Routes, DTO shapes and status codes are R1's. `GET /v2/tasks` from a v1 client stays a typed 404.

**The durable parent**
- **Key:** R1's caller-scoped `(scope, requestID)`.
- **It stores:**
  - R1's fingerprint and the route;
  - the recorded status and body, until the body expires (`api.idempotencyRetentionDays`, default 30) or is redacted;
  - the ordered child operation IDs with their outcomes;
  - the entities touched;
  - each projection's revision before and after;
  - its creation time;
  - its origin path: v1, import (§8.14.4) or migrated R1 ledger record.

  The compact form (everything but the body) lives as long as the dataset.
- **Child IDs:** the first 16 bytes of `SHA-256("lisa-v1-child-v1" ‖ 0x00 ‖ len32(dataset) ‖ dataset ‖ len32(scope) ‖ scope ‖ len32(requestID) ‖ requestID ‖ len32(discriminator) ‖ discriminator)`, where `len32` is a big-endian 32-bit length.

  | Route | Discriminators |
  |---|---|
  | Task or idea PATCH | `field:<name>` for each changed field (an idea's tags among them), then `status` or `lifecycle` |
  | Preferences PATCH | `change:<index>` in request order (R1 allows one key twice) |
  | Notification action | `receipt` (paired-device callers only), then `action`, then `task-complete` when "complete" completes the task |
  | Reminder action | `action`, then `task-complete` |
  | A single-operation route | `single` |

- **Atomicity:** one R2 transaction commits exactly the children R1 would have kept, their projections, the parent and the recorded response. R1's follow-up commits (planning, reminder sync) become durable follow-up work after that commit. R1's late 503 and 500 answers after a commit therefore can't happen, and a `createTask` retry can't create a second task (§1.6).
- **Projection revisions** advance exactly as R1's would: one step per R1 service call that changed something (correction +1, status +1; edit +1, lifecycle +1; each preference change +1). v1 `expectedRevision` semantics are unchanged.

**Route by route**

| v1 route | Children committed (R1's boundaries reproduced) | Recorded and answered |
|---|---|---|
| `POST /v1/plans/{p}/blocks/{b}/actions` | One plan-block operation; validation and conflicts before it | R1 status; RundownDTO |
| `POST /v1/briefs/regenerate` | None: a Core command; a failed composition is recorded as R1 records it | BriefDTO, or R1's error |
| `POST /v1/captures` | One capture; R1's permanent caller-scoped deduplication kept through the capture request key in records and tombstones | 201 or 200 CaptureDTO (no text) |
| `POST /v1/captures/{id}/retrieve` | Core command with libcurl's checks | R1's statuses |
| `POST /v1/tasks` | One create-task | 201 TaskDTO; recorded atomically |
| `PATCH /v1/tasks/{id}` | Revision check (409 "the task changed since it was read"), then all correction fields validated together (400, nothing committed), then field children, then the status child. A refused status (409 "the task cannot move from …") leaves the field children committed with the error recorded | R1's status and body |
| `PATCH /v1/ideas/{id}` | The same shape: edit children, then the lifecycle child (409 "the idea cannot move from …") | R1's |
| `PATCH /v1/preferences` | One child per change in order. The first refusal (403 owner-only key, 400 value, 409 revision, 404, 403 device delete) stops the request, and earlier children stay | R1's, including the full preference list on success |
| `POST /v1/reminders/{id}/actions` | The occurrence-firing action; "complete" adds the task completion | R1's |
| `POST /v1/notifications/{id}/actions` | Receipt (paired devices), then the action, then a task completion if any. A refusal after the receipt (403, 404, 409) keeps the receipt | R1's |
| `POST /v1/event-proposals/{id}/actions` | Review or correction | R1's |
| `PUT …/push-registration`, `…/notification-status`, `PATCH …/notification-preferences`, `POST …/notification-receipts` | Legacy device-local records. Receipts are one child per ID; R1 committed them one by one, R2 commits all or none | R1's; an R2-enrolled device gets `upgrade_required` |
| `DELETE /v1/devices/{id}` | Owner: revocation (roster updated). Legacy device: unpairs itself | R1's |
| `POST /v1/devices/pairing-codes`, `POST /v1/devices/pair` | Legacy devices only, outside the ledger as in R1, because their answers carry secrets | not recorded |
| GET routes | Kept, reading projections | R1's |

**Retries and expiry**
- **Same key and fingerprint:** the recorded response with `Lisa-Replayed: true`. **Different fingerprint:** 422 `requestIDReused`.
- **After the body expires or is redacted** because an entity it contained was deleted, the response is R1-readable and exposes nothing:
  - the original status, with header `Lisa-Replayed: expired`;
  - for content routes (tasks, ideas, captures, proposals, preferences, reminders, notifications, plans, briefs), the body `{}`. R1's queue treats any 2xx as done and decodes the body only with `try?`, so the entry completes, the in-place update is skipped, and the item shows its state at the next refresh (§1.6);
  - for device-scoped routes, the caller's own current device record or device notification preferences, which are not owner content;
  - for 204 routes, an empty body.

  The mutation is never repeated. A deleted item's content never appears, even within the retention period.

**`upgrade_required` on v1**
- **When:** a changed field has an unresolved R2 conflict, which a v1 client can neither see nor resolve; the caller is an R2-enrolled device; or the request has a shape with no R2 operation.
- **Answer:** HTTP 426, body `{"code":"forbidden","message":"Update Lisa on this device to make this change.","lisaCode":"upgrade_required"}`, recorded on the parent.
- **What the frozen R1 app shows (§1.6):**
  - "That didn't work: Update Lisa on this device to make this change.";
  - an action submitted while connected is marked `failed` and discarded at once, so only that message appears;
  - an action queued earlier appears under "Didn't Go Through" with Try Again and Discard on iPhone and iPad, or only in Diagnostics on the Mac;
  - Try Again re-queues under a new request ID and gets 426 again, with no effect.
- **A stale `expectedRevision`** (an old conflict in R1's sense) stays R1's 409 `conflict` with `currentRevision`, shown as "This item changed on your host."

**Acceptance (M3, frozen R1 client from `491c90a`; S-01):**
- a multi-field PATCH with one bad field: nothing committed, 400 recorded;
- a valid correction followed by a refused status: field children committed with the 409 recorded, matching R1's database state field by field;
- a preferences PATCH repeating one key, and one refused at the third change;
- a create retried after an edit, after a deletion (the response body checked to contain nothing of the item), and after body expiry;
- a stale revision (409) and a conflicted field (426, with the frozen client's message and queue state checked);
- an R2-enrolled device on v1 (426);
- a crash between commit and response, then a retry;
- both pairing routes leaving no record.

For every case, a database diff will show the mutation applied at most once.

### 8.14 Migration, cutover and rollback (R2-MIG-01–04; findings 2, 3 and 13; migration authority and backups)

#### 8.14.1 Preparation

1. **The owner stops every R1 writer** and disables its automatic start: the Mac app's login item and any `lisa serve` service, following `docs/MIGRATION-R1-R2.md`.
2. **`lisa core migrate prepare --r1-data-dir <dir>`** takes R1's own data-directory lock and holds it to the end. Under the lock it:
   1. inventories R1's schema and application version, identifiers, secret references (names only), source cursors, schedules, queues, deliveries with their unknown outcomes, device registrations, the audit horizon, and any `data.deleted` events naming captures;
   2. **records the intended dataset ID** (R2-MIG-01 step 5) in the migration record;
   3. writes and validates the **rollback backup**: R1's database at schema v4, plus `runtime-state.json`, `model-requests.json` and `dry-run/captures.jsonl`, with SHA-256 digests in a manifest that also lists the configuration file's digest and secret references;
   4. **fences** R1's database with a schema version R1 refuses;
   5. writes the **migration input**: a backup of the fenced database with the same files.

   No write can happen between the backups and the fence.
3. **If the R1 data is on a Mac** (embedded host; default `~/.local/share/lisa`, from `~/.config/lisa/config.json5`):
   - the owner stops the app, copies the stopped data directory to the server, and runs `prepare` there against the copy;
   - the owner's confirmation that no R1 software can start on the Mac goes into the migration record;
   - the R2 `lisa` for macOS, if it exists after X3, can run `prepare` in place instead.
4. **Secrets** are re-provisioned through the secret files, never through data (R2-MIG-03).

#### 8.14.2 Forward migration (`lisa core migrate run`)

- **Kept:** every identifier; explicit corrections as owner authority; preferences; source cursors; calendar occurrences; brief and plan history; reminder state; delivery attempts and unknown outcomes; device registrations (as legacy registrations that can be upgraded); capture request keys.
- **Authority of migrated values:**
  - `ownerCorrected` fields become owner authority.
  - Other fields of extracted tasks keep model authority, so R1's extraction behavior is preserved.
  - Tasks created by the owner are owner authority throughout.
  - **Notes carry no flag in R1, and the model writes them only at creation.** An extracted task's notes may therefore be model text or owner text. They become one note piece of **ambiguous authority**: protected like an owner value, never replaced by model or source writes, and displayed "from R1, author unknown".
  - Idea fields are owner authority, except the planner's unschedulable fields, which are system authority.
- **Files outside SQLite:** `runtime-state.json` becomes Core's schedules, so losing it would only make sources run early. `model-requests.json` becomes the current day's budget. Dry-run captures are archived.
- **Deliveries, in R1's states:**
  - `outcomeUnknown`, and `inProgress` in the submitting phase, stay unknown and are never resent.
  - `inProgress` in the preparing phase returns to pending.
  - Pending deliveries past validity expire.
  - Core starts with delivery suspended.
- **Reminders and intents** map to occurrences and firings (§8.10.1).
- **R1 ledger records** become compact v1 parents with their bodies until expiry (§8.12.2).
- **Causal metadata** starts from a documented migration origin. No "latest" timestamp is invented to make migrated values win (R2-MIG-02).

#### 8.14.3 Classifying R1 queue entries (finding 2)

**Required:** keep each queued action's input and request identity; decide whether it was applied; convert only known semantics; quarantine ambiguity; never replay blindly (R2-MIG-03).

**What R1's code allows us to conclude (§1.6)**
- A matching error can coexist with committed children: task and idea PATCH, preferences PATCH and notification actions commit before a later refusal.
- `attempts` counts attempts that never left the device, and `lastError` keeps only the latest answer. An entry that got a 504 (proxy, maybe applied, no uncertainty set) and then a 401 shows only the 401, with no `uncertainSince`.
- A 503 can mean "the same request is still being processed", so the request may have been applied.
- Requeue changes the request ID and forgets the earlier one, apart from the original `id`.
- Ledger records expire after 30 days and are written after the mutation.
- Captures were not deletable in R1 production, but R2 can delete them. Audit events, including `data.deleted`, age out after 365 days. Missing capture, request row and deletion audit together therefore prove nothing on their own.

**Evidence, scoped to the original caller, request and child**
- **The file:** status, attempts, `uncertainSince`, last status and message, kept response, `id` and `requestID`.
- **Core's read-only lookups** for both `requestID` and `id` in the caller's scope:
  - the migrated R1 record or a v1 parent, with fingerprint match, status and **attribution**: pre-commit, after a commit, or unknown;
  - for captures, the capture request key in live records or in R2 tombstones;
  - R1's audit horizon, and whether any capture deletion was audited after the entry's `createdAt`.
- **Attribution by R1's exact messages:**
  - **Pre-commit:**
    - the 400 body and schema errors;
    - task title, estimate and deadline 400s;
    - "the task changed since it was read" and "the idea changed since it was read";
    - "send between 1 and 50 changes";
    - "unknown action";
    - "the notification does not exist".
  - **After a commit:**
    - "the task cannot move from …" and "the idea cannot move from …";
    - notification-action errors after the receipt;
    - any refusal of a preference change other than the first.
  - **Unknown:** "the item changed since it was read; reload it and try again", and a 404 from task or idea services.

**Classes**

| Class | Meaning | What the owner can safely do |
|---|---|---|
| A. Provably unsent | Positive evidence that no attempt reached R1 or applied | Converted automatically if its semantics are known and its expected revision still matches; otherwise offered prefilled for confirmation |
| B. Fully applied | Positive evidence of a 2xx for this caller, request and fingerprint, or the capture's key | Nothing; shown in history |
| C1. Rejected, no effect | A definite refusal attributed to before any commit, or from a single-step route | Re-enter deliberately from a prefilled form against current state; no duplicate is possible |
| C2. Rejected, partial effect possible | A refusal after a commit, or of unknown attribution, on a multi-step route | Field by field, the requested value beside the current one; the owner re-applies only what is missing |
| D. Indeterminate | Anything else | The original bytes are kept for inspection; "apply anyway" warns of possible duplication; or discard |

**Rules, first match wins**
1. Fingerprint mismatch on a server record for `requestID` or `id` → **D** (identity collision).
2. Status `done` with its 2xx response, or a server record with 2xx → **B**. If `requestID ≠ id`, "earlier attempts unknown" is noted.
3. A server record with 400, 403, 404, 409 or 413 → **C1** for single-step routes or pre-commit attribution; **C2** otherwise.
4. Capture kind:
   - its key found, live or in a tombstone → **B**;
   - its key absent, no capture deletion audited after `createdAt`, and the audit horizon at or before `createdAt` → **A**;
   - otherwise → **D**.
5. Notification receipts → **A**: re-applying is idempotent.
6. `requestID ≠ id` (re-queued) with no record for either ID → **D**.
7. `pending` with 0 attempts → **A**.
8. Exactly one attempt and no `uncertainSince`, where the last answer was 401 or 429 (both answered before R1's ledger), or a message equal to one of R1's fixed "never sent" descriptions (not paired, credential unavailable, connection refused, host unreachable) → **A**.
9. Exactly one attempt that got a definite 400, 403, 404, 409 or 413 (`conflict` or `failed` in the file) → **C1** or **C2** by attribution.
10. Everything else → **D**, including:
    - `sending`;
    - `uncertainSince` set;
    - two or more attempts without a record;
    - 422, 500, 502, 503 or 504;
    - decoding or other client errors.

**Restart safety:** the import keeps one record per entry, keyed by `id` and `requestID`. Converted operations use the derived IDs of §8.12.2 with a legacy reference, so a re-run never duplicates (§8.14.4). Class D bytes are kept exactly.

**Acceptance (M9; S-02):** frozen R1 queue files and R1 datasets will cover every rule. Among them:
- a task PATCH whose correction committed and whose status was refused (C2, with the field diff);
- a capture missing together with its record and deletion audit after a test-path deletion and audit ageing (D, not A);
- a 504 followed by a 401 (D, not A);
- a lost 409 recorded on the server for a plan-block action (C1);
- a raw `sending` entry with and without a server record (D, or B and C);
- a re-queued entry;
- a restart halfway through, with no duplicates.

#### 8.14.4 Upgrading the Mac (finding 3)

**What the old Mac is (§1.6):** an unsandboxed app that embeds the host in process as the local owner, or is a loopback owner client of `lisa serve`. Its queue at `~/Library/Application Support/org.example.lisa.mac/Client/queue/queue.json` holds owner-scope entries only when sends failed. It has no pending-actions screen.

**Upgrade procedure (`docs/MIGRATION-R1-R2.md`):**
1. Stop R1 (§8.14.1).
2. Migrate the data directory.
3. Install the R2 Mac app under the same bundle ID; it runs sandboxed, so the old path is outside its container.
4. Enroll with pairing text.
5. Import the old queue as described below.

**Owner-authorized, read-only import**
1. **Select:** Settings › "Import changes from the previous Lisa for Mac" opens an open panel aimed at the old `Client/queue/` folder. The app opens the file read-only, copies it into its import area, records its SHA-256, and keeps only a read-only security-scoped bookmark. The original is checked unchanged after the import.
2. **Manifest:** `{file SHA-256, entries: [(id, requestID, kind, method, path, R1 fingerprint)]}`, signed by the Mac. It is uploaded with an `owner-import` challenge (`POST /v2/migration/owner-imports`). Core stores it as pending and returns an import ID; the Mac shows the manifest digest as eight words.
3. **Grant:** the owner runs `lisa core migrate owner-import approve <id> --digest <words>` on the administrative terminal. The approval is signed and bound to the import ID, the Mac's device ID, the manifest digest and scope `owner`.
   - It must be used within 10 minutes.
   - Once used, lookups for exactly that manifest's `requestID` and `id` values stay allowed until the import completes, or for 7 days.
4. **Lookups:** `POST /v2/migration/owner-imports/{id}/lookups`.
   - The first lookup for an entry computes the evidence of §8.14.3 and stores it on the import record; later lookups return the stored result. Redemption is therefore idempotent, and retention running in between changes nothing.
   - **Minimum result per ID:** `{ledgerOrParent: absent | {fingerprintMatches, status, attribution, originPath}, captureKey: live | tombstone | absent, captureDeletionAuditedSince: bool, auditHorizonBeforeCreated: bool}`. Never a body, title or value.
5. **Resumption:** the Mac records per entry: classified, operation IDs converted, done. After a crash it resumes from that record.

**One durable parent for both paths.** A legacy request can reach Core twice: as a fresh device-signed operation from the import, or earlier or later as a Core-attested v1 child (if an R1 client retried it). Both carry the same derived ID but different digests.
- Imported operations carry the legacy reference `{scope, requestID, r1Fingerprint, discriminator}`.
- At intake, Core looks up the v1 parent for `(scope, requestID)`:
  - **parent exists, same fingerprint:** `duplicate` with the parent's recorded outcome, and no new effect;
  - **parent exists, different fingerprint:** `identity_reuse`;
  - **no parent:** Core creates the parent (origin path `import`) in the same transaction as the children, storing the original envelopes and the decision.

  A later v1 retry finds that parent and gets its recorded response.

**Owner-only preferences.** R1 lets only the owner on the host change certain keys. Entries changing those keys, or administrative keys (R2-TRUST-05), are never converted from a device. They appear in `lisa core migrate owner-import list` for the owner to apply with `lisa core preference set` after review.

**Acceptance (M9 harness; X7; S-03):** the checks will cover:
- the import running first and then a v1 retry of the same request;
- a v1 retry first and then the import;
- a crash after Core commits but before the Mac records, then a resume;
- a different body under a reused request ID (`identity_reuse`);
- an expired or mismatched grant (refused);
- a lookup outside the manifest (refused);
- owner-only preferences routed to review;
- the original file's hash unchanged.

**X7 prerequisite:** a genuine old Mac app.
- The owner builds R1's Mac app from the reconstructed `491c90a` tree (§8.18) at or before X3 and records the Xcode version.
- If it doesn't build, X7 uses a fixture queue file produced by the frozen Linux R1 client and placed at the old path, and reports the genuine-app part as `NOT_RUN_ENVIRONMENT`.

#### 8.14.5 Upgrading a paired iPhone or iPad

**What the old companion supports (§1.6):** only `/v1/` with API major version 1 and R1's ten error codes; pairing by code; a Keychain identity `{installationID, deviceID, credential}`; direct push registration; trust of up to eight owner anchors plus an optional certificate pin.
- After migration it reaches Core only if the owner changes its host address and trust settings to Core's. Its migrated legacy registration then authenticates it.
- Queued mutations go through the v1 translation (§8.12.2).

**Linking the old registration to the new identity**
- On first launch, the R2 app (same bundle ID, same container and Keychain access) reads the R1 identity item and queue file read-only.
- Its enrollment request includes `legacyLink {r1DeviceID, r1InstallationID, r1Credential}`. These bytes are secret-bearing and stored like the rest of the request (§8.1.2).
- Core verifies the credential in constant time against the legacy registration's verifier, and checks that the registration is active and unlinked.
- In the consuming transaction (§8.1.2 step 5), Core:
  - records the link;
  - moves eligible device-local settings (notification preferences and categories) to the new device;
  - maps delivery history to it;
  - removes the legacy registration from routing;
  - retires the legacy credential (verifier deleted, state `upgraded`).

  The old registration's push token is deleted when the new device registers its token, and only one of the two is ever eligible.

**Lookups and import:**
- After linking, the new device may look up scope `device:<legacy ID>` with a `legacy-link-lookup` challenge. All its entries are looked up, then classified (§8.14.3).
- If the R1 credential no longer verifies (rotated or revoked), enrollment proceeds without a link, and the import needs an owner approval like the Mac's, bound to scope `device:<id>`.

**What a frozen Linux client can prove:** R1's `LisaClient` and offline queue, built from `491c90a` on Linux, prove:
- wire compatibility: version header, error decoding, status mapping;
- queue state transitions and the file format;
- the link and lookup flows with an R1 credential.

They cannot prove Apple presentation, Keychain access, the sandbox, URLSession trust, or the update of the installed app on a device. X7 covers those.

**Acceptance (M9; X7; S-03):** the checks will cover:
- link and import with a valid credential;
- refusal with a revoked one;
- no device eligible twice at any point (routing checked before and after the link commit);
- delivery history and preferences preserved;
- the old credential refused afterwards;
- on devices at X7: the R1 companion upgraded in place.

#### 8.14.6 Cutover

The R1 host never resumes automatically. The Mac connects as an R2 client. Devices reconcile before normal scheduling starts. The owner reviews, then resumes delivery (R2-MIG-04).

#### 8.14.7 Rollback (finding 13)

**Required:** a compatible pre-migration backup or an explicit reverse migration; never old software on a newer schema; never two schedulers (R2-MIG-04).

1. **Preflight** (`lisa core migrate rollback --preflight`, listener mode) creates **rollback generation R**: a signed record with a counter and a random ID. It is published in capabilities and `GET /v2/rollback`, and lists everything outstanding.
2. **Acknowledgements.** Each device sends a signed `{R, deviceID, incarnation, finalJournalPosition, uncommittedCount, exportDigest?, headSeen}`.
   - The acknowledgement is clean only if `uncommittedCount` is zero after a final sync.
   - Otherwise it must carry the digest of a protected export containing everything uncommitted.
   - **Silence is never read as clean:** a device that hasn't acknowledged is listed as outstanding with its last known position and pending count.
3. **After acknowledging,** a device keeps saving, because capture is never refused.
   - Entries beyond the acknowledged position are **late**. The device shows "Saved on this device. Lisa Core is being rolled back; export this change." and offers export.
   - A late entry is never shown as synced. After Core stops, the app says "Lisa Core was rolled back; export your device-only changes".
4. **Fence** (`--fence`, owner, after preflight review):
   - Core intake is fenced: v2 gets `rollback_in_progress`; v1 gets 503 `unavailable`.
   - Connectors and the scheduler stop. The outbox is suspended.
   - In-flight attempts settle: Core waits until no delivery is `inProgress`, and a `submitting` attempt that times out becomes `outcomeUnknown`.
   - Cancel commands go to every delegated assignment. Confirmations are collected until the owner proceeds, and unconfirmed slots are recorded "may fire locally".
   - Then the **rollback archive** is written: the v5 backup plus a rollback record. The record holds the acknowledgements, outstanding devices, late-entry positions, waiting operations, unresolved conflicts, uncertain and held deliveries, and reservations.
5. **Reverse migration** (`--reverse`, offline; §8.14.8) produces the v4 database and regenerates the two sidecars:
   - `runtime-state.json`: version; jobs with next run, consecutive failures, last run and last outcome; last cycle; last maintenance — all from Core's schedules;
   - `model-requests.json`: version, today's day in the owner's zone, and the count.
6. **Verification on a disposable copy** (`migrate verify-r1 --copy`): the result is copied, and the frozen R1 binary runs `status` and `run-once` with dry-run delivery against the copy only. Opening an R1 host runs recovery and writes, so the real directory is never opened during verification.
7. **The owner starts R1.** R2 never runs a scheduler again on that dataset.

Late edits and unreachable devices stay visible in the rollback report, and are recoverable later through their exports and the post-downgrade tool.

#### 8.14.8 Reverse migration rules and the post-downgrade archive tool

**v5 to v4**
- R2 tables are dropped after being archived. Projections keep R1's record shape; R2 only added optional fields.
- Note pieces become R1's `notes` text in a deterministic order.
- **Fields with several values,** which v4 can't hold:
  - the v4 record keeps the owner-authored value;
  - when owner values conflict, it keeps the one the owner selects in preflight, or otherwise R1's last value;
  - every alternative goes into the report;
  - owner or ambiguous-authority text is never replaced by a model or source value.
- `ownerCorrected` is regenerated from authority.
- **Deliveries:**
  - attempted ones keep their final state;
  - ones R2 created but never attempted become `cancelled` "rollback: not attempted";
  - slots that may fire locally have their R1 deliveries to that device suppressed;
  - uncertain and held deliveries become `outcomeUnknown`.
- Unexpired v1 parents become R1 ledger records, with bodies redacted where §8.12.2 requires.
- Legacy registrations are restored. R2-only devices are listed so the owner can pair them in R1 if wanted.
- **Fallback:** the rollback backup from `prepare`. Owner edits made after migration are then listed for re-entry, and R2's delivery attempts are imported as final states.

**The post-downgrade tool: `lisa archive`** (part of the R2 `lisa` binary)
- **Runs in files mode:** it never starts Core, never runs a scheduler, and never opens an R2 database for writing.
- **Inputs:** the rollback archive, device archives, and the owner's key backup directory (current and retired export keys, signing-key history).
- **`inspect`** lists every entry:
  - its verification: dataset, origin in the archived roster and not revoked at creation, signature, the key it was sealed to;
  - the matching R1 record, read through R1's running owner listener with read-only GETs, using R1's own endpoint file and owner credential.
- **`reconcile`** asks the owner about each entry:
  - Translatable operations (create task or idea, field edits, status, preference changes, captures) are applied through R1's owner listener with R1's revision checks, only after the owner approves.
  - Drafts and ambiguous inputs need the owner to confirm or edit the text.
  - Each applied entry uses an R1 request ID derived from its archive entry ID, so R1's own ledger deduplicates retries within 30 days. An append-only reconcile log records every decision and R1's answer, so a rerun skips finished entries.

**Acceptance (M9; S-13; narrative §19.2):**
- a save after acknowledgement;
- a device that never acknowledges (listed, never read as clean);
- a sandboxed Mac export outside the container (X3, X7);
- loss of the originating installation;
- an export-key rotation before the export;
- an interrupted reverse migration resumed with no partial state;
- provider acceptance across the cutover: accepted before stays accepted, and accepted by R2 arrives as accepted;
- conflicting values that v4 can't hold, reported with owner text kept;
- the frozen R1 `run-once` on the copy sending nothing again;
- recovery after R1 resumes using only the rollback archive, the device export and the documented key backup in a fresh directory.

#### 8.15.2 SQLite capacity: readers, WAL and storage exhaustion

**Required:** storage exhaustion never reports a successful unsaved capture (R2-L33); unsynchronized captures, pending operations, conflicts, uncertain deliveries and replay metadata are never evicted (R2-LIMIT-02).

- **WAL in practice:** `journal_size_limit` only truncates the WAL file after a checkpoint resets it; it does not cap a live WAL. The live WAL grows while any reader holds an old snapshot. It is bounded here by bounding readers and checkpointing:
  - `wal_autocheckpoint` stays on; a passive checkpoint runs after each batch install, and a truncating one after a snapshot swap.
  - Every long reader belongs to Lisa: snapshot generation on Core, staging catch-up passes and export assembly on clients, search queries. Each runs on a read connection registered with a **reader monitor** that knows its start time and purpose.
- **Release before the reserve is threatened.** The store keeps a capture reserve (64 MiB on clients, configurable on Core). The monitor samples free space (`statfs`) and the WAL size every second while readers are active, and acts when either of these holds:
  - free space falls below the reserve plus twice the WAL size;
  - a reader has been open longer than its budget (search 5 s; catch-up pass 2 s; export 60 s; snapshot generation 10 minutes).

  It then interrupts the reader (`sqlite3_interrupt` on its connection), finalizes its statements, ends the read transaction, and runs a truncating checkpoint. The interrupted work is retried later; for snapshot generation, from a new cut.
- **Exhaustion:** `SQLITE_FULL` (or an `ENOSPC` from staging or blob files) aborts only that write's transaction. A capture reports "Not saved: storage is full" with the action needed. Earlier saves are intact, and the replica stays openable.
- **Measured together** (M2, clients; M3, Core): staged tables, staged indexes, the live WAL and the database file at their peak during an installation, against a reserve sized from those numbers.

**Acceptance (S-17)**
- **M2:** the first real use of the rootless engine (§9) runs the replica harness inside a `swift:6.4.2-trixie` container with the database directory on a `--tmpfs …:size=…` mount, so the kernel itself returns `ENOSPC`. Checks:
  - a pinned reader (a long search) during continuous captures: WAL growth measured, the reader interrupted at its budget or at the space threshold, then the WAL truncated;
  - storage filling during a staged installation: the capture before the reserve saved, the capture that doesn't fit reported unsaved, and the database consistent after restart;
  - `max_page_count` for the in-database case on the Fedora host.
- **M3:** the same on Core's snapshot generation and intake.

The engine, context, architecture and image digests of that first run are recorded (O-10).

### 8.16 Transfer sizes, encoding and streaming (R2-LIMIT-01; protocol limits)

#### 8.16.1 Encoding

- **Signed bodies:** one canonical JSON form. UTF-8 (invalid UTF-8 refused), object keys sorted by Unicode scalar value, no whitespace, integers only (instants in milliseconds, decimals as strings), minimal escaping, no duplicate keys, nesting depth at most 16.
- **Signatures:** raw 64-byte P-256 values over a domain-separated prefix plus the body. Nothing re-encodes a signed body.
- **Over HTTP:** signed bodies travel as base64url inside JSON envelopes.
- **In nearby frames:** raw bytes.

#### 8.16.2 The four budgets, checked separately

| Layer | Unit | Limit | Where checked |
|---|---|---|---|
| Semantic | Canonical operation body, including metadata | 64 KiB | At creation (client) and intake (Core), before decoding the payload |
| Semantic | Batch | ≤ 100 operations and ≤ 512 KiB of bodies plus signatures | Client splits; Core checks |
| HTTP | Encoded request body (JSON envelope with base64url bodies) | 768 KiB, which is ≥ 512 KiB × 4/3 plus 64 KiB of envelope | Server, on the bytes actually received |
| Frame | Nearby frame (8-byte header and payload) | 1 MiB total | From the header, before allocation |

- **Streamed enforcement.** The server counts received body bytes whether or not `Content-Length` is present.
  - With `Content-Length` over the limit, it refuses before reading.
  - Without it (chunked), it reads into a bounded buffer and stops at limit + 1, answering 413 (`payloadTooLarge` for v1, oversized for v2) and closing the connection.
  - A body shorter or longer than its declared `Content-Length` is a framing error.
- **Responses** stream change pages, chunks and blobs without assembling them in memory.
- **UTF-8 and escaping:** limits count encoded bytes, so multi-byte characters and escaped control characters count at their encoded size (§8.3.3).

#### 8.16.3 Blobs and staging

- **Blob-backed values:** a capture text, note or description over its value limit becomes a blob of at most 1 MiB. The operation carries its digest and length, so the signature covers the content. The operation waits, as a dependency, until the blob is complete.
- **Staging:**
  - Chunks of 256 KiB are verified by digest and written to staging files, with progress recorded per blob.
  - Interrupted staging resumes from the last verified chunk.
  - A staged blob that no operation references within 7 days expires (an orphan).
  - Staging is bounded at 256 MiB per replica; beyond it, `insufficient_storage` for new blobs.
  - Completed staging is moved into the blob store in the transaction that references it.
- **Core-wide bounds:** storage for blobs, waiting operations and staging is bounded per dataset. Exceeding a bound gives backpressure (`insufficient_storage`) and a health warning, never silent loss.

**What fits where:** every signed unit (operation, batch, roster page, receipt, change page) fits one frame and one HTTP message. Snapshots, artifacts and blobs are paged or chunked, and checked piece by piece. Attachments are still not replicated (R2-DATA-03).

**Flow control:** chunks are 256–512 KiB, within TN3213's advice of at least 64 KiB. Each send waits for buffer space, and each receive is consumed before the next read.

**Acceptance (M1 codec, M3 HTTP, M6 frames; S-16):** the checks will cover:
- exact boundaries: a 64 KiB body accepted and one byte more refused; 100 operations accepted and 101 refused; a 512 KiB batch accepted and one byte more refused; a 768 KiB HTTP body accepted and one byte more refused;
- the same over chunked transfer without `Content-Length`, refused at the byte count and with memory measured;
- a 1 MiB frame accepted, and one byte more closing the session;
- a batch of maximum-size operations whose content needs multi-byte UTF-8 and escaped control characters, with base64 and JSON overhead measured;
- a blob interrupted mid-staging and resumed;
- an orphan expiring;
- staging at its bound.

### 8.17 Data handling: provenance, allowlists, retention and locked behavior (privacy and retention)

- **Provenance:** every record carries its origin (source, capture, device, Core or migration), its authority (owner, model, source, system or ambiguous), source times, last retrieval or sync, revisions, interpretation status, and whether it is canonical, local or provisional.
- **Replication allowlist:**
  - **Clients receive:**
    - owner entities: tasks, ideas, captures, permitted preferences, owner-visible proposal fields, owner reminders, suggestions;
    - derived records: calendar occurrences in the window, briefs for 30 days, plans, bounded evidence excerpts, news cited by briefs or captures, source freshness;
    - trust and coordination: the public roster and artifacts, lineage, the backup catalogue, their own assignments, the trust bundle.
  - **Never replicated:** secrets and secret references; connector configuration and cursors; raw content and full email bodies; deliveries, the submission journal and audit; v1 parents and idempotency records; other devices' credentials or push tokens; Core's model settings.
- **Export allowlist:**
  - Core's owner export: owner entities, derived records, operation metadata, and waiting, rejected and quarantined work. Never secrets, verifiers or tokens.
  - Client archive: unsynchronized work only (§8.6.6).
- **Core retention:**
  - raw content 90 days with a 500 MB cap; delivery history 180 days; audit 365 days; unreferenced feed items 30 days — R1's defaults, §1.6;
  - change-log history 90 days;
  - operation metadata, tombstones (with request keys) and compact v1 parents for the life of the dataset;
  - operation bodies per §8.4.5; v1 response bodies per §8.12.2;
  - backups per the retained set R and owner pins;
  - the recovery ledger for the life of the dataset.
- **Client retention:** the working set; the journal per §8.6.4; blobs by reference count; staging dropped after installation or invalidation; bounded logs.
- **Deletion:** §8.6.7.
- **Locked devices:**
  - The replica and Keychain items are available after first unlock.
  - Before the first unlock after a restart, nothing is saved (§8.6.2).
  - Notification actions and Siri work while locked after first unlock; completing a task requires unlocking.
  - Background refresh may run locked; nearby runs only in the foreground.
  - Secure Enclave keys are usable after first unlock.
- **Diagnostics and logs:** IDs, counters, hashes and states only, with secrets and private content redacted (R2-API-04, CONSTRICTION).

## 13. Commits and buildable checkpoints

- **One file-level operation per commit,** staging only that file. Implementation and documentation are committed separately; messages are `add: …`, `change: …` or `remove: …`. `git status` is checked before every commit, and changes Claude didn't make are never staged.
- **Ordering keeps the tree buildable:** new files before their callers, additive changes before removals, protocol additions with default behavior before conformances.
- **When a change can't be ordered that way** (a signature change touching several files), the commits form a span:
  - the span's last commit is the **buildable checkpoint**, built and tested on the working tree before the next span starts;
  - `R2-CHECKPOINT.md` records the span's first and last commit and the checkpoint's HEAD with the build result.
  - Earlier commits are never checked out to test them, because checkouts aren't permitted (§3).

## 14. Checkpoint and resume (R2-DEV-03; O-7)

- **The record:** a tracked `R2-CHECKPOINT.md`, beginning at M0. It holds:
  - branch and baseline; current milestone; completed requirement IDs;
  - modified and uncommitted files;
  - commands and results, with evidence locations;
  - open conflicts and blockers; pending sessions and experiments;
  - permissions in force;
  - the last buildable checkpoint;
  - the next steps.
- **Updates:** at every milestone boundary and before any pause. Nothing is reverted to look clean.
- **On resume:** the actual files and processes are inspected first.

## 17. Risks

- **Scale.** Much of the Apple code can only be syntax-checked here. Mitigation: portable logic first, thin adapters, early X1–X3, and the shared transport proved at X2.
- **Nearby security.** Design A may fail N-1; Design B needs P-08 for production certificates. If both fail, nearby stops and everything else continues.
- **Apple retrieval** may be infeasible under R1's policy (E-1). Then it stays off on that platform, and the Apple and release gates stay open pending the owner.
- **Rootless versus target host.** Networking, UID mapping and SELinux differ, so those checks repeat on the target.
- **Fedora drift:** libxml2 2.15, OpenSSL 4.0 (E-5), Swift 6.3.2 versus 6.4.2.
- **Recovery depends on owner actions:** fencing another host, keeping off-host copies of the recovery ledger and backups, and backing up secret files. The documentation and CLI ask for each.
- **Inherent limits, documented:**
  - revocation reaches a device only when it learns of it;
  - an isolated device's only copy can be lost;
  - exactly-once delivery is impossible, and released holds can duplicate;
  - handoffs and the 32-request cap can leave coverage holes;
  - RFC 7050 can't learn range-specific prefixes;
  - per-device model budgets aren't a global cap.
- **Migration** is verified on synthetic data only. R1's Apple apps may not build (E-12).
- **Owner availability:** X1–X7 need the owner's time; only N-1 and E-1 gate production designs.

## 18. Stopping conditions

Work on an affected item stops only when:
- an action needs authorization outside the approved scope;
- an enforced platform restriction needs the owner;
- a concrete technical blocker can't be resolved within scope;
- credentials, Apple sessions, the target host or live validation are needed;
- a deciding experiment hasn't run where its result is a stated prerequisite.

Independent work continues, and each blocked operation is reported with its exact cause.

### 19.1 Sibling restores, a rotated key, a newer revocation, a disconnected device, shared data and a provider acceptance (N-A)
