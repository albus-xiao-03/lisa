### 1.5 Documentation and dependency research (R2-DEV-04)

Read on 2026-11-19 and 2026-11-20 from developer.apple.com's public documentation data and GitHub's public API; nothing private was sent.
- **TN3213** (republished 2026-07-14):
  - Multipeer Connectivity is deprecated in Xcode 27.
  - Network framework's TLS-PSK "doesn't work with QUIC, it doesn't support TLS 1.3, and it only works with the older Network framework API".
  - The technote recommends TLS-PKI: mutual authentication, a local `SecIdentity` and custom trust evaluation. Apple platforms can't create a digital identity, and it names swift-certificates.
  - Peer-to-peer Wi-Fi is opt-in. Connections are deduplicated by peer identifier, and identifiers are rotated or avoided. Framing, flow control (chunks of at least 64 KiB), keepalives and send timeouts are the app's job.
- **Security reference:**
  - The documented `tls_ciphersuite_t` values include no PSK suite.
  - From iOS 12 and macOS 10.14: local identity, verify block, required peer authentication, `add_pre_shared_key`, TLS server name and the TLS exporter (`sec_protocol_metadata_create_secret`).
  - From iOS 13 and macOS 10.15: the PSK selection block and the negotiated suite and version.
- **Network framework:** `NWConnection.currentPath`, `NWPath.remoteEndpoint` and `NWParameters.preferNoProxies` exist from iOS 12 and macOS 10.14. No public NAT64-prefix API was found in the documentation checked, so clients discover prefixes with RFC 7050 (§8.8).
- **TN3151** (revised 2026-07-23): URLSession is the HTTP choice. For a specific gap, "a simplistic HTTP client … on top of a TCP API" is acceptable. Connect by name, never resolve-then-connect. Test on DNS64/NAT64 networks. Use Apple's trust evaluation.
- **TN3179:**
  - Local network privacy applies from iOS 14 and macOS 15, and service types go in `NSBonjourServices`.
  - On iOS, a background operation while permission is undetermined is denied silently.
  - Denial shows as −65570 for Bonjour and `localNetworkDenied` for connections.
  - Test on macOS 15.1 or later.
- **`UNNotificationRequest.identifier`:** scheduling with the same identifier replaces the earlier request.
- **swift-certificates (for P-08):**
  - Version 1.21.1, released 2026-10-26: commit `84f03fafeca28c19f5fc4b528df3d22ce8896bd7`, Apache-2.0, `swift-tools-version:6.1`, no `platforms` restriction.
  - Requires swift-crypto `"3.12.3"..<"6.0.0"` (its `Crypto` and `_CryptoExtras` products) and swift-asn1 `from: "1.1.0"`.
  - On Darwin, `Certificate.PrivateKey` wraps a `SecureEnclave.P256.Signing.PrivateKey` or a `SecKey`.

## 2. Objective

R2 turns Lisa into a distributed system with one authoritative service:
- **Lisa Core** runs in Docker on the owner's Linux server, behind the owner's VPN. It owns the canonical dataset, the connectors, the scheduler and every external delivery.
- **Lisa for Mac, iPhone and iPad** are clients. Each one:
  - keeps a durable local database and works fully offline (R2-CAP-03);
  - applies the owner's changes immediately;
  - synchronizes with Core over HTTPS, and with nearby enrolled devices without Internet access;
  - uses an explicitly configured model provider when Core cannot be reached.

R2 succeeds as R2 §20 defines. Lisa may be in any of these conditions: Core reachable, Internet without Core, nearby devices only, isolated, reconnecting after concurrent changes, or after a Core restart or restore. In each one, owner work is preserved, uncertainty stays visible, state reconciles without silent loss, and the boundaries around personal data and external actions hold.

## 3. Working constraints

`CONSTRICTION.md` overrides R2, this plan and every other instruction. For R2 that means:
- **Git:** stay on `feature/distributive`, using `git add` and `git commit` locally. Never branch, push, pull, fetch, merge, rebase, cherry-pick, stash, clean or run `git config`. Use `git reset` only with scoped permission, and never amend. Consult only the current branch's history.
- **Commits:** one file-level operation per commit, staging only that file. Implementation and documentation are committed separately, in the `add: …` / `change: …` / `remove: …` style.
- **Modularity:** one responsibility per file and module; a protocol at every boundary with a platform facility or external service (§7.2.3); no catch-all utility file; an acyclic module graph; Swift 6 access control and concurrency safety.
- **Platforms:**
  - The portable package imports no Apple-only framework.
  - Apple code is written here and only syntax-checked until an owner-run session reports a build or a run.
  - No mock, stub, no-op or Linux-only substitute stands in for required production behavior.
- **Tests (O-5, O-6):**
  - The R1 suite runs unchanged.
  - R2 harnesses are temporary, in a fresh `.tmp/r2/<run-id>/` per run.
  - Frozen R1 artifacts live under `.tmp/r2/<M0 run>/frozen/` with recorded hashes.
  - Reproducible scenario records (commands, inputs, hashes) go in the tracked `docs/VERIFICATION-SCENARIOS.md`.
  - There is no persistent R2 suite.
- **Temporary files:** only in `.tmp/` at the project root, and never removed, overwritten, renamed or repurposed.
- **Environment:**
  - Use the installed Swift 6.3.2 with SwiftPM.
  - Containers run only through the owner-configured rootless engine, within the authorized scope (§15).
  - No `sudo`; host administration stays with the owner.
  - No new project dependency, image publishing, production deployment or live external action without its own permission.
  - `Package.resolved` is preserved.
- **Security and privacy:** no secrets in source, fixtures, documentation or history; synthetic data only; no live accounts; nothing private is sent to an external service.
- **External actions:** dry-run transports and controlled substitutes only.
- **Reporting:** R2's statuses (`PASS`, `FAIL`, `NOT_RUN_ENVIRONMENT`, `NOT_RUN_CREDENTIALS`, `BLOCKED_PERMISSION`, `OUT_OF_SCOPE`), keeping implemented, compiled, executed, tested and verified apart, and the evidence classes of §10.1 separate.

## 6. Where R2 refactors R1

1. **Owner data changes only through operations** applied to a merge state (§8.3). R1 records become projections written in the same transaction. Validation moves into pure domain code that clients run too.
2. **The store records every change.** Each write to a replicated collection appends a change-log entry inside its transaction, and deletions leave tombstones. The store also gains a second read-only connection, streaming queries, savepoints and an explicit disk-full error.
3. **Agenda inputs become portable** in `LisaAgendaInputs`.
4. **Delivery learns ownership,** with immutable occurrence IDs, command generations kept apart from observed firing, and serialization against push attempts (§8.9).
5. **Devices get keys and a lifecycle:** enrollment, credential reset, rotation and revocation (§8.1). R1's legacy pairing stays for v1 devices only.
6. **v1 becomes a translation layer** with durable caller-scoped parents and deterministic child operations (§8.11.2).
7. **Clients get a new core** (LisaClientCore, LisaReplicaStore, LisaSyncEngine). LisaClient stays for v1 callers and queue import.
8. **The apps change shape:** the Mac becomes a sandboxed client, every app gets every workflow, and new Apple adapters are added.

## 7. Target architecture

### 7.1 Topology and authority (R2-ARCH-01, R2-ARCH-02)

- **Lisa Core**, one container on the owner's Linux server:
  - **Holds:** the canonical SQLite dataset, the operation ledger, the change log, snapshots, content blobs, the epoch lineage and the signed device roster.
  - **Runs:** the connectors, the scheduler and the outbox for email, calls and APNs.
  - **Serves:** the v2 API and v1 translation over HTTPS on the VPN address, plus the administrative CLI.

- **Each client** (Mac, iPhone, iPad):
  - **Holds:** its replica, its journal and its device keys.
  - **Runs:** local planning, briefs and search; nearby sync and relay; delegated and locally created notifications; optional direct inference; owner-requested public retrieval; SwiftUI and Siri.
  - **Secrets:** it holds no Core secret.
- **Connections:** clients reach Core over the VPN and HTTPS, and each other over authenticated nearby sessions. APNs and model providers are reached by outbound connections only.

## 8. Designs

Each design becomes a `docs/DECISIONS.md` entry from D-53 on. Every review item states its design, what happens after failure or retry, and its acceptance check.

### 8.1 Identity, enrollment and trust (R2-TRUST-01–05)

#### 8.1.1 Identities

- **Dataset:**
  - `datasetID`: random 128 bits.
  - `recoveryEpoch`: random 128 bits plus a sequence number, recorded in the epoch lineage (§8.1.4).
  - Core's signing key: P-256, in a secret file, with a key history (§8.1.5).
  - Core's export key: a P-256 key-agreement key in a secret file. The roster carries its public key, and it opens protected exports (§8.5.5).
- **Device:**
  - `deviceID`, assigned at enrollment.
  - An operation-signing key (P-256).
  - A nearby transport key: a key-agreement key for Design A, or a TLS key for Design B (§8.6).
  - A device-generated 256-bit Core credential, of which Core stores only the SHA-256 verifier.
  - The trust anchor from the pairing payload (§8.1.2).

  Keys live in the Secure Enclave where available, otherwise as Keychain items available after first unlock on this device only.
- **Incarnation per launch:**
  - Every launch that opens the replica starts a fresh random 128-bit incarnation, with sequence numbers starting at 1.
  - The first operation of an incarnation names its predecessor and that predecessor's last sequence number, forming the incarnation chain.
  - A same-device restore that rolls back both the replica and the Keychain can't repeat an identity, because the next launch starts a new incarnation and the chain shows the fork.

#### 8.1.2 Enrollment and the trust bootstrap (direction 3; issues 4 and 5)

**Design**

1. **Token.** `lisa core device enroll --name … --class iphone|ipad|mac` stores an enrollment record: a random 128-bit ID, the token hash, a 10-minute expiry, an attempt counter, state `open`, the intended name and class, and Core's intended host name. The token is 32 random bytes.
   - Issuance and verification use one function: `tokenHash = SHA-256( ASCII "lisa-enroll-token-v1" ‖ 0x00 ‖ token )`, where `token` is the 32 raw bytes.
   - The payload carries the token as unpadded base64url. Core decodes it, refuses any length other than 32, then hashes.
   - **Vector:**
     - token = bytes `00 01 … 1f`;
     - input (53 bytes) = `6c6973612d656e726f6c6c2d746f6b656e2d7631` `00` `000102…1f`;
     - SHA-256 = `e74f49bf65f5c648421c64994582a9b22ef0f1ab253fefaceb1241f83fe313db`;
     - token in the payload = `AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8`.

     Computed on 2026-11-20 with coreutils `sha256sum` and OpenSSL 4.0.3, which agree.
2. **The owner-authenticated pairing payload.** It is shown once, on the owner's administrative terminal. The owner carries it to the device by typing or pasting text, or by a QR code made with local Apple components (below); the owner's custody of it is what authenticates it. It holds:
   - the format version;
   - Core's URL (`https`, host and port): the intended host name;
   - the trust mode: `pin`, for a self-signed Core, or `ca`, for an owner's private CA, carrying the CA certificate's SHA-256;
   - in either mode, Core's TLS SPKI SHA-256 pin;
   - the fingerprint of Core's signing key, the dataset ID, the enrollment ID, the token and the expiry;
   - a 4-byte checksum (the first bytes of SHA-256 over the rest).

   The text form is `lisa-pair:3:` followed by base64url, grouped for reading.
3. **Text pairing is fully usable** on every device; the checksum pinpoints typing errors.
   - **QR rendering:** Core's CLI renders no QR code, because no QR encoder is approved. This missing dependency is recorded, and not requested.
   - **On Apple devices:** an already-enrolled Mac can render the owner's text as a QR code with CoreImage's built-in `CIQRCodeGenerator`, and an iPhone or iPad scans it with VisionKit's data scanner. These are local, identified Apple components. The first device always uses text.
4. **Device preparation.** The device generates its keys and its 256-bit credential in the Keychain, then builds and signs the request.
   - **The request** holds the enrollment ID, token, dataset ID, trust mode and pins, device details, public keys (and, for Design B, the certificate), the credential verifier and the incarnation-chain start.
   - **The exact request bytes** contain the token, so they are secret-bearing. They are kept only in a device-only Keychain item, never in the replica, logs or diagnostics.
   - **That item expires** at the payload's expiry plus a 24-hour retry grace, and is deleted on success, on `enrollment_consumed`, `enrollment_expired` or `enrollment_invalidated`, or when the grace ends.
5. **Pinned TLS.** This extends R1's `PinnedServerTrustEvaluator` (§1.6), which trusts only owner-supplied anchors, checks the host name and fetches nothing. R1 pinned the whole leaf certificate; R2 pins its SPKI, so a renewed certificate with the same key needs no re-pairing, and a new key uses the overlap of §8.1.5.
   - In `pin` mode, Core's leaf SPKI must equal the pin. Only then does that leaf become the only anchor, and it is evaluated with the SSL policy for the intended host (validity, name, Apple's server-certificate rules).
   - In `ca` mode, the chain Core presents must contain a CA certificate whose SHA-256 equals the payload's. That certificate becomes the only anchor, the chain must validate for the intended host, and the leaf SPKI must equal the pin.

   The token is never sent otherwise.
6. **Core verification order,** in one write transaction:
   1. Unknown enrollment ID: `enrollment_unknown`.
   2. **Consumed, with the same request digest:** return the stored response (`duplicate`), whatever the expiry. This is checked before the open-enrollment branch.
   3. Consumed with another digest: `enrollment_consumed` (409), with a security event.
   4. Invalidated or expired: the matching typed error.
   5. Token hash compared in constant time. On a mismatch, commit `attempts + 1`; at 5 the enrollment is invalidated.
   6. Signature, keys, fields and the 10-device limit. On a failure, commit `attempts + 1` without consuming.
   7. Consume: record the state and request digest; create the device, keys and credential verifier; sign a new roster and the authorization record; store the public-only response. Commit, then answer.
7. **Completion.** The device verifies Core's signature against the fingerprint from the payload, stores the results and deletes the Keychain retry item.
8. **Design A's discovery secret** is never part of the enrollment response. It is fetched separately (§8.6).

**After a failure or retry:** a response lost after commit, a crash or a retry after expiry resends the identical bytes and receives the stored response (step 6.2). Other failures behave as revision 2 described.

**Acceptance (M1, M3, X2)**
- **M1:** LisaTrust's hash function will reproduce the vector above.
- **M3:** a harness against the real TLS server, using a test-only libcurl transport that pins, will check:
  - the success path in both trust modes;
  - a wrong pin and a wrong host name in each mode, with no token reaching the server log;
  - five wrong tokens, which invalidate the enrollment;
  - a bad signature, which counts an attempt without consuming;
  - two concurrent requests, which produce one device;
  - a response dropped after commit, retried after the enrollment's expiry, which returns the stored response;
  - the device limit.
- **X2:** an iPhone will enroll by pasting text, through URLSession with the pin. The probe's diagnostics will show the Keychain retry item during the attempt and its deletion afterwards.

#### 8.1.3 Roster and revocation

- **Contents:** the roster is signed by Core, identified by (epoch, version), and re-signed at least daily so that trust age stays fresh while devices are connected. It names the dataset, issue time, policy version, maximum nearby trust age (30 days by default), each device's keys, status and capabilities, and Core's TLS pins (current and next, §8.1.5).
- **Revocation entries** carry the commit position at which they happened. They are permanent (union rule): no later roster or epoch removes them.
- **Devices:**
  - keep the newest verified roster and refuse older versions within an epoch;
  - pass rosters on to peers;
  - refuse revoked peers, and stop forwarding or applying their new operations.

  An expired roster stops new nearby exchanges only.
- **`lisa core device revoke`** (owner, administrative): raises the roster version, revokes the credential, cancels pending deliveries and assignments, and rejects every new operation from that origin, whatever time it claims. Committed data stays.
- **Documented limit:** a device without the update can't know of the revocation.
- **Transport:** HTTPS with application authentication even over the VPN; validation is never disabled.

#### 8.1.4 Trust after a restore, and repeated recovery epochs (direction 6; issue 10)

**Design**
- **Fencing first.** `lisa core restore` fences the data directory it replaces, and a Core started on a fenced directory refuses to run.
- **Gated recovery mode.** The restored Core starts in recovery mode, which gates every mutation path:
  - v2 operations, v1 mutations and CLI owner mutations are refused;
  - the runtime cycle (ingestion, planning, reminder firing, the outbox) is paused;
  - delivery is suspended.

  Open in recovery mode: negotiation, trust evidence, receipt lookup and read-only status. Devices authenticate by signing a Core challenge with their roster key, because the restored database may lack their credential verifiers.
- **Epoch lineage.** Each epoch has a Core-signed record: epoch ID and sequence, parent epoch, the restored backup's ID and cut (epoch, position), the creation time, and the owner's confirmation.
  - Devices store the lineage. The chain of owner-confirmed epochs is the active history.
  - A superseded epoch's receipts remain provenance only.
- **Repeated restores.** Restoring the same backup twice creates two distinct epochs with the same parent cut.
  - Operations committed in the first restored epoch are above the cut, so journals resubmit them to the second (§8.5.3).
  - A receipt counts only within its own lineage.
- **Receipts across revocation or key rotation.**
  - A receipt is verified with the Core key valid at its commit position (key history, §8.1.5).
  - "Committed before revocation" holds only when the receipt and the revocation are in the same lineage and the receipt's position is earlier.
  - Otherwise, an operation from a revoked origin is rejected and kept for inspection.
- **Merging trust evidence.** Presented rosters, verified by Core's key history, add every revocation they carry and re-register devices enrolled after the backup as "membership unconfirmed". `lisa core trust import` merges an off-host roster copy.
- **Order of reopening:**
  1. The owner reviews and confirms membership (`lisa core trust review`, then `lisa core trust confirm`). This admits ordinary operations and resumes the runtime cycle, except delivery.
  2. `lisa core delivery review`.
  3. `lisa core delivery resume`.

  Uncertain deliveries stay held (§8.9.5).

**After a failure or retry**
- **A revocation that no device reported** stays unknown until the owner revokes again; sync stays closed until confirmation.
- **Forged or foreign rosters** are refused, with a security event.
- **Recovery state** is persisted, so a restart mid-recovery resumes it.

**Acceptance (M3)** — one harness scenario will:
1. Revoke device C, with C's operation X committed before the revocation and operation Y after it. A receives the newer roster.
2. Restore the backup, then check that C, v1, CLI and runtime mutations are all refused during recovery.
3. Merge A's roster, and reject Y when B relays it.
4. Reinstate X through its same-lineage receipt.
5. Restore the same backup again. The two epochs will be distinct, and operations from the first restored epoch will be replayed into the second.
6. Verify a receipt signed before a Core key rotation.
7. Confirm membership, and check that delivery stays suspended until it is resumed.

#### 8.1.5 Key and credential lifecycle (direction 3; issue 5)

- **Credential reset:**
  - `lisa core device reset-credential <id>` issues a one-time reset token, hashed like an enrollment token but with the label `lisa-reset-token-v1`, valid for 10 minutes and shown to the owner.
  - The device presents it with a new verifier, signed by its existing signing key. Core replaces the verifier atomically, and the old credential stops working at once.
- **Core TLS key and pin rotation:**
  - The signed roster carries `tlsPins: [current, next]` with validity windows. Devices accept either pin during the overlap (30 days by default), and Core switches certificates inside it.
  - A device that missed the whole overlap gets the new pin from a peer's Core-signed roster, or by re-pairing.
  - Core's health warns 30 days before its certificate expires. An expired certificate is never accepted.
- **Core signing-key rotation:**
  - The new key is announced in a roster signed by both the old and the new key, with an activation position.
  - Devices keep the key history (key, valid from, valid until), so historical receipts and batches stay verifiable with the key valid at their position.
- **Device key rotation:** a key-update operation signed by both the old and the new key; Core issues a new roster.
- **Core export-key rotation:** the roster announces the new public key. Exports name the key they were sealed to, and Core keeps retired export keys so it can still open older exports.
- **Design B device certificates** are renewed at 80% of their lifetime through key updates.
- **Revocation:** §8.1.3.
- **Acceptance (M3, X2, X7):**
  - M3 harness: credential reset (the old credential will be refused); a pin overlap and switch; a device offline through the whole overlap, recovering through a peer's roster; signing-key rotation with historical receipt verification; device key rotation; roster renewal; an expired Core certificate refused.
  - X2 and X7: the same reset and pin overlap with real Keychain items.

### 8.2 Operations, identity and dependencies (R2-SYNC-01, R2-SYNC-02)

#### 8.2.1 Envelope, digest and duplicates

- **Fields:**
  - protocol and schema versions, and the dataset ID;
  - origin device, incarnation and sequence number;
  - operation ID: random 128 bits; v1 children use deterministic IDs (§8.11.2);
  - entity type and ID; operation type and payload;
  - dependencies and observed versions;
  - policy version;
  - creation time, for display and audit only.
- **Digest:** SHA-256 over the complete canonical signed body: everything above.
- **Signature:** raw 64-byte P-256 ECDSA over `"lisa-r2-op\n"` followed by the body. Relays forward the exact bytes.
- **Duplicates:**
  - Same ID, same digest: `duplicate`, carrying the current receipt.
  - Same ID, different digest: `rejected: identity_reuse`, with a security event.
  - Same (device, incarnation, sequence) under another ID: `rejected: sequence_reuse`, with a security event.
- **Receipts:**
  - Waiting operations get signed provisional receipts.
  - Final receipts follow when the operation is decided, and every decision is a change-feed entry.
  - A retry while waiting returns the same provisional receipt.

#### 8.2.2 Dependency outcomes and bounds (direction 5)

| Situation | Outcome |
|---|---|
| A dependency not present | `waiting_for_dependencies`, with a provisional receipt. After the waiting limit (14 days): `rejected: dependency_missing`, with a recovery hint |
| A dependency rejected | `rejected: dependency_rejected` if the entity never existed; otherwise applied with the rejected version ignored |
| A cycle among waiting operations (only forged or corrupt input can create one) | Every operation in the cycle is `rejected: dependency_cycle`, with a security event |
| Too many dependencies | At most 32 declared dependencies per operation; more is `rejected: malformed` |
| Too much waiting | At most 1,000 waiting operations per origin incarnation and 64 MiB of waiting bodies dataset-wide. Beyond that, new submissions get `insufficient_storage` (backpressure). Waiting operations are never dropped |

#### 8.2.3 The operation catalog, including the missing operations (direction 10)

- **Already in revision 2:**
  - capture: create;
  - tasks: create, edit a field, complete, cancel, reopen (naming the terminal actions it reopens);
  - notes and tags: add a note, change tags;
  - ideas: edit a field, change lifecycle;
  - reminder occurrences: acknowledge, dismiss, snooze;
  - event proposals: review, dismiss, correct;
  - preferences: set, delete, confirm;
  - plan blocks: accept, lock, reject, defer, complete, move;
  - any owner item: delete, restore as a new identity;
  - conflicts: resolve.
- **Added:**
  - **Create idea directly**, not only through a capture.
  - **Owner reminders:** create (due time, optional subject, note), edit, cancel. A new entity type: before Core accepts it, its creating device owns delivery (§8.9).
  - **Suggestions from fallback inference:** propose (authority model, from a device), then accept or dismiss (owner). Accepting creates the task, idea or proposal through ordinary owner operations, with the suggestion as provenance.
  - **Actions on a provisional plan:** a plan intent (accept, lock, move or reject a local block), keyed by date, zone, subject and range, because local blocks have no canonical IDs. Core reconciles intents with canonical planning. An intent that no longer fits surfaces as a conflict and is never rescheduled silently.

**Acceptance:** codec vectors will be checked at M1 and Core outcomes at M3. Each table row will have a case, including a forged two-operation cycle, the 32-dependency boundary and the waiting-storage backpressure.

### 8.3 Merge rules (R2-SYNC-06, R2-WORK-03)

#### 8.3.1 Rules

Each owner field has a merge class, and each operation names the versions it observed.

| Situation | Rule |
|---|---|
| Duplicate operation | Applied at most once, by ID and full digest |
| Edits to different fields | Separate registers, so they merge |
| Concurrent edits to one scalar field | Multi-value register: every unobserved candidate survives and a conflict opens |
| Owner correction versus a model or source value | Authority per value: model and source writes never replace an owner value; they are kept as suggestions |
| Concurrent note additions | Separate note pieces (§8.3.2); both kept. A v1 `notes` text edit replaces exactly the pieces it observed |
| Tag additions and removals | Observed-remove set |
| Completion or cancellation versus an edit | Status is separate; the edit applies and the terminal state stays |
| Concurrent completion and cancellation | Both recorded; terminal; reminders and deliveries suppressed |
| Reopen | Names the terminal actions it reopens; an unseen one stays effective |
| Acknowledge or dismiss versus a snooze | The occurrence is suppressed; the snooze stays in history |
| Concurrent snoozes | The latest instant, capped at the policy maximum |
| Deletion versus edits | The tombstone dominates; edits are kept as superseded while retention allows; restore creates a new identity |
| Concurrent plans or briefs | Separate artifacts, never merged |
| Plan intents versus canonical planning | Core reconciles; an intent that conflicts with a busy event or a held block surfaces as a conflict |
| Conflict in a planning field | Plan with the earliest deadline and longest estimate, marked uncertain; escalation held |
| Resolution | Names every reviewed candidate; a newer candidate remains as a new conflict |

Causal readiness, convergence (every rule a join of sets, with a deterministic display order), and no last-writer-wins: as revision 2.

#### 8.3.2 Bounded pieces and deterministic overflow (direction 5; issue 7)

- **Pieces.** Growing collections are separate pieces, never part of the item's own state:
  - a note is a note record keyed by the operation that added it, at most 64 KiB;
  - a conflict candidate is a candidate record holding one value and its version, at most 64 KiB;
  - the item's own state holds field registers and references, and is bounded at 64 KiB because each field is bounded.
- **Why this fixes order dependence:** two individually valid concurrent edits never depend on each other's size, so both survive in either arrival order. Revision 2's aggregate entity-state bound could have refused whichever edit arrived second.
- **Aggregate limits are advisory.** For example, 1,000 notes per item. They are checked only when a device creates a new operation from its own view, never while merging, so overflow is deterministic and order-independent. Past the advisory limit the UI asks the owner to archive.
- **Core's storage bound** is global backpressure (`insufficient_storage` for new submissions), never a per-item refusal that would depend on order.
- **Acceptance (M2):** two concurrent 64 KiB edits to different fields, and two concurrent notes added to an item already at the advisory limit, will each be applied in both orders on two replicas and Core, with identical results.

#### 8.3.3 The authority path for model, source and system writes (direction 10)

- **Every Core-originated write to an owner entity** goes through `AuthorityWriter` as a Core-signed operation with an authority:
  - `source`: R1's ingestion, including the event proposals that its mail ingestion (`MailBatchProcessor` in `Sources/LisaIngestion/MailIngestion.swift`) creates from calendar invitations;
  - `model`: `ExtractionService` tasks and proposals, inferred preferences, and accepted fallback suggestions keep their model provenance;
  - `system`: rematching state and planner annotations.
- **Owner actions** (reviews, corrections, edits) are owner operations.
- **Derived records** (calendar occurrences, emails, evidence, news) are source records outside owner merge; they replicate as derived records.
- **Acceptance (M3):**
  - an invitation-created proposal will be corrected by the owner;
  - its email will then be reprocessed;
  - the owner's correction will remain effective, and the model's value will be kept as a suggestion.

### 8.4 Core: ledger, change feed, coverage, backups and epochs (R2-SYNC-03, -05, -07, R2-CORE-04, -06)

#### 8.4.1 Ledger and intake

- **Schema v5 adds:**
  - the dataset, epoch lineage and recovery state;
  - operations, dependencies, merge states, pieces, conflicts, and provisional and final receipts;
  - origin progress and incarnation chains;
  - the change log, partition coverage, tombstones and blobs;
  - rosters, key history, enrollments and reset tokens;
  - replication checkpoints, snapshots, validated backups and the replay floor;
  - occurrences, ownership and delivery control;
  - v1 parents;
  - schedules and the model budget.
- **Intake** runs in one write transaction with a savepoint per operation:
  1. bounds, dataset, epoch, schema and recovery state;
  2. origin, signature, digest and reuse checks;
  3. authorization;
  4. dependencies;
  5. merge, projection, pieces, conflicts and tombstones;
  6. delivery and assignment suppression, serialized as in §8.9.3;
  7. change-log entries, the operation record (which is also the idempotency record) and the final receipt;
  8. durable follow-up work, run after commit.

#### 8.4.2 Snapshots

- **Building:** from one consistent cut on the read connection, streamed into 512 KiB chunks.
- **Manifest:** signed, with paginated chunk lists (at most 4,096 entries per page), the dataset, epoch, cut, versions, counts, the causal summary and the coverage descriptor.
- **Parsing:** length-prefixed records are parsed across chunk boundaries as a stream.
- **Time bound:** generation is bounded in time, because its reader holds back WAL checkpoints (tested with a pinned reader, §8.14).

#### 8.4.3 Change batches and filtered coverage (direction 4; issue 8)

- **Coverage descriptor:** the working-set filter a batch serves. It lists each collection and its window (for example, occurrences from D−30 to D+90, with D the window anchor), has a canonical hash, and is published with the working-set definition.
- **Batch binding.** Core's signature covers the dataset, epoch, start and end cursor, coverage descriptor and its hash, the window anchor, and the entry count and digest.
- **Per-partition cursors.**
  - Replicas keep one cursor per partition (collection and window).
  - A batch advances only the partitions its descriptor covers completely.
  - A narrow batch never advances a wider replica's cursors past records it omitted.
- **Relay between differently filtered replicas.**
  - The receiving replica installs the overlapping entries and advances only the overlapping partitions.
  - It fetches the rest from Core, or from a peer whose coverage includes it.
- **Empty batches.** When nothing in a coverage changed, Core returns a signed empty batch that advances its cursors.
- **Gap recovery.**
  - A batch is accepted only if its start cursor equals the partition cursor, or the replica already holds the entries between them.
  - Otherwise the replica asks again from its own cursor.
  - If Core no longer has that range (`cursor_expired`), the replica takes a snapshot.
- **Rolling windows.**
  - The window anchor advances daily.
  - Records entering the window arrive as window-entry changes. A replica whose anchor lags requests a backfill for the new slice.
  - Records leaving the window are evicted as cache, never treated as deleted.
- **Causal proofs after compaction.** Once operation bodies are compacted, Core's signed causal summary (decided ranges per origin, plus version sets) proves inclusion. Peers forward these summaries, paginated at 256 KiB per page.
- **Cursors never move backward within an epoch.** Changing epoch happens only on the recovery path, with a verified lineage record.
- **Acceptance (M3, M6):** the harness will check a relay from a narrow replica to a wide one, in which uncovered partitions must not advance; empty batches; a window roll with backfill; a gap; a tampered descriptor, which must be refused; and a cursor-expired recovery.

#### 8.4.4 Validated backups, the replay floor and replay coverage (direction 6; issue 9)

- **Validated backup record:** the backup ID (SHA-256 of its manifest), epoch, cut position, creation time, validation time and file digests. `lisa core backup validate` writes it.
- **Replay floor:**
  - The owner keeps a number of backups restorable (`backup.retainRestorable`, 2 by default).
  - The replay floor is the cut of the oldest of them.
  - Capabilities publish the floor and the list of restorable backups (ID, epoch, cut).
- **Pruning rule.** On Core and on every replica, an operation body, and any blob it references, may be dropped only when both hold:
  - its canonical effect is installed on that replica, so no overlay still needs it;
  - its commit position is at or below the replay floor, so every restorable backup contains it.
- **What can be recovered, exactly:**
  - Restoring a restorable backup X can replay every operation above X's cut whose body survives on a reachable device. The second pruning condition keeps those bodies, apart from cap evictions.
  - For a backup that is no longer restorable (below the floor), the range from its cut to the floor cannot be replayed.
  - After a cap eviction (§8.5.3), the evicted range is reported and cannot be replayed.
- **Acceptance (M3):**
  1. Take backup A, then later backup B, keeping 2 restorable.
  2. Prune, then restore A: everything above A's cut will be replayed from journals.
  3. Repeat while keeping 1: the plan's reported unrecoverable range will match exactly what is lost.
  4. Force a cap eviction: it will be reported in health.

### 8.5 Clients: store, journal and effective view (R2-DATA-01–05, R2-SYNC-04, -05, -08, R2-LIMIT-02)

#### 8.5.1 Store, atomic changes and states

- **Location (O-8):** one SQLite database per installation, inside one replica directory that also holds the `-wal` and `-shm` sidecars, staging, blobs and temporary export staging.
  - The directory is owner-only, protected until first unlock on iPhone and iPad, and excluded from device backups by `isExcludedFromBackup` on the directory, which covers its contents.
  - It is never copied between devices.
- **Contents:** as revision 2, plus the local state generation, partition cursors, the lineage, the key history and plan intents.
- **Atomic local change (R2-DATA-02).** One write transaction:
  1. validates the command;
  2. allocates the ID and this launch's next sequence number;
  3. signs through `ReplicaSigning`;
  4. stores the operation with its original input;
  5. updates the view, and the index through `ReplicaIndexing`;
  6. advances the local state generation;
  7. records follow-up work.

  The app says "saved" only after commit. Disk-full, I/O and signing failures are reported as they are.
- **States (R2-SYNC-04):** saved on this device; copied to another device; submitted to Core; committed; committed with a conflict; rejected; waiting for dependencies; needs review. A peer copy never counts as a Core commitment.
- **Effective view:** canonical state plus pending operations, recomputed per item on every change. Revoked and rejected operations leave the view but stay in the journal.
- **Working set, provenance and time:** as revision 2, with the coverage descriptor of §8.4.3. A filtered replica says it is incomplete, and nothing missing is read as deleted.

#### 8.5.2 The snapshot installation point (direction 4; issue 6)

- **Local state generation G.** A counter in the replica, advanced in the same transaction as every journal change, receipt, rejection, revocation, canonical batch install, working-set change and conflict resolution.
- **Staging:**
  - It records its starting generation G0 and the snapshot's cut.
  - Verified chunks go into staged tables inside the live database, each in its own short, resumable transaction.
  - The staged view is built from the staged canonical tables plus the journal as of G0.
- **The installation point** is one short write transaction:
  1. **Check:** every chunk digest in the signed manifest has been verified.
  2. **Reconcile:** if G > G0, everything recorded after G0 is applied to the staged view: journal operations re-applied; receipts and rejections applied, with rejected overlays removed; revoked origins' pending operations dropped; working-set changes re-applied.
  3. **Invalidate if stale.** The staged cut is dropped and staging restarts from a newer position when:
     - a canonical batch beyond the snapshot's cut was installed after G0;
     - the epoch changed;
     - the coverage descriptor changed;
     - reconciliation can't apply a change exactly.
  4. **Never backward:** the swap requires the snapshot's cut to be at or after every installed partition cursor in the same epoch, or a newer verified epoch.
  5. **Swap:** rename the staged tables over the live ones and set cursors, epoch and coverage. Journal, captures, conflicts, receipts and assignments are untouched.
- **Concurrent captures** take the same write lock, so each commits before G0, between G0 and the point (and is reconciled), or after it.
- **A crash before the point** leaves the old view intact; one after it leaves the new view intact.
- **One database file:** SQLite in WAL mode does not commit atomically across attached databases.
- **Storage:**
  - Staging needs twice the snapshot size plus a 64 MiB reserve, and stops before the reserve, so captures keep room.
  - `SQLITE_FULL` surfaces a truthful "not saved".
  - `journal_size_limit` is 16 MiB, with passive checkpoints after batches and a truncating one after the point.
- **Acceptance (M2):** the harness will check:
  - a rejection, and separately a revocation, arriving during staging, both of which must be reconciled;
  - a canonical batch beyond the cut installed during staging, which must invalidate the staging;
  - an attempt to install an older cut, which will be refused;
  - captures during staging and at the point;
  - process kills at each step on real files;
  - real filesystem exhaustion (§8.14).

#### 8.5.3 Journal retention and replay (direction 6; issue 9)

- **Uncommitted operations** are never dropped.
- **Committed bodies** are kept until the pruning rule of §8.4.4 allows dropping them: the effect is installed, and the position is at or below the replay floor. Blobs follow their operations.
- **Visibility.** An overlay leaves the view only when the canonical state containing its operation is installed, never when the receipt arrives.
- **Caps.** At most 90 days or 64 MiB of committed bodies per replica. An eviction above the floor is recorded with its range and reported: "recovery coverage reduced for backups older than …".
- **After a restore** (a new epoch in the lineage), the device resubmits every retained body above the restored cut. Core verifies them (§8.1.4) and applies them, keeping the old receipts as provenance.
- **What can and can't be recovered:**
  - Owner changes that reachable devices still hold can be recovered.
  - CLI and v1 changes made after the backup cannot: their callers keep no signed journal.
  - Core-derived results are re-derived from the restored cursors.
  - Deliveries after the backup are held as uncertain (§8.9.5).
- **Acceptance:**
  - **M2, replica side.** A device's replica and key material will be copied, as an encrypted same-device backup would be. The device will continue, then the copy will be restored. Checks: a new incarnation at launch, a correct chain, no sequence reuse, and the overlay visible until the canonical change installs.
  - **M3, after the ledger exists:** the real Core incarnation test. The fork will be recorded, pre-backup pending operations will return `duplicate`, and new operations will be accepted. A negative control will use a per-installation incarnation.
  - **M3:** the scenario of §8.4.4.

#### 8.5.4 The production direct HTTPS sync path (R2-SYNC-08)

- **Owners:**
  - LisaSyncEngine (the Core session);
  - `CoreTransport` over LisaClient's URLSessionTransport;
  - `Apps/Shared/Trust` (both trust modes of §8.1.2);
  - LisaCoreAPI and LisaAPIServer on Core.
- **Milestones:** built in M3. X2 runs it on Apple devices through `Apps/Probe`, before the first full app at M5.
- **Reconciliation order:** as revision 2. Blobs are uploaded before the operations that reference them.
- **Linux evidence:** URLSession on Linux cannot take a custom anchor (R1 D-45), so the harness carries the same logic over the test libcurl transport with pinning. URLSessionTransport also runs over plain HTTP on loopback.

#### 8.5.5 Export and the only-copy risk (O-8)

- **Protected export** covers unsynchronized owner work: uncommitted journal entries with their inputs and signatures, blobs, quarantined items, and unresolved conflicts with draft resolutions.
  - **Protection.** Only the owner's Core, or the same installation, can open the file:
    - a random content key encrypts it with AES-256-GCM;
    - the content key is sealed with HPKE (RFC 9180; DHKEM(P-256, HKDF-SHA256), HKDF-SHA256, AES-256-GCM) to two recipients: Core's export key from the roster (§8.1.1), and this installation's own export key in the Keychain;
    - the device signs the sealed file.

    HPKE is in the approved swift-crypto `Crypto` module: its 5.1.1 checkout has the `P256_SHA256_AES_GCM_256` suite. On Apple it is CryptoKit's, which needs iOS 17 and macOS 14, below R1's targets of iOS 18 and macOS 15 (`Apps/project.yml`). No new dependency.
  - **Location:** a file the owner chooses through the system exporter. While the file is inside the app's container it also has complete file protection.
  - **Re-import:**
    - by the same installation, while its keys survive;
    - by `lisa core import-journal`, which opens the file with Core's export key and verifies every signature. Nothing is duplicated, because operation IDs are kept.

    Another device can't open the file, by design; `docs/OFFLINE-BEHAVIOR.md` explains this.
- **A peer copy is not a Core commitment.** "Shared with a nearby device" means a second device holds the operation and can relay it, so losing the originating device no longer loses the work. It is still uncommitted: Core can still reject it, and losing both devices still loses it.
- **The only-copy risk.** Until Core commits it, work exists only on the devices holding it. An isolated device with the only copy loses it if the device is lost, wiped, or restored from a device backup, because the replica is excluded from backups.
  - The app shows "Only on this device: n changes" and offers export.
  - `docs/OFFLINE-BEHAVIOR.md` explains the risk.
- **Acceptance:**
  - **M5, Linux,** the harness will check:
    - export, then re-import by the same installation and by `lisa core import-journal`, which must produce no duplicates;
    - a second installation, which must fail to open the file;
    - a modified file, which must fail its signature check;
    - a restored installation, with and without keys, which must keep identities safe (§8.5.3).
  - **X3, devices:** the exclusion attribute will be inspected on the replica directory and its sidecars, and an export round trip will be run.

### 8.6 Nearby synchronization (R2-NEAR-01–05; direction 3)

- **Capabilities:** TN3213 and the Security reference, as in §1.5. Lisa uses the older `NW*` APIs, which the deployment targets support.
- **Session layer** (both designs; as revision 2):
  - each side's hello is signed with its operation key and bound to the TLS exporter;
  - inventories, then bounded exchanges in §8.15 frames, then peer acknowledgements;
  - explicit keepalives, send timeouts and backpressure; 30-second idle close;
  - deduplication by device ID; random Bonjour instance names.
- **Design A: pair-specific pre-shared keys.**
  - **Pair key:** K_ij = HKDF-SHA256 over the P-256 agreement between the two devices, with the dataset ID as salt and the sorted device IDs as info.
  - **Key selection:** rotating 15-minute discovery tags in the TXT record: HMAC-SHA256 under the discovery secret, over the window and the device ID, truncated to 16 bytes. The PSK identity is the initiator's own tag.
  - **The discovery secret is distributed separately.** `GET /v2/trust/nearby-secret` is authenticated, answered with `Cache-Control: no-store`, never part of the replayable enrollment response, and stored in the Keychain.
  - **Rotation:** on every revocation and every 30 days. Devices keep the current and previous versions for 7 days.
  - **Disconnected peers:** a peer that already holds the newer version passes it on only inside an authenticated session. A device offline beyond the grace must reach Core or a refreshed peer first. Revoked devices never receive new versions.
  - **Limits:** TLS 1.2 only, and a PSK suite only by raw value (§1.5).
- **Design B: roster-bound mutual TLS.**
  - **Handshake:** TLS 1.3 with mutual authentication required. The verify block accepts a peer only if its leaf key matches an active roster entry; no CA chain or host name is involved.
  - **Discovery:** the initiator connects to the discovered services (at most 9) and learns the peer's identity during the encrypted handshake.
- **Certificate provisioning, keeping X1 evidence apart from production issuance:**
  - **X1, proof-only.**
    - Certificates come from a fixed-template encoder compiled only into `Apps/Proof`, signed with the device's Secure Enclave key through CryptoKit, labeled proof-only, and never linked into a product.
    - The same source file is compiled by a Linux harness to check its output with the `openssl` command.
    - X1 evidence therefore covers Network framework mutual TLS with a Secure-Enclave-backed identity and roster pinning, not production issuance.
  - **Production, if selected: swift-certificates, pending P-08.**
    - The pin would be 1.21.1 (commit `84f03faf…`).
    - Compatibility: tools 6.1, which builds with Swift 6.3.2 and 6.4.2; swift-crypto `3.12.3..<6.0.0`, satisfied by the pinned 5.1.1; swift-asn1 `≥ 1.1.0`, satisfied by the pinned 1.7.4.
    - Expected lockfile impact: one new pin, with the existing pins unchanged. This is confirmed by resolution only after authorization.
    - It also builds swift-crypto's `_CryptoExtras`, which adds BoringSSL-backed code to the Apple apps; binary size will be measured at X4.
    - With the Apple-protected key: a Secure Enclave `SecKey` (`kSecAttrTokenIDSecureEnclave`, stored permanently) signs the certificate through `Certificate.PrivateKey(SecKey)` without leaving the enclave. The certificate is added to the Keychain, Security pairs it with the key into a `SecIdentity`, and `sec_identity_create` hands it to Network framework.
    - It would be linked only by the Apple apps, through the conditional `LisaDeviceCertificates`. Until then, no dependency or lockfile change is made.
  - **Device behaviors still to verify with the selected library (X4):**
    - creation signed by the Secure Enclave on a Mac (Apple silicon or T2), an iPhone and an iPad;
    - `SecIdentity` formation in the data-protection Keychain, including the sandboxed Mac;
    - TLS 1.3 mutual authentication on all three device pairs;
    - key extraction in the verify block;
    - renewal and rotation;
    - behavior while locked after first unlock;
    - reinstall followed by a key update.
- **X1 is a prerequisite.** The production transport in `Apps/Shared/Nearby` is written only after N-1's device result is recorded. The portable session layer proceeds meanwhile.
- **Failure handling, background limits and relay rules:** as revision 2.
- **Acceptance:**
  - **Linux (simulated link):** the harness will cover hello and authentication, exporter mismatch, unknown and revoked peers, resume, deduplication, R2-L04, L15, L17 and L36, the R2 §18.2 scenario, and the coverage relay of §8.4.3.
  - **Apple:** N-1 at X1; the production transport at X4.

### 8.7 Capabilities and transitions (R2-CAP-01–04)

- **Tracked separately:** authenticated Core reachability and compatibility; each fallback provider; nearby availability; data freshness and coverage; notification permission and schedule coverage; enrollment and trust; storage health.
  - Core reachability comes only from an authenticated exchange, never from a VPN or path signal.
- **Features follow the capability they need,** as specified in `docs/OFFLINE-BEHAVIOR.md`.
- **Safe transitions:** a connectivity change never interrupts a durable capture, replaces a draft, clears the database, resends a finished inference, replays an expired delivery or resets retries.

### 8.8 Offline intelligence, inference and public retrieval (R2-CAP-03, R2-INT-01–05, R2-WORK-01–04; direction 9; issue 14)

**Offline intelligence, local plans and local briefs:** as revision 2, with plan intents (§8.2.3) for actions on provisional plans.

**Destination policy (inherited from R1, §1.6)**

| Destination | R1 policy | Client path |
|---|---|---|
| Owner-requested public URL or feed | `publicOnly` | `LisaHTTP1` over the verified `NWConnection` |
| Model endpoint named by DNS (a provider) | `publicOnly` | Same |
| Model endpoint `localhost`, or a loopback or private IP literal | `allowLocalNetworks` | Same |
| Model endpoint over plain `http` | `loopbackOnly` | Same (meaningful on Mac only) |
| Core | The owner-configured, pinned endpoint (§8.1.2) | URLSession |

**What R1 enforces (§1.6), and the Apple path keeps:**
- every resolved address is checked before a socket is opened to it, and refused addresses are skipped;
- the connected address is checked again before the request is sent;
- no proxy, because with one the checked address would be the proxy's;
- TLS 1.2 or later with peer and host verification;
- redirects re-checked hop by hop: none for model calls; for sources, at most 3 by default (at most 10);
- a non-idempotent request sent at most once per exchange.

**Checks, in order**
1. **Before any connection:**
   - R1's URL policy: scheme, no credentials, host syntax, port.
   - The endpoint's scope, judged as `ConfiguredHostScope` does.
   - Names are resolved with the system resolver (`getaddrinfo`, off the main thread). IP literals are used as they are.
   - On an IPv6-only path, network-specific NAT64 prefixes are discovered with RFC 7050: the same resolver looks up `ipv4only.arpa` AAAA, prefixes of 32 to 96 bits are derived per RFC 6052, and the result is cached for the path.
   - Every address is classified with R1's `NetworkAddress` plus those prefixes; an address inside a prefix is judged by its embedded IPv4 address. Refused addresses are skipped, as R1's gate does. If none is permitted, the request fails with R1's "resolves only to addresses Lisa does not connect to".
2. **Connecting, before TLS:**
   - `NWConnection` to one permitted IP endpoint at a time (IPv6 first, then IPv4, with a short stagger), never by name, with `preferNoProxies` set.
   - TCP and TLS therefore reach only checked addresses.
   - This deliberately departs from TN3151's advice to connect by name (§1.5): connecting by name lets the system resolve again and connect before any check can run, which R1's gate never allows.
3. **TLS** (for `https`):
   - the system TLS stack, minimum TLS 1.2;
   - the URL's host as the TLS server name (`sec_protocol_options_set_tls_server_name`, iOS 12 and macOS 10.14) for SNI and certificate validation;
   - default trust evaluation.
4. **Before the first HTTP byte:** `currentPath.remoteEndpoint` must equal the chosen endpoint. Any other endpoint means a proxy, relay or rewrite, so the destination is unverifiable.
5. **HTTP:**
   - one request: GET for retrieval, POST for model calls, and a POST is never re-sent on a new connection;
   - bounded headers, body and time;
   - no redirects for model endpoints;
   - for retrieval, each redirect re-runs checks 1–4 on a new connection, under R1's limits.

**Fail closed.** A destination counts as unverifiable if:
- resolution fails;
- NAT64 discovery fails on an IPv6-only path;
- the connected endpoint is not the chosen one;
- the path type is not covered.

The request is then never written. A retrieval shows "Couldn't verify where this link leads; not fetched" and is left for Core. A model call ends as `unverifiable_destination` with its budget released, because nothing was sent. Nothing is ever retried through URLSession.

**Platform limitation.** If X1 or X5 shows the platform can't do one of these, the inherited boundary can't be implemented on that platform:
- connect to an IP endpoint while validating TLS for the URL's host name;
- report the connected endpoint before the first write;
- discover NAT64 prefixes.

Public retrieval and DNS-named providers are then disabled on that platform, and the limitation is recorded in `docs/INTEGRATIONS.md` and `docs/OFFLINE-BEHAVIOR.md`. Core retrieval stays available.

**The feasibility proof comes forward to X1.** `Apps/Proof` includes a fetch probe, run with no Core configured:
- an owner-authorized public URL will be fetched over `https`, with the certificate validated for its host name;
- a name that resolves only to a private address will be refused before any connection, checked with a listener on the owner's network that records whether a TCP connection arrived;
- a name with both public and private addresses will connect only to the public one;
- a configured system proxy will not be used, and the connected endpoint will be the chosen one;
- an IPv6-only NAT64 network (macOS Internet Sharing) will be classified correctly.

The production path follows at M7, and is checked again at X5.

**Inference (R2-INT-04, -05)**
- **Atomic reservation.** One transaction creates the request record: identity, inputs, provider, model, template version, consent version and the planning-zone day. It reserves one unit of that day's budget (refused at 10) and sets the status to `reserved`.
  - Before any byte is sent, the status `sending` is persisted.
  - The outcome is then `answered` (valid or invalid), `failed_before_send` (unit released) or `uncertain` (after a timeout or connection loss post-send: usage counted, never resent automatically).
- **Repairs:** at most one, reserving its own unit in the same way.
- **Consent, model and template changes:**
  - A request keeps what it used.
  - Withdrawing consent cancels requests not yet sent and releases their units.
  - Results under an old template stay labeled as such.
  - The same intent under a new template is a new request.
- **Planning-zone changes:**
  - The day is the planning-zone date at reservation.
  - A rolling 24-hour cap of 10 also applies, so zone changes and clock rollback (the last-seen wall time is persisted) cannot create extra capacity.
- **Deleted supporting evidence:** results citing it are invalidated, and their suggestions withdrawn with a visible reason.
- **Acceptance (M7):** the harness will check:
  - the five workflows against a loopback OpenAI-compatible server;
  - a crash at each status;
  - repair counting;
  - consent withdrawal and a template change;
  - a zone change at midnight and a clock rollback;
  - deletion of supporting evidence;
  - an unverifiable destination, which sends nothing and releases the unit;
  - the policy table, driven through the test resolver and byte stream, will cover: public, private, link-local, IPv4-mapped, the well-known and a network-specific NAT64 prefix, mixed answers (only permitted addresses dialed), a connected endpoint other than the chosen one, a redirect to a private address, and R1's redirect limit.

### 8.9 Notifications and external delivery (R2-NOT-01–06; direction 7; issues 11 and 12)

#### 8.9.1 Immutable occurrence IDs

- **Occurrence ID:** the first 16 bytes, in base32, of SHA-256(`"lisa-occurrence-v1"` ‖ 0x00 ‖ dataset ‖ 0x00 ‖ kind ‖ 0x00 ‖ subject ‖ 0x00 ‖ slot).
  - It is fixed when created. Core records which R1 keys map to it.
  - This corrects revision 2: R1 keys change when a task's change sequence or a block's start changes (§1.6).
- **Mapping from R1 keys.** R1 keys reminders at three levels (§1.6), and the slot leaves out the mutable parts:

| R1 key | R1 level | R2 occurrence: kind, subject, slot |
|---|---|---|
| `deadline:task:<id>:<seq>:<offset>` | Reminder | deadline, task `<id>`, offset |
| `deadline:task:<id>:<seq>:soon` | Reminder | deadline, task `<id>`, `soon` |
| `dateonly:task:<id>:<seq>` | Reminder | dateonly, task `<id>`, none |
| `overdue:task:<id>:<date>` | Reminder | overdue, task `<id>`, date |
| `block:<plan>:<block>:<startMs>` | Reminder | block, plan and block, none |
| `proposal:<id>:<date>` | Reminder | proposal follow-up, proposal `<id>`, date |
| `reminder:<reminder ID>:<firing ms>` | Notification, one per firing | That reminder's occurrence. Each firing, the first or one after a snooze, is a generation |
| `brief:<date>:<zone>` | Notification | brief, none, date and zone |
| `commitmentChange:<subject>:<seq>` | Notification | commitment change, subject, change sequence: each change is its own slot |
| `notify:<notification key>:device:<id>`, `email:<notification key>:<address>`, `brief-email:…`, `call:task:<id>:<notification key>` | Delivery | Kept unchanged on migrated deliveries and linked to their occurrence and generation. New deliveries are keyed by occurrence ID, generation and recipient |
| (new) owner reminder | None | owner reminder, reminder `<id>`, none |

- **When R1 logic replaces a key for the same slot** (a change-sequence bump, or a moved block), the occurrence keeps its ID and gets a new generation. A change that removes the slot (a deadline removed, the task closed) cancels the occurrence. A moved deadline therefore keeps one occurrence with a new trigger.
- **OS request identifier:** `lisa.r.` followed by the first 26 base32 characters of SHA-256(`"lisa.local-notification.v1"` ‖ 0x00 ‖ dataset ‖ 0x00 ‖ occurrence ID ‖ 0x00 ‖ device ID). It is stable for each occurrence and device. R1's APNs collapse identifiers are unchanged, and neither identifier is used for idempotency.

#### 8.9.2 Commands kept apart from observations

For each occurrence and device, Core keeps:
- the command generation: the latest assignment, schedule(g) or cancel(g);
- the scheduled generation the device confirmed;
- the fired generation the device observed;
- the state.

Commands at or below the stored command generation are stale and ignored. Observations — `scheduled(g)`, `fired(g)`, `absent(g)` — are facts about generation g and are never discarded as stale. For example, `fired(g)` arriving after `cancel(g+1)` was issued records an alert that fired before the cancel, so the slot is not reclaimed.

#### 8.9.3 Serializing reservation against push attempts

Reservation for local scheduling happens in a transaction that checks the slot's Core-side delivery:

| Delivery state | Reservation |
|---|---|
| None, or pending and unclaimed | Suppress the delivery and reserve |
| Claimed or in progress (preparing or submitting) | No reservation now; retried after the attempt finishes |
| Accepted, confirmed or unknown | No reservation: already delivered or uncertain |

In the other direction, the outbox never claims a delivery whose slot is reserved or owned by a device.

#### 8.9.4 States, handoff and uncertainty

- **States:** R2-NOT-03's list (Core-owned, reserved, local confirmed, scheduling failed, suppressed or cancelled, expired, outcome unknown), plus `fired`.
- **Handoff, replacement, cancellation, expiry, delivered alerts and reconciliation:** as revision 2, using the identifiers and generations above.
- **Uncertain presentation:** after the trigger, with no evidence in the pending or delivered lists or in callbacks, the outcome is unknown and is never reclaimed.
- **Device disconnected during a handoff:** the slot stays reserved and uncertain. Expiry makes it expired or unknown, and a later report can resolve it.
- **Late reports** are accepted whenever they arrive, as observations. Reports from a superseded epoch are evidence only.
- **Ownership across restores:** a restored Core marks every reservation newer than the backup as unknown. Devices report their assignment inventories at reconnection, and ownership is rebuilt from those reports. Slots without a report stay unknown until one arrives or the occurrence expires.
- **Locally created reminders:** owned by the creating device until Core accepts them; then Core adds future slots for the other devices, with no replay of missed past reminders.
- **The Mac:**
  - Its bundle ID is added to `notifications.apns.topics`.
  - It gains the `com.apple.developer.aps-environment` entitlement.
  - Its App ID needs Push Notifications enabled and a provisioning profile that includes it, from the owner's developer account.
  - X6 verifies this with that account; without it, `NOT_RUN_CREDENTIALS`.

#### 8.9.5 External delivery after a restore (issue 11)

- **Held as `uncertain_after_restore`:**
  - every delivery pending, claimed or in progress in the restored backup;
  - every occurrence due between the backup's cut time and the restore time;
  - every slot that could have been delegated.

  Any of these may have been attempted in the lost timeline — including an email, call or push the provider accepted after the cut, which looks pending in the backup.
- **Never sent automatically,** and still held after `lisa core delivery resume`.
- **Resolved only by:**
  - evidence, such as device reports or provider records the owner checks;
  - an explicit owner release of that item (`lisa core delivery release <id>`), after which it is sent at most once;
  - expiry.

**Acceptance**
- **M3, portable,** with scripted providers:
  1. Take backup A.
  2. An email, a call and a push will be accepted after A's cut.
  3. Restore A: all three will be `uncertain_after_restore`.
  4. They will stay held after `resume`.
  5. One explicitly released item will be sent once.
  6. Occurrences due between the cut and the restore will be held.
- **M4:** the same in the container.
- **M8,** the harness will check:
  - a moved deadline, which must keep one occurrence ID and one pending OS request, with a new generation;
  - `fired(g)` reported after `cancel(g+1)`, which must be recorded and keep the slot;
  - a reservation attempted while a push is in flight, which must wait, with no double delivery;
  - a late report after a restore;
  - a crash at each handoff step;
  - the revision 2 checks.
- **X6:** the same checks on devices.

#### 8.11.2 v1 identity and replay (direction 1; issue 1)

**Design**
- **Parent.** Each legacy mutation gets a durable parent keyed by R1's caller-scoped ledger key, `<scope>:<request ID>`. It holds:
  - R1's fingerprint;
  - the ordered child operation IDs;
  - the R1-equivalent response (status and body);
  - creation and expiry times;
  - a compact identity, kept for as long as the dataset is live.
- **Child IDs.** The first 16 bytes of SHA-256 over an unambiguous encoding: `"lisa-v1-child-v1"` ‖ 0x00, then, for each of dataset ID, scope, request ID and discriminator, a big-endian u32 length followed by the UTF-8 bytes. Discriminators:

| Route | Discriminators |
|---|---|
| Task or idea PATCH | `field:<name>` for each changed field (an idea's `tags` among them; v1 has no separate tags route), then `status` (task) or `lifecycle` (idea) |
| Preferences PATCH | `change:<index>`, in request order, because R1 allows one key twice |
| Notification action | `receipt` (for paired-device callers only, as in R1), then `action` |
| A single-operation route | `single` |

- **R1's order and partial outcomes, committed atomically.**
  - **Task and idea PATCH:** the revision check, then the field children, then the status or lifecycle child.
  - **Preferences PATCH:** children in request order. The first refused change stops the request, and the earlier children stay committed, as in R1 (§1.6).
  - **One transaction** commits every child R1 would keep, their projections, the parent and the recorded response. R1 used several transactions.
- **Retries:**
  - same key and fingerprint: the recorded response, with `Lisa-Replayed: true`;
  - a different fingerprint: 422.
- **After the response body expires** (R1's `api.idempotencyRetentionDays`, 30 days by default), the compact parent remains. A retry receives the original status, a body regenerated from current state, and `Lisa-Replayed: regenerated`. Never a second application. R1 would have applied it again.
- **Exceptions kept:** `POST /v1/devices/pairing-codes` and `POST /v1/devices/pair` stay outside the ledger, as R1 does, because their responses carry a code or credential.
- **`upgrade_required`** (426, typed) when:
  - a field to change has an unresolved conflict;
  - the caller is an R2-enrolled device;
  - the request has a shape with no R2 operation.

**Route table:** as revision 2, with these rows corrected:

| v1 route | R2 behavior |
|---|---|
| `PATCH /v1/tasks/{id}`, `PATCH /v1/ideas/{id}` | Field children, then the status or lifecycle child, in R1's order. A failed later child leaves the earlier ones committed with the recorded error, atomically |
| `PATCH /v1/preferences` | One child per change, in order; stops at the first refusal; earlier children committed; R1's response recorded |
| `POST /v1/notifications/{id}/actions` | Receipt child, then action child |

**Acceptance (M3) with a frozen R1 client.** The frozen client is R1's `LisaClient` and `lisa`, built at M0 from `491c90a`, with recorded hashes. The harness will check:
- a multi-field task PATCH: deterministic child IDs, and a crash between children must leave either none or the full set R1 would keep;
- a multi-preference PATCH whose third change is refused: the first two kept, the error recorded, atomically;
- the same key twice;
- a crash followed by a retry, which returns the recorded response;
- a retry after body expiry: regenerated, not applied again;
- each `upgrade_required` case;
- both pairing routes leaving no record.

#### 8.13.3 Classifying R1 queue entries (direction 2; issue 2)

**Inputs:**
- the entry as found in the raw file: status, attempts, `uncertainSince`, the last error's HTTP status, and the kept response;
- Core's evidence through `R1RequestEvidenceReading`: the migrated ledger record for (scope, request ID), with its fingerprint and stored status;
- transactional evidence: the capture's request key, which R1 stores in the capture itself, in the same transaction (`Sources/LisaOwnerData/CaptureService.swift:67–96`), and R1's `data.deleted` audit events.

| Found in the file | Evidence | Class |
|---|---|---|
| `done`, with its 2xx response | — | Applied |
| `conflict`: the client received a 409 | — | Rejected: the owner's input is recoverable and offered for re-entry against the current state |
| `failed`, last status 400, 403, 404 or 413 (answers R1's server records as definite), no `uncertainSince` | — | Rejected, input recoverable |
| `failed`, last status 422 (`requestIDReused`) | — | Quarantined: something else was applied under that request ID |
| `pending`, 0 attempts | — | Never sent: converted, or quarantined if its meaning or revision no longer holds |
| `pending` with attempts, no `uncertainSince`; last status 401, 429 or 503, or no status (R1 found it unsent) | Lookup | Not applied (the host answered without applying it, or nothing was sent), unless a ledger record says otherwise |
| Possibly sent: `sending`, where a request may have gone out; `pending` or `failed` with `uncertainSince`; last status 502 or 504, where a proxy answered and the host may have applied it; `failed` with any other status, or with none | Record, same fingerprint, 2xx | Applied |
| Same | Record, same fingerprint, 400/403/404/409/413 | Rejected, input recoverable. A lost 409 stays a rejection |
| Same | Record with a different fingerprint | Quarantined (identity collision) |
| Same | No record; a capture with that request key exists | Applied |
| Same | No record; a capture, with no such key and no capture deletion audited since the first attempt | Not applied: converted |
| Same | No record; a capture, with no such key but a capture deletion audited since | Quarantined: the owner may have deleted it |
| Same | No record; notification receipts | Re-applied (idempotent) |
| Same | No record; any other kind | Quarantined. Absence is not proof: records expire, and R1 wrote them after the change's own transaction |

**Restart safety:**
- The import keeps one record per entry, keyed by the original entry ID and request ID.
- Converted operations take deterministic IDs from (dataset, scope, request ID, discriminator), the same derivation as v1 children. So an import re-run after a crash never duplicates.
- Quarantined entries keep their original bytes.

#### 8.13.4 The Mac queue and the paired mobile upgrade (issue 3)

- **Where the old Mac queue is:** `~/Library/Application Support/<bundle ID>/Client/queue/queue.json`, outside the R2 app's sandbox container. Its requests used scope `owner`, and its captures are keyed `local-owner:<id>` (§1.6).

  - **Bounded lookups.** Core then answers owner-scope lookups only for the request IDs in that imported file, and audits them.
  - **Classification** follows §8.13.3 with scope `owner` and capture key `local-owner:<request ID>`.

#### 8.13.6 Rollback (direction 8; issue 13)

**Preflight** (`lisa core migrate rollback --preflight`) lists everything outstanding, which the owner resolves or accepts:
- **Unsynchronized client work:**
  - each enrolled device sends a signed acknowledgement that its journal is clean (everything committed, no drafts), or produces a protected export (§8.5.5);
  - devices that do neither are listed as outstanding, with their last-known pending counts.
- **Waiting operations,** exported in the rollback archive.
- **Unresolved conflicts.** v4 can hold only one value per field:
  - the v4 record keeps the owner-authored value;
  - when owner values themselves conflict, it keeps the one the owner selects in preflight, or else R1's last value;
  - every alternative is listed in the report;
  - owner text is never overwritten with a model or source value.
- **Ambiguous historical authority** is shown the same way, without overwriting owner text.
- **Old owner corrections:** R1's `ownerCorrected` flags are regenerated from owner authority.
- **Uncertain deliveries** become `outcomeUnknown`.
- **Reservations on unreachable devices:** those slots' R1 deliveries are suppressed ("may fire locally") and listed.

**Reverse migration (v5 to v4):** as revision 2, plus regenerated `runtime-state.json` (from Core's schedules) and `model-requests.json` (today's count, in the owner's zone), in R1's formats.

**Verification** uses the frozen R1 binary on a disposable copy only, because opening an R1 host runs recovery and changes data. The rollback directory itself is never opened during verification.

**Acceptance (M9):** the harness will check:
- a client disconnected during rollback: it must be listed as outstanding, with the export path working;
- conflicting values that v4 can't represent: they must be reported, with owner text preserved;
- an interrupted migration, which must resume with no partial state;
- provider acceptance across the cutover: a delivery accepted before migration must stay accepted, and one accepted by R2 after cutover must arrive in v4 as accepted;
- the frozen R1 `run-once`, on a copy, which must send nothing again.

### 8.14 Limits and performance (R2-LIMIT-01–03; direction 5)

### 8.15 Transfer sizes, encoding and chunking (R2-LIMIT-01; directions 5 and 8)

**Three layers, checked separately**

| Layer | Unit | Limit | Checked |
|---|---|---|---|
| Semantic | An operation's canonical body | 64 KiB | At creation and at intake |
| Semantic | A batch | At most 100 operations and 512 KiB of bodies plus signatures | The client splits batches; Core checks |
| Semantic | A note or conflict-candidate piece; an item's own state | 64 KiB each | At creation and at intake |
| HTTP | Encoded request body (JSON envelope with base64url bodies) | 768 KiB: 512 KiB × 4/3, plus at most 64 KiB of envelope | The server refuses from `Content-Length` before reading |
| HTTP | A snapshot or blob chunk response (`application/octet-stream`, raw) | 512 KiB plus headers | Before sending |
| Frame | A nearby frame (8-byte header, then raw payload) | 1 MiB in total | From the header, before allocating |

**Other bounds:**
- causal-summary pages: 256 KiB;
- manifest pages: 4,096 chunk entries;
- roster key-history pages: 64 KiB;
- declared dependencies: at most 32;
- waiting operations: per §8.2.2;
- orphan blobs (uploaded, never referenced): expire after 7 days;
- staged blobs: 256 MiB in total;
- retries: finite per attempt cycle, with persisted next-attempt times.

**What fits where:** as revision 2. Every signed unit (operation, batch, roster, receipt) fits one frame and one HTTP message. Snapshots and blobs are chunked and checked chunk by chunk.

**Larger content:** a capture over 64 KiB becomes a blob of at most 1 MiB, sent in 256 KiB chunks, as revision 2.

**Exact boundary tests (M1, M3, M6):**
- a 64 KiB body accepted, and one byte more refused;
- 100 operations accepted, 101 refused;
- a 512 KiB batch accepted, one byte more refused;
- a 768 KiB HTTP body accepted, one byte more refused before reading;
- a 1 MiB frame accepted, one byte more closing the session;
- the base64 and JSON overhead measured on the largest valid batch.

### 8.16 Data handling rules (direction 11)

**Provenance.** Every record carries:
- its origin (source, capture, device or Core) and its authority;
- source times, and the last retrieval or sync;
- revisions;
- its interpretation status;
- whether it is canonical, local or provisional.

**Replication allowlist**
- **Clients receive:**
  - owner entities: tasks, ideas, captures, permitted non-secret preferences, the owner-visible fields of proposals, owner reminders and suggestions;
  - derived records: calendar occurrences in the window, briefs for 30 days, plans in the window, bounded evidence excerpts, news referenced by briefs or captures, and source status (freshness only);
  - trust and coordination: the public roster, the lineage, their own assignments, and the trust bundle.
- **Never replicated:** secrets and secret references, connector configuration and cursors, raw content, full email bodies, deliveries, audit, idempotency records and v1 parents, other devices' credentials or push tokens, and Core's model settings.

**Export allowlist**
- **Core's owner export:** owner entities, derived records, operation metadata, and waiting, rejected and quarantined work. Never secrets, verifiers or push tokens.
- **Client export:** unsynchronized work only (§8.5.5).

**Storage and deletion**
- **Core retention:**
  - raw content 90 days, delivery history 180 days, audit 365 days, unused feed items 30 days;
  - operation metadata and tombstones for as long as the dataset is live;
  - operation bodies per §8.4.4;
  - v1 parents in compact form for as long as the dataset is live.
- **Client retention:**
  - the working set, with the journal per §8.5.3;
  - blobs follow their operations;
  - staging is dropped after installation or invalidation;
  - logs are bounded.
- **Deletion** propagates to canonical records, replicas, search indexes, generated briefs and plans, reminders, deliveries, assignments and blobs. Verified at M5 and M8.

**Locked-device behavior**
- The replica and the Keychain items are available after first unlock. Before the first unlock after a reboot, nothing runs.
- Notification actions and Siri work while locked after first unlock. Completing a task requires unlocking, as in R1.
- Background refresh may run while the device is locked; nearby sessions run only in the foreground.
- Secure Enclave keys are usable after first unlock.

### 8.17 Compatibility, fixtures and live-service limits (direction 11; O-6)

- **Old clients:**
  - R1 companions and the R1 Mac app use v1 through the translation layer until they are upgraded.
  - Legacy devices are never roster members.
  - R2 clients negotiate v2, and an unknown required feature gets `upgrade_required`.
- **Fixture reproduction:**
  - **Frozen at M0** under `.tmp/r2/<M0 run>/frozen/`, each with its SHA-256:
    - R1's `lisa` binaries, debug and release;
    - the R1 `LisaClient` build used by the frozen-client harness;
    - synthetic R1 data directories and queue files.
  - **Scenario records** go in the tracked `docs/VERIFICATION-SCENARIOS.md`: commands, inputs, expected hashes and which frozen artifacts each scenario uses.
  - **Runs** use fresh per-run directories, and nothing is removed.
- **Live-service limits:**
  - No live mailbox, calendar, X, Discord, model provider, SMTP, Twilio or APNs is contacted without the owner's separate authorization.
  - Owner hardware implies no such authorization.
  - Otherwise these checks are `NOT_RUN_CREDENTIALS`.

- **Scale.** Much of the Apple code can only be syntax-checked here. Mitigation: portable logic first, thin adapters, early sessions X1–X3, and `Apps/Probe` before M5.
- **Nearby security.** Design A may fail N-1 (TLS 1.2, undocumented PSK suites). Design B needs P-08 for production certificates. If both fail, nearby stops; everything else continues.
- **Rootless versus production.** Rootless networking, UID mapping and SELinux differ from the server, so those checks are repeated there.
- **Destination verification on Apple** may prove infeasible (E-1). Then those features are disabled on clients and the platform limitation is recorded.
- **Fedora drift:** libxml2 2.15 and OpenSSL 4.0 (E-5), and Swift 6.3.2 versus 6.4.2.
- **Snapshot installation** can make a capture wait. Waits are measured and counted in p95.
- **Backup coverage** depends on `backup.retainRestorable` and the caps, both reported.
- **Inherent limits, documented:** revocation reaches a device only when it learns of it; the only-copy risk on isolated devices; exactly-once delivery is impossible; handoffs can leave visible gaps.
- **Migration** is verified on synthetic data only.
- **Owner availability:** sessions X1–X7 need the owner's time; only the production nearby transport depends on a session result.

## 18. Stopping conditions

Work on an affected item stops only when:
- an action needs authorization outside the approved scope;
- an enforced platform restriction needs the owner;
- a concrete technical blocker cannot be resolved within the approved scope;
- credentials, Apple hardware sessions, the production host or live validation are needed, or a deciding experiment hasn't run where its result is a stated prerequisite.

Independent work continues in every case, and each blocked operation is reported with its exact cause.
