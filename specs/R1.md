**Release:** R1  
**Specification date:** 2026-11-15  
**Amended:** 2026-11-15 — owner-requested notification additions (NOTIFY-01–NOTIFY-07, L25–L31, A11–A16)  
**Primary implementation environment:** Claude Code in a Linux sandbox  
**Primary operational platform:** macOS  
**Companion platforms:** iOS and iPadOS  
**Implementation language:** Swift

## 1. Instructions to the implementing agent

Implement Lisa according to this specification. Deliver working software, tests, setup documentation, and an accurate implementation report.

Read all applicable repository instructions, including `AGENTS.md` and `CONSTRICTION.md` if present, before changing the repository. Do not modify those instructions or weaken this specification to make the implementation appear complete.

Resolve routine implementation details independently. Record significant architectural choices and assumptions in `docs/DECISIONS.md`. Ask the owner only when a missing decision prevents safe or coherent implementation.

Do not create or switch Git branches. Do not push, publish, provision paid services, send real messages, or place real calls during implementation unless separately authorized.

External credentials must not be necessary to build the portable application or run its automated acceptance tests.

The absence of credentials or an Apple SDK is a verification limitation. It is not permission to replace required production adapters or Apple application code with empty interfaces, pseudocode, or permanent mock implementations.

Use these verification statuses consistently:

- `PASS`: executed successfully, with evidence.
- `FAIL`: executed and failed.
- `NOT_RUN_ENVIRONMENT`: the required platform or toolchain is unavailable.
- `NOT_RUN_CREDENTIALS`: the implementation exists, but a live check requires credentials or account access.
- `OUT_OF_SCOPE`: explicitly excluded by this specification.

Never describe unexecuted Apple builds, live integrations, or device behavior as verified.

## 2. Product purpose and established boundaries

Lisa is a personal secretary for one owner.

Lisa maintains an understanding of the owner’s commitments, preferences, interests, and ideas. She produces a useful daily rundown, prepares a morning brief, helps ideas find space in the owner’s schedule, and follows up when attention is needed.

The primary experience must revolve around the owner’s day, commitments, and ideas. A conversational input field may be included, but a chat transcript alone does not satisfy R1.

### 2.1 Established requirements

| Area | Requirement |
|---|---|
| Email access | Lisa uses her own mailbox. The owner forwards or CCs selected messages to that address. |
| Personal mailbox | Lisa does not connect to or search the owner’s personal mailbox. |
| Calendar access | Lisa reads calendar subscriptions supplied by the owner. |
| Calendar modification | Lisa proposes additions and reminds the owner about missing events. She does not directly modify the owner’s calendars. |
| Memory | Lisa remembers explicitly supplied preferences and preserves captured ideas. |
| Planning | Lisa creates and updates a daily rundown and proposes time to explore ideas. |
| Briefing | Lisa combines commitments, relevant email, deadlines, ideas, and relevant news into a morning brief. |
| Sources | The product supports information originating from Apple News, X, and Discord through available, authorized access paths. |
| Follow-up | Lisa tracks outstanding commitments and sends reminders. |
| Communication | Lisa can email and call the owner when enabled and warranted by configured policy. |
| Notifications | Lisa delivers native notifications to the owner’s iPhone and iPad, and supports notifications on the Mac. |
| Apple integration | Lisa integrates with Siri and supports a user-configured alarm-related morning briefing workflow. |
| Technology | The implementation is Swift-based, with native Apple interfaces using SwiftUI. |

### 2.2 R1 design defaults

The following are implementation decisions for this release, rather than additional facts previously supplied by the owner:

1. One Mac acts as the authoritative operational host.
2. An iPhone and iPad companion provides access to the rundown, brief, capture actions, notifications, and Siri integration.
3. The portable engine also runs headlessly on Linux.
4. SQLite stores authoritative application state.
5. Each companion device communicates with the host through an authenticated API and keeps a bounded local cache.
6. Model access is configurable. R1 does not require one particular model vendor.
7. Phone calls use a configurable telephony provider; the initial production adapter is Twilio Programmable Voice.
8. R1 has one owner and no multiuser or organizational permission system.
9. Remote notifications use ordinary Apple Push Notification service (APNs) alert notifications sent by the authoritative host. Each companion device registers separately.

Keep these defaults configurable or isolated behind appropriate interfaces where practical.

### 3.1 Explicit exclusions

R1 does not require:

- Access to the owner’s personal mailbox.
- Calendar-account write access or automatic calendar changes.
- Messages, invitations, or calls to third parties.
- Automatic purchasing or account provisioning.
- Autonomous browser operation to access private feeds.
- A general-purpose agent with unrestricted shell or filesystem access.
- Model training or fine-tuning.
- Continuous background execution on iOS.
- Silent pushes as a guaranteed background-execution mechanism, PushKit, or Critical Alerts.
- Automatic wake-from-sleep guarantees for the Mac.
- Cloud synchronization, public Internet hosting, or multiple authoritative hosts.
- A notification relay service, public endpoint, or other cloud backend for Lisa. APNs is used only as Apple’s delivery service.
- Apple Watch, CarPlay, or an App Store release.
- Full attachment understanding, OCR, or arbitrary document analysis.

## 4. Architecture and platform requirements

### ARCH-01 — Portable core

Create a Swift Package containing the portable domain and application logic.

The portable build must not import SwiftUI, AppKit, UIKit, App Intents, EventKit, SwiftData, or other Apple-only frameworks.

Use Swift 6 language mode. Pin and document an available stable toolchain and compatible dependency versions. Record actual compiler versions in the verification report.

Foundation networking differences between Linux and Apple platforms must be handled explicitly.

### ARCH-02 — Separation of responsibilities

Maintain clear boundaries between:

| Component | Responsibility |
|---|---|
| Domain | Entities, state transitions, validation, planning constraints |
| Application services | Ingestion, reconciliation, planning, briefing, reminders |
| Persistence | SQLite repositories, migrations, transactions |
| Integrations | Mail, calendars, news, model inference, delivery providers |
| Runtime | Scheduling, lifecycle, recovery, health |
| API and CLI | Authenticated commands and queries |
| Apple applications | SwiftUI presentation, device integration, local caching |
| Apple adapters | Keychain, notifications, App Intents, speech-related integration |

Keep business rules out of views and transport handlers.

Prefer small, cohesive modules over a large service object containing the entire application.

### ARCH-03 — Authoritative host

The Mac is the authoritative host in normal operation.

The macOS application may embed the runtime. The headless executable must offer an alternative host mode.

Exactly one runtime may own a data directory at a time. A second writer must fail clearly or connect as a client; it must not start a competing scheduler.

Document that ingestion and host-based delivery stop when the authoritative host is stopped, asleep, or disconnected.

### ARCH-04 — Dependency discipline

Use maintained dependencies where they reduce risk, particularly for networking, MIME, and calendar parsing.

Small C interoperability layers for SQLite, libcurl, or similar platform libraries are permitted. The domain and application logic must remain Swift.

Do not make Python, Node.js, Claude Code, or another developer-agent CLI a production runtime dependency.

Development scripts may use standard supporting tools.

## 5. Persistent data and time model

### DATA-01 — Required entities

The implementation must represent at least the following concepts. Exact type and table names are implementation choices.

| Entity | Minimum information |
|---|---|
| Source | Type, configuration reference, enabled state, cursor, last attempt, last success, freshness, error |
| Evidence | Source identity, external identity, timestamps, original excerpt or content reference |
| Email | Message identity, sender/recipients, subject, body, thread references, received time |
| Calendar occurrence | Source UID, occurrence identity, start/end, timezone semantics, status, availability |
| Task | Title, status, priority, deadline precision, duration estimate, evidence, confirmation state |
| Event proposal | Proposed details, evidence, uncertainty, calendar-match state, review state |
| Idea | Original capture, description, tags, priority, duration estimate, lifecycle state |
| Preference | Key/value, explicit or inferred origin, evidence, confirmation, update time |
| News item | Source, original URL, title, accessible text, publication/retrieval times, relevance reason |
| Plan | Local date, timezone, revision, blocks, constraints, explanations |
| Brief | Date, timezone, version, text, spoken text, source references, generation state |
| Reminder | Subject, rule, due time, acknowledgement, suppression and escalation state |
| Delivery | Channel, recipient, payload reference, idempotency identity, attempts, outcome |
| Audit event | Action, actor, timestamp, affected identifiers, outcome |

### DATA-02 — Persistence

Use SQLite with versioned, transactional migrations.

Persist ingestion cursors, user corrections, preferences, plans, reminder state, and delivery state across restarts.

A failed migration must leave the previous data recoverable. Do not silently recreate or discard the database.

Use stable identifiers and explicit revisions for mutable records.

### DATA-03 — Time semantics

- Store instants in UTC.
- Preserve the source timezone or local-date semantics needed to reproduce the original meaning.
- Use an IANA timezone for planning and daily briefing.
- Represent date-only deadlines and all-day events distinctly from timed instants.
- Do not silently convert a date-only deadline into an invented exact time.
- Resolve relative dates against a documented source timestamp and timezone.
- Keep ambiguous dates unresolved until clarified or governed by an explicit user setting.
- Handle daylight-saving transitions and timezone changes.
- Inject a clock into time-dependent logic; tests must not depend on the actual wall clock.

A timestamp such as “updated at” does not substitute for the time an event actually occurs.

### DATA-04 — Provenance and correction

Every extracted commitment, proposed event, and summarized source claim must retain a path back to its evidence.

User corrections take precedence over subsequent model suggestions. Reprocessing the same source must not silently overwrite a correction.

Preserve the original captured idea or message separately from generated summaries.

### DATA-05 — Retention and deletion

Provide documented retention settings for raw source content, generated records, logs, and delivery history.

Support deletion of individual captured items and preferences. Remove or invalidate dependent search entries and generated caches.

Deleting or disabling a source must clearly state whether previously imported records are retained.

Backups and exports must preserve enough version information to restore coherently.

## 6. Input sources

### INGEST-01 — Common connector contract

Each source adapter must provide:

- Validated configuration.
- Incremental synchronization where supported.
- Bounded pagination and payload sizes.
- Stable deduplication.
- Persisted progress.
- Cancellation and timeouts.
- Retry classification and rate-limit handling.
- A visible health and freshness state.
- Deterministic fixtures for automated tests.

A partial or failed retrieval must not be treated as a complete empty result.

Do not advance a cursor past data that has not been durably processed.

### MAIL-01 — Lisa’s dedicated mailbox

Implement an incoming mail adapter for a separately configured Lisa mailbox.

A practical R1 baseline is IMAP over TLS. Provider-specific authentication may be supported through documented configuration.

Do not request access to the owner’s personal mailbox.

Use read-only retrieval behavior. Fetching a message must not mark it read, delete it, move it, or modify remote flags.

Support common MIME structures, encoded headers, plain text, sanitized HTML text, and forwarded messages. Parse calendar attachments through the calendar ingestion path.

Do not execute attachments, scripts, remote images, or linked content.

Unsupported attachment types must remain visibly unsupported.

### MAIL-02 — Identity and extraction

Deduplicate using source-specific identifiers. For IMAP, account for both mailbox UID validity and message UID. Preserve Message-ID and thread references when available.

Identify potential:

- Commitments and deadlines.
- Meetings or events.
- Requests requiring a response.
- Changes or cancellations affecting an earlier item.
- Information relevant to the next brief.

Being CC’d on a message does not automatically make every request in that message the owner’s task.

Preserve distinctions between confirmed commitments, possible commitments, and informational content.

Incoming email is source material. It must not change Lisa’s permissions, recipients, credentials, or operating policy.

### CAL-01 — Read-only subscriptions

Implement calendar ingestion from configured HTTPS iCalendar feeds and local `.ics` fixtures.

Treat private subscription URLs as secrets.

Support the common event, timezone, recurrence, exclusion, and exception structures needed for real subscribed calendars. At minimum, cover:

- Timed and all-day events.
- UTC, named timezones, and explicitly configured floating-time interpretation.
- Daily, weekly, monthly, and yearly recurrence.
- Interval, count/until limits, common day/month selectors.
- Additional dates, excluded dates, and overridden occurrences.
- Cancelled events and transparent availability.

Use bounded recurrence expansion.

Document the exact supported subset. An unsupported construct must produce a visible warning and conservative planning behavior; it must not silently become a one-off event. [S4]

### CAL-02 — Reconciliation

A successful complete refresh must reconcile additions, changes, cancellations, and removals.

An interrupted fetch, authentication failure, or parsing failure must not delete previously known events.

Calendar changes must invalidate affected plans and future reminders.

If an enabled calendar needed for planning is stale or incomplete, Lisa must label availability uncertain and avoid presenting newly proposed time as confidently free.

### EVENT-01 — Missing-calendar detection

Compare extracted event proposals against subscribed calendar occurrences.

Use stable identifiers where available. Otherwise consider normalized title, time, location, and participants without treating a loose similarity as proof.

Support these states:

- Needs clarification.
- Not found in subscribed calendars.
- Possible match.
- Matched.
- Dismissed.
- Owner reports added; awaiting subscription refresh.

The owner must be able to confirm a match, dismiss a proposal, or correct its details.

Lisa may remind the owner about an unresolved event proposal according to policy.

Provide an `.ics` export for a reviewed proposal. Importing it into a personal calendar remains an owner action.

Do not claim an event was added merely because an export was created.

### NEWS-01 — Common news workflow

Implement ingestion from RSS/Atom feeds and manually supplied URLs or text.

Each item must retain its origin, publication time when known, retrieval time, and accessible-content boundary.

Rank items using explicit interests, source preferences, recency, relevance, and duplicate detection.

Explain briefly why an item was selected. Provide controls such as “more like this,” “less like this,” and mute source/topic.

Do not summarize inaccessible article content as though it was read. A title-only item must remain labeled accordingly.

### NEWS-02 — X

Implement a production read adapter for selected accounts through the official X API, using configurable credentials and bounded polling.

Preserve post identifiers and links. Handle pagination, deleted/unavailable content, authentication failures, and rate limits.

Do not assume the owner’s account or API entitlement permits every endpoint. Surface denied capabilities explicitly.

R1 does not require access to the complete personalized home feed. [S5]

### NEWS-03 — Discord

Implement a production read adapter for explicitly configured channels accessible to an authorized bot.

Respect channel permissions and message-content restrictions.

Do not use the owner’s normal Discord account token or implement a self-bot.

If Lisa cannot be installed in a server or cannot access message content, provide a manual link/text capture route and display that automatic monitoring is unavailable.

Do not post to channels or send Discord messages in R1. [S6]

### NEWS-04 — Apple News

Support owner-shared Apple News links and text through the capture workflow, and permit relevant publisher feeds as additional sources.

Apple documents its News API for publishing and managing publisher content. R1 must not assume this provides access to a user’s personalized Apple News feed. [S7]

An Apple News item supplied manually must be labeled as shared content.

If automatic personalized-feed access is unavailable through a supported interface, document that limitation. Do not simulate monitoring or bypass authentication or paywalls.

## 7. Memory, capture, and model inference

### MEM-01 — Preferences

Support explicit preferences for at least:

- Timezone and planning windows.
- Protected time and scheduling buffers.
- Brief timing, length, and topics.
- News interests and muted sources/topics.
- Reminder timing and channel preferences.
- Quiet hours and call escalation.
- Idea exploration duration and frequency.
- Model endpoint and data-sharing policy.

The owner must be able to inspect, edit, and delete preferences.

Inferred preferences must be distinguishable from explicit ones. Inference must not silently change delivery permissions or other consequential settings.

### IDEA-01 — Capture and lifecycle

Accept ideas through the CLI, native applications, API, and Siri integration.

Save the original input immediately, independently of model availability.

Support tags, notes, estimated exploration duration, priority, and optional deadline.

Support at least: inbox, available for planning, scheduled, explored, and archived.

A proposed exploration block does not imply the idea has been explored.

If an idea repeatedly cannot be scheduled, keep it visible and explain the constraint.

### MODEL-01 — Provider boundary

Define a model-provider interface independent of the rest of the application.

Deliver:

1. A deterministic provider for tests and demonstrations.
2. A working configurable HTTP adapter for an OpenAI-compatible Chat Completions endpoint.
3. A documented fallback when inference is unavailable.

The endpoint, model identifier, credentials, timeouts, and request limits must be configurable. Do not hard-code a paid model requirement.

Provider compatibility must be tested against the supported request/response subset rather than assumed from a provider’s marketing description. [S8]

### MODEL-02 — Structured output

Use validated structured results for extraction and classification.

Validate:

- Required fields and types.
- Permitted enums.
- Referenced source identifiers.
- Dates, durations, and bounds.
- Output size.
- Evidence references.

An invalid model response may receive a bounded repair attempt. It must not trigger an unbounded retry loop.

Uncertain information must remain uncertain. Confidence labels must not be presented as calibrated probabilities unless actually calibrated.

### MODEL-03 — Authority separation

Models may propose summaries, classifications, tasks, and plans.

Deterministic application services must enforce:

- Recipient restrictions.
- Delivery permissions.
- Calendar boundaries.
- Scheduling constraints.
- State transitions.
- Rate and spending limits.
- Confirmation requirements.

Models must not receive arbitrary shell, SQL, filesystem, or delivery execution privileges.

Instructions embedded in email, calendar descriptions, news, or Discord messages must be treated as untrusted content.

### MODEL-04 — Degraded operation

Without an available model:

- Captures still persist.
- Calendars still synchronize.
- Confirmed tasks remain manageable.
- Deterministic planning and reminders continue.
- Briefs may use a clearly identified structured template.
- Items requiring interpretation remain pending.

Never present canned demo content as live inference.

Cloud model requests require an explicitly configured endpoint and data-sharing setting. The default demonstration must send no private content externally.

## 8. Daily rundown and idea scheduling

### PLAN-01 — Contents

The daily rundown must combine:

- Calendar commitments.
- Confirmed tasks and deadlines.
- Proposed work blocks.
- Proposed idea exploration.
- Unresolved event proposals.
- Overdue or blocked items.
- Material source-health warnings.

Clearly distinguish fixed calendar events from Lisa’s proposed blocks.

### PLAN-02 — Hard constraints

A proposed block must not overlap:

- A busy calendar occurrence.
- Protected time.
- A locked plan block.
- Another proposed block.

Respect configured planning windows, buffers, duration requirements, and deadline boundaries.

Do not split a task or idea unless it is marked splittable.

Do not invent travel time. Use an explicit configured buffer or mark the missing information.

### PLAN-03 — Deterministic baseline

Provide a documented deterministic planning algorithm.

Its baseline ordering must prioritize:

1. Fixed and locked commitments.
2. Confirmed deadline-sensitive tasks.
3. Other confirmed tasks by explicit priority.
4. Eligible ideas within the configured exploration budget.

Use stable tie-breaking so identical inputs produce identical plans.

Do not fill every free minute by default. Respect a configurable maximum allocation of available time.

If work cannot fit, report it as unscheduled with a reason rather than violating constraints.

### PLAN-04 — Proposal and revision behavior

Lisa may automatically propose blocks in her own rundown. This does not modify any external calendar.

The owner can accept, move, lock, reject, defer, or complete relevant items.

Replanning must preserve locked blocks and completed work. It must not repeatedly reintroduce rejected suggestions without a relevant change.

When a calendar changes, identify what changed and explain affected proposals.

### PLAN-05 — Freshness and uncertainty

Plans must record the source revisions and freshness on which they were based.

Unconfirmed extracted deadlines must not silently become firm scheduling constraints.

When availability is uncertain, Lisa may show provisional suggestions, but must identify the uncertainty and avoid automatic escalation based on those suggestions.

## 9. Morning brief

### BRIEF-01 — Required content

Produce both a readable brief and a speech-friendly version covering, when relevant:

1. Today’s fixed commitments.
2. Important deadlines and tasks.
3. Email requiring attention.
4. Unresolved or missing-calendar events.
5. Proposed idea exploration.
6. Selected relevant news.
7. Material changes and source failures.

Do not pad empty sections.

Distinguish “nothing relevant was found” from “the source could not be checked.”

### BRIEF-02 — Grounding

Every factual source-based item must link to its supporting record or original source.

Preserve uncertainty and avoid unsupported conclusions.

The spoken version should use natural phrasing and omit raw URLs and internal identifiers.

Both versions must convey the same material commitments, warnings, and uncertainty.

### BRIEF-03 — Scheduling and versions

Generate briefs at a configurable local time and on demand.

Use one canonical daily brief identity per local date and timezone, with explicit revisions.

Concurrent requests must not produce duplicate daily deliveries.

Keep the latest successful brief available if regeneration fails, while marking its age and status.

Do not require a live model request at the moment an alarm-related action runs.

### BRIEF-04 — Length

Provide configurable brief length with a concise default.

Estimate spoken duration from text and expose that estimate without claiming precise playback timing.

If content exceeds the target length, prioritize deadlines and commitments and make omitted lower-priority material available in the full view.

## 10. Reminders, notifications, email, and phone calls

### REM-01 — Reminder lifecycle

Support reminders for:

- Upcoming confirmed deadlines.
- Overdue confirmed tasks.
- Upcoming accepted plan blocks.
- Unresolved event proposals.
- Relevant changes to confirmed commitments.

Support acknowledgement, snooze, dismissal, and completion.

Acknowledging a reminder does not complete its underlying task.

Task completion, cancellation, or deadline changes must cancel or recompute obsolete reminders.

### REM-02 — Policy defaults

Defaults must be visible and editable. The following are R1 starting values, not established personal preferences:

| Setting | Initial behavior |
|---|---|
| External delivery | Dry-run until configured |
| Brief delivery | One scheduled delivery per local day |
| Normal deadline reminders | 24 hours and 1 hour before a timed deadline |
| Overdue reminders | At most once per local day |
| Quiet hours | 22:00–07:00 in the configured timezone |
| Event-proposal follow-up | At most once per day per unresolved proposal |
| Call escalation | Disabled until explicitly enabled |
| Maximum calls | One per underlying commitment per day; three total per day |
| News escalation | Included in briefs; no phone calls |
| Date-only deadlines | Require a configured reminder time; retain date-only meaning |
| Device notifications | Every paired device with notifications enabled; dry-run until APNs is configured |
| Notification content | Generic text without item details; details appear in the app |
| Notification interruption level | Standard; no Critical Alerts |

A newly discovered item must not generate a burst of every historical reminder it would previously have received.

### REM-03 — Delivery outbox

Persist delivery intent before attempting an external side effect.

Use stable reminder and delivery identities, transactional claiming, and restart-safe state transitions.

Distinguish:

- Pending.
- Suppressed.
- In progress.
- Accepted by provider.
- Confirmed delivered, when supported.
- Failed.
- Outcome unknown.
- Cancelled.

Provider acceptance does not prove the owner read an email or answered a call.

If a network failure leaves the outcome unknown and the provider cannot safely deduplicate or reconcile, do not blindly retry the side effect.

Do not claim exactly-once external delivery where the provider cannot guarantee it.

### EMAIL-01 — Outbound email

Implement a production SMTP-over-TLS adapter or a documented equivalent mail-provider adapter.

Send from Lisa’s configured identity only to owner-approved addresses.

The application must enforce recipient restrictions independently of model output and source content.

Support briefs and reminder messages with clear subjects and readable text.

Provide a dry-run transport that captures intended recipient, subject, and content without sending.

Do not reply to source-message senders or reuse their recipients automatically.

### CALL-01 — Outbound phone calls

Implement a Twilio adapter that places an outbound call to the configured owner number and speaks a short, escaped text message.

Use provider-supported call creation and speech instructions. Recording and transcription are outside R1. [S9]

A call requires all of the following:

- Calls are explicitly enabled.
- The destination is an approved owner number.
- The underlying commitment is confirmed.
- The commitment satisfies a configured urgency rule.
- It remains incomplete and unacknowledged.
- Quiet-hour and escalation rules permit the call.
- Rate limits permit the call.

Do not let a model’s use of “urgent” alone authorize a call.

A useful initial urgency rule is a high-priority confirmed deadline within 15 minutes, following an unacknowledged earlier reminder. Keep the rule configurable.

After a long outage, re-evaluate urgency before calling. Do not replay expired call jobs.

### REM-04 — Recovery

When the host resumes:

- Reconcile current time and persisted jobs.
- Suppress obsolete reminders.
- Coalesce missed low-priority notifications.
- Respect daily limits and prior acknowledgements.
- Generate at most one catch-up brief within a configurable catch-up window.
- Record what was skipped and why.

### NOTIFY-01 — Notification events and routing

Send notifications for:

- Reminders covered by REM-01 whose delivery policy includes notifications.
- Important changes to confirmed commitments.
- Availability of the daily brief.

The authoritative host decides whether a notification is warranted, which devices receive it, and when. Presenting or acting on a notification on another device must not create an independent decision engine or scheduler.

By default, deliver each notification to every paired device with notifications enabled, including both the owner’s iPhone and iPad. Do not silently choose one device.

Support per-device enablement and per-device notification preferences, such as notification categories and content detail.

### NOTIFY-02 — Device registration

Each companion installation pairs separately through authenticated registration with its own revocable credential (API-01).

Associate each APNs device token with an authenticated registration, its app identifier, and its APNs environment. Handle token updates, invalid tokens, reinstallation, and device removal. [S12] [S13]

Possession of an APNs device token must not authenticate a client to Lisa.

Protect device tokens and redact them from ordinary logs.

Removing a device revokes its credential, stops new deliveries to it, and cancels its pending deliveries.

### NOTIFY-03 — Per-device delivery and reconciliation

Persist delivery state separately for each device in the delivery outbox (REM-03).

Use stable notification, revision, and delivery identities so that recomputation, retries, and restarts do not create duplicate deliveries or uncontrolled retries.

Document retry limits, expiry, stale-notification handling, and uncertain-outcome behavior. Do not send a notification after its validity window ends or after its subject is resolved.

Distinguish provider acceptance, receipt reported by the app, and owner acknowledgement. Do not claim exactly-once delivery or that every notification is displayed.

When an acknowledgement or completion reaches the host, suppress obsolete pending and future deliveries for every device, and reconcile the other devices when they next connect. Do not promise immediate removal of a notification already displayed on an offline device.

### NOTIFY-04 — APNs provider

Use ordinary APNs alert notifications as the remote-delivery mechanism.

Send through the APNs provider API over HTTP/2 with full TLS certificate validation and token-based provider authentication. Verify the HTTP/2 capability of the transport actually used instead of inferring it from HTTPS support. [S10] [S11]

Keep the provider signing key on the host in the platform secret store (SEC-01). Keep development and production configuration separate.

Handle provider responses, including invalid tokens, authentication errors, throttling, and temporary failures, according to documented rules. [S13]

Provide a dry-run transport that records intended deliveries without sending them.

Do not rely on silent pushes as a guaranteed background-execution mechanism. Do not use PushKit or Critical Alerts.

Document the Apple Developer Program, signing, entitlement, provisioning, and configuration prerequisites.

### NOTIFY-05 — Presentation and notification actions

Deliver native notifications on iPhone and iPad, and support notifications on the Mac.

Notifications must not depend on the companion remaining in the foreground or polling the host.

Provide notification actions that open the relevant item and, where appropriate, acknowledge, snooze, or complete it. [S15] Submit actions through the authenticated API with stable request identities and revision checks.

Queue actions durably while the host is unreachable, and show their pending status until they are synchronized.

Detect notification permission that is denied or later changed, report it to the host, and show it in settings and health.

### NOTIFY-06 — Notification privacy

Send minimal payloads. [S14] By default, notification content contains no item details; details appear after the owner opens the app. More detailed content is an explicit per-device setting.

Respect system notification settings, lock-screen preview settings, and Focus. Interruption levels above the standard level require explicit owner configuration.

Document what each notification sends to Apple’s push service (SEC-03).

### NOTIFY-07 — Connectivity, host availability, and escalation

Document how push delivery works when a device is away from the host’s network, and separately what connection a device needs to open current data or submit notification actions.

## 13. Security, privacy, and operational behavior

### SEC-01 — Secrets

Use a secret-store abstraction.

- Apple production applications: Keychain.
- Linux development/headless deployment: environment variables or explicitly protected secret files.
- Tests: synthetic credentials only.

Do not store credentials in the main domain database, source fixtures, logs, screenshots, or committed configuration.

Redact private calendar URLs, authentication headers, access tokens, and message bodies from ordinary logs.

### SEC-02 — Input and network boundaries

Validate and bound all imported content.

Sanitize HTML, disable XML external entities, reject unsafe URL schemes, and constrain redirects.

Do not fetch arbitrary links merely because an email or model response contains them.

Network requests must be tied to an explicitly configured connector or owner-initiated retrieval.

Protect any URL-fetch feature from accessing local files, cloud metadata endpoints, or unintended private network services. Explicitly configured local model endpoints are a separate permitted configuration.

### SEC-03 — Data routing

Document what is stored locally and what is sent to each provider.

Send only the minimum necessary content to the configured model.

Disabling a provider must stop new requests to it.

Do not claim database encryption unless implemented and verified. Document reliance on operating-system storage protection where applicable.

### OPS-01 — Runtime

Provide:

- A bounded synchronization loop.
- Persisted schedules.
- Graceful shutdown.
- Cancellation.
- Backoff with jitter where appropriate.
- Provider rate-limit handling.
- A single-owner data-directory lock.
- Source-specific failures that do not terminate unrelated processing.

Use structured, redacted logs and expose useful health information.

### OPS-02 — Resource bounds

Configuration must bound:

- Incoming message and feed sizes.
- Items per synchronization pass.
- Recurrence expansion.
- Concurrent network requests.
- Model input/output and request count.
- Retry attempts.
- Log growth.
- Cache and retained raw-content size.

Choose reasonable documented defaults and test limit violations.

Never run unbounded model repair, polling, or recurrence-expansion loops.
